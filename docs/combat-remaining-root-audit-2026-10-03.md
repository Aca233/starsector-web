# 剩余高 ms 根因审计 — 2026-10-03

## 结论与边界

用户要求“先找到根本原因再”：本轮停止功能重写，仅检查指标定义、现有 CPU profile 和一次最终默认版本的调用计数。没有修改生产源码，没有提交、发布或操作桌面。

**重型场景的持续超预算，来自串行权威步里按实体、按挂点执行的决策/查询工作量，以及仍在重复的读表、校验、候选搜索；不是有一个“模拟速度限制”开关挡住性能。** 具体机制已定位如下，但没有做反事实删减实验，不能许诺任一改动的收益。

原版对照：目标 0.98a-RC8；`C:/starsector-core`、`C:/decompiled` 均不存在。原版算法、操作及 UI 等价性待核实。本次仅诊断已有 Web 执行，不修改玩法或 UI。

最小对照：本地原版证据缺失 → 预期保持已有 Web dt/频率/控制/射击结果 → 当前差异是内部执行的工作规模与重复准备 → 用既有重型场景的 profile、调用链、120 步计数和最终统计/RNG核验诊断。不能据此宣称原版也用这种算法。

## 1. 显示的 ms 是什么

`src/network/host.worker.ts:261` 是 elapsedCost/samples。计时从 `:444` 的玩家控制/边沿命令之前开始，经过可选 AI await、权威 advance、deferredWorldMessages，到 `:510` 结束。之后快照生成/发布不在这个区间里。

所以这是**每步墙钟**，不是 RTT，也不能无条件叫纯 CPU。可选子 Worker 等待、系统抢占等可以计入；渲染、网络 RTT、快照耗时另有指标。`src/network/LanBattle.tsx:1315–1327` 有对应显示。解除追赶上限或强制跑60次，不会消除单步工作，可能只是扩大积压。

本审计用同步引擎、无网络/渲染/异步等待，证明引擎本身足以超预算。没有抓到用户当前重型浏览器的现场分项，不能把所有现场尖峰都归到 CPU。

## 2. 无生产改动的 CPU profile

冻结的是上次接受的 `authority-context/stage.mjs`（最终默认选择器/通用绑定守卫调整之前），不是冒充最终源码。既有22根舰/176实体/734挂点、seed917、standard，150预热+120采样。

| 阶段 | profile 窗口平均 ms/步 |
|---|---:|
| 整步 | 39.756 |
| fleetAI（含根舰/模块决策与阶段准备） | 11.858 |
| fire-query（含开火帧准备与各挂点规划） | 12.384 |
| motion（移动积分，不含其它碰撞/决策） | 0.766 |
| wingsDrones | 2.369 |
| shipCollision | 1.584 |
| projectilesBeams | 2.863 |

**AI+fire-query=24.242ms，单这两项已经超过60Hz的16.667ms预算。** GC采样权重仅2.76%，没有证据把GC称为主要根因；堆增长也不等于内存泄漏。采样独占叶中 Ship、NumericAcquisitionFrame、Autofire、WeaponControl、TacticalPositioning、ThreatAssessment 等分散占用，未发现一个便宜函数解释全部慢。包含栈重叠，不能相加冒充精确耗时。

这39.756与上次45.103的测试条件、profiler开销、机器状态不同，**不是新增优化收益**。

## 3. 最终默认版本计数确认的执行原因

只在冻结的 `default-boundaries/default.mjs` 副本函数体内插入计数/计时，模块初始化前插入，保持原有方法身份基线；没有运行后替换prototype、改变Math、触碰生产文件或使用假的权限标记。仅在150预热后开启120步计数。

计时是插桩包含耗时，嵌套不能重复相加；用于定位分布，不是性能验收。这次整步39.347ms，仍不是优化后的结果。最终170实体/90弹丸、双方完整统计、235/243发射与RNG `[917,15731318768774,222]` 和保留回执相符；没有重跑完整状态逐字段witness。

### A. 模块承担了根舰的通用移动规划

调用链：`CombatEngine.ts:912` 模块循环 → `CapitalShipAI.decide` → `chooseCombatVelocity` / `yieldFireLane` / `avoidCollisions` / `planVelocity`。没有按挂载模块拆出专用移动决策边界。

120步实际：根舰决策2,400次（20/步）；模块6,720次（56/步），模块占决策次数73.68%。模块decision包含耗时约 **4.282ms/步**；其中互不嵌套的移动建议组件：位置搜索1.366、让射界0.421、避障0.487、控制求解0.048，合计约 **2.322ms/步**。

但 `Ship.ts:1116–1136` 对 isAttachedModule 不执行独立平移积分；位置来自母舰同步，只保留相关旋转/引擎表现。于是当前实现为不能独立移动的组件也算了完整的假设移动候选。

这不是“全部模块AI可以删”：防御、目标、独立旋转、系统回调和UI解释仍有作用。尤其avoidance还输入系统战术参数。**4.282ms不是可保证节省的数值，2.322ms也不是已经证明可无行为影响全删的收益。** 根因是职责未拆，而不是模块数量本身错误。

位置score试算：模块10,208次、根舰3,106次。避障候选：模块4,313次、根舰21,320次；总轨迹步×障碍配对1,659,320次。避障大量成本来自根舰，不能错误地全归给模块。

### B. 数值化仍保留全量矩阵和局部多候选搜索

`CombatEngine.ts:853` 每步planFleetAI；计数120次/120步。`FleetTactics.ts:79–93` 每步将存活实体读为数值行；`NumericalFleetPlanner.ts:25–35` 仍创建两张N*N矩阵，构建所有距离/影响。诊断包含耗时约 **2.438ms/步**。

`TacticalPositioning.ts:65–145` 对多个速度候选反复算自己的枪、射界、敌方枪、障碍与逃生；`TacticalNavigation.ts:81–146` 对避障候选逐轨迹步测试附近物体。之前的空间树缩小了附近列表，但没有改变这些内部乘法循环。

这里不是断言全量矩阵可以随意稀疏化；舰队分配有顺序、总和、claim和相同分数tie语义。它解释为什么“换成数值/加树”只会改善常数，不自动去掉工作规模。

### C. 开火仍有大量实际工作与重复阶段准备

每步处理约 **728.78个挂点访问**（含禁用挂点遍历），根舰开火规划4.059ms、模块3.761ms、飞机1.354ms，合计约 **9.174ms/步**。这些射击行为不能一概删去。

实际数值树查询61,294次/120步，粗筛后 **684,375候选行=5,703.13/步**；仍要做角色/拦截/射界/预算/阻挡精查。树指标sourceRows=10,315,368是原scope长度累加，**不是实际扫描了这么多行**；树已排除约93.37%的该候选基数。

`ShipStepBatch.ts:71` 每步创建CombatFireFrame；`CombatFireFrame.ts:26–40` 创建对象接触/位置平面、数值帧、另一个acquisition树。`NumericAcquisitionFrame.ts:68–91` 仍每帧做成员/prototype/不可变metadata/nativeVector/finite检查，再捕获阶段关系与状态。数值帧create包含约 **1.829ms/步**。对象规则适配层并未随着数值查询消失；profile也采到范围/系统修饰符/isPhased等读取。

可见开火的根因不是“树完全没用”，而是减少一次候选范围后，整个每挂点的规划/精查/适配链仍在，并且每帧重新准备多套查询表示。

### D. 确实有整帧回退，但不能用它解释所有高 ms

最终默认：120帧中114创建成功、6因unownedDefault拒绝。快速绑定返回111,207次，通用返回6,677次；**快速返回比例94.34%**。bind成功19,772，domain拒绝1,035，scopeFallbacks=0。

已记录6个缺少当前成员资格的飞机id，见 `count-final-summary.json/foreignFrameRows`。`ShipStepBatch.ts:49–52` contacts由先前entry/source名单取并集；数值帧稍后用当时的`owner.ships`重新核验。union中6个飞机对象已不在当前名单，严格默认因此拒绝整个数值帧，所有挂点走回退。这是**名单生存期/阶段成员证明不一致**，不是未知getter或完整重写失效。

最终264数值帧/270步不同于显式numeric=true的旧接受回执270帧；这次使用最终默认，不能用旧回执掩盖该差异。飞机被移除的具体事件未逐个记录；FighterSystem有死亡清理等路径，不能凭id虚构退场原因。

没有逐帧回退vs非回退耗时，不能声称回退只占5%的时间，也不能定量解释最大尖峰。CPU profile已在270数值帧版本下显示24.242ms的AI+fire，因此不存在“仅把这6次回退消掉就能60Hz”的证据。

## 4. 对前面小修的解释与下一步边界

之前主要修了对象读取常数、候选过滤、绑定开销。它们有效，但没有拆除通用模块移动规划、每tick全量舰队读表/矩阵、每mount多阶段规则链和多套临时查询表示。**这些是在同一串行关键路径上反复乘起来的任务规模；改指标或解除追赶限制不能消除它。**

后续如果进入重写，目标应是：拆出根舰平移与模块局部防御/武器/旋转职责；在严格阶段内合并热读与共同查询；修正名单生命周期的授权来源，而不是放宽外部对象守卫。保留dt、决策频率、RNG/求和/tie顺序和原有可见操作。不以减少单位/挂点、跳帧或改玩法伪装根治。

**本轮停在根因报告；尚未实施这些方案、测量反事实节省量或达到60Hz。** 生产快照中11个src文件hash仍与上一轮final-source相符。现场浏览器尖峰、跨机性能和原版等价性仍待核实。
