# Steam 格式选择与发送策略适配（2026-09-19）

## 范围与状态

本轮是 LAN 字段字典用于 Steam 的第三版**离线候选**，不是已启用的联网修复。没有启动 Steam、调用原生 SDK、绑定端口、邀请玩家、修改防火墙，亦没有打包部署。未改变协议协商、8 秒保护、物理频率、人数、舰船数量或字段精度。

## 具体改动

- `server/steam/experimental/selective-state-codec.mjs`：普通 `prepare` 完全沿用 SMF1/JSON；只有 sender 已选出完整信封后才试 SKD1 字典。与**当前 SMF1/JSON 赢家**比较实际压缩 payload 和应用分片开销，而不是只与 JSON 比较。至少额外节省超过16字节才采用，否则返回原对象。危险/超限数据保留旧路径。
- `server/steam/experimental/selective-anchored-sender.mjs`：先用原编码成本决定 anchor / delta / full，再替换完整信封的线上表示。`target.full` 不变，commit 映射回原 choice，保留 ownership、generation/revision、重复提交与 ACK/reset 失效保护。
- 小差分仍用原编码；不每个 offered state 都提前试字典。同一完整 reference 使用单项缓存供多人共享；清理缓存不破坏已经持有的包。
- 锚点刷新及差分收益判断继续按**原成本**计算；应用 flight/native admission 仍以**真正发出的包长**计费。没有虚构 ACK、扩大窗口或占用虚假的参考字节额度。

这里的“选择完整信封”发生在 `prepareState` 阶段，**不是确认包已经发送**：尚未开始的任务仍可能被更新状态替换。`selectionDiagnostics.selected` 和 `savedWireBytes` 仅是准备阶段的选中次数/潜在节省，不能当已发送流量。继承的 `snapshotBytes` 有意表示原格式的调度摊销成本，不表示候选线上流量。

## 验证方法

1. 单测：选择反例、真实字典赢家、缓存、危险输入回退、120次 offer 的惰性试编码、680帧跨锚点的策略解耦、完整状态/差分解码、commit/ACK/reset 防护。
2. 成本基准：三份完整32舰录制状态；9客机同锚点/错位锚点共享广播；预热、两轮反序、保留所有 raw samples。所有客机输出完整 JSON 相等。准备 fixture 与相等校验在计时区间外；首次全量的额外试编码成本单独计入。
3. 链路模型：原 room/session/wire/pacer + 显式 native lane/flight/FIFO 模型。仅在 artifact bundle 中替换 codec/sender/decoder；baseline 与 candidate 同样注入 fixture 与观测点。复用 packed bit **只适用于这个封闭模型，不代表完成新格式能力协商**。
4. 完整树重放保留录制文件所有舰船和字段，只替换 seq、matchId、tick、marker、producedAt；逐份检查实际交付的整棵 JSON 树。它不是实时战斗演算，更不是双机 Steam 实测。

第一份状态两轮首次完整编码 host median 为原方案的 **1.385 / 1.358倍**，超过原1.10门槛；对应 guest median 为 **0.820 / 0.874倍**。不能把首帧额外试编码的开销藏进预热，也不能用 guest 变快抵消 host 不合格。

9人共享、120帧的同锚点场景仅1次试编码（8次共享命中）；错位锚点9次。全部差分 payload 的 SHA-256 序列相同，逐包应用 wire 没有增大；四组 steady host ratio **0.969–0.994**，guest ratio **0.966–0.991**，均通过原1.10门槛。这个小状态基准没有实际选中字典，不能据此声称字典编码本身更快。

因此：**稳态门槛通过，首次全量 CPU 门槛未过，默认不开启。**

## 链路模型结果：必须保留失败

输出：`artifacts/steam-selective-state-20260919/link-1/`。12组中 **9组通过、3组失败**：原/候选 healthy-nine 都未达到既定吞吐门槛，候选 recorded-collapse-three 还发生断线。

### 原四个小状态固定场景

| 场景 | 原/候选每客机 steady Hz | 原/候选最大 age P95 | 结果 |
|---|---|---|---|
|healthy-three|59.4–60|164ms|均通过|
|healthy-nine|28.6–30.6|180ms|均未过每人≥40Hz、合计>420Hz门槛|
|collapse-nine|1.0–1.2|1692ms|均通过原骤降门槛|
|low-start-nine|2.6–3.2|936ms|均通过|

去掉新增格式统计字段后，四场景的整份 baseline/candidate 模型结果严格相等，包含各客机更新、FIFO、flight、超时与回收指标。此前旧候选的3272ms弱网回退未再出现；但这只是**不再损害原小状态路径**，不能解释成新字典路径已通过弱网。

这四场景的候选 SKD1 成功解码数都是0；其中3场有6次“准备选中”，但未到达解码器，所有可观测模型结果仍与原方案相同。准备次数分别6/386/575/617，不等于发送次数，证明拥塞时仍有未开始任务被替换的无效试编码，不能把单纯的缓存或惰性准备夸大为完全消除此成本。

### 确实经过字典解码的完整32舰重放

- 健康3客机：原方案59.8–60Hz，候选59.8–60Hz；age P95均156ms、均不断线。候选实际成功解码 **6个 SKD1 包**，完整JSON验证3964次（原3957次）。
- 带宽从8Mbps骤降至256Kbps，并叠加每37包丢包/每23包乱序：原方案9.8/16/13.8Hz，age P95为648/616/468ms，3客机均存活；**候选客机3在29760ms、客机2在30304ms断开**，主机最后失败为 `wire-state-ack-timeout`。候选虽实际成功解码4个SKD1包，且无解码错误，但两客机末5秒都无状态交付，不能用剩下客机22.2Hz/384ms掩盖失败。
- 候选 host FIFO峰值28065B，低于原34581B，**包/队列更小并不等于连接更稳定**。未改8秒保护来掩盖超时。
- 所有场景关闭后的 wire/native pending 都归零；这是清理通过，不表示仍然连通。关闭前的 candidate orphanBytes=17933仍如实保留在原始记录里。

目前仅能定位到模型的可靠状态ACK超时；不能断言用户真实Steam断开的根因相同，也不能声称每个差异已做因果消融。模型使用固定包序号丢包，包长/调度变化会影响后续丢包命中，仍需更多种子、时序分析和真实SDK验证。

首次汇总错误地把“准备选中”当作“必然送达”，报告断言因此失败。已改为独立统计选择和成功解码，保留原运行脚本与两份bundle的SHA-256，并对12份已完成的原始场景记录做 `--report-only` 校验和重新汇总；没有重新挑选更有利的网络样本。汇总仍以exit 1保留上述3组真实性能/连接失败。

**决定：这版候选不进入默认联机。** 首次全量CPU与完整树弱网连接两项都不合格，不能以小状态回归通过替代。
