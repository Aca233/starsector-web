# Phase23：优先发送关键状态，解除本地回执等待，复用同帧编码

日期：2026-09-21。**本轮改动已实现，但没有完成“所有客机稳定完整状态 60 Hz / 所有负载延迟下降”的目标。**

## 已落地、默认启用的改动

1. **小状态在完成物理步后优先发布**：运动状态和已启用的关键战斗状态不再等本轮全量 `capture/encode` 完成；追赶物理步时也可在完整步边界发布。仍遵守各自单槽背压，不发布半步状态、不重复同 tick、不修改 1/60 物理步或六步追赶上限。当前普通 LAN 场景启用的是运动流；不要把尚未协商启用的关键战斗字段说成已启用。
2. **本地 I/O 完成记录**：在隔离环境中，现有 socket Worker 用每私有端口 **52 字节**共享内存记录实际 `send`/`skip` 处理结果。权威 Worker 可轮询精确 tick 的完成记录，不必再等待消息回执排到事件循环。原 MessagePort 回执仍负责唤醒和不支持 SAB 时的回退。单槽大小、远端消费 ACK、服务器信用窗口都没增加。这不是远端收包确认。
3. **同一采集帧的展示/网络双通道复用编码片段**：只缓存刚采集的不可变 `world/ships/crafts/craftSpecs/layouts/deployment` 根字段；音效、物理输入确认和性能头每次仍重新写。生命周期沿用现有 `capturedFrame` 的精确 tick/engine 失效规则；缓存量不超过帧字节上限，首个输出被 transfer 后也不会破坏缓存。两路本来就能共享整包时不再额外分配缓存。输出仍是字节一致的 SWF2，不引入新网络协议或重连基线。
4. 日志新增 `hud.authority.io.sharedCredit/sharedCompletions`、`hud.authority.captureReuse.encodedFragments`，能核实是否真正启用/复用，而不是仅显示目标频率。

以上共享 LAN/Steam 浏览器权威代码；Node 专服和非隔离浏览器保留原回退。构建级回退分别为 `VITE_LAN_LOCAL_IO_CREDIT=false`、`VITE_LAN_CAPTURE_ENCODING_CACHE=false`。没有改生涯模式、原版玩法、UI、n2n/防火墙或用户桌面。

## 没有假装做完的部分

- **全量采集和首次编码仍在权威 Worker**。本轮是优先级/完成通知/重复工作优化，不是把完整序列化彻底搬到另一个线程。
- **没有新增跨帧低频字段协议**。当前 P1 已不传静态 spec/大量仅模拟字段，已有无损增量和压缩继续有效。本轮消除的是同帧重复编码，不能把它说成减少了 VPN/互联网实际线速字节。
- 没有改高 Hz 显示、复制帧凑数、提高接收信用伪造消费 ACK，或把插值画面 FPS 当权威状态 Hz。
- 没有实际多机 n2n 或 Valve/Steam SDK 对局验证，也没有提交、推送、发布或更新用户安装包。

## 验证结果

### 完整双通道准备函数：相同世界、逐包比对

`paired-encoding-cache.json`：22 舰、169 弹体、tick600，120 组交替先后顺序，两种回执顺序，实际 transfer 输出。

- 平均同帧两通道采集/发送准备耗时：**6.33 → 4.96 ms（约 -22%）**；P50 6.10 → 4.78 ms，P95 8.43 → 6.46 ms。
- 两边都仅采集120次；240个发布输出逐字节相同，原世界哈希不变。
- 这是局部函数耗时，不是网络 RTT 下降22%，也不是整场游戏加速22%。最终重新构建/复跑另存 `paired-encoding-final.json`，不覆盖第一次证据。

### 实际渲染、5 人 22 舰，同机回环比较

seed917，5个真人席位使用 Onslaught、17艘AI Hammerhead，真实 LanBattle/Worker/桌面 helper/WebGL，各窗口20秒。不是禁用渲染的跑分。

第一组有效观察（`probe-v2-control` / `probe-final-repeat`）：

| 指标 | 改前 | 改后 v2 |
|---|---:|---:|
| 物理采样率 | 59.93 | 59.94 |
| Worker 全量发布/s | 34.27 | 42.05 |
| 中转实际转发到各客机/s | 33.20–33.70 | 36.15–36.85 |
| 客机运动 Hz 的采样中位数 | 27–29 | 51–56 |
| 客机完整 Hz 的采样中位数 | 28–31 | 38–40 |
| 客机输入确认 P95 | 81–86 ms | 78–88 ms |

实际转发均值与 HUD 采样中位数是不同统计，不能混为一谈。v2权威末样本共享完成617次、编码片段复用2238次，确认功能确实运行。

最终 v3 避免“已共享整包时再缓存片段”的额外分配。第二组有效运行 `probe-v3-control` / `probe-v3`：

- 客机运动中位数 **27–28 → 47–50 Hz**；完整中位数 **28–31 → 31–34 Hz**。
- **输入确认反而从75–86升至107–130ms**，不能宣称本轮已经稳定降低端到端延迟。
- v3整段物理约57.85/s，发生恢复/接收信用计数重置；权威探针完整子窗口58.17/s。重置后的累计 ACK 不能相减计算负 Hz，汇总工具现在明确标为 `ackCounterReset`，消费率置 null。
- 两段测量期整机CPU忙碌均值约83%与89%，峰值约92%与98%。这说明运行负载不同，但不是特定进程/改动导致回退的证明；不据此替失败结果开脱。
- 原因仍包含全量采集/首次编码、物理与渲染争用，以及客机实际消费/回执背压。生产更多包不等于客机就能全部消费。

### 最终 v3 连通/阻塞/重连验收

真实渲染，每组22舰、15秒测量，再阻塞房主主线程800ms、同局重连、关闭房间和回收资源；不降低既有断言阈值。

| 人数 | 客机运动 Hz 中位数 | 完整 Hz 中位数 | 阻塞中450ms内实际全量发布 | 同局重连/清理 |
|---|---:|---:|---:|---|
| 3 | 60 | 51–52 | 28 | 通过 |
| 4 | 59 | 30–31 | 20 | 通过 |
| 5 | 42–44 | 24–26 | 24 | 通过 |

三个场景都实测客机输入确认在房主主线程阻塞期间继续前进。五人重负载依然没有完整60Hz，不能用三人结果替代五人保证。

### 失败证据保留

`validation.json`列出所有尝试及清理结果。早期原始对照与候选都有持续过载失败；另有一次私有测试探针唯一锚点失效（修复探针后重跑）、一次欢迎握手超时、一次阻塞450ms只发4包而低于原有5包门槛。失败日志未删除、未修改生产超时/验收阈值使其“通过”。这些运行不计作性能验收；最终3/4/5人验收均另存。

**结论：关键运动流的低 Hz 有实测改善，同帧重复编码也减少；但完整60Hz和高负载下稳定低延迟尚未解决。** 下一步若继续，需要实质拆离全量序列化并按真实消费能力安排重/轻状态，而不是再盲目加发送频率或接收信用。
