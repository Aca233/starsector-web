# 联机实施计划：客户端主机计算 + 服务端中转 + 局域网部署

更新日期：2026-09-17
状态：P1 双人局域网预览版已实现并完成本机双浏览器验证，详见 lan-multiplayer.md。其余阶段仍为计划；十人百舰容量、跨物理设备网络和后续高级功能未验收。

## 1. 已确定的方向

- 保留现有单机模式、配装流程和 WebGL2 渲染，不因联机迁移 WebGPU。
- 战斗计算尽量留在客户端：由指定的计算主机运行整场权威模拟。
- 独立的服务端程序负责房间、身份、输入路由、状态转发和连接管理，不运行完整战斗模拟。
- 同时支持两种部署：独立机器运行中转服务；局域网主机电脑同时运行中转服务和游戏客户端。
- 两种部署共用协议和游戏逻辑，只改变连接地址和运行位置，不维护两套联机实现。
- 先做双人可玩闭环，再验证单房间 10 名玩家、约 100 艘参战舰船。后者是压测目标，不是已验证容量。
- 适用于朋友之间信任计算主机的对局，不承诺严格竞技防作弊。

术语：

- 房主：管理房间、配置规则和开始对局的玩家。
- 计算主机：承担完整战斗模拟的玩家客户端；可以不是房主。
- 中转服务器：管理连接和分发数据的 Node.js 服务，不是战斗伤害裁判。
- 普通客户端：发送操作，进行本地预测、插值和画面显示。

## 2. 两种部署方式一起纳入计划

### A. 独立服务器中转

计算主机 → 中转服务器 → 其他玩家：发布战斗状态与事件。
其他玩家 → 中转服务器 → 计算主机：发送操作命令。

服务器可运行在另一台局域网电脑。后续若需要异地联机，可在同一协议上增加公网部署与 HTTPS/WSS 配置；当前不部署公网服务。

### B. 局域网同机部署（优先交付）

一台玩家电脑同时运行：

1. Node.js 中转服务及游戏网页/资源服务。
2. 游戏客户端，其中独立 Worker 负责权威模拟，主线程负责操作和渲染。

其他玩家连接同一路由器，通过主机的局域网 IP 和端口打开游戏并加入房间。主机自己也以客户端身份接入，使用与普通玩家一致的消息协议。

- 不需要购买额外服务器、公网 IP、域名或路由器端口转发。
- 计划提供统一启动入口和可读的局域网访问地址；命令在实现前不视为已存在。
- 仅提供游戏构建产物、明确允许的资源和联机接口，不暴露工作区、原版安装目录或任意文件。
- 明确选择监听地址与端口；提示用户允许 Windows 专用网络通信，不自动修改防火墙或路由器规则。
- 提示主机有线连接、十人场景优先千兆网络，并检查访客 Wi-Fi / AP 客户端隔离。
- 主机电脑同时承担模拟、渲染和中转，省去的是额外机器，不是消除这台电脑的计算负载。

## 3. 权威与职责边界

| 组件 | 职责 | 不负责 |
| --- | --- | --- |
| 中转服务器 | 房间、成员身份、阵营/席位、控制权授权、主机任期、准备状态、协议校验、转发、断线检测 | 全场 AI、物理、伤害、独立验证战斗结果 |
| 计算主机 | 所有舰船 AI、移动、武器、弹丸、碰撞、伤害、胜负、权威状态发布 | 向其他客户端直接开放连接 |
| 普通客户端 | 操作采集、自己舰船的有限运动预测、远端状态插值、画面和音效 | 决定最终血量、命中、死亡、胜负 |

初版不做“十台电脑分别权威计算十艘船”，不采用所有客户端完整重算世界的严格帧同步，也不按每位玩家分配一份独立战斗。

未来只有在实测证明 AI 是主要瓶颈时，才考虑下放非权威 AI 决策；最终行动执行和伤害判定仍归计算主机。

## 4. 房间与对局流程

1. 创建房间或输入房间码加入，取得成员凭证与重连凭证。
2. 选择阵营、旗舰、允许的配装和 AI 舰队；房间限定总舰船数及规则。
3. 房主指定计算主机；不把创建房间的身份与计算权威硬绑定。
4. 检查协议版本、内容版本和双方可用配置；不匹配时开战前明确拒绝。
5. 主机创建初始战斗状态；所有客户端完成资源准备并确认后开始。
6. 战斗结束后，由有效任期内的计算主机提交结果，回到房间，可再次准备开战。

默认从两个阵营开始，允许双人对战或同阵营合作对 AI。更多阵营、自由混战及中途改变阵营不在首版范围。

玩家身份、阵营、实体 ID、当前控制舰船 ID 必须分别表示。不能继续用“本地玩家/敌人”二值概念同时代表控制权和阵营。

单机存档与联机对局隔离，首版不写回永久战损、奖励或舰队资产。

## 5. 时间步、输入和显示

初始调试参数，不是已经验证的网络或性能保证：

- 计算主机保持现有 60Hz 固定模拟步长。
- 连续操作约 30 次/秒发送；主机在模拟步边界消费输入。
- 状态广播约 20 次/秒；渲染帧率独立于网络频率。
- 远端插值缓冲初始约 50–100ms，依据网络抖动调整。
- 不等待所有玩家每一帧输入到齐；输入超时清零，避免无人控制时持续开火或推进。

输入协议应包含对局 ID、成员身份绑定、控制对象、输入序号、估计模拟步以及操作内容。

- 连续输入表达当前按键/瞄准状态。
- 开火触发、切换护盾、使用系统等离散操作分别编号，确认和去重，不能因位置快照合并而丢失。
- 主机自己的操作也经过同一命令执行边界，不依靠 UI 直接改动模拟对象。
- 普通客户端只预测自己的有限运动并保存尚未确认的输入；收到确认状态后重放未确认输入并校正。
- 不在普通客户端独立决定碰撞、伤害或整场战斗结果。小偏差平滑修正，大偏差明确服从主机。
- 原始网络状态与显示位置分离，渲染插值不得反写权威状态。

## 6. 状态同步与带宽预算

### 开战初始化

发送配置、成员/舰船归属、阵营、初始状态、规则、随机种子、对局 ID 和主机任期。配置采用内容 ID 引用，避免重复发送静态定义。

### 状态快照

包含模拟步、快照序号、基线标识、已处理输入序号，以及舰船、重要弹丸等动态状态。

- 先实现可恢复的完整状态，再加入差量快照、紧凑字段和必要的二进制编码。
- 差量必须引用客户端确实拥有的基线；缺失时请求完整状态，不猜测应用。
- 周期性提供完整状态恢复点，并支持重连、入场加载后追上当前对局。
- 收到过期对局、旧任期或倒退序号的数据时拒绝应用。

### 战斗事件

开火、命中、爆炸、死亡和系统启动采用独立事件 ID 去重。普通弹丸可按生成参数重建显示轨迹，制导或其他非直线运动按需修正；销毁和伤害仍以主机为准。

纯视觉粒子、烟雾、镜头与装饰效果本地生成，不逐颗同步。不进行画面视频串流。

### 背压与限流

- 输入、重要事件和状态更新分开处理。
- 尚未进入发送队列的旧位置快照可合并；不能随意丢弃已有基线依赖的差量或重要事件。
- 限制消息大小、发送频率和每连接缓冲量。持续过慢的连接停止增量流，断开或要求重新同步，不无限堆积内存。
- 服务器向其他玩家复制主机上传的数据；不能把 CPU 节省当作带宽也同比降低。
- 实测记录主机上传、服务器总出站、单客户端接收及峰值。十人百舰下同时统计弹丸数量，而不是只统计舰船。

## 7. 主机 Worker 与现有项目接入

- 将模拟生命周期从 React/渲染循环分离，整理音效、DOM、资源准备等依赖后，在 Dedicated Worker 中运行权威战斗。
- 主线程继续使用现有 WebGL2 渲染，接收适于显示的数据，不每帧复制全部带循环引用的游戏对象。
- 复用现有战斗规则、舰船、武器、固定步长和随机源；联机入口与现有单机入口分开。
- 不能把现有存档或只含画面字段的快照视作完整战斗检查点。
- Worker 只能减少模拟直接阻塞 UI，不能保证后台标签页、系统休眠或进程挂起时持续正常推进。
- 检测模拟停顿，通知客户端进入等待状态；不在恢复后无限补算积累的时间步。

## 8. 断线、主机退出与恢复

| 情况 | 首版处理 |
| --- | --- |
| 普通玩家输入超时/断线 | 清除持续输入，主机上的临时 AI 接管；设重连保留窗口 |
| 普通玩家重连 | 验证重连凭证、替换旧连接、发送完整状态；追上后交还控制权 |
| 慢客户端或状态落后 | 限制外推，请求完整同步；不拖住其他玩家的模拟 |
| 计算主机短暂卡顿 | 提示等待主机；限制客户端预测时间 |
| 计算主机退出/崩溃 | 对局进入暂停或失败状态并明确结束，不静默产生第二份权威 |
| 中转服务关闭 | 显示连接中断；同机局域网部署关闭主机电脑时整场结束 |

后续完整主机迁移需要：

1. 保存 AI 内部状态、随机源、武器冷却、系统状态、弹丸、输入确认位置等可恢复的完整模拟检查点。
2. 服务端先冻结对局，只选出一个新计算主机，分配新任期并拒绝旧主机继续发布。
3. 通过检查点和必要的有序输入/事件记录恢复，客户端重新同步，准备后继续。
4. 单独验证恢复一致性与等待时间，不承诺无缝或零丢失迁移。

检查点恢复仅解决可用性，不让服务器获得独立防作弊能力。

## 9. 安全与信任模型

- 玩家只能控制被授权的舰船；服务器检查房间、身份、控制权、消息结构、频率和体积。
- 只有指定计算主机能发布本对局的状态、事件和结果；任何客户端提交的身份字段都不能代替连接认证。
- 房间码用于发现房间，不单独充当可伪造的控制凭证；重连凭证与成员绑定。
- 对网页来源、WebSocket 升级请求和静态资源路径做校验；不开放任意服务端命令或文件访问。
- 受信局域网可从 HTTP/WS 起步，但不提供链路保密性；公网或不受信网络必须另行配置 HTTPS/WSS 和访问控制。
- 可防止普通客户端越权发消息，不能阻止计算主机伪造伤害和胜负。
- 主机本地确认更快，客户端预测不能完全消除主机优势。严格竞技公平与独立战斗审计不属于该轻量架构的承诺。

## 10. 实施阶段与完成标准

阶段进度（复选框表示该阶段的实现，不代表全部规模与网络环境已验收）：

- [ ] P0：确定协议、实体归属和生命周期边界；记录当前单机性能基线，确认无浏览器依赖的模拟入口。
- [x] P1：局域网同机启动、网页资源服务、房间/准备、双人各一艘船，打通操作 → 主机判定 → 状态分发 → 结果 → 再开一局。
- [ ] P2：本地预测、远端插值、输入/事件去重、完整状态恢复；验证独立中转机器与同机部署使用相同协议且均可游玩。
- [ ] P3：计算主机 Worker 化已提前用于 P1；继续实现阵营及 AI 舰队，逐级压测 2/4/10 人与 2/20/50/100 艘船；不直接把目标上限标记为可用容量。
- [ ] P4：差量/紧凑编码、背压、普通玩家重连、临时 AI 接管、长时间对局与后台停顿处理。
- [ ] P5：在可恢复检查点完整后，开发主机迁移，再考虑观战、中途加入和公网部署。

验收要求：

- 单机模式、原有配装和存档行为不被联机修改破坏。
- 两种部署均能从加入、准备、战斗走到结果和下一局；使用真实不同设备验证，不以同机两个标签页替代全部网络验收。
- 血量、命中、死亡和胜负保持一致；死亡、开火等事件无重复结算。
- 不会控制他人舰船，断线后无残留按键，重连不会产生重复成员或第二个控制者。
- 非主机玩家卡顿或断线不阻塞全场；主机故障时有明确行为而非无限黑屏等待。
- 记录模拟步 CPU 耗时分位数、渲染帧耗时、消息延迟、校正频率、带宽、内存和队列峰值。
- 60Hz 目标下为模拟、序列化和调度留出余量，不能仅凭平均值小于 16.67ms 宣称稳定。
- 服务器与同机部署分别统计资源；不把负载搬到玩家电脑宣传为整场总计算量消失。

遵守当前项目要求：后续使用类型检查、lint、构建及明确范围的直接运行验证；不因本计划重新创建已被要求移除的测试文件/测试运行器，也不进行手工资源哈希或大小审计。

## 11. 暂不承诺

- 不承诺百舰稳定帧率、固定服务器 CPU 节省百分比或固定硬件容量。
- 不把“网页可被局域网访问”当作已经实现战斗联机。
- 不实现游戏视频串流、强制 WebGPU、多客户端分片权威物理或严格全员帧同步。
- 首版不包含账号平台、自动匹配、排行榜、永久战役经济或完整反作弊系统。

最终架构：保留单机；计算主机统一模拟；轻量服务器中转；局域网同机和独立服务器部署共享实现；普通客户端预测与显示。先验证双人闭环，再逐级扩展并记录真实容量。
