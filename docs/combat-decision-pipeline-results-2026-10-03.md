# 战斗高 ms 根因与结构性修复（2026-10-03）

## 结论

高 ms 是每步实际 CPU 工作超出预算，不是可以简单取消的网络/计时器限速。本次已改执行结构，而非继续给 getter 加缓存：原有只读决策边界统一覆盖主舰和附属模块，舰队分配由对象嵌套查询改为数值批处理。已接入实际主机 Worker，并在受验证范围内默认启用。

**同一重载场景 55.27 → 39.79 ms/步，降低 28.0%；仍未达到 60Hz 所需的 16.67 ms，不能宣称整个模拟速度问题已解决。**

## 根因证据

- 场景显示 22 艘主舰，实际参与模拟的是 176 个实体：56 个附属模块、98 架飞行器，共 734 个武器挂点。只看主舰数严重低估工作量。
- 原有 `nativeThreatPhase` 要求整批满足纯 native hook；22 个 authored 主舰不满足，导致整阶段的共享关系/导航索引没有启用。154 个其它实体满足 native，全部 176 个满足当前 exact-authored 条件。不是因此删除安全门，而是使用已有封闭主机和精确行为的额外准入。
- 旧索引在主舰规划后关闭，56 个模块的完整目标、威胁和避碰规划仍重新扫全场。旧导航把最快飞机/最大舰体带来的边界扩大到整个索引，且扫描还重复读取本来就不作为障碍物的飞机状态。
- 舰队支援/压力/评分多次穿过 Ship/Vector/系统读取计算相同单位关系；光束和其它来源解析重复 `ships.find`。
- 先前保留的同场景阶段测量：舰船 AI 19.44 ms、火控 15.44 ms、飞行器 5.93 ms，而物理积分仅 0.80 ms。说明不能把“物理”当成主要原因；这些数值来自之前窗口，不冒充本次对照数字。2701-sample CPU profile 的包含栈计数有重叠，也不能加成耗时占比。

## 改动的实际结构

1. `CombatDecisionScene` 在既有延迟提交的主舰+模块规划阶段建立一次敌对关系、源 ID 和空间关系。模块不再被留在阶段外；控制/效果/飞行/物理前关闭，失效引用退回实时读取。
2. 避碰 broad phase 按非飞机实体建树，每个节点用自身最大半径/速度做保守筛选，而不是被全局极值撑大。返回顺序不变，仍用原有精确距离/扫掠风险逻辑；异常输入退回旧扫描，没有截断候选上限。
3. `NumericalFleetPlanner` 一次编译既有 readiness，批量构建距离/影响表，保留原顺序浮点求和、逐舰占用分配、目标粘性对象身份、显式命令、分数并列规则与进攻路线。没有减少决策次数或换战术规则。
4. 接入 `CombatEngine`、`CombatAIPhase`、`ThreatAssessment`。主机已通过的结构化数据命令边界内默认启用；未注册或自定义 inline 引擎保留旧实现。`VITE_COMBAT_DECISION_PIPELINE=false` 可明确禁用。先前负收益的 state-core/复制 motion 仍默认关闭。

## 同场景对照

既有 2 玩家/20 AI、三种 authored 舰体、seed 917，双方都使用同一数值火控实现及原有其余开关。唯一算法差异是本次决策管线。ABBA，每组预热 150 步、计时 120 步。

| 项目 | 旧管线 | 新管线 | 降幅 |
|---|---:|---:|---:|
| 全模拟步平均 | 55.2655 ms | 39.7904 ms | 28.0% |
| fleetAI 阶段平均 | 18.7128 ms | 10.5600 ms | 43.6% |

四组原始全步平均依次为 56.810669、41.397033、38.183758、53.720349 ms。没有只挑最好一组；单机四组结果不能代表所有设备。火控/飞行器算法本轮未改，不能把它们的跨阶段时间变化归因于独立重写。

每个新管线组 270 步执行 20,520 次主舰/模块规划，其中模块 15,120 次；导航原全场源行计数 3,588,188，保守树返回 224,624 个候选（减少 93.74%）。这不是“所有碰撞计算减少 93.74%”。同样场景、同样决策次数和完整随机状态，没有减单位或提高 dt。

四组 270 步完整状态/随机见证相同，结束均为 170 实体、90 弹体、玩家 235 发/敌人 243 发。另有 12 组稠密舰队命令/相位/幅能/位置输入完整 FleetPlan 精确对照，`standard` 和 `large-battle-v3` 实际同步/Worker 场景对照，以及生命周期/异舰/换表/非有限数回退检查。不是只测一个 DTO。
