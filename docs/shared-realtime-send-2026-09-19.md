# Steam / LAN 共享实时发送准入（2026-09-19）

## 结论与适用范围

本次把浏览器端的连续输入、快照发送准入做成同一套策略，Steam 与 LAN 均由 `LanConnection` 使用。减少的是**浏览器 → 本地/局域网中继的已过时发送积压**，不是替换两种底层网络。

这不是“真实 Steam 延迟已降低到某个毫秒数”的证明，也不代表所有弱网断线已修复。没有打包桌面端，没有进行两台电脑或真实 Steam 会话验收。

- 60Hz 物理步进、正常网络的输入节拍及原 `InputSendBudget` 不变。
- 不缩减舰队、不删字段、不量化数据、不改协议版本、不放宽 8 秒超时。
- LAN 现有二进制/JSON 分支保留；Steam 不因此开始接收 LAN 二进制格式。
- 默认 Steam 仍是 `gateway.mjs` 的旧可靠 P2P（`sendP2PPacket(..., 2, packet)`）。Sockets v012 仍属实验注入路径，不能用它的测试结果代替默认 Steam 路径。
- 上一轮未通过 CPU/弱网门槛的 selective/SKD1 候选仍未接入默认路径。

## 官方资料和 GitHub 调研

1. [Valve GameNetworkingSockets](https://github.com/ValveSoftware/GameNetworkingSockets)：可靠/不可靠消息、分片、不同 lane 的优先级和权重等属于传输机制。上层快照压缩/差分并不是该库替应用自动完成的工作。
2. [Steam Networking Types](https://partner.steamgames.com/doc/api/steamnetworkingtypes)：发送队列延迟和 RTT 是不同指标；`NoNagle` 仅跳过小包聚合等待，不能消除拥塞队列；`UnreliableNoDelay` 会丢弃不能及时发送的不可靠消息，并非“可靠且零延迟”。
3. [ISteamNetworkingSockets](https://partner.steamgames.com/doc/api/ISteamNetworkingSockets)：lanes 可分隔不同流的队头阻塞，不能依赖跨 lane 的接收顺序。
4. [GameNetworkingSockets #68](https://github.com/ValveSoftware/GameNetworkingSockets/issues/68)：按上层序号舍弃过时更新有参考价值，但不能把离散动作与可覆盖状态盲目一起丢掉。
5. [GameNetworkingSockets #108](https://github.com/ValveSoftware/GameNetworkingSockets/issues/108)：大初始同步、小增量及避免强推发送速率的讨论可供设计参考。这是历史讨论，不作为当前 SDK 拥塞控制实现的精确说明。

本次采用的是在应用入口限制过时数据入队、区分连续状态与离散操作的原则。**没有**据此直接打开不可靠发送、调整 SDK 全局发送率、切换默认 Steam SDK 或添加新网络依赖。

## 实现

### 共用准入门 `RealtimeSendGate`

- 不拥有 payload 队列；忙时由生产者下次回调重新采样。
- 本地队列为空时，可发一份快照或输入。
- 新提交的消息可以带**另一类的一份伴随消息**：输入 → 快照或快照 → 输入都可以。
- 伴随许可只持续一个 60Hz 周期，且只在成功发送后消耗；探测不会延长许可。
- 伴随消息不会再派发另一张许可，避免“快照/输入交替”形成无限队列；同类不能连续追发。
- 两种回调顺序均测试，避免房主的某一类消息由于总是排第二而永久饥饿。
- 关闭连接清理许可；异常缓冲量不放行。

`bufferedAmount` 是浏览器 WebSocket / I/O Worker 的本地发送计数，**不是** Steam SDK 队列长度，也不是端到端 ACK。这里的保护不能撤回已经交给内核或 Steam 的字节。

### 连续输入和离散动作

旧入口在 `bufferedAmount > 65536` 时直接 `actions = []`，可能把尚未提交的开盾等操作一起清空。

新入口在背压检查成功之后才消耗发送预算并构造输入：

1. 忙时不构造输入、不推进 seq，也不因积压直接清掉已有动作。
2. 恢复后读取当前按键/瞄准，不补发每一帧历史控制状态。
3. 本地发送返回成功才推进 seq、记录预测和清除已提交动作。
4. 发送失败保留 seq 和已有动作；下一次正常回调重试。

保留原来最多 16 个待发动作的上限及显式失焦/reset 清理逻辑。因此这里不是无限动作缓存，也不能承诺任意长断网期间所有操作永不丢失。发送成功只代表**本地准入成功**，不是对方已执行；生产者中保留的动作也不能算已经交付。

ping、`state-consumed`、部署、finish、leave 等不受新增实时准入门限制，但仍遵守原连接状态、大小及底层传输限制。它们并不因此能在 TCP/可靠 P2P 中越过已经发送的数据。

快照忙时在外层封包前返回 skipped；Worker 已经产生快照本身的 CPU 工作不被此处撤销。大型快照自身的编码、传输耗时仍需另行处理。

## 验证口径

- `scripts/check-realtime-send-policy.mjs`：编译实际 `protocol.ts`，提取实际 `LanBattle` 的 `sendInput`，WebSocket 构造器直接抛错，禁止真实联网。26 项通过，包括 LAN 二进制保真、失败发送保留动作/序号、关闭清理和两种回调顺序各 600 次快照+输入。
- `scripts/bench-realtime-send-policy.mjs`：修改前后实际客户端和 UI 生产者，共享一套虚拟本地 FIFO；LAN/Steam 各自覆盖 input-only、state-only、混合（快照先/输入先），健康、低带宽、骤降后恢复。
- 快照为约 30KB 合成 JSON，不是完整 32 舰实战；模型不含 Steam 路由、真实丢包、远端绘制或用户操作到显示延迟。
- 16 秒持续以 60Hz 提供样本，再排空已提交队列；拥塞时实际接纳的网络更新会减少，**不等于物理模拟降频**。
- FIFO age 只算本地入队到模型排出，不含动作在生产者里的等待时间。不能把它当作真实 ping 或按键响应延迟。

完整结果及哈希保存在 `artifacts/shared-realtime-send-20260919/`。第一次大回归的浏览器 roster 测试由于未安装 Playwright 无法启动，不能算通过；没有为了绕过它安装依赖、占用浏览器或开放服务端口。

## 本地 FIFO 对比结果（最终 fifo-3，共 48 组）

LAN 与 Steam 共用入口在该模型中结果相同。以下只列一份；单位为 ms、B，提交数为整个 16 秒采样期的本地准入次数，不是远端渲染帧数。

| 模式 | 场景 | FIFO age P95，旧 → 新（ms） | 峰值排队，旧 → 新（B） | 接纳消息数，旧 → 新 |
|---|---|---:|---:|---:|
| 仅输入 | 健康 | 0 → 0 | 172 → 172 | 960 → 960 |
| 仅输入 | 低带宽 | 16022 → 36 | 65684 → 172 | 893 → 320 |
| 仅输入 | 骤降后恢复 | 3858 → 36 | 37936 → 172 | 960 → 640 |
| 仅快照 | 健康 | 12 → 12 | 30079 → 30079 | 960 → 960 |
| 仅快照 | 低带宽 | 353 → 229 | 46449 → 30079 | 71 → 69 |
| 仅快照 | 骤降后恢复 | 341 → 229 | 46459 → 30079 | 515 → 514 |
| 混合，快照先 | 健康 | 12 → 12 | 30251 → 30251 | 1920 → 1920 |
| 混合，快照先 | 低带宽 | 348 → 230 | 46556 → 30250 | 1026 → 138 |
| 混合，快照先 | 骤降后恢复 | 334 → 229 | 46580 → 30251 | 1473 → 1028 |
| 混合，输入先 | 健康 | 12 → 12 | 30251 → 30251 | 1920 → 1920 |
| 混合，输入先 | 低带宽 | 342 → 230 | 46451 → 30250 | 1026 → 138 |
| 混合，输入先 | 骤降后恢复 | 317 → 12 | 46357 → 30251 | 1473 → 1028 |

参数：健康 2,500,000 B/s；仅输入弱网 4,096 B/s；快照/混合弱网 131,072 B/s；骤降发生在第 4 秒，第 12 秒恢复。输入与快照均按 60Hz 提供样本。

**必要的代价说明**：低带宽时混合流的 138 次准入是约 69 份快照 + 69 份输入，不是仍有 60Hz 的实际远端更新。省掉的是过时样本积压。动作检查统计的是“已交付 + 仍由生产者保留”；持续弱网结束时有 1 个动作仍待发送，不能当作已交付。模型不测动作等待时延。恢复场景 P95 会受恢复后大量健康样本影响，不能代替弱网阶段自身的表现。

## 扩展回归中尚未解决的问题

默认 Steam 的共享上行模型有 **1 项失败**：

- 测试：scripts/check-steam-shared-link.mjs 中 9 guests、8 Mbps → 256 Kbps、保持 8 秒超时。
- 上行在虚拟第 12 秒骤降，9 个客机约在第 20.168 秒以 1013 / Steam link stalled 关闭，随后房主关闭对应连接。
- 该模型直接运行默认 gateway 和虚拟可靠链路，不经过本轮的浏览器发送入口；gateway 及 reliable queue 与本轮前哈希相同。
- 因而这次共享入口修复**没有覆盖该严重弱网断线**，不能将扩展回归报成全通过，也不能据此宣布可以无风险发布。
- 其余 5 项共享链路模型通过。默认输入队列独立回归 1470 个断言通过。原大回归输出（149 项中 148 通过、1 失败）保留为 tests-final.txt；其中实时策略测试是补完双向顺序前的 23 项，最新为单独重跑的 26 项，不混淆计数。

lint、TypeScript 检查及 48 组 FIFO 对比通过。最终核心回归 146/146 通过（含最新共享策略 26 项）；扩展共享链路仍为 5/6 通过。每条命令退出码见 core-final.txt、verification-exits.json。浏览器 roster 测试尚未完成（缺少 Playwright），没有双机实测或桌面打包。

## 修改边界

生产修改仅限 `src/network/RealtimeSendPolicy.mjs`、对应类型声明、`src/network/protocol.ts` 的准入调用及 `src/network/LanBattle.tsx` 的 `sendInput` 和 import。

`before.json` 保存本轮开始时的源码哈希。原输入预算、协议配置、默认 Steam gateway 及 reliable queue 的哈希保持不变。工作区其他音频、画质、舰船系统、更新器等并行修改不属于本轮，未覆盖或提交。

## 仍需真实验收

重新构建后，用两台电脑分别测 LAN 和 Steam：同版本、同舰队规模，对照健康网络与上行受限情况，记录网络更新率、发送积压、输入响应、快照新鲜度及断线原因。尤其要区分浏览器 → relay 的 RTT 与真实 Steam 端到端传输。

本次只解决共享入口上的一段排队问题。若 Steam SDK 的可靠队列、路由、远端消费或超时仍是瓶颈，需要依据实际指标继续定位，不能用本地模型推断已经修复。
