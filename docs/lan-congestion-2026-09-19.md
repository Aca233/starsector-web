## 可复现的代码问题

原 `LanStateCredits` 使用最近五个原生 ping/pong RTT 的最小值计算 `ceil(RTT*60/1000)+1` 个在途帧（2～64，上限32MiB）。应用消费回执不参与网络 RTT，这一点是对的，但**原生 ping 同样排在快照所在的 TCP FIFO 中**。当大状态阻塞链路、旧低延迟样本被五个高延迟样本逐渐挤出后，窗口可能反而扩大，继续塞入更多状态。

`ws.bufferedAmount === 0` 仅表示 ws/Node 侧待发量，不代表已经进入内核 TCP、桌面桥接或远端线程的字节全部消费。因此原 socket 零缓冲门禁不能独自防止这个反馈问题。

## 本轮改动

- 原生探针发送时记录消费窗口 epoch、状态发送计数和是否无在途快照；接到匹配 pong 时传回同一个令牌。
- 只有整个探针期间没有在途状态、没有新状态发送的干净采样，才允许重新学习更大的 RTT 基线。忙时更低的有效采样仍可缩窗；忙时更高的采样**真实记录和显示，但不能用于扩窗**。
- 在 welcome 后立即发起一次原生探针，尽可能在加载资源、开始快照之前建立基线；后续沿用原有1秒探针定时器。全新连接在首个快照前、空闲发送队列上的首探针可建立初始基线，即使首批快照在pong返回前开始发送（FIFO不能让后来快照插到这个ping前面）；避免缓存资源快速开局使健康高RTT线路永久卡在2帧。此例外不适用于可能残留旧数据的reset epoch。大控制消息已排队时仍发送心跳，但标记为忙时采样。
- 清理/重同步产生新 epoch，旧探针不能污染新的统计。重连创建全新窗口。
- 仍保持原先2～64帧、32MiB预算、160条游戏请求/秒、60Hz目标、1/60物理步长。没有延长超时、改变快照格式/精度、删实体、丢弃已发送数据或给输入/结束控制套快照门禁。

**限制**：若开局前没有拿到干净样本，会保守使用2帧窗口，直到拿到干净样本。真实线路 RTT 在持续传输期间上升时，不再自动扩窗，可能暂时牺牲吞吐以避免积压；空闲时可重新学习，重连也会重新建立基线。此修复不是带宽估计器，不保证极低带宽或很大的单帧也能低延迟。

## 局域网专用诊断

沿用现有应用 pong 携带有限的只读数据，不新增高频 HTTP 请求或 SDK 采样：

- 中转累计收到房主多少帧、最近上传包未压缩大小、中转本次解码和校验耗时；
- 每个接收端的消费窗口占用、未压缩在途字节、ws 待发量；
- 最近原生 RTT 与用于窗口的 RTT 基线，忙时未用于扩窗的采样数；
- 已发快照数量，以及因 socket 忙、消费窗口满而跳过的**尚未发送**状态数量；
- 该服务端连接是否协商 permessage-deflate。

房主最多显示9个接收端，客机仅看到自身；不含 SteamID、resume token、玩家名字或地址。旧服务端无字段则不显示，Steam 不走该诊断。原生 RTT 到浏览器网络端/桌面桥接，不是GPU已呈现；显示“已协商”不表示每个小包都压缩，不伪造线上字节或速率。

### 单接收端离线模型（不是双机实测）

固定每帧44,324B、基线20ms、目标60Hz；4秒处从充足带宽降至100,000B/s（0.8Mbps），35秒恢复。模拟1MiB内核发送缓冲和有序传输，接收消费5ms；同FIFO中的原生心跳也会排队。它不模拟实际丢包、Wi-Fi、主线程CPU、压缩或游戏重连/超时。

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 最大窗口 | 55帧 | 3帧 |
| 最大实际在途 | 27帧 | 3帧 |
| 最大待传字节 | 1,092,868 | 130,480 |
| 弱网区间已到达状态年龄P95 | 10,937ms | 1,315ms |

弱网下每秒只能传约2.26个这样的包，**这次修改没有把带宽不足变成60Hz**，1.3秒也不是合格的实时体验。模型数字仅证明阻止了窗口的自我放大，不证明用户截图已修复，更不能用模型声称实际十秒积压不会触发游戏保护。

独立Steam共享链路回归仍为5/6：9客机共享上行8Mbps骤降256Kbps，约20.168秒仍出现 `Steam link stalled`。与既有基线失败一致，未删测试或延长8秒保护。这不是LAN截图的结论。
