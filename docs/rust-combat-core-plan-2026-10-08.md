# 常驻 Rust/Wasm 战斗内核迁移方案

日期：2026-10-08；状态更新于 2026-10-09。P0/P1 领域已验收；P2/P3 已有常驻完整战斗实现和七包各自整场到结算的差分证据，P4 已接入本地 Worker、LAN/Steam 权威与真实呈现/恢复。正式 Cargo/LTO 构建 cf8c3f8a 的完整混编 ABBA 已通过严格与几何合同，但性能未过：simulation TS32.334/Rust55.661ms，roundtrip TS51.824/Rust95.893ms，默认仍 TS、fullBattleReady=false。后续火控几何、近炸、系统发布及弹体投影优化必须绑定新正式构建重新完成性能门槛，再在同一 SHA 完成整场、UI、结算、联机恢复验收；历史其它 SHA 的成功不代替最终通过。实际回执见 [交付记录](rust-combat-core-results-2026-10-08.md)及各领域任务记录。

用户本轮接受 Rust 内核方向，并明确选择“浏览器与桌面共用 Rust/Wasm”以及“允许限定的几何舍入差异，规则结果严格一致”；桌面原生 Rust 是后续可独立评估项。本文是新方案，不复活 [2026-10-04 已撤回的全核心派工](combat-core-replacement-plan-2026-10-04.md)，也不重新启用失败的 TS 数值实验。

## 目标与玩家体验

在现有权威 Worker 内用常驻 Rust/Wasm 执行完整战斗规则，减少热循环对象间接读取、重复准备、分配与 GC；输入、UI、画质、舰船数、挂点、弹体、物理频率、真实射速、伤害及现有已启用规则保持。

玩家继续用当前部署、驾驶、自动驾驶、目标/武器组、技能、防御、战术命令、暂停/撤离和结果界面。语言迁移不成为新的玩法选项。性能目标通过同场景实际权威步和发布链证明；1.7–2.5 倍只是上一答复的条件估算，不是保证。能运行 Wasm、局部内核变快、搬运节点变少，都不等于完成。

## 范围与交付边界

最终迁入 Rust：

1. 完整实体身份/关系、舰队命令和 AI 记忆、主舰/模块/舰载机/无人机决策。
2. 挂点/武器组/tracker、弹药/装填/连射、瞄准/友伤/在飞火力预算与真实发射提交。
3. 舰体运动、局部时钟、模块姿态、terrain/引力、舰体和小行星碰撞。
4. 护盾/相位/幅能/装甲/结构、系统/舰装/伤害监听和生命周期。
5. 弹体/导弹/光束/近炸/空雷/穿透/爆炸/殉爆、死亡/停靠/补机/部署/胜负及结算必要统计。
6. 七个内置包当前使用的战斗能力；按注册能力迁移，不把舰体 ID 硬编码进通用求解器。

TS 保留资源/内容加载、配置与安装、外部输入/房间权限、既有传输、React/UI、绘图/音频以及不反作用于模拟的粒子/尾迹表现。纯表现算法可继续 TS，但其消费的随机流、事件时序与状态须纳入对应合同，不能影响核心 RNG 或延迟真实规则。

本次不做生涯语言迁移、桌面原生第二后端、并行 Wasm/SAB/SIMD/GPU 规则求解、新 UI、降低精度/物理频率、缩容、分波或屏外停止模拟；不提交、打包或发布生涯更改。P1–P3 是开发中间成果，不能把仅接了一块的小内核称为“完整 Rust 内核”。

## 数据所有权和执行合同

- 一个战斗只有一个可变权威：TS 后端或 Rust 后端二选一。Rust 后端迁入字段由 Rust 独占；TS 呈现副本永远不是下一步输入，不能通过逐属性 getter/setter 把旧 solver 留在热路径。
- 在已有 `CombatAuthority` tick/epoch 边界接入；保留重入、取消、完整提交后 tick 增长和房间命令排序。Rust 首版单线程，不增加额外计算 Worker。
- 身份用 slot＋generation，另存语义遍历序号。数组按实际实体数量增长，无新增玩法容量截断；槽位复用不能改变相同距离/相同命中的平局规则。
- f64 保留当前数值精度；整数身份、标志和索引使用明确整数类型。RNG 与身份分配按 JS 当前实际加法/截断顺序移植，不把 f64 游标擅自换为 u32。
- 规格/装配/几何初次进入后常驻；换装/部署/生成/回收/分离/传送/状态修订通过具名命令更新，不每步导入全世界，也不扫描 JS 对象图来推断修改。
- 内存增长/导出视图有 memoryEpoch；JS 只在 publish 后读取当前合法视图。不能保留已增长内存的旧 TypedArray，不能把未提交阶段的内存暴露为有效 frame。
- 初版粗粒度 ABI：`create(specs, initialState)`、`apply(commands)`、`advance(tick, dt)`、`publish()`、`destroy()`。init/spec 更新可以编码复杂结构；稳态输入为批量命令，输出为呈现列与事件，不跨边界传每舰/每弹对象。
- Rust 内部仍分正确阶段。弹体命中和伤害按当前有序位置执行；护盾过载、目标死亡、生成/爆炸与资源扣除必须影响后续查询。不能预先冻结所有命中，再在步尾统一扣血。

## 扩展和内容兼容

现有 TS 系统/武器/舰装回调直接修改对象，不能无成本地在 Rust 常驻状态上继续执行。首版规则如下：

- 七个内置包及目标混编场景的能力全部迁成 Rust 中已登记行为或可表达的数据规则；TS 能力登记和 Rust 支持版本分别核实。不能拿现有 `hostCapability` 当 Rust 支持凭据。
- 每场初始化先验证完整配装、模块、机翼、系统、舰装、效果及可生成实体的能力闭包。任一未知能力令整场在推进前选择原 TS 后端，保留现有内容和操作；列出原因供开发诊断。禁止运行一半 Rust 再无依据切回 TS。
- 已知内置包大面积整场回退表示该阶段未完成。最终验收重型场景必须实际 Rust 执行，不能消掉特殊装备或把它们交给旧 solver 后宣布覆盖。
- 新可信 TS 回调保持旧后端兼容；获得 Rust 性能需要实现对应 Rust 能力或未来有明确定义的命令式扩展。首版不承诺任意 JS 函数在新核心直接执行，不把新扩展沙箱作为额外项目。
- 在活动 Rust 战斗中禁止改变后端能力闭包的热替换；现有内容重载边界保持。发现未知运行时规则时报告内部错误并保留最近已确认输入/回执，不静默删规则。

## 界面布局、完整操作流程和失败处理

界面沿用当前布局、按钮位置、快捷键、禁用与关闭处理，不新增“Rust 设置”页面。开发期用独立显式开关选择后端，默认路径保持到最终门槛通过。

1. 玩家按当前流程选择配装/舰队/房间并部署。宿主在开战前完成内容检查、Wasm 加载和权威初始化，沿用当前 loading/loaded 回执。
2. 取消或关闭时销毁准备中的 Wasm 实例，不递增 tick、不部署两份舰队、不占用输入设备。
3. Wasm 不可用、CSP/下载/ABI/内容检查失败：在尚未推进时按既有 TS 后端启动，保留命令语义；原因进入开发诊断。该场不计 Rust 成功样本。
4. 正常驾驶/命令由当前输入层发送；宿主验证权限、epoch、序号后在原允许边界 apply。一个完成步只产生一次确认、统计/结算和呈现发布。
5. 暂停/重连/撤离/结算仍沿用当前规则。Rust runtime trap 不重试半步，不把未完成 frame 发布；进入当前故障/恢复流程。
6. 恢复只使用相容 build/backend/content 指纹、seed 和已确认日志，在新私有实例中重放并核对。成功后原子替换；失败保留原回执并明确报错，不将 TS 显示副本恢复成权威。

## 联机、并发和存档

- LAN/Steam 房间现有宿主选择与权限保持；客户机不获得 Wasm 可写内存或伤害权限。命令幂等、输入 ACK、过载保护和持久化结算不删减。
- Rust tick 与命令批次绑定 epoch/tick/序号；过期命令、重入、过期 generation 拒绝。发布只在完整提交之后，显示时钟不推进规则。
- 网络字段和呈现布局优先复用现有合同；确需变化时同步更新协议与生产者/消费者，不冒用旧版本。首版不使用跨浏览器逐位 lockstep，继续权威复制。
- 不修改生涯 schema/SQLite。战斗结算仍匹配待结算遭遇、一次性应用；普通游戏快照不写入裸 Wasm 内存。
- 回放保留现有 build/protocol/content 相容门槛，并区分后端/规则版本；不承诺旧 TS 战斗日志跨构建可在 Rust 自动恢复。

## 验收标准

**行为与覆盖**：相同配装/seed/输入/角色/规则；比较完整状态、两条 RNG、每挂点 tracker、真实资源/目标/发射/伤害/死亡/生成/回收/胜负。整数/身份/目标/决策/clock/HP/armor/flux/ammo/RNG/生命周期保持严格。用户已确认限定几何舍入：只对预先列明的位置/速度/角度及纯几何派生字段使用 `max(1e-9, 32*Number.EPSILON*max(1,abs(old),abs(new)))`；非有限值严格比较，逐项保留差异日志，不扩大到实际 timer/资源/目标/行为。不得把阈值越过引起的真实决策差异算浮点误差。原版依据、Web 差分和实机/UI 验证分别报告。

**性能**：先冻结当时默认 TS 与 Rust 两臂，保留相同装备、实体、输出、物理步和环境；复用现有 seed917/22 主舰/20AI 三舰混编场景，场景版本一起冻结。完整权威步计入命令、规则、提交；完整宿主链另计 publish/capture/encode/IPC，明确不同机器的网络链不串行混算。一次 ABBA，保留全部原始样本，无挑选重跑。

- 留用性能门槛建议：完整权威步均值至少减少 30%，两组配对均改善，P95/P99 不退化；完整宿主交付链均值至少减少 20%，必要权限/回执/恢复正确。
- 若声称该规模实时 60Hz，须在真实浏览器/Electron Worker 下验证每步约 16.67ms 的预算、尾部、实际完成步率和不累积债务；仅平均值达标不能宣布实时交付。
- 1.7–2.5 倍不是验收事实；最终用均值/P95/P99、实际步率和链路数据回答“提高多少”。门槛未过时保持实验状态，禁止仅凭新语言默认启用。

## 本轮进度

### P1b 本次实施方案：幅能、局部时钟、通用系统生命周期

目标是让开发核心连续推进真实常驻资源和系统状态，玩家操作、UI、联机权威与存档均不改变；继续保持 `fullBattleReady=false`。本块不接入生产战斗，不迁移系统 AI、目标选择、引力自动坍缩、武器执行、任意回调、护盾展开/相位状态机、CR 或全部 upkeep；这些能力不得仅凭通用状态机被宣布支持。

一次初始化舰船资源配置，注册不可变生命周期规格，再按原 `allSystems` 顺序安装任意数量的系统槽位。资源、计时、充能、阶段、待结算激活费用和待派发计数常驻 Rust；输入仅为具名激活/中断/重置/幅能操作/真实属性修订。规格表示通用计时合同，不是完整系统能力准入凭据。规格不得热替换，未知规格、旧实体代次、重复安装和非法批次原子拒绝；正常激活失败保留状态并返回有序结果。

推进顺序：先用当前相位效果和系统时间倍率取样 world/tactical/subjective dt；通用系统按 subjective dt 更新；保留过载/排散中断、逐槽激活费用结算，然后按 tactical dt 推进现有 FluxTracker 与 `advanceHullModFlux` 的硬幅能/零幅能修正，最后运动用已取样 subjective dt。当前相位效果与外部时间倍率只接受具名状态/属性修订，不在每步回传世界；相位自身状态机仍待迁移。实施实查发现 `NativeSystemFactory.ts` 在当前 custom-only 构建直接拒绝旧原生系统，时间贝壳文件没有注册；因此本块不迁移或声明支持其时间程序，实际系统 modifiers/效果留待能力逐项迁移。
