## 2. 弹体事件化的否定结果（不可当作优化启用）

`ProjectileEventStream.mjs` 提供有界、事务式 create/update/remove、epoch/revision、基线/目标 CRC、规格模板和精确字段恢复；本机弹体 ID 是 PRNG float64，不是整数。生成时间、负零、实体重排/ID 重用、畸形包、资源限额与 prepare/commit 隔离都有测试。

原始 22 舰录制有 152–196 个弹体，其中很多导弹持续导引。每帧精确保留所有运动字段时，独立事件流并没有变小：

- 60Hz：旧完整帧平均 20268.7B；拆后细节 11727.2B + 弹体 9769.7B，合计反而更多。
- 5Hz：旧 30457.4B；拆后 18121.3B + 13361.6B，也没有收益。
- 编码/恢复约数毫秒每帧，不能用增加 CPU 成本换一个“事件流”名称。

这里使用的是**还含旧插值字段的原录制**，与上一节原生配对战斗并非同一序列。两组绝对字节不能跨表比较。后续应转向真正的视觉生命周期/轨迹推进与权威校正，而不是继续优化一个无收益的精确大对象拆包器。

## 3. 共同修正：计算预算不足不再膨胀为全量流量

此前同一 broadcast 的差分计算次数/时间用尽后，剩余客机会退回完整状态。这在多人基线不同步时形成反馈：计算忙 → 全量大包 → 队列变旧 → 基线更分散 → 更多大包。

现在 LAN 和 Steam 可靠 P2P 在 `budgetFallback` 时推迟**未发送**的状态：

- 不提交差分基线，不领取/释放 ACK credit，不保留待发旧世界，不重传它。
- 下一轮轮转发送最新权威状态，已有可靠生命周期/控制不受此 gate 限制。
- LAN 增加无副作用 `canReserve`，只在编码决策通过后实际 `reserve`。
- Steam 的同步路径和真实 worker proposal 路径走同一发送决策，未发送 proposal 不在 worker commit 子集中。
- 日志区分 `codecDeferred` / `codec-work-budget` 与网络 ACK/客机消费不足，避免下次再把 CPU 饱和错算为网络 RTT。

回归实际 relay / SteamPeer 路径：延后时没有网络包、基线/信用不动，下一份新状态从原基线精确恢复。真正不支持/超大的投影、新连接、重同步的全量基线仍保留。

## 4. Steam 多人反馈及房间上限

发现两项原有门槛失败的具体原因：

1. **只排空一名客机就测“空闲 RTT”**：其他客机仍占用共享出口，排队样本会抬高基础 RTT；部分客机还会长时间停在单帧探测模式。多人房间禁止这种向上重学，取消未完成的独占探测；较低新样本仍可降低基线，正常拥塞反馈继续运行。单客机原有路由变化机制保留。
2. **总在途额度随客机数增长**：9 人的 64KiB/人容许太大的已发送尾队列，8Mbps 突降 256Kbps 后输入回执会等到原 8 秒保护触发。普通多人状态改为同一房间至多 224KiB 的自适应上限；已发债务不会因缩窗消失，单个超大基线例外和单客机专用控制器保持原合同。不是对任意低带宽的安全保证。

实际生产 Gateway / codec，虚拟共享 FIFO，合成小状态和输入；**不是用户游戏帧率**：

| 场景 | 修复前 | 修复后 |
|---|---|---|
|9 客机，8Mbps→256Kbps|全部在约 20 秒关闭，队列峰值 282339B|没有关闭，峰值 231203B；最坏 pong 年龄 7120ms；最终全状态仍只有约 0.8–1Hz|
|9 客机，512Kbps 启动|最终 1–2.4Hz，公平性失败|最终 2.4–4.8Hz，P95 状态年龄约 1000–1016ms|
|9 客机，健康 8Mbps|约 60Hz|约 51.2–53Hz，P95 160ms；满足既有每人≥40Hz/合计>420 门槛，但较旧的健康峰值有吞吐代价|
|3 客机，健康 8Mbps|60Hz|60Hz|
|80/300/1500ms 混合路径|快客机不应受最慢客机限制|60/60/19.2Hz，原门槛通过|

明确取舍：共享出口上限限制了健康 9 客机的峰值；不能称作“所有链路更快”。更高吞吐与突降后的低延迟要靠分层状态、可取消未发大数据、分片/字节调度，而非无界增窗。没有放宽或删除旧断言。
