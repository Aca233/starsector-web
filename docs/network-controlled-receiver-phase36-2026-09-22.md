## 实测

下表Hz/FPS为各客机各自窗内HUD中位数范围；输入为各客机窗内样本P95范围。AuthorityHz由Worker的900tick/实际耗时计算，不使用显示端tick冒充。

| 人数/轮次/臂 | AuthorityHz | 客机完整Hz | 客机FPS | 输入P95 ms |
|---|---:|---:|---:|---:|
| 3 / A-B / 原版 | 59.964 | 60 | 60.0 | 43.2–47.0 |
| 3 / A-B / 候选 | 59.984 | 60 | 60.0 | 42.8–59.9 |
| 3 / B-A / 候选 | 59.972 | 59 | 60.0 | 46.1–47.6 |
| 3 / B-A / 原版 | 59.908 | 60 | 60.0 | 44.1–48.9 |
| 5 / A-B / 原版 | 59.924 | 53 | 36.8–42.6 | 77.5–110.3 |
| 5 / A-B / 候选 | 59.717 | 47–48 | 36.8–46.5 | 86.0–114.4 |
| 5 / B-A / 候选 | 59.916 | 55–56 | 46.9–54.4 | 71.8–78.5 |
| 5 / B-A / 原版 | 59.928 | 51–55 | 36.8–46.5 | 72.4–80.1 |

5人A/B的apply中位范围4.60–4.78→3.92–4.25ms，但完整Hz反而53→47–48；B/A又有较好的FPS表现。字节轨迹相同后仍有运行时/调度/GC/GPU共享等变动，不能把单项恢复快就解释为端到端保证快。

本场景模拟接近60Hz而副本完整Hz/FPS较低，证明**不能一律把“客机Hz低”归咎于房主物理没有60Hz**；也不能由同机5窗口推断异地用户一定是GPU或接收端瓶颈。

## 另一个已复现的覆盖缺口（尚未修改生产）

`LocalFirePrediction.record()`先记录held，再因离散命令屏障/过旧完整帧拒绝首发；后续持续held不再是rising，空cycles也不能取得repeat信用。baseline-2真实运行中炮塔预测正常，但三台均predicted/repeated=0；将选组完整ACK与开火分开后baseline-4/5与8轮比较均产生真实repeat。这是“功能开关启用不等于该次交互实际预测”的具体案例。

下一项应验证**从完整权威ACK和唯一新确认弹体安全恢复当前持续扳机的预测信用**。不能简单解除命令屏障，不能从运动ACK、旧弹体、歧义弹体、未发送/已松开的输入生成假子弹；限额、弹药/幅能/冷却和命中权威不变。该改动尚未实现，不把诊断写成已修复。
