# 荣光女王级「不屈誓约」——固定分段模块舰方案 v0.2

日期：2026-09-25。状态：设计变更，未接入游戏、未生成新图、未验证战斗或联机。  
本稿替代 [v0.1](gloriana-design-v0.1.md) 的单一舰体结构与美术拆分方式，保留双舷火力、战列敕令和可配装武器的设计方向。

## 1. 设计目的与原著边界

用户明确要求将荣光女王改为模块舰，以表现巨舰的规模和分区损伤。采用固定连接的舰体分段，而不是可脱离无人舰、变形合体舰或战斗中自由拼装。

战锤帝国巨舰提供形象与规模灵感；下述十段拓扑、战损收益和游戏资源规则均为 Web 适配，不声称原著指定荣光女王必须分成这些可破坏模块。「不屈誓约」仍是自拟舰名，不是官方命名舰。

目标体验：整舰是一艘连续、完整、缓慢而强大的舰队旗舰；战损可以先剥夺火力、鱼雷与推进能力，再威胁核心，而不是只有一根巨大血条。

## 2. 首版拓扑：一个核心＋九个固定子模块

总共十个受损实体。所有子模块固定安装于核心，不独立航行、不绕母舰旋转，不采用炮塔式独立舰体转向。

```text
                    [B 装甲艏段]
 [L1 左前炮廓]       [C 中轴核心]       [R1 右前炮廓]
 [L2 左中炮廓]       [C 中轴延续]       [R2 右中炮廓]
 [L3 左后炮廓]       [C 旗舰堡垒]       [R3 右后炮廓]
           [EL 左动力段]     [ER 右动力段]
```

图中三个 C 标签表示同一个纵向核心，不是三个实体。图只表达连接关系，不是生成图的构图模板。

| ID | 数量 | 主要职责 | 被摧毁后的拟定结果 |
| --- | --- | --- | --- |
| C | 1 | 纵向龙骨、指挥堡垒、核心控制及背部能量挂点 | 整舰死亡，只结算一次舰船损失 |
| B | 1 | 厚装甲艏、舰艏导弹挂点 | 失去相应武器和前部实体防护，留下真实缺口，不立刻算整舰阵亡 |
| L1–L3 / R1–R3 | 6 | 每段一个大型实弹挂点和局部点防御位置 | 损失该段武器与装填接收资格，其余炮廓继续作战 |
| EL / ER | 2 | 主要推进器组 | 按存活动力能力降低整舰推进性能；不让子模块自己移动 |

核心保留少量辅助推进能力作为撤退设计候选；双动力段损失后是否还能缓慢脱离、需要多低的速度，留待简模验证。不得未经验证以永久失控旋转作为“真实损伤”。

## 3. 完整外观与模块身份

- 正常状态看起来是一艘完整的荣光女王，不是十艘小船围在一起，也不是悬浮零件拼图。
- 模块交界通过装甲咬合、阶梯甲板、检修缝和局部结构凹槽表达；不用荧光分割线、编号或巨大空隙。
- 中后段旗舰堡垒归 C，成为唯一主要视觉中心；炮廓和动力段是它周围的功能体量。
- 侧舷模块沿长轴形成前—中—后的节奏，避免六块尺寸完全相同的盖板。
- 模块是舰体结构，不是已经装好的炮塔。所有可装武器继续作为独立资源绘制，模块底图中不画炮管、炮塔上半部、光矛或导弹发射机构。

## 4. 战损与胜负规则

- 各段有自己的碰撞、装甲与结构。不能让核心使用覆盖全舰的大矩形精确碰撞，把对外部模块的命中吞掉。
- 核心的精确碰撞只覆盖它实际拥有的结构；外接半径可覆盖组装体用于宽相筛选，不能代替精确命中。
- 根实体不是空间站免伤骨架；不添加 `vastbulk` 来偷做巨舰，不继承“炮台全灭就判核心死亡”的站体规则。
- 核心死亡或整舰撤退传播到剩余子模块；一艘旗舰只占一次部署费用、一个主舰身份及一次最终战损记录。
- 炮廓被毁后不在原位置继续出现可开火的武器。完整模块图、受损残迹与独立残骸需要明确区分。
- 不默认把模块死亡爆炸设为足以秒杀相邻模块的连锁反应；局部战损必须能真实持续存在。
- 残骸碰撞、脱落与淡出策略需要单独验证。第一版允许有限残迹表现，但不能用纯视觉碎片冒充仍在作战的实体。

## 5. 战列敕令适配

继续采用左右舷优先装填，但不把三段左炮廓视为一门虚拟大炮。

- 核心接受指令并锁定选定舷，向该舷存活、接入总管的炮廓分配装填工作。
- 每发弹的工作量、每座炮的待发弹和发射间隔仍属于实际武器；不跨模块复制弹药。
- 总供弹工作率及单接收端上限明确计算。炮廓减少时，不能把全部产能无限集中给最后一门炮。
- 被摧毁、撤退或禁用的模块不得继续接收工作；模块丢失不能解除已支付的代价或重置冷却。
- 只剩单舷并不意味着“无代价无限加速”：可用产能、状态时长、转向代价与单炮上限均需原型测试。
- 核心失能时禁止新敕令；存活炮廓是否仍可普通射击由真实武器／局部幅能状态决定。

玩家可以把受损一舷转离主要敌人，保住另一侧战力，也可以集火敌舰前部或动力段争取局部突破。这样“该打哪一段、该保护哪一舷”与原有装填决策结合，而不是再叠一套无关小游戏。

## 6. 护盾、幅能、控制与预算

### 防御方案

首轮简模以模块各自的装甲、结构和局部幅能为基础，不先假定共享虚空盾已经实现。最终倾向一套有整舰身份的虚空盾表现，但其伤害路由必须另行确定：

- 若采用整舰共享盾池，需要权威侧对跨模块命中只扣一次盾资源，并正确处理边界、过载、相位与模块丢失。
- 若采用独立分区盾，则明确它是适配方案；控制重叠区域，不能无意叠出十层完整主力舰防御。
- 两者尚未定案，不在生图中烘焙任何盾效果；护盾定案是正式战斗验收前的阻断项，不能以蓝色特效代替逻辑。

### 玩家控制

设计目标是玩家控制整舰移动、目标和主武器组；子模块不成为九个需要分别驾驶的单位。全舰武器组路由与“AI 自动射击模块”的边界必须验证。现有构造路径会把附属模块设为 AI 火控，不能因此宣称全舰手动齐射已经可用。

### 预算

DP 只按整舰计算。OP、装甲、结构、耗散、幅能容量、武器与舰装效果按部件分配，再核对整舰总预算。不能给每个炮廓完整巡洋舰规格后仍沿用旧的整舰费用。

核心光环／技能／插件跨模块生效时，声明只算一次还是按部件计算，防止重复叠加。此前约 100 DP／360 OP 只是单体概念起点；模块化后必须重新对照，不作为已锁定指标。

## 7. 素材生产改为“总装锁定—同坐标分层”

1. 先生成完整、无武器、未爆炸的组装态概念图，选择漂亮且有结构逻辑的外形。
2. 在锁定总装上人工确认 C、B、六段炮廓和两段动力的分界、遮挡顺序与锚点。
3. 建立同一世界比例与同一坐标基准的十层素材，再逐段补全被遮挡接口。不能让模型独立设计十艘小船后硬拼。
4. 核心图只保留核心实际结构与必要的连接内骨架，不保留完整外部装甲的“底图复制件”；否则子模块被毁后画面仍然完好。
5. 每段单独记录透明边界、pivot、moduleAnchor、挂点及精确碰撞；模块接缝可以有少量视觉覆盖，不能依赖互相重叠的厚碰撞制造多次伤害。
6. 母版分层不等于“一次生图能返回 PSD 图层”。生成图只能作输入，最终切分、接口修补、透明与对齐仍需制作和验收。
7. 所有武器图、系统图标、引擎尾焰另行生产；炮廓舰体和炮塔从第一步就不是同一个资源。

拟定素材身份为 C、B、L1–L3、R1–R3、EL、ER；无需把这些字母画在图片上。导出尺寸与裁切方式待总装确认，不提前随意裁十张不同尺度的图。

## 8. 当前技术证据与差距

本轮阅读：
- `docs/modular-ships-and-stations.md`：项目已有模块挂接、独立受击／死亡、部件改装、整舰部署和快照基础；文档也明确不能自由替换模块舰体或增删结构，网络记录不是双机实测。
- `src/engine/content/ShipSpec.ts`：`modules`、`moduleAnchor`、`moduleCombat` 等结构存在。
- `src/engine/content/ModuleGeometry.ts`：挂点减去旋转后的模块锚点。
- `src/engine/simulation/Ship.ts`：母子关系、作战模块判定、附属模块构造及 AI 火控默认路径。
- 本机 `starsector-core/data/hulls/module_armour1.ship`：实际模块资源具备自己的中心、轮廓、moduleAnchor 与图像；其脱落相关内置配置不能盲目复制给本船。

新增／待验证：整舰手动火控、模块损失到母舰推进能力的聚合、共享供弹、可能的共享盾池及其显示／同步。现有模块基础不等于以上功能自动完成。

没有修改原版模块规则，没有操作原版实机，也没有宣称已验证这艘原创舰的玩家／AI／网络行为。

## 9. 最小原型验证清单

- 十个实体、一个舰队身份；移动与旋转后没有位置漂移。
- 逐段命中与摧毁：只扣正确实体，未错误重复结算护盾或结构。
- 摧毁一个炮廓停止对应火力，其余炮廓及资源状态不重置。
- 摧毁单／双动力段改变整舰推进而非子模块各自漂移。
- 艏段损失后的图像、碰撞和导弹挂点同步消失或转成明确残迹。
- 核心死亡／整舰撤退传播正常；子模块不单独计算部署或战损。
- 敕令、模块丢失、局部过载、重开与保存组合没有产能复制。
- 玩家可以读懂选中部件、局部血量和整舰状态，操作不变成十船微操。
- Worker 显示及宣称支持的多人状态另验，文档阅读不算测试通过。
