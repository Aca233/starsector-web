# 真正的多核模拟实验：几何预计算（2026-09-17）

## 结论

**不接入正式战斗；本轮没有可保留的模拟净提速。**

100艘舰，4个 Worker 的完整固定模拟步 **84.08 → 90.96 ms**，耗时增加 **8.19%**，对应计算吞吐 **11.89 → 10.99 步/秒**（下降 7.57%）。不是渲染 FPS。

多核确实加速了独立内核：单线程 13.08 → 4 Worker 最慢分片 4.15 ms，约 **3.15倍**；但这不等于完整模拟提速。即使相对于新增的单线程预计算版本，4 Worker 也只是弥补一部分额外工作。

实验钩子已从 ThreatAssessment.ts 撤回；该文件恢复到本轮开始时的内容。4个新增实验模块及带钩子的候选文件归档到 artifacts/multicore-simulation-2026-09-17/experiment-src/，不进入正式源码、主循环或发布包。保留之前已有的其他优化和其他任务的所有改动。

## 百舰直接数据

| 方案 | 完整步均值 ms | 完整步 P95 ms | 模拟计算吞吐 步/秒 | 耗时相对原算法 |
| --- | ---: | ---: | ---: | ---: |
| 原算法 | 84.08 | 110.50 | 11.89 | 基准 |
| 仅加钩子，不预计算 | 84.44 | 113.00 | 11.84 | +0.44% |
| 单线程预计算 | 98.90 | 123.70 | 10.11 | +17.64% |
| 2个 Worker | 92.87 | 116.20 | 10.77 | +10.46% |
| 4个 Worker | 90.96 | 116.20 | 10.99 | +8.19% |

仅加钩子组用于分辨候选的分支/代码布局变化与真正并行收益，不算独立优化成果。百舰6个连续30步分组中，2/4 Worker 均比各自对应的原算法分组更慢。

## 做了什么

- 初始 Node CPU 采样中，威胁评估累计约占25.84%。该占比仅用于选热点，采样下的步耗时不用于和浏览器结果计算提速。
- 不是把整个串行模拟搬进一个 Worker。这里用2/4个持久 Worker，按被评估舰船分片，同时计算炮口到目标的距离、单位方向、舰体/炮塔转角。
- 每个模拟步捕获只读几何输入，传输 Float64Array，等待各分片完成；安装短期缓存后仍按原顺序调用同步 AI/固定步。伤害、护盾、幅能、射程修正、系统启动和决策提交保持原线程。
- 每次缓存读取重新核对实际几何和原生钩子；变化时走原计算。未知扩展禁用该加速，Worker 异常仅执行一次原生模拟，取消后不偷偷推进。
- 输出缓冲在下一步回传复用；无 SharedArrayBuffer、COOP/COEP、阻塞主线程等待或忙等。没有降AI频率、扩大 dt、跳模拟步或减精度。

### 成本拆解（100舰，4 Worker，均值）

| 项目 | ms/步 |
| --- | ---: |
| 输入捕获/打包 | 0.71 |
| 发出任务到结果齐备，包含内核 | 4.49 |
| 最慢 Worker 计算，已含在上项 | 4.15 |
| 4个 Worker 计算时间合计，非墙钟耗时 | 15.11 |
| 剩余主线程模拟，包含缓存读校验 | 85.59 |
| 完整步，包含上面的等待、安装、清理等 | 90.96 |

原算法完整步 84.08 ms；加缓存后剩余主线程仍为 85.59 ms，并没有获得可见的净缩短。不能简单把失败归咎于通信：等待与最慢内核之差约 0.34 ms；主要问题是重复/提前计算及结果安全校验没能减少足够的原线程工作。

100舰共1300挂点，矩阵130000个槽，65000个敌对几何对，输出5,200,000字节/步；4 Worker 输入合计252,800字节/步。实际每步平均消费 28836.7 个结果，缓存失配为0。预计算做了不少原逻辑会提前排除或不需要完整角度计算的工作。

## 测量口径与范围

- Intel i5-13490F，16逻辑处理器，Windows 11（10.0.26200），Chromium 151.0.7922.34，Node 24.13.1。浏览器无头运行，不含绘制和音频输出；不是实机帧率或输入延迟验收。
- 固定种子0x51180；同样的 Onslaught 密集编队、舰体/武器初始朝向；每步1/60秒。每方案60步预热、180步计量，共240步；10/50/100舰各一轮交替比较。
- 五个独立页面持有相同初始模拟，按每个固定步轮换并反转方案顺序。任何时刻只推进一个方案，不让几组压测同时争抢核心。自身不同时执行构建、剖析或其他验证。
- 计时在页面内，从输入捕获前到等待、安装、权威模拟、清理完成；统计每步完整活跃墙钟耗时之和。**不计测试驱动在其他页面工作造成的闲置时间，也不把该吞吐叫实际游戏运行 TPS/FPS。** 原始全组连续跑结果另外保留，但不作为验收主数据。
- Worker 一次性启动、Wasm加载和预热在计量前完成。各方案碰撞后端均先确认 ready；探索性连续跑的遥测中本场景实际批次均走 TS 路径，未把“Wasm ready”等同于“Wasm正在加速”。
- 源码冻结后构建主入口和 Worker，避免其他任务修改改变某一组算法。对照只包含本轮几何原型，不与昨晚的版本总提升、单Worker快照实验拼接百分比。
- 机器上还有其他用户任务。初始整组连续测试受负载漂移影响明显，因此改用固定步紧密交替；没有关闭其他程序。本结果没有重复实验的置信区间，不能外推到所有设备/战况。

## 正确性与诊断

- 初始 Node 对照：2/10/100舰各120步，1/30/60/120检查点相等。
- 浏览器真实 Worker：10/50/100舰，各方案在60/120/180/240步的模拟图序列化SHA-256均与原算法相等。100舰240步为 3736226b422392a451881c297d727002b6ddfd9b973619d075c717d6417a2cc2。
- 比较 engine 与 playerAI 的可枚举状态、数组、Map/Set、类型数组、对象共享引用及特殊数值。只规范化函数为占位、kernelMs为墙钟标记；不宣称序列化比较覆盖函数代码、WeakMap隐藏状态或Wasm线性内存的每个字节。
- 264组内核算术边界检查：有符号零、极小距离、NaN/Infinity、角度接缝；使用相同Vector2/signedAngle操作与Float64，无近似计算。
- 专项诊断通过：目标/炮口/炮塔/半径/偏移变化、主线程数学方法覆盖、自定义钩子回退、作用域关闭/重叠、等待时变更舰队数组、模拟异常清理、拒绝异步回调、Worker创建/发送/响应形状/崩溃及等待中dispose。
- 诊断脚本仅保存在忽略的artifacts目录；未恢复项目测试套件/运行器，也未做素材哈希或大小审计。

## 后续判断

这证明的是**这个小粒度、逐次安全校验的并行拆法不合算**，不是“多核永远没用”。若继续投入，应先设计能批量执行更大工作量的只读模拟阶段，并明确该阶段与后续有序状态提交的边界。完整AI决策和连续命中伤害目前存在顺序依赖，不能简单把100艘舰各扔给线程后合并；那可能改变战斗结果。此项架构改造尚未实现，本报告不预报其提速倍数。
