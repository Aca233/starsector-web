# Resident Rust/Wasm combat core — development foundation

The migration plan is [rust-combat-core-plan-2026-10-08.md](../../docs/rust-combat-core-plan-2026-10-08.md). Browser and Electron use the same Wasm build. This directory implements resident identities/generations, transactional commands, the two exact existing random streams, motion, flux, local clocks, generic system lifecycle tables, shield/phase/void-shield state, data-based resource upkeep, armor/direct hull damage, weapon health/pre-fire clocks/ammo/disable cancellation/groups, damage-decal envelopes, engine controllers/damaged motion, component propagation and actual weapon/engine critical side damage. **It is not a complete battle backend.** AI, aiming/charge/burst/beam emission and shot debit, collision/hit selection, CR/PPT/deployment and arbitrary modifier producers, special upkeep, actual system effects, content admission and production presentation remain pending; `core_full_battle_ready()` returns zero. No ordinary combat entry imports this development binding.

`RustCombatCore` creates a private instance, uploads initial bodies once, applies explicit control/stat/lifecycle commands, advances resident state, and copies publications. A publication is never the next step's input. Destroyed handles and invalid command transactions are rejected; a failed validation does not commit a partial tick. Memory views are reacquired after growth, and returned publications cannot write authority.

Build with an existing stable Rust compiler and its matching Wasm standard library:

```powershell
./scripts/prepare-rust-wasm-toolchain.ps1
./scripts/build-rust-combat-core.ps1
node scripts/check-rust-combat-core.mjs
node scripts/check-rust-combat-core.mjs --lifecycle
node scripts/check-rust-combat-core.mjs --shield
node scripts/check-rust-combat-core.mjs --damage
node scripts/check-rust-combat-core.mjs --engines
node scripts/check-rust-combat-core.mjs --weapons
```

The preparation script downloads the matching standard library from `static.rust-lang.org`, verifies its SHA-256 and extracts it into the git-ignored project artifact directory. It does not run the archive's installer, change global PATH or modify the user's installed toolchain. The build is offline and has no crate dependencies. Override `RUSTC_BIN`, `CARGO_BIN` or `RUST_SYSROOT` only when selecting another matching prepared toolchain.

The concentrated check compares the actual TypeScript `SimulationRandom` and production `MotionKernel`, exercises atomic rejection, generation reuse, independent instances, closure and retained publications across memory growth, and repeats the domain check in a fresh headless Chromium dedicated Worker. The long Node random check crosses the binary64 integer-precision boundary. This is correctness evidence for these domains, **not a whole-game performance or 60Hz claim**. Build and verification output stay in `artifacts/rust-combat-core-20261008/`; no release Wasm asset is installed yet.

The lifecycle check uses actual TS `FluxTracker`, `ShipSystem`, the Ship clock reader and `advanceHullModFlux`, with a narrow owner/input adapter and notification-only callback witnesses. It checks 19 entities over 100 steps in Node and a real dedicated Worker. It runs the existing foundation with only 4k RNG samples after the ABI update, preserving the earlier long-cursor evidence without repeating 5M samples. Notifications are retained until cumulative acknowledgement; snapshot reads never consume them, and copied resource/system output cannot write authority.

The shield check extends this with actual TS `Shield`, Ship prepare/integrate/toggle/vent methods, registered Adun barrier resource modifiers, and a narrow owner adapter. It disables unported deployment/CR progression and supplies resolved MotionKernel output; it does not substitute shield, phase or fee algorithms. It compares 14 entities over 100 steps in both runtimes, keeps per-field geometry differences in the result JSON, checks atomic rejection and owned shield output, and confirms system upkeep works without an installed shield. Standard hit brightness remains presentation-only. Standalone absorption does not select hits or apply armor/hull damage.

The damage check uses actual TS `ArmorGrid`, `ShipDamageState`, the Ship direct-hull-damage method and weapon-health functions. It compares 12 entities and 144 weapon-health slots over 120 steps in both runtimes. Cells retain Float32 writes while calculations/HP remain f64; returned armor loss preserves pre-store arithmetic. Damage-decal creation/flashing consumes the resident visual RNG, and intensity is a pure TS projection from copied envelopes. Both random streams roll back with failed commands/steps. This does not admit arbitrary damage listeners, full weapon disable/firing side effects, engine controllers, component maps, critical malfunctions or death/explosion handling.

The engine check uses actual TS EngineController, Ship prepare/integrate/finish, shipMotionStats, ComponentDamage and Ship critical-malfunction methods. It compares 12 entities, 36 engine slots and 84 weapon-health slots over 150 steps in both runtimes. Critical callbacks execute resident hull/armor/self-source propagation synchronously before repair and later components; they are not notification-only placeholders. Tests cover real scheduled severe damage, nonlethal armor and lethal branches, interlocks, cascade/restart, extended last-engine veto, repeated permanent compensation, zero critical chance RNG, restore, valid source handles, rollback and copied publication. Only pose/velocity/angle and maneuver-thrust geometry use the fixed allowance. CR/deployment producers, modules, full firing and production authority remain excluded.

The weapon check uses the actual TS ShipWeaponControlSystem pre-fire advance/disable methods, Ship prepare/integrate/finish, modifier readers and critical-malfunction methods. It compares 11 entities and 68 weapon slots over 100 steps in both runtimes. It checks rate limits, reload/lifecycle clocks, ammo, recoil/glow/spread, cycle cancellation, repair and permanent group removal, including duplicate members. Scheduled critical damage runs before repair/cancellation; explicit critical damage runs after cancellation/finalization. A lethal scheduled failure still finishes the current weapon loop and world-time scars, then freezes ship updates next step. This check does not call empty emitters or claim full firing. Mount/cycle inputs are initial-only, and incomplete topology, commands during installation, repeated initialization, invalid rail indices, rollback and publication ownership are checked.

ABI **6**, domain mask **4095**, command width **26**, header **29**, body **67**, system **29**, shield **67**, armor **36**, scar **18**, weapon-health **23**, engine-controller **49**, engine-slot **30**, weapon-controller **30**, weapon-mount **39**, weapon-group **16**, event **10**, all wire words f64. Armor cells are published consecutively and copied back to Float32 storage. Identity fields are validated u32. Bodies can remain motion-only; resource, shield and armor initialization are explicit and one-time. Commands 5–9 initialize resources, revise flux stats/clock inputs/ship flags and perform flux operations; 10 registers immutable lifecycle metadata, 11 installs a slot, 12 activates/interrupts/resets/enables/disables it, and 13 dispatches notification witnesses. Commands 14–22 configure/revise shields, aim/forced-phase input, void-shield specs, shield/vent operations, upkeep stats/policies, standalone absorption and mitigation multipliers. Commands 23–32 initialize armor/HP, revise multipliers, write cells, apply standalone armor/direct hull damage, install/damage/disable weapon health, revise health-only repair policy and synchronize decals. Commands 33–34 atomically initialize the complete ordered engine topology; 35–38 revise engine health/motion policy, execute engine operations and revise damage attributes; 39–40 perform component propagation and combined armor/hull/propagation. Commands 41–45 atomically initialize the complete weapon controller/spec/initial state/groups/membership; 46 revises effective weapon attributes, 47 performs real weapon critical damage/finalization, 48 clears the pending display queues. Weapon installation owns its health topology and disables legacy per-component repair policy writes. Sources are resident generation-checked ships. After engine records/slots/indices come weapon controllers/mounts/groups/member IDs/disabled-repaired IDs, then events. Events retain two detail words for coordinates or component identity. Installed shields and engines own their active/phase/flameout fields. Definitions and upkeep controls (including blockWeapons/forceAutofire) are lifecycle subrules, **not whole-system capability admission**. Non-finite packet values are rejected except Infinity for an explicitly toggled ACTIVE duration; unbounded initial ammo uses a validated finite marker. Publications separately allow Infinity for never-hit shield contact age, permanent weapon disabled timers and explicit unbounded ammo. Full state/side-effect migration must finish before production integration.
