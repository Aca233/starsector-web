## 1. 结论与当前方向

**技术上可行，但当前需要新建生涯层，再把已有舰队持久化与多人战斗接起来。**

根据后续讨论，方向修订为：**同一个世界内，玩家可以各自行动，也可以加入合作，再退出恢复独立行动。**这替代早期“首版强制共享一支舰队”的建议，不需要先做共享舰队版再推翻。

“加入”的具体产品规则尚未逐项确认。本文建议区分：加入朋友的世界、结伴航行、临时联合出击，以及可选的代驾授权；这些都不自动转移资产所有权。战中增援保留为目标，战前加入作为第一阶段实现建议，而非用户已同意的限制。

先以 2 人验证独立行动和汇合作战，再以 4 人验证并发行为；人数是建议验收目标，不是已验证容量。已有战斗协议的 10 人上限不能当作生涯容量证明。当前不做持续在线宇宙、跨世界携带资产、PvP 经济或无缝主机迁移。

## 2. 已有基础与真实缺口

以源码为准；历史联机文档中的协议号、容量与同步频率有阶段性差异。

| 项目 | 已核实的能力 | 与联机生涯的差距 |
| --- | --- | --- |
| 主入口 | `src/App.tsx`、`src/studio/NativeHome.tsx` 提供设计、技能、LAN、Steam、战斗等入口 | 未发现生涯入口或星区世界运行循环 |
| 持久舰队 | `src/engine/game/GameState.ts` 有稳定 member ID、结构、CR、装甲格、装备弹药、库存形状、战前检查点、战果记录 | 单一舰队、单一 pendingCombat；无玩家归属、世界位置、市场、任务、殖民与经济规则 |
| 本地结算 | `beginCombat` 校验拥有关系；`settleCombat` 只接收当前 pending ID，校验参战名单、舰体与武器身份 | 可复用原则，不是服务器事务或反作弊裁判；没有联网资源分配、持久命令回执 |
| 战斗适配 | `CombatHandoff.ts` 把持久记录与实时 Ship 隔离；保留未出场预备舰战前状态 | 依赖单机 CombatSession 和双边名单，不能原样套到多人控制映射 |
| 本地存档 | `GameSaveStore.ts` 使用注入式存储；`CombatView.tsx` 接入 localStorage，保护坏档与已观察到的外部写入 | 浏览器本地写入不是多用户事务；GameSession 先更新内存再保存，失败允许仅内存继续，不适合持久联机资产 |
| 多人战斗 | `LanWorld.ts`、`host.worker.ts` 已有房主权威模拟、席位、分队、AI、部署；客机发送输入与展示状态 | `src/network`、`server` 未接入 GameSession / GameSaveStore / CombatHandoff |
| 联机战报 | `CaptureBattleReport.ts`、`battle-report.d.mts` 包含 ID、队伍、席位、部署状态、结构、CR、时间 | 没有持久 member ID 绑定、装甲格、剩余弹药与完整配装状态，不能作为生涯结算 DTO |
| 服务端 | `server/lan-server.mjs` 有身份会话、权限、房间、加载和结果校验 | rooms / sessions 是内存 Map；房间结果不是落盘世界存档；服务重启不恢复这些对象 |
| 内容与设计 | 已有 Design、设计校验、内容注册与 manifest | 设计器是自由配置工具，不负责库存扣减或生涯解锁；runtime revision 不能单独充当跨设备内容一致性凭据 |
| Steam | 已有网关、可靠队列、快照窗口及研究代码 | gateway 明确区分默认 legacy 路径与测试注入 sockets 路径；本轮未做真实双账号跨网验收，不能把实验路径当作生产保证 |

### 三个不可直接拼接的地方

1. **临时舰体身份。** `registerLanDesign()` 将编译后的 spec ID 设为 `lan-player-N`；`captureFleetMember()` 当前从 `ship.spec.id` 取 hullId。直接相连会把临时注册 ID 带入长期存档。必须保存基础舰体 ID + 规范化配装，并显式绑定 runtime entity ID 与 durable member ID；玩家 ID、席位、舰船 ID 不能混用。
2. **配装持久化不完整。** Design 包含 vents、capacitors、systemTypes、modules 等，当前 FleetMember 没有这些完整字段。要先定义可往返重建的持久 loadout，而不是只补一项 hullId。母舰模块不是独立舰队资产；首版可明确排除模块舰，支持前必须验证模块损伤/弹药往返。
3. **显示战报不等于资源账本。** CR 当前战报取 `currentCR`，本地持久捕获使用 `currentCR - pendingCombatCRLoss`；需要统一结算口径。装甲、弹药、预备舰、撤退舰、战沉舰都要从权威战斗实例采集，不能从客机最后一帧推算。

## 3. 产品模型：独立舰队 + 可选合作

| 方式 | 玩家行为 | 资产与控制边界 |
| --- | --- | --- |
| 各自行动 | 各自探索、贸易、接任务、遭遇战 | 每人独立舰队、货舱和资金；市场与世界状态共享 |
| 结伴航行 | 约定地点汇合，由队长带路，随时在允许的时机解散 | 只共享航行指令；不合并钱包或舰船所有权 |
| 联合出击 | 附近玩家接受邀请，同一阵营共同参加一次遭遇 | 每人选择自己的参战舰船；各自驾驶，AI 管理其余舰船 |
| 授权代驾（可选） | 加入朋友舰队，驾驶对方授权的舰船 | 所有权不变，一舰最多一个驾驶者；未带入的自有舰队必须停靠或托管，不能同时远程获利 |

### 建议规则

- 加入同一世界，不等于加入同一舰队；组队，也不等于资产赠送。转移舰船/物资必须走另外的显式交易。
- 结伴需双方确认，并由权威服务检查同地点/有效距离；远处玩家先赶来，不因接受邀请瞬移。
- 队长获得航线指挥权，不获得出售队友舰船、花费队友资金或任意编辑队友配装的权限。协同舰队航速与油料消耗需另定规则，不能让高速领队免费拖带其他舰队。
- 所有玩家可分别遇敌；A 作战时 B 可以跑商，C 可以改装，条件允许时 B/C 也能另开战斗。跨玩家交易需要双边原子提交。
- 战斗只锁定实际参战舰队及关联资产；其位置停留在遭遇地点，不可再次遇敌、交易或把同一艘船派到另一场战斗。
- 世界只有一个权威时钟，个人菜单不暂停世界。进入战斗不冻结全世界；首版不提供个人时间加速。战斗/航行时间比例、被锁舰队的补给与维修计时需显式规则，不能同时在两层重复扣费。
- 战前加入最简单：有效距离内申请 → 同意 → 选舰 → 冻结名单 → 共同加载。建议先验证这个流程。
- 战中增援不是技术上禁止，但要新增到达时间/距离判定、增援入口、DP 准入、加载就绪、名册变更和一次性结算约束。现有战斗部署功能不等于已经支持网络新玩家热加入。
- 非战斗阶段允许退出结伴，在当前合法位置继续独立行动；战斗中“退出队伍”不等于瞬间撤离或免除损伤，必须走撤退/战斗结束规则。
- 战利品规则在开战前确定；建议首版使用明确的个人奖励额度 + 有限物品分配，不复制同一份战利品给所有参与者。贡献分配、队长分配或平均分配尚待选定。

因此核心不是独立模式与联机模式切换，而是：**一套世界规则下，临时改变协作关系、驾驶授权和参战名单。**

## 4. 架构：一个世界权威，多场独立战斗

建议在现有 Node 服务旁增加 CampaignService；复用战斗引擎，但需要改造当前房主/房间绑定，不能声称现有 Worker 已能直接托管任意多场生涯战斗。

```text
玩家 A / B / C：各自世界 UI、命令、只读镜像
                │ 经认证的命令 / 邀请 / 加入请求
                ▼
CampaignService：唯一世界写入者、世界时钟、权限、资产事务
  ├─ CampaignDomain：舰队、市场、任务、Party 协作关系
  ├─ CampaignRepository：持久存档、版本、去重回执、检查点
  └─ EncounterCoordinator：遭遇集合、参战锁、计算主机分配
       ├─ Encounter 1 → 指定客户端 Worker → A 与 B 联合作战
       └─ Encounter 2 → 另一计算主机 Worker → C 独立作战
                │ 各场完整的可靠结算 DTO
                ▼
同一世界服务：按该场锁定资产提交，不覆盖其他人的新进度
```

一个世界写入者不代表只能有一支舰队或一场战斗。世界事务串行/原子提交；各场实时战斗独立推进。建议先验证最多两场同时运行的情况，不把全部战斗都压到同一个房主浏览器上，也不承诺未经压测的并行容量。

世界服务管理资产、身份与时钟；每场计算主机管理物理、伤害与 AI。世界服务不重新计算每发炮弹，因此仍是信任好友计算主机的模式，不宣称解决房主作弊。

建议世界原型从 5–10Hz 权威 tick 开始，离散交易立即处理；这是待测起点，不是性能指标。现有战斗 60Hz 目标保持不变。客户端不能自行扣资源；世界和战斗不需要全客户端确定性锁步。

部署仍需要房主电脑或独立机器的 Node 世界服务；浏览器可作客户端，Steam 走桌面集成。纯 GitHub Pages 不承载世界服务。房主退出后仍想继续，需要常驻世界服务；公开互联网部署另验认证、TLS/WSS、限流和备份，不直接暴露 LAN 服务当作完成。

### 状态与身份

新增 CampaignState / CampaignSave，不无声升级旧 GameState v1：

- 根：schemaVersion、campaignId、revision、worldTick、世界 seed / PRNG 状态、规则版本与内容指纹。
- players：长期 playerId、身份、权限、个人资金和任务。凭据由服务验证，不能信任客户端自报 actor；临时 seat 不是长期身份。
- fleets / members：fleetId、ownerPlayerId、位置、完整持久 loadout、结构/CR/装甲/弹药和货舱；owner、驾驶者、队伍、战斗阵营是不同字段。
- parties：成员舰队、队长、邀请与航行授权；加入 party 不迁移资产。Party 与 Encounter 是独立关系，不做成互斥枚举，因为结伴状态可跨战斗持续。
- encounters：多场遭遇集合；每场保存 encounterId、battleAttempt、matchId、computeHostId、名单版本、成员绑定、参战资产锁、局部战前检查点、状态与结算回执。
- content：基础舰体 ID + 规范化设计，覆盖 vents/capacitors/systemTypes/modules 等；去除 updatedAt 等非语义字段。runtime registry revision 不能单独证明不同设备内容相同。

### 事务与协议

独立 campaign 协议/能力协商，命令携带 campaignId、authorityEpoch、requestId 和相关对象的预期版本。全局 revision 用于事件顺序和镜像恢复；舰队/市场/遭遇的局部版本用于冲突检测，不能因为别人在别处买了一件装备就让已合法锁定的战斗结果永久无法提交。

去重键至少包含世界、玩家、requestId；同 ID 不同 payload 拒绝，重试先查历史回执。authorityEpoch / battleAttempt 用于拒绝旧进程、旧 Worker 写回，改变 epoch 不能让同一奖励再次兑现。asset 锁与多行更新在一个事务内执行，竞争申请只成功一次。

持久化优先评估 SQLite；先确认便携 Node、Electron 服务和安装包的可用驱动，不假设当前已经具备。Repository 保留内存测试实现。状态、资源变更和去重回执必须一起落盘，成功后才显示交易/结算完成；失败进入只读/暂停与重试，不套用本地模式的 memory-only 成功体验。

旧 GameSaveStore、沙盒与设计库保持隔离。单机资产若允许迁移，显式导入新世界副本并检查来源/内容；不合并运行中的多个世界，不覆盖原存档，也不承诺原版 Java 存档兼容。

## 5. 加入、战斗结算与局部恢复

### 每场遭遇的状态机

`FORMING → PREPARING → RUNNING → SETTLING → COMMITTED`

异常进入该遭遇的 RECOVERY_REQUIRED；其他不相关舰队不因此回档或停止。等待邀请应有有界时间/默认处理，不能靠无限准备阻塞自己的遭遇或逃避代价。

1. 遭遇形成后，权威服务验证所在位置、参战资格及未被其他场占用。附近玩家可申请/接受邀请；多舰队与资产按稳定顺序在同一事务中取得锁，避免重复参战与死锁。
2. 冻结每艘舰船的持久 ID、配装、状态、所有者、驾驶授权和战利品规则；落盘局部战前检查点与名单版本。首次扣费与检查点原子提交，加载重试不能重复扣费。
3. 所有参战客户端内容校验、DP 校验、加载就绪后启动该场 Worker。不参战者继续世界活动。准备失败只处理该场，按明确的释放/恢复流程归还锁。
4. 首版建议运行中名单不变；未来增援通过独立可靠事务增加锁定资产和名单版本，先准备资源/内容，再在指定权威 tick 生效。不得直接改客户端名单或将同一舰船再次计入结算。
5. Worker 在固定步结束点生成完整 EncounterOutcome，覆盖登记舰船的存活/撤退/预备/战沉与持久状态。结果走可靠可重试消息，不从可丢弃快照推算。
6. 服务验证 computeHost 身份、epoch/attempt、名单版本、结束原因、配装不变和状态范围，在事务内更新该场参战资产、奖励、任务及回执，释放锁并递增世界 revision。
7. **提交的是这场战斗的局部资产变化，不是开战前整个世界的副本。**其他玩家期间产生的航行、交易、任务与另一场战果必须保留。市场/任务的共享条件在事务中重新检查。
8. ACK 丢失查询同一 encounterId 的已提交回执；不新建遭遇再领奖。世界位置/舰队可操作状态在持久提交成功后恢复。

### 断线与崩溃

| 故障 | 建议行为 |
| --- | --- |
| 普通参战玩家短断线 | 该场 AI 接管其舰船，允许恢复原授权；不复制舰船或影响别人的战斗 |
| 非参战玩家掉线 | 撤销控制输入，按停留/停靠策略处理其舰队；掉线不能自动无敌或免除已发生的遭遇 |
| 一场计算主机丢失 | 只把该场置为恢复待处理；未解锁前资产不可交易，其他场和世界活动继续 |
| 未提交战斗重开 | 仅恢复该场冻结资产/战前状态，生成新 battleAttempt；已提交的其他玩家进度保留，worldTick 不倒退；局部位置仍按该场锁定地点与恢复规则处理 |
| 服务提交成功但回执丢失 | 查询去重回执，不能再次扣费/奖励 |
| 结果未落盘即丢失 | 明示该场需要从检查点重开；不能宣称保存了未持久化战果 |
| 世界服务崩溃 | 整体暂时不可用，重启读取已提交世界与未完成遭遇集合，逐场恢复；不会从某一场旧快照覆盖全世界 |
| 房主退出，世界服务也关闭 | 世界暂停，原拥有者恢复；首版不承诺无缝主机迁移 |

局部检查点重开可损失未完成战斗的时间，也可能被用来重试失败战斗；首版不是铁人或竞技公平模式。相同 seed 用于初始化，不等于完整输入回放或跨环境逐位确定性。

联合出击可以分开撤退，但首版建议整个遭遇提交前保持相关资产锁，避免撤出舰先交易、末尾旧结算又覆盖交易。更早释放已撤舰资产需要分段结算设计，另立里程碑。

## 6. 最小可玩切片

网络/持久模型从一开始支持多玩家、多舰队、多遭遇；内容仍保持小规模：

- 一个小星区，1 个港口、少量航点、基础交易/维修/补给和 1 类任务；每名玩家获得明确的初始舰队与独立资产。
- A 出发遇敌，B 在港口交易；A 结算后，B 的交易不丢失。两场独立战斗也可分别结束，不互相写坏状态。
- 双方汇合并结伴，接受联合出击邀请，各自选舰、各自驾驶，战后舰损写回各自资产、奖励按预先确定的规则分配。
- 退出结伴后，各自从当前合法位置继续活动；重启恢复各自资产及正确位置，未完成遭遇按局部检查点恢复。
- 改装应用需要真实库存扣换；自由设计器只提供草稿，不能生成无限武器。未支持舰体/模块明确禁用，不静默丢字段。

第一可玩切片必须包含“独立 → 汇合 → 联合作战 → 分开”，而不是只做永久共享舰队。代驾和战中增援可在这条链路通过后追加，不能将建议分期当成用户已放弃这些能力。

这只能叫合作生涯原型，不是原版完整生涯复刻。Crew、D-mod、打捞、成长、声望、黑市、殖民、势力战争与剧情仍需独立设计/移植。规则简化要明确标注。

## 7. 分阶段实施与停止门槛

### P0：身份与模型接缝

拟建 src/engine/campaign/、server/campaign/，以及 src/network/CampaignCombatAdapter.ts；本轮不新增实现。

交付：完整持久 loadout、多舰队/多遭遇 DTO、owner/controller/party/team 身份分离、member/entity 绑定及局部检查点。

门槛：改装船保存→重启→重建一致；同型不同配装不串状态；预备舰不损耗；未通过往返验证的模块舰不进入原型。

### P1：资产事务、邀请与锁

交付：唯一世界写入者、可靠存档、身份权限、邀请/接受/退出命令、对象版本、资产锁和幂等回执。

门槛：两人购买最后一件商品只成功一次；同舰不能被两个遭遇占用；入队不转移所有权；退出不复制资产；伪造 actor 与旧 attempt 拒绝；写盘失败不显示成功。允许互不相干的两场结果先后提交，不因全局 revision 变化造成错误拒绝或覆盖。

### P2：LAN 双人“可分可合”闭环

交付：独立试验入口与最小世界状态，适配既有 host.worker 的每场权威身份/房间关系；不改变自由 LAN 对战和沙盒。

门槛：A 战斗时 B 可活动；各自同时打一场后独立结算；汇合后联合作战，再分开。覆盖单场计算主机丢失、另一场继续、重试回执、撤退/死亡/预备舰、服务重启；其他人的新进度不因恢复旧遭遇而倒退。

先做同机隔离端，再用两台物理设备测试，两者不互相替代。**P2 不通过，不扩大全银河或殖民内容。**

### P3：小星区与四人验收

交付：航行、港口、任务、维修、协同行进的时间/资源规则，以及联合战利品分配。

门槛：建议至少一轮 60 分钟的四人“各自/结伴/多场遭遇/退出”流程；记录持久提交延迟、战斗输入延迟、CPU/网络积压和各资产摘要。时长和人数是测试目标，不是已有成绩。

### P4：战中增援、代驾与 Steam 分别验收

这三项是可独立排期的功能门槛，不要求绑在一次发布中：

- 增援：距离/到达时刻正确、入场资源准备与 DP 准入、名单可靠更新、战斗结束边界拒绝过期加入、退出/重连/重复消息不重复生成舰船或奖励。
- 代驾：授权可撤销，一舰单驾驶者，所有权不变；未带入的自有舰队不能变成第二个免费操控角色；撤销与断线不造成控制冲突。
- Steam：同一完整构建、两账号、两设备、不同网络真实测试，加弱网/恢复；验证默认网关与新增事务消息，不用实验传输单测替代生产验收。

首版不承诺固定工期；在 P0/P1 明确模型和运行时依赖后，再按实测变更量估算。

## 8. 尚待确定的产品细则

核心方向已明确为“可以各自，也可以加入”。以下是后续需要细化的规则，不阻碍先验证领域模型：

- “加入朋友”默认是结伴带自己的舰队，还是也提供直接驾驶朋友舰船的入口？本文将两者分开，避免隐式资产合并。
- 联合奖励使用何种分配方式；个人任务是否共享进度，任务奖励如何防重复领取。
- 世界/战斗时间比例、组队航速、燃料补给分摊，以及战斗中舰队的物流计时。
- 战中增援的距离、到达窗口、出生点、上限；先验证战前加入不代表否定中途支援。
- 退出、离线托管、长时间未完成遭遇如何处理，避免掉线获利或永久锁住舰队。
- 地图探索和情报是否共享；现有 LAN 公开战场不能直接代表世界战争迷雾策略。

推荐原则：**所有权独立、协作可选、加入需确认、退出有规则、恢复只影响故障范围。**

## 9. 调研验证与交付边界

初次调研新增本文档；后续讨论仅修订规划方向，不改生产逻辑、不启动/重启联机服务、不构建覆盖 dist、不操作用户存档、不导入原版资源、不打包、不发布。

审查了入口、GameState / Codec / Session / SaveStore / CombatHandoff、DesignModel / LanDesign、LAN 协议 / 世界 / Worker / 战报、服务端会话与 Steam 网关等源码。

初次调研通过 esbuild 内存打包现有纯状态与 SaveStore，使用合成舰船 DTO、隔离 Map 存储执行 **10 项检查，全部通过**：

1. 出击 DTO 与调用方隔离复制。
2. 战后结构与弹药写回。
3. 相同战果不重复结算。
4. 未知遭遇不覆盖当前待结算状态。
5. 错误舰船身份拒绝结算。
6. 未来存档版本拒绝读取。
7. 重读存档保留战前结构与弹药检查点。
8. 已观察到的外部写入阻止覆盖。
9. 存储失败明确返回 memory-only。
10. 沙盒结算不改变持久舰队。

这些检查证明的是**已有单机纯状态契约**，不验证真实舰体内容、配装往返、物理战斗、多人事务或跨网性能；第 8 项也不证明同时多写入具备原子性。未运行全量构建或 Steam 测试，不把历史报告的通过项当成本轮结果。

本次方向修订未重跑上述检查，也没有验证尚未实现的多遭遇事务或加入/退出功能。

**推荐下一步：做 P0–P2 的双人可分可合实验，先证明“各自活动不互相阻塞、汇合参战不改变资产归属、战后只提交一次、单场恢复不回滚别人”，再扩展生涯内容。**
