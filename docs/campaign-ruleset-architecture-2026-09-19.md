# 生涯架构准则：原版优先，可替换的大改结构

> 最新实现为 reference.cooperative **0.6.0**：普通跳跃、缺油漂移、持久随机与整套跳跃机制替换测试已接入，累计124项测试通过。下文阶段性数字/缺口保留历史语境；最新边界以 [跳跃进度](campaign-transitions-progress-2026-09-19.md) 和 [实现账本](campaign-implementation-progress-2026-09-19.md) 为准，生涯尚不可完整游玩。

日期：2026-09-19。性质：根据用户要求修订的设计基线；基础实现正在推进，远未覆盖完整玩法。

此前阶段实现为 `reference.cooperative` 0.4.0：有限原版后勤、领域事务、编队/遭遇骨架、世界时钟与 Worker 在线调度。该阶段 78 项运行测试通过，但没有可玩的生涯 UI。代码进度见 [实现账本](campaign-implementation-progress-2026-09-19.md)，最新时间策略、整套 simulation 替换测试与数据库版本限制见 [统一模拟进度](campaign-simulation-progress-2026-09-19.md)。

> **默认生涯尽量还原指定版本的原版；通过清晰的规则边界允许大幅修改。分阶段交付意味着覆盖面逐步扩大，不意味着默认另做一套简化生涯。**

本准则优先于早期前探/实现文档中的临时简化玩法建议。可分可合的联机方向保留。没有承诺原版 Java 存档/Mod 二进制兼容、完整规则已还原，或任意修改都无需改内核。

## 1. 先定义“还原”的对象

建立 OriginalReference 基线，记录原版版本、相关资料版本和证据来源；不将本地安装的全部 Mod 当作原版。已观察到本地启动日志 0.98a-RC8，有限后勤依据和源文件 SHA-256 已记录；这不证明全部安装内容/反编译源码同版本或未修改，也不是完整生涯规则核验。

默认规则集以机制为单位验证：

- 航行：航速、燃料、补给、传感器、地形与航行能力。
- 舰队：船员、货舱、维护、维修、CR、军官、技能及舰装的生涯效果。
- 交互：遭遇、接战、追击、撤退、战后回收、打捞和奖励。
- 市场：供需、价格、关税、黑市、交易限制及经济周期。
- 势力：个人声望、正式归属/委任、外交、行动后果与事件。
- 殖民：人口、稳定度、危险度、可达性、产业、短缺、维护、管理员与防御等经来源核实的规则。
- 世界内容：星区生成、探索、任务、对话和剧情条件。

导入到名称/数值不代表机制已经实现。尤其不能预设殖民供需必然等价于“仓库逐件投入原料、逐件产生商品”：先核实原版的单位、抽象尺度与更新顺序，再实现。个别无法证实的行为标记为未知/近似，不自创公式后称为原版还原。

还原不要求首个版本包含整个银河、全部剧情和所有产业；可以在一个小测试星区先准确实现一种交易、维修或产业机制，再扩大内容覆盖。

## 2. 五层边界

```text
客户端表现层
  原版风格 UI、规则说明、地图、管理面板、战斗展示
        │ 查询视图 / 经认证的命令
联机与协作层
  身份、连接、邀请、代驾、同步、每场计算主机与恢复
        │ 协作命令 / 版本化 MultiplayerPolicy
世界执行内核 CampaignKernel
  实体身份、权限边界、调度、事务、锁、事件、保存与迁移
        │ 只读上下文 / 注册规则服务 / 验证后的效果计划
CampaignRuleset
  航行、后勤、经济、殖民、外交、成长、任务、世界生成
        │ 内容引用与规则配置
内容与场景包
  势力、产业、商品、星球条件、任务文本、星区初始状态
```

战斗引擎仍在 EncounterStart/Outcome 边界后独立运行。生涯技能或舰装跨层生效时，通过有来源、版本和校验的修正/配装合同进入战斗，不直接修改战斗全局变量，也不把战斗规则复制一份到生涯层。

### 内核应稳定什么

稳定的是执行与一致性：对象 ID、引用完整性、声明的写集合、权限验证、事务提交、重复请求处理、时钟推进记录、事件顺序和状态迁移。

内核不应写死：某产业每月利润、人口上限、税率、舰队维护公式、宣战条件、剧情、世界布局，或“一名玩家永远只能拥有一支舰队”。

也不把可能变化的玩法约束伪装成普适存储约束。例如账户是否允许债务由已选择的账户/经济合同决定，不能为了某个原型给所有资金字段永久加“不得为负”的统一限制。结构、安全和原子性仍由内核检查。

## 3. 默认规则集与联机差异分开

建议的组合方式：

- **原版基准规则集**：按明确版本实现原版语义，作为默认生涯规则的基础与测试基线。
- **合作联机配置**：在相同经济/殖民/后勤实现上组合 MultiplayerPolicy，适配多人时间、加入退出、授权、奖励参与者映射。
- **大改规则集**：显式替换某些规则 provider、内容或世界生成；有独立版本及兼容声明。

不维护两份“原版经济”和“联机经济”。联机造成的实际偏差记入差异清单：个人暂停、时间压缩、并行遭遇、战中增援、多人拥有资产、个人/势力奖励、掉线后的局部检查点等。

每项差异都记录：原版基线行为 → 联机冲突 → 采用策略 → 对数值/节奏的影响 → 验收案例。前文“世界不停、各自行动”是联机需要，不应以“与原版相同”描述。

默认不因为制作困难而擅自降低燃料/维护成本、免除殖民危机、增加奖励或跳过声望后果。测试夹具可以使用合成船、虚拟市场或简化奖励，但必须隔离在实验规则集/测试入口，不能保存为正式默认规则世界。

## 4. 扩展不能仅靠更多 JSON

| 修改层级 | 例子 | 扩展方式 |
| --- | --- | --- |
| 数据内容 | 新商品、势力、产业定义、价格参数、星球条件 | 有 schema 的内容包、引用校验和命名空间 |
| 新行为 | 新产业效果、事件、技能、生涯能力 | 注册可信代码实现，内容引用 behavior ID |
| 子系统替换 | 改用有限实物物流、不同人口模型、全新外交 | 选择新的规则 provider；明确依赖合同和数据迁移 |
| 根本模型变化 | 完全不同的空间拓扑、账户模型或回合结构 | 显式升级/扩展内核 API 与 schema，不假装普通配置就能做到 |

由用例驱动接口，先实现原版 provider，再用一个真正不同的替换 provider 验证边界。不要先建无限抽象的插件框架，也不要等默认逻辑遍布 UI、存档和服务后才补扩展点。

可优先划分的服务：TravelRules、LogisticsRules、MarketRules、ColonyRules、FactionRules、EncounterRules、ProgressionRules、QuestRules、WorldGenerationRules。名字是设计示意，不要求一次性为每个公式建立接口；同步事务中可以跨服务读取，但写入必须形成可校验的统一计划。

## 5. 规则执行合同

建议规则模块获得只读上下文与显式 API：

- 当前模拟时刻、规则/内容版本、只读查询接口。
- 内核提供的可复现随机源；按系统/事件分流，保存必要状态。
- 当前动作的身份、能力和参照版本，不是任意伪造的 actor。
- 返回类型化的 EffectPlan，例如资源变动、组件更新、日程与领域事件。

由内核在一个事务中验证版本、权限、引用、写集合和规则合同，然后统一提交。规则代码不直接写数据库、发网络消息、改 React 状态，或向其他模块的私有对象随意赋值。

纯计算与持久提交分开；外部通知从已提交 outbox 发送。执行顺序/经济阶段明确且有界，不依赖 JavaScript import 的偶然顺序；限制递归事件链，错误不能造成半份收益或默默跳过维护费。

同输入的可复现结果有利于回归，但不等于原版 Java 与 Web 逐位一致，也不要求所有客户端参与确定性锁步。仍由世界服务和本场计算主机分别持有权威。

安全边界：同进程可信 JS/TS 模块不是沙箱，接口限制不能阻止恶意代码访问宿主。首阶段只运行明确安装的可信代码；JSON 内容不执行脚本，不因加入房间而自动下载执行未知规则包。

## 6. 替换、冲突与注册规则

现有 `DefinitionRegistry` 重复 ID 拒绝、注册内容冻结；`ModManager` 内容注册与行为分离，这些原则保留。

不能为了大改把注册器改成“后加载者覆盖先加载者”。建议：

1. provider 使用命名空间 ID 与 API 版本，例如 reference.market 与 overhaul.market。
2. 规则集清单明确选择某项服务由哪个 provider 提供；先解析依赖/冲突，再一次性构建运行目录。
3. 同时选择两个互斥经济 provider 时明确报错，不按加载顺序碰运气。
4. 数据补丁声明目标、预期版本和改变内容，可追踪来源；显式有序组合不等于任意静默覆盖。
5. 新 provider 若改变单位/语义，不能只保持同名函数就声称兼容。消费它的殖民、任务、UI 等服务必须声明兼容 capability 或提供适配器。
6. 原版规则集不能藏在通用内核的 `if (id === '某产业')`、`if (faction === '某势力')` 分支里。

大改既可组合已有模块，也可替换整套规则集。内容定义与表现元数据配套，复杂管理 UI 提供有边界的扩展入口；不能假装所有全新机制都能自动被现有表格呈现。

## 7. 世界状态、存档与 Mod 兼容

世界状态应区分：

- 核心身份与关系：Player、Faction、Fleet、Member、Location、Colony、Market、Party、Encounter。
- 有 schema 的模块状态：各系统明确拥有自己的字段/组件；扩展状态采用命名空间，不用无约束的 `any` 袋子替代合同。
- 可重建的派生数据：不作为唯一存档事实来源，不能反复累加导致数值漂移。

资产 owner 使用 Player/Faction 的显式联合类型；驾驶、经营和指挥是可授予的能力。殖民地所有者、市场经营者、管理员和所在星球不是一个字段。公共舰船可以被个人驾驶，但不因此改变归属。

存档至少绑定：saveSchemaVersion、kernelApiVersion、规则集 ID/版本、参考原版版本、已启用规则/内容包及版本、规范化有效配置摘要、各模块 schema 版本、必要 RNG/日程状态。

初期沿用严格同构建门禁；将来允许兼容构建时，必须比较有效规则/内容清单，而不是 registry revision 或显示版本。摘要用于一致性，不等于能防止恶意主机作弊。

改变规则集需退出运行状态，在存档副本上执行显式迁移和验证。缺包/旧模块无迁移时拒绝加载或提供只读诊断，不静默替换默认产业、删除未知模块状态、恢复成默认船。联机中途不热换经济/外交规则；纯视觉变化另行定义兼容策略。

原版游戏 Mod 所依赖的 Java API、生命周期和脚本语义不自动兼容。可移植数据与需要重写的行为分别列出，不承诺“把原版 mods 文件夹放进来就能运行”。

## 8. 还原度账本与测试

沿用现有内容支持状态“不支持就明示”的原则，建立生涯机制清单，区分：未研究、只有来源资料、已实现待核验、已验证覆盖范围、已知近似、联机必需差异。

每项包含来源版本/路径或文档、公式与更新顺序、输入/输出单位、边界条件、观察样例、测试范围以及未知项。战斗已支持的混合舰装不能因此把其生涯效果标为支持。

验证方式：

- 小场景特征测试：固定资源、舰队状态和日程，比较计算结果与经核实的原版证据。
- 边界/性质测试：库存和资产一致性、修改者顺序、重复周期、重复消息、保存恢复。
- 周期累计测试：连续多轮交易/维护/生产后的余额与状态，避免单轮看起来正确、长期漂移。
- 随机机制：记录随机源和条件；必要时比较分布，不把一次样本相同当作还原证明。
- 联机测试：两场遭遇并发、局部恢复、资产授权和过期消息不能改变原有规则结果。
- 替换测试：不改 Kernel/网络传输即可换一个真正不同的经济或殖民 provider；缺失兼容能力能在开局前失败，而非中途写坏存档。

来源代码/规则阅读按当前要实现的机制定向进行，原版安装目录只读。不为此次架构讨论扫描全部资源或重新导入，更不把文档中列出的原版机制当作本轮已验证事实。

## 9. 修订后的落地顺序

1. 固定原版参考版本，建立机制清单与联机差异清单，选定第一个可核验垂直切片。
2. 建立最小世界内核、事务/存档与规则集装配；复用现有注册器思想，不大改已有战斗扩展。
3. 选一条有明确证据的链路，例如“市场补给/维修 → 舰队航行消耗 → 战斗 → CR/战损/战后处理”，在小场景中按原版语义实现。缺失环节明示，不用自创奖励填补正式默认。
4. 接可分可合联机适配，同一批默认规则在单人参考运行与合作运行中复用；只在差异清单位置应用多人策略。
5. 扩展势力、市场和殖民机制时，同样逐机制核验。少做若干产业是范围控制；把整个殖民经济替换为简易印钞机不是还原。
6. 尽早用一个独立 overhaul 规则集做架构验证：例如替换殖民供需语义，并为市场/运输消费者提供显式适配。不得反向改变默认基准规则。
7. 再扩展更多内容、剧情、战略 AI、动态增援和 Steam 发布验收；优先级按验证依赖调整，而非先铺内容再修存档。
