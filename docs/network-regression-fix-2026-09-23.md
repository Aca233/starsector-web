# 联机回归修复 — 2026-09-23

## 证据和边界

- 基线：已发布 v0.2.11（417a932）；用户双端会话日志，含 Steam legacy-p2p 和 LAN。
- 日志中的 LAN 客机状态频率中位数曾为 4/7Hz，而房主保持约60Hz；Steam 出现8秒未确认窗口、反复重连、输入序号未推进。
- 此次修改传输/同步保护、无损显示投影与诊断，不改战斗规则或生涯。保留现有未提交工作；不提交、推送、打包或发布。
- 没有 v0.2.6 同一真实线路的对照运行，不能声称已证明每项变更的真实WAN增益。此前3次Worker错误缺具体位置，不能凭这些旧日志声称已修好崩溃。

## 修改

### 1. Steam 同步通知幂等

原 server/steam/gateway.mjs 对每次 launch 都 resetSnapshots，接收端也每次 reset motion/component。server/lan-server.mjs 在尚未恢复操控时，会为重复 resync 重发同一 syncId 的 launch；这不是新同步批次，却不断丢掉已建立的增量参考、正在准备的快照及运动基线。

现在以 matchId + syncId + minTick 区分批次。同批次的 launch 仍正常传递，但不重置两端缓存；新批次和 welcome/match/ended/roomClosed 仍重置。网络和消费确认账目不因重复通知而清空，也没有增加窗口或延长8秒超时。

原有 check-steam-binary-gateway 用例新增双端校验：4次重复launch不得重置，下一状态保持binary-delta；新syncId必须恢复binary-full。该同一用例对未改动的v0.2.11失败（实际重置4次），修复版本通过。

### 2. LAN/Steam 共用运动通道恢复

AutoMotionAdmission 不再一次拥塞后整局永久禁用。仍维持750ms完整世界时效及tick距离校验；恢复另需：
- 降级后至少1秒；
- 当前同步批次内至少3次真实、推进tick的完整世界消费确认；
- 确认序列跨越至少500ms，帧发送年龄及确认间隙不超过375ms；
- 恢复时当前世界的发送年龄及tick距离也不超过375ms。

重连/可见性切换只清除恢复证据，不自行清除降级；旧ACK、重复ACK、成批迟到ACK不能恢复。重复登记同一待确认序号不能刷新发送时间。模块不拥有、释放或伪造网络credit。恢复计数进入脱敏诊断。Steam自身的持续丢失/拒收保护保持不变。

### 3. LAN预测压缩能力（后续收敛为按拥塞启用）

客户端默认协商motion-reference解码能力；VITE_LAN_MOTION_REFERENCE=false仍可显式关闭。后续端到端验证发现无条件启用会增加健康链路CPU，最终改为服务器测到拥塞才使用，见下节。它只影响压缩参考，不改变权威状态精度，不把Steam误协商成LAN编码。保留原有编码CPU预算及普通差分回退。

旧本机测量已显示，关闭此项能降低CPU但使同场景流量约增加17%；真实日志是交付受限，因此先恢复旧默认，而非把本机CPU下降当成普遍网络收益。此调整的真实WAN收益尚待同构建双端复测。

### 4. 可诊断但不泄露的失败信息

Worker异常通过本地消息传递Error种类、受限错误类别和最多6个数字堆栈位置；不保存任意异常文字、路径、URL、身份或世界内容。日志保留重连关闭码与白名单原因，可区分握手/心跳/解码失败及Steam状态确认/消费确认超时。环形日志淘汰后的小型生命周期摘要也保留这些字段。

## 第二轮：修复实际吞吐回退

### 明确边界

以下修改不是原版玩法/UI变更：沿用原有字段、数值、顺序、原生读取限制及网络协议，不改变AI、物理频率、显示精度或控制权限。因此以修改前完整快照/显示图和消费信用语义为对照，不操作用户桌面。新的专服发送唤醒只适用于专用权威Worker；用户日志中的普通玩家房主不走该专服捕获门控，不能将这个收益单独冒充真实线路的完整根因。

### 实现

1. **LAN单次投影**：此前先执行RenderShipProjection.project，构造武器定义字典、射程表、盾/辐能/系统和载机父投影，LAN随后把它们覆盖重做。现在共享基础字段表，只捕获最终需要的数据；保留原生读取适配检查、字段顺序、每次重采样和已捕获帧的所有权。作用于LAN和Steam共用的权威快照生产路径。
2. **完整状态窗口恢复旧余量**：SnapshotDeliveryWindow取消“观测BDP小于半帧就只留两个总槽”的新特例，恢复ceil(idleRTT * deliveredHz) + 2，再受既有闲时上限/字节上限约束。55ms路由、4–10Hz消费的退化场景不再自动挤掉第三个流水线槽。未伪造ACK、清空在途账目或延长超时。
3. **发送完成即时唤醒**：专服WebSocket写出/压缩完成时调用既有resume gate，而非每帧等16ms fallback定时器。回调绑定原socket、room和authority实例，过期完成不唤醒新实例；仍须真实消费信用和其它就绪条件。没有原生完成通知的transport仍保留有界轮询。
4. **预测压缩不再无条件开启**：客户端声明的是支持能力。LanDeltaSender.prepareForDelivery在现有拥塞控制器把capacity降到idleCapacity以下后才启用motion-reference；恢复后最多保留5秒，避免压缩后的队列刚排空就来回切换。健康/本机链路用普通精确差分。两种模式始终保留相同原始完整字节作为下一基线，切换不重置credit或降低精度，未协商的客户端永远不发预测标记。

### 验证及不隐瞒的失败候选

- 类型检查、两批改动文件lint：通过；未重跑全工程。
- 10项发送窗口 + 7项既有纯显示场景 + 42项压缩/权威生命周期/网络启用场景：通过。
- 55ms低频窗口和即时发送唤醒的两个新增用例，对原v0.2.11均失败、对修复版通过。发送完成用例另验证“只唤醒检查，不释放接收端credit”、重复完成幂等和旧authority回调无效。
- 同一冻结18舰引擎、ticks1201–1320、交替前后采样的120帧，完整二进制逐字节一致；后续动态值/原地定义修改仍重采样。捕获P50 6.216→5.0145ms（约-19.3%），P95 10.2078→8.6674ms。这是CPU局部对照，不是实际网络Hz。
