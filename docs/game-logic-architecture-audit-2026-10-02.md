# 当前游戏逻辑与根本重构边界（2026-10-02）

> 后续状态：本文保留本次重构前的审计。全场阶段更新第一块已实现，当前行为、验收与未解决问题见 [实现结果](combat-phased-world-results-2026-10-02.md)，修改前对照见 [来源与实施边界](combat-phased-world-source-notes-2026-10-02.md)。

本次为当前工作区源码审计，不是新一轮性能补丁。结论：战斗已有权威宿主、Worker、索引和显示投影，但内部仍以可变 Ship 对象为中心，按顺序穿插决策、状态推进、移动、开火和回调。前两轮减少了重复查询，没有替换这个运行模型。主要架构约束已在源码中确认；各项剩余成本的最终占比不能仅凭结构推断。

## 1. 证据与范围

- 审计的是本地当前代码，包括 2026-10-02 已有两轮改动；保留所有已有实现。
- 本机 `../starsector-core`、`../decompiled` 不存在。本轮不能重新核实原版源码或实际操作。历史审计记载 0.98a-RC8，只作历史来源，不作本轮原版等价证明。
- 最小对照：历史原版来源/当前 Web 源码 → 保留装配、幅能、护盾、弹药、命中、模块和战果的玩家语义 → 当前更新顺序成为并行约束 → 后续用真实混编战斗、技能/模块/舰载机和联机回执验收。当前没有修改玩法/UI，原版实机/UI验收待核实。
- 用户已允许内部大改、效果相近即可。因此后续不应把“完整对象快照与随机流逐步完全相等”作为所有新架构的唯一验收条件；仍须明确列出更新顺序变化，以及实际平衡、操控和联机行为的验证结果。
- 本次只读代码并新增此文档，无桌面操作、性能重跑、提交、发布或生涯打包。

## 2. 当前游戏并不是一个统一运行时

| 部分 | 当前状态所有者/数据流 | 与重型战斗性能的关系 |
| --- | --- | --- |
| 菜单、改装、技能与方案 | App / StudioApp、内容注册表、方案草稿与方案存储 | 生成装配输入；不是每个战斗 tick 的数据库 |
| 单人战斗/设计试战 | GameSession → CombatSession → LocalCombatKernel / CombatAuthority → CombatEngine | 核心模拟仍是同一个 CombatEngine；Worker 隔离 UI，不自动并行一场战斗 |
| LAN / Steam 房主战斗 | 输入 → host.worker → CombatAuthority → CombatEngine → 显示状态/关键状态 → 传输 → 客户端 | 仍是同一核心；增加输入、捕获、编码、同步与背压成本 |
| 专用服务器战斗 | 每房间 Node Worker → 同一个 host.worker.ts | 房间之间可并行；一房间内部仍沿用现有更新顺序 |
| 持久舰队/战斗交接 | GameState + CombatHandoff，出击 DTO → 活对象 → 一次战果写回 | 已有良好边界；不是完整生涯世界 |
| 参考生涯规则 | CampaignWorker / CampaignRepository / Kernel / 规则服务 / SimulationLoop | JSON 世界、命令计划、版本校验、SQLite 事务；与战斗不同 |
| 原生生涯开发运行时 | NativeCampaignRuntime 常驻对象图 → 开发仓库 → 场景投影 | 另一条未完成路径；有 Engine 分发，但完整自然推进尚未向 Worker RPC/HTTP 开放 |

当前 App 普通入口是菜单/工作室；LAN、Steam、战斗实验各有入口。生涯还有独立 `src/campaign/client/main.tsx`，不能把 GameSession 的持久舰队字段当作完整生涯已经接通。

## 3. 战斗世界里实际在模拟什么

### 状态不是“22 条船”

CombatEngine 同时管理主舰/增援/预备队、模块舰、战机、轰炸机、无人机、弹丸、光束、水雷、地形、残骸、命令、统计和视觉效果。

- `allCapitalShips` 是含预备队的身份列表。
- `capitalShips` 过滤预备队/撤离舰。
- `combatShips` 展开每个根舰的模块树。
- `ships` 再加入战机、轰炸机、无人机。
- 上述 getter 和 `Ship.assemblyShips` 当前反复构造数组，不是稳定的实体存储。

现有重型场景是 2 人类 + 20 AI 根舰，但初始有 176 实体、734 炮位。炮位是独立瞄准/生命周期工作，舰载机和模块也各自推进；根舰数不足以描述工作量。

### Ship 是可变聚合对象

Ship 持有位置、速度、输入、当前目标、父子模块、护盾、幅能、装甲、CR、所有技能系统、引擎、武器控制器、状态效果及视觉状态。AI、物理、武器、命中、技能和部分显示读取都沿着这些引用工作。父舰技能可以影响模块；载荷/系统状态可以改变属性。

当前存在明确的入口所有权，但没有统一的阶段写权限：很多被调用函数仍拿到可以修改的 Ship/World 引用。`CombatAuthority` 保证一次推进、epoch 与重入边界，不等于它内部每个阶段已可并行。

## 4. 一次真实战斗 tick 的顺序

宿主目标步长为 1/60 秒。以下顺序来自 `CombatEngine.fixedUpdateStages`，不是概念性建议：

1. 宿主采样人类输入/命令。单人玩家自动驾驶和 LAN 受控舰操作位于宿主控制阶段。
2. 引擎前置：玩家时间技能可调整全局 dt；推进 combatTime、效果回调、可见性、电子战。
3. 捕获共享武器威胁观察数据。现有新数值阶段可选 Worker；完成后才继续同一步。
4. 生成舰队计划；依次运行敌方/增援根舰 AI，设置目标、护盾/排散/技能意图和运动输入。
5. 推进指挥点、共享模块幅能规则，创建火控世界/在途火力预算。
6. **依次推进每个 combatShips 实体**：遇到附着模块先跑模块 AI，再处理撤退/目标，随后完整调用 Ship.update。
7. 更新命令抵达、中队机库、战机、轰炸机、无人机。它们读到的是步骤 6 已改变的状态。
8. 地形、状态系统、技能世界回调、重力、小行星及其碰撞；这些回调也可生成/回收舰体、水雷和效果。
9. 对 combatShips 做两两舰体碰撞；同步模块姿态。
10. 武器每帧效果、弹丸移动/拦截/命中、光束伤害。命中立即改变护盾/装甲/舰体，并可触发新效果。
11. 尾迹、水雷、特效生命周期，补做毁伤、模块全灭、部署/撤退、胜负判定。
12. 完整步提交后，由宿主按发布机会捕获显示/关键状态、编码、发送；接收端消费确认，进行显示插值/有限预测。

**主舰 AI、模块 AI和舰载机并不处于统一观察时刻。** 第 6 步还把每舰内部的多个系统捆在一起，产生跨舰的混合状态。

### 一个 Ship.update 内部又是什么顺序

状态效果/船插监听 → 战备推进/死亡检查 → 旧姿态记录/模块同步/目标 → 峰值性能 → 技能时钟和技能推进 → CR 故障/系统取消 → 护盾维持费、技能载荷、激活成本 → 运动积分 → 护盾朝向/展开 → 武器瞄准和开火 → 贴花、引擎控制及维修等尾部状态。

武器控制器内部已经有“先解各炮位，再发射”的局部分离，但范围只在**一条船**内：

炮位计时/维修 → 挂点获取目标/截获/射界/友军遮挡/开火决定 → 自动交替组选择 → 按挂点顺序花费幅能/弹药、推进充能/连发、生成弹丸/光束。

## 5. 哪些顺序必要，哪些是架构制造出来的

### 可以改变的人工依赖

例如两舰 A、B：A 先移动并瞄准，看到 B 的旧位置；随后 B 移动并瞄准，看到 A 的新位置。不是双方同时观察旧世界，也不是双方同时观察积分后的新世界。模块还可能观察到前面舰船刚生成的弹丸。

逐舰顺序因此成为当前行为的一部分。简单把 Ship.update 丢进多个 Worker，要么出现共享写冲突，要么复制世界后合并得到另一个行为。之前为了保留旧行为只能做预测、资格校验、局部提交和回退。

所有舰船的读阶段并不天然必须这样串行。明确规定“读哪个阶段、何时写入”后，目标获取、威胁评估、局部导航、炮位截获等可以并行算出结果。

### 必须定义清楚的结算依赖

- 同舰多炮共享幅能/弹药和交替组；不能同时花掉同一笔资源。
- 两次命中同一护盾，第一次可能过载；第二次应重新按已结算状态处理。
- 舰体碰撞同时改变两个实体；有关联的碰撞不能无约束同时写速度。
- 父舰技能、模块死亡/脱离、战机回收与发射涉及多实体。
- 爆炸/命中回调可以生成新实体，必须明确本步生效还是下步生效。

这些要求的是**有规则的提交阶段**。不要求寻敌、几何、候选筛选等全部等待上一次写入。

### 共享随机流也是依赖

CombatEngine 把同一个 SimulationRandom 传入舰船、中队、无人机和水雷。武器散布、ID、故障、爆炸等按调用顺序消耗随机数。随意调度 Worker 会改变随机数分配，即使输入相同也可能改变后续所有结果。

新核心需要按实体/用途划分随机流，或按战斗 seed、tick、实体 ID、事件序号确定随机值；保持新模型自己的可重放性。用户已允许内部变化，没必要让旧随机流顺序永久锁住新模型。

## 6. 慢在哪里：算法、布局、运行契约叠加

| 已确认结构 | 后果 | 根本处理 |
| --- | --- | --- |
| AI/炮位反复查询跨实体状态 | 工作量随实体、挂点、局部候选数一起增长 | 每阶段共享实体/属性表与空间索引，限定查询邻域 |
| combatShips 舰体碰撞无外层空间候选筛选，直接双重循环 | M 个主舰/模块有 M(M−1)/2 次调用，之后才在 resolver 内排除 | 空间粗筛生成实际候选对，相关碰撞集中处理 |
| 可变对象+父子引用+组合属性 | 数值计算反复穿过对象方法；跨线程需要重新编码/验证 | 连续数值列作为热状态；对象用于装配和外部适配 |
| 技能/命中/监听回调拿可变世界 | 写集合难预先确定；索引缓存必须保守失效 | 声明输入与输出，生成状态变更/生成/伤害事件 |
| 主舰/模块/舰载机不同更新阶段 | 难统一分区；旧观察顺序成为兼容负担 | 统一实体阶段，不按舰种分别跑完整小世界 |
| 共享随机流 | 调度顺序影响结果 | 分流或事件键随机，稳定提交序 |
| 发布时从状态图抽取投影并递归打包 | 快照在权威线程上有额外 CPU 工作 | 直接维护版本化数值显示记录与增量事件 |
| 多种旧 codec/资格/回退/实验路径共存 | 架构复杂、核心仍被旧语义限制 | 新核心确定一种生产状态契约，迁移后退役旧热路径 |

不能说整个游戏都没索引：弹丸对舰体已有空间索引、普通弹丸批量几何，AI 有部分导航/威胁索引，火控有范围/阻挡筛选。也不能说生产 LAN 仍发送整个权威对象：已有专门显示投影、打包数值、特效事件与独立通道。问题是这些措施仍围绕对象核心构建，成本与阶段边界没有统一。

已有关联测量：上一轮最终 Node 分段约根舰 AI 11ms、舰船/武器 24ms、战机/无人机 6–7ms；不同修订/运行窗口不可直接拼成同一总数。最新真实浏览器重型场景约模拟 63–65ms/步、捕获 28–32ms/次、编码 15ms/次，tick15 后过载，未进入稳定窗口。

60Hz 的步预算是 16.67ms；仅模拟这一项仍需约 3.8 倍吞吐提升。快照不必每物理步发送，所以不能把捕获/编码数值直接加到每步；应按 `60×每步成本 + 发布Hz×每次发布成本` 看权威端负载。当前没有最终修订的稳定逐子阶段浏览器占比，不把结构审计冒充完整 profiler。

## 7. 生涯逻辑单独看

### 参考规则路径

玩家命令 → 身份/世界/epoch/预期实体版本校验 → 规则同步生成 changes/events → 校验写集合/版本 → 新 JSON 世界 → SQLite 事务写世界、幂等回执、outbox → 玩家投影。

SimulationLoop 默认 50ms 调度，按世界时钟累计 ticks，提交 `world.advance`，不是每实体运行战斗 Ship.update。Kernel 对计划前后世界做验证与 JSON 复制；仓库存储整份世界 JSON，并非每实体一张可直接查询的热表。世界扩大后的复制/验证/序列化成本值得另行评估，当前没有测量证明其已经是主要性能瓶颈。

### 原生开发路径

常驻 NativeCampaignRuntime 保存模块化原生对象图，含经济、市场、路线舰队、阵营、记忆、能力、交互、情报、位置等服务。Engine 分发 managers → 经济/记忆/阵营 → 时钟/位置 → scripts；普通模式用 60 槽分摊后台位置，当前地点逐帧推进，fastAdvance 分发更多位置。

内部依然有 live context 和顺序回调，完整服务连接仍有缺口。Repository 的 host-only frame 事务推进驻留图，再生成 checkpoint envelope、整份保存和事件回执。当前源码明确“尚不开放 Worker RPC/public HTTP tick，需真实服务完整”；CampaignWorker 没有 frame-advance 消息，NativeCampaignApp 导航回执仍提示“世界推进仍在接入”，部分核心界面禁用。不能把有 Engine dispatch 函数当作完整可玩生涯。

数据库**已经存在**。SQLite 解决持久化、事务、幂等与恢复；既不计算战斗截获/碰撞，也不能消除战斗对象之间的读写依赖。为每 tick 数值计算改成 SQL 查询会引入另一层边界，当前无证据支持收益。生涯自然运行更适合内存权威状态加周期 checkpoint/命令日志；改变持久化频率要先定义崩溃恢复和回执持久性，不直接删掉已有事务保障。

## 8. 真正的新战斗运行模型

目标是替换 Ship.update 为中心的更新契约，保留装配数据、资源、HUD/操作和可复用数学公式。

```text
输入/部署命令
  ↓
状态与技能推进 → 构建阶段属性、实体视图、空间候选
  ↓
同阶段观察 → AI/导航意图（按实体分块，可并行）
  ↓
统一运动积分 → 模块约束/舰体碰撞 → 更新几何视图
  ↓
同阶段火控查询（按舰/炮位分块，可并行）
  ↓
按舰资源与武器生命周期提交 → 生成弹丸/光束
  ↓
弹丸积分/候选接触计算 → 按规则结算伤害/爆炸/生成/死亡
  ↓
完整 tick 提交 → 数值显示记录/事件 → 发布与渲染
```

这里有多个明确的观察阶段，不是强行让整个 tick 永远只看一份旧快照。阶段间有屏障，阶段内读记录不变、结果写独立缓冲。伤害造成盾失效时重检相关接触，碰撞关联实体集中处理；“统一结算”不能简化成任意把伤害求和。

必须同时改变：

1. **热状态布局**：稳定实体槽/ID，位置、速度、阵营、幅能、盾状态、炮位、弹丸等放进连续数据表。禁止每步复制整个对象世界来假装不可变；只读边界由缓冲/阶段写权限保证。
2. **更新契约**：Ship 不再负责完整更新一舰。移动、系统、武器、伤害按全世界阶段批量运行。父子模块关系用显式 ID/约束描述。
3. **效果契约**：回调返回控制/属性/生成/伤害/视觉事件，不能从纯查询阶段随意 mutate 世界。需要立即生效的效果写入明确提交点。
4. **查询契约**：共用空间分区和属性版本；不要每个 getter 重算，也不要无条件缓存一整帧中所有变化。现有索引可迁移，精确几何保留。
5. **线程契约**：Worker 获得数值范围和输出槽；结果携带 epoch/tick/stage。不会给每个 Worker 克隆完整引擎，再合并任意对象改动。
6. **输出契约**：热状态直接产出版本化 motion/weapon/health 数据和视觉事件；渲染无需恢复成可模拟 Ship 图。现有 detached 显示合同可作为兼容适配入口。
7. **时钟契约**：保留高频控制/物理/武器生命周期；昂贵战术可按较低频率和事件重算。已有部分 20Hz 采样，不能把再加“20Hz”当作新架构完成。相位/技能的主观时钟需分别推进。

## 9. 重构应怎样落地，避免再做一轮外围补丁

第一块交付应是一条真正可玩的新核心纵向链路：人类与 AI、主舰与模块、移动/护盾/幅能、自动火控、发射/命中/死亡，跑现有真实装配；随后接中队、组合技能、特殊武器与联机输出。不能停在新的 DTO、离线数值探针或 Worker 示例。

启动时选择一个战斗核心；开发期保留旧核心作为参考与未迁移内容的明确退路。不要默认每步双跑旧/新引擎，那会把成本翻倍。新模型自洽和可重放是要求；不再永久维护所有旧对象 getter/Proxy 的热路径行为。未迁移内容须显式列出，不能用静默简化能力伪装支持。

验收分两层：资源/命中/状态机等必须正确的规则用对照检查；更新顺序/随机分配已经允许变化的部分，检查短长战斗结果分布、操控、技能作用、舰载机、多人权威及过载行为。最终以真实重型联机的可操作性、整步耗时/CPU、发布成本和延迟为准；不以局部 kernel 提速或画面 FPS 代替。
