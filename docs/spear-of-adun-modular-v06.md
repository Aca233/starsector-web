# 亚顿之矛 v06：功能模块舰方向

2026-09-27。用户提出重制版应为模块舰。本决定替代“继续给单体v05添加方舟技能”的下一步安排。**以下是制作/接入方案，不是已经注册的运行舰体。** 旧v05和已保存方案保持不变。

## 原版证据 → 宿主能力 → 差异 → 验证

- 本机0.98a-RC8：`data/hulls/onslaught_mk1.ship` 的WS026/WS027为STATION_MODULE；`data/variants/onslaught/onslaught_mk1_Ancient.variant`将挂点绑定左右装甲模块方案。模块是独立舰体/贴图/碰撞/装配，不是同一艘船上的装饰区域。
- 宿主 `ShipSpec.modules/moduleSlots`、`Ship` 构造器及 `syncModulePose/syncModuleTree` 已支持父子实体。`GlorianaPack.glorianaShips()`沿用这条管线，不需新建第二种“亚顿模块引擎”。
- 现有子模块默认AI火控；动力模块的 `inheritParentEngineCommands` 只同步喷焰指令，不自动实现战损减速。不能据此声称舰艏主炮手动控制、全舰机库召回或战损推进联动已经存在。
- 原版实机本轮未操作，亦未启动可见浏览器。此次先确定几何分割与功能所有权，实际单模块战损、核心死亡传播、配装/存档和Worker联机须在新舰实装时验证。

## 第一版拓扑：一核心＋四附属实体（Web设计候选）

| 制作角色 | 功能与图像归属 | 模块失效后的目标行为 |
| --- | --- | --- |
| CORE 太阳核心/指挥主干 | 中部固定骨架、完整旋转环；全舰指令与太阳能资源 | 核心毁坏结束整舰作战；只记一次母舰损失 |
| FORE 舰艏武备段 | 舰艏、肩部和前部XL原生机构；前部S/M候选位 | 失去前向专武及该段武器，不让核心在原位置继续出炮 |
| PORT 左舷支援段 | 后部左侧外伸装甲与该侧L/S候选位；拟承担一侧舰载支援 | 该侧武器停用，所属甲板停止新出击/补充；在外战机命运另明确实现 |
| STARBOARD 右舷支援段 | 后部右侧对称结构；与左侧独立受损 | 同上，但不连带抹掉另一侧能力 |
| AFT 后部工程段 | 后部中央固定装甲/尾部与后肩M、尾部S候选位；推进功能需核实真实喷口 | 目标为推进能力下降，而非只让尾焰消失；减速比例尚未定 |

这不是原作官方舱段图、航母数量或炮位表。左右支援段的机库用途属于拟议Web功能分配；不把外壳纹路指认为已证实的原作机库门。模块数量先控制在5个实体，不因74公里舰长就复制数十个实体。

旋转环仍是CORE内部的**动画部件**，不是独立炮塔或每片都能炸掉的战斗模块。源骨骼数量、渲染图层数量、可受损模块数量是不同概念。

## 四档与模块并行

- S/M/L/XL保持严格同档换装，不能把“模块槽”当第五档武器槽。
- 每个武器槽只有一个模块所有者；旋转中心、承座、枪口转换到该模块局部坐标。
- FORE_PROJECTOR是单套EXTRA_LARGE内置机构，12个源控制段仍不变成12门炮。
- 继续使用烘焙舰体＋独立二维武器，不要求舰船包作者为武器建模。刚完成的生图改绘仅是外观候选，不把带甲板的合成图贴到会旋转的炮头上。

## 模型审计揭示的分割约束

审计 `artifacts/spear-of-adun/model-research/module-components.log`：

- Object_61 的左右主件是两个独立连通块，可沿真实结构归属拆分。
- Object_63 是贯穿后部中央的单一连通结构，不可按屏幕左半/右半硬切。
- Object_93包含跨越两翼的巨大连通片和独立翼尖，不能把“同一材质网格”直接当一个模块，也不能只用矩形裁图切成两张。
- 原始UV接缝会形成重复顶点；审计在位置焊接后看连通块，仅用于归属判断，没有合并或破坏实际UV/法线。

因此先按源结构拆分网格归属；跨模块的连通装甲在被原有中央护甲遮住的接口处处理，保留真实搭接。各模块毁坏时需要合理的断面/接口与正确显隐。不得用黑条、光晕或重复贴图遮住硬切，也不能复制一块装甲给两个模块造成重复承伤。

## 接入必须解决，不能假装已有

1. **主炮控制**：把根舰手动开火/编组意图传给FORE专武，不能被子模块默认AI火控擅自释放。普通侧舷炮可以独立自动火控。
2. **能量归属**：太阳能是全舰共享能力资源的设计方向，不是给每个模块复制完整太阳锻炉倍率；模块普通幅能是否独立与护盾覆盖策略需一起定标。
3. **战机指令**：根舰的出击/召回要明确覆盖存活支援模块；一侧损毁不能无限补机，也不能无依据让在外战机凭空消失。
4. **推进战损**：在实际推进规则中计算工程段状态，不把继承喷焰命令当作速度/转向联动完成。
5. **破坏与碰撞**：每段有自身碰撞与结构，核心不能继续用包住整舰的巨大矩形承伤；环的镂空与旋转姿态需核对碰撞近似，不能用一张实心多边形把中间空洞全填死。
6. **版本兼容**：先独立完成新模块定义与贴图闭包，再决定替换/迁移。不能原地把旧v05的26个槽改成五段，导致存档武器失配。

## 接下来的制作顺序

源几何模块归属与搭接 → 各段二维图层/受损断面及坐标 → 固定挂接与模块配装 → 前部主炮手动链路/独立受损 → 再接太阳能与航空支援。当前不再先给旧单体舰新增技能，避免之后重复拆迁。

### 二维合成发现的实际阻碍

`check-spear-of-adun-module-art.py` 集中核验25张PNG均为RGBA、尺寸正确且未碰画布边缘。源母版与分件场景拼合的可见区域RGB平均绝对误差为0.0147/255，仅1个像素的某通道误差超过8；几何分件未明显改变整舰外观。

但是，**五个战斗模块不能简单等同为五张按层序叠加的完整贴图**。枚举120种静止叠放顺序，最佳仍为PORT → STARBOARD → AFT → CORE → FORE（后到前）；纯舰体版本仍有2,140个像素的RGB误差超过8，最大179/255。目视差异集中于尾段与核心、两翼之间的交错遮挡，不是调整总层序就能消除。

因此：

1. 当前`*-complete.png`/`hull-*.png`为完整几何导出，不直接发布为最终运行图层。
2. `*-visible.png`仅记录静止完整场景的可见部分，不能代替所有动画和战损状态；不得把被遮住的有效几何直接抹掉来伪造通过。
3. 下一步须按真实遮挡拆**视觉子层**，仍保持5个战斗实体；环动画另做跨姿态合成核对。完整导出保留其他模块的间接光/阴影，模块损毁后需另检查残留阴影。
4. 模块移除图是Blender几何显隐审阅，不是游戏爆炸、断面或战损效果。当前不制作占位封口，不静默替换v05。

验收入口：`python scripts/check-spear-of-adun-module-art.py`。完整几何/动画重开核验脚本为 `scripts/check-render-spear-of-adun-modules.py`（含重渲染，已有证据时不必反复运行）。


## 2026-09-27 二维绘制子层：实际深度烘焙

上一节的五图总层序阻碍已进入专门的二维烘焙管线。此节描述源资产制作，不修改旧v05，也不增加战斗实体；新状态与验收数据见 `spear-of-adun-module-layers-v06.json`。

### 不是把源对象随意拆成更多战斗模块

- `inspect-spear-of-adun-module-layers.py`直接读取母版，在5种姿态采样真实射线深度。明确发现AFT↔PORT、AFT↔STARBOARD和AFT↔CORE的双向遮挡；第42帧还存在FORE↔CORE双向遮挡。换总层序无法解决。
- `bake-spear-of-adun-module-depth.py`从同一正交相机输出每个模块完整RGBA与真实Z通道。制作分辨率1024×2048，输出子层仍回到512×1024源画布；不是把高清三维模型放进游戏。
- `build-spear-of-adun-module-layers.py`按实际深度排序每个覆盖像素，将反向交叠部分分配到前景子层。每个绘制项只有一个`owner`，仍是CORE/FORE/PORT/STARBOARD/AFT之一；没有第六个承伤实体。
- 所有源像素来自实际烘焙，不调用生图重画轮廓，不画黑条/发光线掩盖接口。未添加的二维武器不烘焙进船身。

### 避免切层造成的透明裂缝

直接分割高分辨率RGBA后分别缩图会丢失接缝覆盖率，因此最终颜色与轮廓以各模块的完整512×1024渲染为准。高分辨率深度只确定覆盖份额；份额转换为source-over叠加的条件alpha，保证同一模块的子层重新叠合时还原原始透明度。

更靠后的子层可保留本模块自身的不透明内部像素作搭接底图，但远离真实半透明边缘；不借用邻段装甲，不让背景镂空变实心。重新组装还需检查旋转、1/2与1/4缩放；这不是连续任意缩放下的数学像素等价证明。

### 供后续游戏接入的明确契约

1. 先按存活模块过滤`owner`，该模块的所有前景补片必须同时隐藏；不得只移除底图。
2. 其余绘制项按`drawOrder`从后向前绘制。贴图已裁紧，用`offsetFromModuleAnchorPx`相对模块锚点定位；这些仍是制作源像素，不是已批准的游戏世界比例。
3. 变换整舰时，每个子层使用相同父子坐标链。切换姿态时整组子层原子替换，不能让新环帧和旧遮挡片混用。
4. 运行只需裁切PNG和坐标/归属清单；Blender、EXR和深度数组仅是离线证据，不是运行依赖。
5. `output/spear-of-adun-art/module-layers-v01/review.html`为可直接打开的本地制作审阅页。页面使用真实PNG逐层绘制，可选择已烘焙姿态、转向、移除/恢复四个附属模块。它不是设计界面里的新舰，也不是模拟战斗。

### 仍然不得宣称完成的部分

- 当前仅烘焙8种核对姿态，不是最终连续动画图集；“姿态轮播”不是最终战斗动画。
- 完整模块的间接光与接触阴影来自其他模块仍存在时的场景。移除后与重新光照的模型参考仍有差异，需制作受损照明/接口，不能用深度分层正确冒充战损成品。
- 原始几何显示的接口不等于已制作断裂内构、焦蚀与战损材质。
- 无头审阅页测试只覆盖二维图层、显隐、变换和异步姿态同步；游戏独立血量、碰撞、模块火控、航空和推进联动尚未接入。

制作入口：先运行深度烘焙，再构建二维子层，最后集中运行 `check-spear-of-adun-module-layers.py` 和 `check-spear-of-adun-module-layer-preview.mjs`。证据在 `output/spear-of-adun-art/module-layers-v01/verification.json` 与 `browser-verification.json`；原版游戏实机本轮未操作。


### 本轮集中验收结果

- 8个姿态，逐姿态11/12/10/11/11/11/11/11个裁紧子层；仍为5个模块归属。
- 8×16种附属模块显隐组合加160次单模块原尺寸/旋转/缩放检查，共288项离线案例通过本管线阈值。
- 静止完整场景相对真实模型参考的可见区RGB平均绝对误差，从五层的0.7455/255降到0.2035/255；8姿态最差0.2081/255。交界抗锯齿不是逐像素等价，不将平均指标当作全画面无差异证明。
- 单个模块全部子层拼回后，原尺寸alpha最大误差不超过1/255；避免了首版分图缩放产生的接缝透明缺失。1/2、1/4和17°转向另有独立记录。
- 第0/3000帧完整拼合RGB平均差0.000116/255；第375帧确有大量核心环像素变化，不是用整体2D平面转动冒充环运动。
- 8个采样姿态的引用PNG合计2,937,421字节（约2.80 MiB）；此数不代表最终连续动画图集大小。EXR、深度数组与母版均不计入未来运行依赖。
- 无头浏览器核对8姿态加载、16种模块显隐、整舰转向和快速切帧的原子替换；无脚本报错或缺失图片。没有启动可见窗口、操作用户浏览器或改动5173服务。
- 已目视审阅四状态拼合板，以及第375帧完整/移除左翼的真实Canvas截图。素材归属与姿态同步通过；移除后的接触阴影与战损断面仍未放行。
