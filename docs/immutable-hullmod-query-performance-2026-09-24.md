# 元数据热路径与多核校准修正：性能验收（2026-09-24）

## 最终保留内容

本轮相对于上一轮已接受的多核成本保护，新增两部分：

1. **只读插件成员查询复用**：`Ship.hasVastBulk` 使用 `HullModPresence.containsVastBulk`，只缓存内部登记、深不可变、稠密、普通原型名单的原生 includes 结果。每次仍读取实际 includes 方法，保留双名单/双 spec 读取的短路顺序。动态/浅冻结/带洞/自定义方法继续实时查询，不缓存目标、相位、碰撞、伤害或火控状态。
2. **本地多核成本保护不再被冷启动与定时重试误导**：
   - 初始 24 步串行样本仍用于是否试跑；真正开始 Owner 试跑后，用交替串行探针替换冷启动比较基线，再使用 0.5 EMA。
   - 至少 3 个新鲜串行探针、12 个并行完整步后才能判亏损；原 1.15×+0.5ms 阈值、每 8 次尝试一个串行探针不变。
   - 亏损后至少等 60 秒；还需要舰队数量变化或持续串行成本较上次暖态基线增长至少 25%，才重建 Worker。不是单靠定时器重新支付启动成本。
   - 获利的 Worker 仍保留。新战斗 reset 清空全部校准/拒绝状态，取消与池销毁契约保留。**LAN 默认模式没有启用这些本地策略。**

生产写集：`Ship.ts`、新增 `extensions/HullModPresence.ts`、`multicore/CombatMulticore.ts`、`multicore/CombatWorkerBudget.ts`。上一轮 `AuditedCombatMulticore.ts` 改动完整保留，本轮未再改它。没有恢复先前被否决的 fire-control batch/tree/world wire，也没有接入 GPU compute。

## 真实 CPU 剖析

基准增加 `--profile serial`：在自建无头页面的指定生产 local Worker 上通过 CDP 开启/停止 CPU profiler，不连接用户浏览器，不操作桌面。

`artifacts/fleet-cpu-20260924/profile/serial.cpuprofile`：200 Onslaught，180 tick 预热、90 tick 采样。

- 模拟栈累计约 5532 ms；武器控制 update 累计约 2535 ms。
- fleet planner 累计约 623 ms（约 11%），不是最大的热点。
- `hasVastBulk` 自身采样约 206 ms；相位/碰撞状态也很热，但属于动态读集，本轮不缓存它们。
- 包含时间不能相加；profiler 会影响执行速度，此运行只用于定位，不能用其绝对耗时计算优化收益。

冻结基线为**上一轮已经接入原生成本保护的版本**，不是更早无条件使用 4-worker 的慢版本。

最终工件：`artifacts/fleet-cpu-20260924/workload-ba200/result.json`；源图 `baseline-sources.json` 与 `workload-sources.json`。已逐字核对四个保留生产文件与最终测试源图一致。

| --- | ---: | ---: | ---: |
| 模拟均值 | 62.662 ms | 59.678 ms | **−4.76%** |

200舰约59.7ms仍远超16.67ms的60Hz模拟预算，**这不是大规模实时率问题已经解决**。

### 加新鲜探针、尚未加工作量重试条件

- `final-ab100/result.json`：100舰、150预热+180测量，模拟23.195→22.204ms，往返38.981→37.738ms，往返P95 49.160→48.580ms；状态/权威对照通过。该结果早于最后的重试条件修正，不拿它冒充最终版本的另一组完整验收。

## 范围与取舍

- 新策略以稳定性为优先：若舰队规模与总串行成本都相近、但内部热点构成变化，可能延后重新发现多核收益；不是保证永远选到全局最快方案。
- 只测试了本机这些固定场景，普通/自定义名单功能走等价回退并有契约检查，但没有穷举所有混编/模组的性能。
- 往返包含Worker通信与编码，**不是实际输入到屏幕延迟或FPS**。未测GPU计算收益/整个电脑的占用率。
- 全程无头；自建浏览器/服务器已关闭；未启动子代理、暂存/提交/推送、打包发布或更改未完成生涯代码。
