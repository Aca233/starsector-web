# 真实 Worker 多核测量与成本保护（2026-09-24）

## 本轮结论

**提高 CPU 占用率不等于降低延迟。项目已经有 4 个 AI Owner Worker，但旧原生 Onslaught 通道绕过了耗时保护，在本机两个大规模场景中持续比完整串行更慢。**

本轮保留的生产改动只有：将已有的完整模拟步 wall-time 成本保护应用到原生本地通道，仍按机器/战况试跑决定是否使用多核，而不是把多核永久关闭。没有加线程、修改 Worker 计算内容、删校验、降低精度或改变 AI/物理频率；没有修改 LAN 调度策略，也没有接入 GPU compute。

## 1. 测量方式

新增 `scripts/benchmark-real-workers.mjs` 和测试专用 `scripts/lib/real-worker-audit.mts`：

- 全新、无用户配置的**无头 Edge 153**，16 个逻辑 CPU，`crossOriginIsolated=true`，真实 SharedArrayBuffer。
- 页面 → 生产 `local-combat.worker` → 生产 `owner.worker`。每步通过 `stepScheduled()`，不使用旧 Node 串行探针冒充多核。
- 实际回收/转移 presentation 和 visual 两个 ArrayBuffer；同一固定输入和种子，每步 1/60 秒，不删舰/武器/特效。
- 串行参考、冻结旧版默认多核、新版默认策略三个独立世界，逐步交替运行，**不同时驱动三个世界**。200 舰测试反转交替次序。
- 100/200 舰验收各 150 tick 预热、150 tick 测量；不是同一个场景的完整 ABBA 重复，因此不宣称统计显著性或所有机器均有同样收益。
- 每 tick 比较有效 presentation 数值区（不比较回收 buffer 的未使用容量）、结构/元数据、replay witness、声音、命令结果、胜负。每 30 tick 比较完整权威二进制与隐藏 Autofire 跟踪器/目标/随机状态；都在计时区间之外。
- 测试构建才注入审计请求和单调递增批次完成标记；生产协议/代码没有调试接口。批次计数只统计回执中出现的**新**指标，不重复计入串行探针的旧指标；退休瞬间被清空的最终指标不作完整批次数承诺。
- 所有源图冻结/哈希、构建与结果位于 `artifacts/real-workers-20260924/`；构建拒绝导入生涯模块。这是测试工件，不是发布包。

## 2. 未修改时的真实多核成本

`baseline/result.json`：100 Onslaught，90 tick 预热 + 120 tick 测量。

| 指标 | 关闭多核参考 | 旧默认 4-owner |
| --- | ---: | ---: |
| 模拟步均值 | 19.540 ms | 26.048 ms |
| Worker 往返均值 | 31.204 ms | 37.726 ms |
| 每步真实提交的预测 | 0 | 98.825 |

旧默认每步：pack 4.663 ms、wait 4.401 ms、validate 2.154 ms、merge 0.242 ms；重算仅 0.054 ms。因此并非 Worker 没启动或全部回退。wait **包含**同步/计算，merge **包含**重算，不可把子项再次相加。

`diagnostic200/result.json` 进一步给出 200 舰带诊断计时的分段：pack 11.996 ms，wait 9.911 ms，validate 5.538 ms。pack 内 own 编码约 1.870 ms、world 编码约 2.054 ms、支持判定约 0.805 ms；其余还有预阶段可见性/电子战、目标/舰队计划等工作。该诊断不是最终性能验收，不能把局部最大值相加或把所有剩余时间归给某一个函数。

## 3. 保留改动及验收结果

修改文件：

- `src/engine/ai/multicore/CombatMulticore.ts`：原生通道也记录完整步耗时，亏损时退休 Owner pool。
- `src/engine/ai/multicore/AuditedCombatMulticore.ts`：本地成本 gate 作用于两种 codec，初始化前和已有 pool 的串行探针都遵守 gate；保留 LAN 无本地 context 的行为。内部参数更名为 `allowOwners`，不再暗示原生通道可豁免。

复用现有策略：24 个串行样本、至少 12 个并行样本、每 8 次尝试包含真实串行探针；并行 EMA 超过串行 EMA × 1.15 + 0.5 ms 时退出，60 秒迟滞后可再试。未改变这些阈值。所有探针仍执行完整权威步，pool 在本次 batch 完成后销毁。

下表来自同轮、同场景的旧版/新版配对，而不是拿不同运行的绝对数作差：

| 场景 | 指标 | 旧默认 | 新默认 | 变化 |
| --- | --- | ---: | ---: | ---: |
| 100 Onslaught | 模拟均值 | 27.292 ms | 20.694 ms | **−24.18%** |
| 100 Onslaught | 模拟 P95 | 32.730 ms | 25.265 ms | −22.81% |
| 100 Onslaught | Worker 往返均值 | 41.458 ms | 34.866 ms | −15.90% |
| 100 Onslaught | Worker 往返 P95 | 47.675 ms | 41.915 ms | **−12.08%** |
| 200 Onslaught | 模拟均值 | 72.612 ms | 62.285 ms | **−14.22%** |
| 200 Onslaught | 模拟 P95 | 84.455 ms | 73.080 ms | −13.47% |
| 200 Onslaught | Worker 往返均值 | 94.462 ms | 85.763 ms | −9.21% |
| 200 Onslaught | Worker 往返 P95 | 108.675 ms | 98.995 ms | **−8.91%** |

- 工件：`guard-ab100/result.json`、`guard-ba200/result.json`；源图：`baseline-sources.json`、`guard-sources.json`。
- 新版 100 舰在 tick 25 启动、26 使用 Owner、62 判亏损退出；200 舰在 25 启动、27 使用 Owner、163 退出。**200 舰测量窗口仍包含退出前的并行步，没有删掉这些较慢样本。**
- 在这两次测量里，收益来自退出不划算的并行路径，不是 Owner 算法本身变快，也不是 GPU 加速。
- 同轮关闭多核参考的模拟均值分别 20.731 / 61.446 ms。新版接近它，而不是比串行凭空再快 24% / 14%。
- 冷启动单独记录 `initMs`，但先后构建/脚本缓存不同，不能从这些初始化数值宣称启动提速。预热前完整成本分布没有留存，本表不是从开战起的全程平均值。
- 100 舰最终也未达到 16.67 ms 模拟步预算；大规模实时率问题仍未解决。

## 4. 拒绝的固定字段 wire 实验

试验曾将 world 间接路径读写改成固定字段静态函数，同时保持 Float64、标签、字段顺序和逐 tick 重读。

`wire-ab/result.json`（100 舰、120 预热 + 150 测量）：pack 4.681 → 4.265 ms，但模拟仅 27.217 → 26.735 ms，Worker 往返均值 40.563 → 40.179 ms，往返 P95 **47.285 → 48.995 ms**。不足以证明整体值得保留。

**已完全撤回** `Protocol.ts`、`Owner.ts` 的试验修改，并删除新增 WorldWire 文件；二者内容已恢复为冻结源图。候选仅归档在 `wire-sources.json`，不是运行代码。不为约 1% 的平均值改善引入数百行新 codec 和更差尾延迟。

## 6. GPU / 更高占用率的下一阶段边界

目前渲染本来就在 WebGL2；本轮没有 WebGPU compute。下一步若要靠更高硬件利用率获得真正额外吞吐，必须改变**数据流和任务范围**，不只是增大线程数：

1. 从本轮 pack/validate/预阶段的重复数据准备入手，建立能验证读取依赖且不重复完整计算的批任务；保留未知扩展与依赖变化的串行回退。不要拿“假设没有变化”的缓存代替校验。
2. GPU 更适合视觉粒子、尾迹这类状态可留在 GPU 的批工作。把同步权威 AI 搬上 GPU 再每 tick 回读，可能引入新的等待；WebGPU 普通浮点计算也不是现有 JS Float64 的直接替代。
3. 权威碰撞/威胁候选若试 GPU，只可先做无漏项的保守候选生成，CPU 保留精确裁决/原顺序；必须连同上传、提交、readback、候选复核一起测。没有正确性证明和整体时间收益前不默认启用。

**范围限制**：本测试没有浏览器绘制、输入排队、显示器呈现、真实联机网络；Worker 往返不是 input-to-photon。未测整个电脑的 CPU/GPU 利用率，不能从 4 个 Worker 或 16 个逻辑 CPU 推断占用百分比。
