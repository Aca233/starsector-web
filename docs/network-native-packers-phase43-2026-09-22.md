# Phase43：生成式捕获循环未过门槛，默认路径不变

## 决定

**不启用候选，不声称这轮降低了实战延迟。** Phase38、Phase41 等已验证修复保持；生产 CombatSnapshot/BinarySnapshot/host Worker 没有被实验覆盖。本轮目标仍是实际3–5人高负载联机，而不是让局部循环跑分通过。

## 实验做了什么

当前实际房主 Worker 采样曾显示 pack 自耗时约10.18%（Phase39，仅该样本）。Phase40固定属性读取和Phase42数字缓存均未达到完整管线门槛。因此这轮保留原来的Object.values读取，尝试把**其后的字段投影循环**专用化，而不是再次换读取方式。

在22船、900tick真实交火中记录57个 `(raw keys, projection)` 布局，1251个字段槽，单布局最多83槽。为这些布局生成有限静态TypeScript函数，固定字段索引和递归projection；保留标量判断、function过滤、原顺序递归、原数组就地压紧，以及每次新鲜raw keys验证。未知布局仍走旧循环，生成代码不做eval、不缓存模拟值。

候选只在测试/实验中引用。生成文件约504KB，还带来代码体积和编译成本；没有因为局部计时改善就忽略这些成本。

## 正确性证据及边界

`node scripts/check-native-record-packers.mjs`，显式指定Phase43旧/新捕获器和冻结源码：58/58通过。

- 57个生成函数对照原循环：特殊值、function过滤、递归projection与调用顺序、输入/输出内容、递归抛错后的写入前缀、未知签名回退。
- 22船真实交火推进1200tick，每30tick比较完整投影和二进制、恢复后全世界字节；检查旧捕获不随源状态推进变化、动态字段增删/函数转换、循环/稀疏数组和普通非native路径。
- 这是上述用例覆盖，不是所有模组/内建对象篡改/外部修改布局表的语义认证。候选未达到性能门槛，没有进行上线前全部边界扩展。

## Chromium完整管线对照

同一22船轨迹，3/5个顺序接收副本；A/B和B/A各一次，60预热+180测量tick。计入capture+encode+全部接收端decode/apply。每tick完整权威字节相等，每30tick及最后检查完整恢复世界。接收副本数量不是同机实际多人性能；没有传输、delta、压缩、渲染或RTT。

| 副本/顺序 | 采集P50比例 | 生产端P50比例 | 完整P50比例 | 完整P95比例 |
|---|---:|---:|---:|---:|
| 3 / A→B | 1.0550 | 1.0395 | 1.0057 | 0.9942 |
| 3 / B→A | 0.9333 | 0.9650 | 0.9882 | 0.9495 |
| 5 / A→B | 0.9883 | 1.0017 | 0.9961 | 0.9761 |
| 5 / B→A | 0.8726 | 0.9327 | 0.9952 | 0.9858 |

比例为候选/对照，越低越好。原门槛每对完整P50≤.95、P95≤1.10，生产端P50≤.85，字节不增。**全部未达到门槛**，程序退出1，原始结果保留。没有继续测该候选的Node压缩/增量或实际多人性能，更没有把此前已通过的编译版验收冒充这次候选验收。

## 下一步约束

这次加上Phase40/42，已否定继续围绕同一通用捕获循环叠加这几类局部替换。不能据此否定所有网络视图、变更登记或直接编码；只能说明这些具体实现的完整收益不足。

下一阶段先拆出舰船/世界各自的捕获成本及线字节，针对真正占比大的部分减少完整图的重复工作，而不是继续扩展此生成器、放宽门槛、扩大旧帧队列或降低Hz。

证据位于 `artifacts/network-stream-20260922/phase43/`：`before.json`、`CombatSnapshot.before.ts`、`CombatSnapshot.candidate.ts`、`shapes.json`、`unit.log`、`chromium/chromium-receiver.json`。本轮没有改生涯、使用子代理、打开可见窗口、提交、推送、构建新安装包或发布。

## 补充：真正的状态大头（诊断，不是优化成绩）

同一22船构成，分别2或5艘玩家攻势、其余锤头；种子917，全部AI近距离交火。Node同步诊断在tick130–900每10tick采样，共78帧；根计时会引入开销，不等于桌面实际帧耗时/RTT。

- 舰船根捕获约占46–47%，世界根约53–54%；不能仅凭舰船字节多就认为舰船占全部捕获CPU。
- 舰船状态约占完整未压缩二进制的70%；世界约25%，布局字典约5%。
- 另在tick300/600/900做字段字节归类（只有3帧/构成，不和78帧均值混用）：

| 字段 | 2玩家构成平均字节 | 5玩家构成平均字节 |
|---|---:|---:|
| damageDecals（烧痕/闪光等） | 58248 | 44437 |
| armor（逐格装甲） | 33753 | 38458 |
| weaponControl | 31440 | 33008 |
| engineController | 7621 | 7574 |
| shield | 5549 | 5129 |

其中damageDecals约占这些完整帧的26.5%/21.2%。这是**未压缩的字段编码字节占比**，不是实际线路流量或CPU百分比，更不是潜在延迟改善百分比。子树大小减掉自身SWF2头；不能把子树单独拿去当完整可恢复快照。

这改变了下一步方向：优先研究伤痕这类纯呈现状态如何随权威受击/装甲状态，在客机推进外观动画，避免每次重复还原全部闪光计时。`ShipDamageState.advance`含逐次随机闪光，`Ship.ts:391`传入visualRandom；不能直接挪走循环导致共享视觉随机序列变化，也不能省掉真实装甲/受击状态。需要明确外观初始化/修正、创建/删除、冷加入/重连以及本地与权威字段的所有权，再做纵向实验。本轮**没有启用该方案**。

原始证据：`root-costs.json`、`ship-field-costs.json`、各自采样入口及编译bundle。生成代码和fixture做了仅消除lint告警的清理后，58项测试再次通过；原计时所用生成器输出另存`native-record-packers.measured.ts`，并核对其SHA与性能报告inputs一致。最终定向oxlint无告警，生成器一致性及mjs语法检查通过。没有为未通过性能门槛的候选重建生产版本。
