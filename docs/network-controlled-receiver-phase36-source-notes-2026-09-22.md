# Phase36：实际多人接收端对照方法（实现前）

目标仍是实际多人延迟/Hz。Phase35 接收恢复候选只有稳定CPU收益，没有稳定实际联机收益，仍不启用。

本阶段只改无头测试工具，不改玩法/界面/生产调度。此前原版证据见 Phase35 source-notes；本阶段没有原版对应的网络压测接口，未进行原版桌面验证。

问题：旧工具从不同模拟时刻开始，墙钟输入不同，截图发生在测量窗内。使用测试专用Vite转换：首个普通中立tick后暂缓模拟，让真实客户端完成新帧同步并通过实际链路提交固定输入；只在启动阶段清空暂停时间，释放后原有60Hz调度/新鲜输入/过载/重连保护完全不变。测试转换不进入发布构建。

固定同一世界瞄准点、W和第四武器组连续射击，仍由DOM事件触发真实采样/传输/确认/预测。所有玩家输入到齐且新鲜才释放。预热120tick，比较121至1021的900tick，使用Worker自己的实际墙钟差计算Hz，不把900tick直接当作15秒。每300tick保存完整权威投影（空ACK和0诊断耗时，正常本地特效投影），不偷偷删业务字段以实现哈希相同。检查点有捕获/编码开销，单独记录但不从测量扣除。

截图移到计时后。保留预测/开火/确认弹体、800ms主线程阻塞中发布和ACK推进、原局重连、错误/年龄阈值。先做重复基线检查输入与检查点，存在差异先解释，不能把随机战斗差异算作优化收益。不放宽超时/保护，不降低Hz，不发布。

启动夹具修正记录：baseline-0错误地等待房主也通过relay收自己的tick1，触发原有12秒保护，失败保留，没有放宽保护。baseline-1选择第一组不覆盖可预测炮塔；baseline-2把分组命令和开火同批发送，真实预测器的命令屏障拒绝首发，持续按住不会自己重新建立repeat，因此保留断言失败。

最终夹具分两阶段：tick1暂缓并通过真实网络收齐第四组选择（不移动、不射击）；释放60个原有物理tick使分组/炮塔稳定，在tick61暂缓。等待所有真实副本收到61，再并行触发W+开火（无命令），收齐新鲜输入后正式释放。测量仍121–1021。准备输入和释放输入都留存比较，不绕过命令屏障/ACK或调整预测器生产代码。baseline-4已通过原有全部断言。

另发现值得后续验证的实际预测覆盖边界：LocalFirePrediction.record在命令屏障/过旧权威帧时拒绝初次rising；held仍变true，后续持续开火且cycles为空不会自动恢复重复预测。本轮不擅改该安全合同；应另加从真实已确认弹体建立repeat的严谨测试，不能简单放开屏障。
