# STARSECTOR WEB — 舰船即界面
## 先看这个：用直白的话说明要做什么

这次就做三个主要界面，不扩展其他玩法：

1. **游戏主页面**：显示一艘大的战舰、游戏标题，以及唯一一个按钮——**舰船设计**。黑色背景、清楚的大标题和有层次的灯光，让它像正式游戏的主页面，不像普通网页后台。不添加其他菜单、隐藏入口或快捷操作。
2. **舰船改装页面**：点击“舰船设计”直接进入。参考原作，中间显示船和挂点，左边选武器 / 舰船插件，右边看 OP 与参数、调整幅能，底部编辑武器组。选船、新建 / 打开 / 保存方案与进入战斗都在这里完成，不分散成多个首页按钮。换了武器，船上的外观与实际配置都要跟着变。
3. **战斗页面**：使用当前配置进入已有战斗。保留能玩的战斗逻辑，统一仪表、按钮、字体与提示的外观。结束试战后回到编辑器继续调整。

“舰船即界面”只是说三个页面都围绕玩家正在编辑的那艘船展开，不是让玩家去操作什么抽象空间。“电影感”只是构图和灯光更讲究，不是新增电影、片头或 3D 游戏。“空间过渡”只是切换页面时船图短暂移动或缩放，不改变玩法。

先看概念效果图确定外观，再做真正能点、能改装、能战斗的界面。下面的详细艺术指导给实施者使用，不要求玩家理解其中的设计术语。

## 可以调用生图，但图片不是可操作界面

用户允许调用生图工具。可用于：主页面与改装页的概念效果图，以及确有需要的背景、氛围图和材质。

- 概念图必须标明是设计参考，不能宣称已经实现或可以操作。
- 舰船外观优先参考项目的真实资源，不随意把原舰体换成完全不同的船。
- 实际交付中的按钮、文字、挂点、参数和状态反馈仍要用真实 UI / 绘制代码实现，不能把整张生图铺满屏幕后当成游戏界面。
- 不为了美化而更改舰船碰撞轮廓、挂点坐标或战斗规则。
- 生图服务失败就如实说明；不谎称已生成，不擅自改用另一个收费模型或 API。

## 艺术指导优先版 · 主页面 / 原作式改装 / 实战验证

你是一名世界顶级 Creative Developer、科幻游戏艺术指导、数字空间设计师、交互设计师、实时图形工程师和游戏 UI/UX 架构师。

现在请为当前 Starsector Web 游戏建立一个完整、有鲜明艺术观点的数字世界，并在现有项目中真正实现它。

这不只是“把 UI 改成深色”。

也不是在既有表单外面套一层科幻边框。

我要的是一种具有强烈视觉身份、电影级构图、精密工业质感和成熟游戏交互的体验：

**让一艘可以被设计、修改和亲自驾驶的战舰，成为整个界面的中心。**

第一眼，它是一件令人想要拥有的工业造物。

进入编辑器，它变成可以被理解、操作和重新配置的工程对象。

进入战斗，它离开展示台，成为你亲自验证的设计。

整个游戏应当让玩家产生：

“这不是网页里的一艘船。这个数字空间，就是为这艘船建立的。”

## A01｜项目的灵魂：THE SHIP IS THE INTERFACE

用户确认：当前只有局内战斗能够正常使用。

本次需要新增 / 完成主页面与舰船编辑能力，统一目标范围的 UI/UX。造船参考原作 Refit：选择固定舰体，配置武器、舰装、幅能和武器组，再进入战斗验证。

不要擅自添加经济、战役、殖民地或工业生产系统。

但也不要因为范围收敛，就把视觉 ambition 一起收敛成普通后台。

**艺术目标要大胆，玩法范围要准确，操作结果要可靠。**

主概念：

THE SHIP IS THE INTERFACE.

辅助叙事：

DESIGN. ARM. PROVE.

这些英文可以作为少量展示性排版；玩家操作保持清楚的中文，不把游戏做成看不懂的英文艺术展。

整个视觉叙事只有三幕：

- **PRESENCE / 存在**：主页面，第一次看见你的战舰。
- **INTENT / 意图**：编辑器，把你的选择写入舰船。
- **PROOF / 验证**：战斗，让每一个决定接受真实反馈。

三幕不是需要向下滚动的官网章节，而是玩家能反复往返的真实游戏状态。

## A02｜艺术方向：不是未来仪表盘，而是未来军工造物

整个体验应同时具有：

深空的寂静
重型舰体的分量
精密仪器的秩序
航天制造的严谨
编辑式排版的张力
军事装备的可用性
先锋数字展览的空间关系
长时间使用仍然清楚的操作界面

关键词：

Cinematic Industrial
Neo Editorial
Naval Architecture
Orbital Drydock
Precision Interface
Scientific Luxury
Machined Darkness
Quiet Monumentality

气质可以参考高端工业产品摄影、航天技术图纸、博物馆大型机械展陈、建筑事务所的版式与原作改装界面的操作逻辑。

不要直接复制品牌，也不要变成光滑到失去个性的“苹果风飞船”。

**保留 Starsector 舰体的装甲层次、涂装、非对称细节、磨损与战斗机器感；高级的是观看与操作它的方式，不是把所有舰体改成银色玩具。**

## A03｜视觉核心：THE FLAGSHIP OBJECT

原参考提示词的液态金属核心，在本项目里由“真实舰船”接替。

不是随便在右边放一张缩略图。

舰船必须拥有：

- 清楚的视觉重心。
- 有分量的尺度。
- 经过设计的周围留白。
- 与标题、工程标注和界面层级的前后关系。
- 从主页面到编辑器再到战斗的连续身份。

主页面可以让舰体占据约一半画面，处于中央偏右或偏上的非对称位置。

舰船周围是深而安静的负空间。局部照明、浅淡的装配平面和少量坐标基准让人感觉它正停在某个轨道船坞里，但不要求构建一整座无关的 3D 船坞。

利用真实精灵图、透明边缘、背景明暗、分层构图与必要的轻量效果形成空间。不要假装项目已经有不存在的完整 3D 舰船模型。

不能只是给一张船图加 drop-shadow 然后宣布“电影级”。必须通过整体构图、光比、尺寸、遮挡与有意义的标注建立存在感。

舰体艺术资源本身保持可信；材质氛围优先作用于展示环境，不能把原图涂成一块发亮剪影。

## A04｜颜色与材质：黑色仪器，温银文字，少量信号色

基础色：

- `#080909`：深而不死的暖黑，作为空间背景。
- `#121617`：带微弱冷倾向的石墨，作为仪表底板。
- `#1A2023`：抬升的结构层。
- `#343C40`：加工边缘与结构线。
- `#EEECE4`：温银白，作为最重要文字。
- `#B8BBB5`：钛灰，作为普通读数。
- `#939C9C`：次级标记，仍需满足实际可读性。
- `#8DBEC6`：克制的冷青交互光。
- `#D0AA71`：低饱和琥珀，供少量工艺细节使用，不能与告警语义混淆。

材质分成三种，不能所有东西一个透明灰色框：

1. **空间层**：深黑、平静、有细微明暗梯度，不用满屏亮星点制造噪声。
2. **仪器层**：近乎不透明的石墨底板，极细的受光上沿与暗下沿，像被装进舰桥的精密设备。
3. **标注层**：温银文字、短刻线、细引导线与局部信号色，像悬于观察平面上的工程标记。

可以使用极低强度的细纹理，但不能覆盖正文、引起噪点闪烁或做成脏旧金属贴图拼贴。

不要到处刷金属渐变。真正有质感的地方应该少而准确。

阵营、危险、武器类型依然使用清楚的原作语义。实弹黄、能量蓝、导弹绿等功能色保留在应该出现的位置，不为了统一灰白而抹掉信息。

**展示色负责气质，语义色负责操作。两者不能互相取代。**

## A05｜排版：把原提示词的尺度张力带回来

拒绝“所有字都是 14px、所有标题都只是加粗”的后台排版。

建立三套相互协调的文字尺度：

### 展示尺度

仅用于主页面和少量非战斗过渡。

STARSECTOR
WEB

或一个真实舰体名称，可以达到桌面约 7–12vw 的视觉尺度，配合较紧的行距与明确的网格关系。

允许展示性文字部分越过边界、被舰体遮挡，或作为低对比的背景层。但必须同时保留清楚完整的游戏标识。

不是所有页面都放巨型字，也不让玩家为了看菜单而绕过标题。

### 操作尺度

用于菜单、装备、参数与编辑操作，保持清楚中文与可靠点击区域。

标题与正文通过尺寸、字重、位置和留白区分，而不只靠五种颜色。

### 仪器尺度

等宽数字、型号、OP、挂点编号、快捷键和短标注。

使用 tabular-nums，读数稳定。小字提供发现细节的乐趣，但不能把关键操作缩成 9px。

数字可以比标签显著更大。普通参数整齐对齐，关键 OP 或幅能读数具有明确视觉锚点。

**允许艺术性裁切的是装饰性标题，不是武器名、成本、警告或按钮。**

## A06｜主页面：一艘战舰的出场，而不是一个菜单模板

第一次进入，玩家看到的不是六张功能卡片。

应该是一幅构图完整、但已经可以立即操作的画面：

- 深黑空间中，真实舰船停在中央偏右。
- 一束不夸张的冷光感揭示舰体边缘与装甲结构。
- 左侧巨大的展示标题与小尺度菜单形成强烈比例反差。
- 舰体局部可以穿过展示文字所在层，形成空间关系。
- 画面下方只有一条精密的状态基线，不出现传统网页 Footer。
- 少量真实舰体型号、方案名称与配置摘要作为工程标记分布，不乱飞。

主页面只有一个功能按钮，准确写作：

**舰船设计**

按钮与标题沿清楚的基线布置。可以使用温银文字、短引导线和细边框形成精致的排版式按钮；hover 时略微提亮，focus 清楚可见。不要膨胀成大胶囊，也不需要廉价渐变 CTA。

其他画面元素用于展示，不做第二个可点击入口，不加隐藏菜单、首页设置或“进入战斗”快捷按钮。

按钮文案始终是“舰船设计”，不因是否有草稿而换成“继续编辑”。点击后直接进入舰船编辑器；新建方案、选择舰体、打开已有方案和战斗验证都由编辑器承接。

唯一按钮应足够醒目、可点击且支持键盘，不因入场动画而延迟可用。

首页的美术不能靠看不见的交互撑起来。静止截图本身就要有足够的构图力量。

**主页要像一个高级游戏的主界面，不像介绍这款游戏的官方网站。**

## A07｜从首页到编辑器：同一艘船，空间开始服从你

这里是可以继承原提示词“空间变形”魅力的关键位置。

点击“舰船设计”时，不要只把首页瞬间替换成一个表格。

理想视觉连续性：

1. 首页的展示标题沿自己的排版方向退去。
2. 同一艘船在视觉上移动到工作台中心，调整到适合编辑的尺度。
3. 舰体周围的少量装饰标记转化为真实挂点、轮廓和工程读数。
4. 左右工具区域从边界建立，OP 与武器组进入固定位置。

这不是一段用户必须等待的长动画。使用短、可打断、减少运动时可直接跳过的过渡；正常情况下约 250–400ms 即可建立连续感。

不旋转整张 2D 舰船图伪装成 3D 相机，不随意生成舰体不存在的侧面。

加载时间与转场分开处理。内容尚未就绪就准确说明，不播放无尽电影感进度条。

## A08｜编辑器：精密设计台，而不是左右三栏后台

参考原作 Refit 的操作关系，但以新的艺术指导重新组织观看方式。

中心是舰船，不是白色画布。

背景是比主页面更均匀的暗石墨工作平面，辅以极淡网格、少量尺寸基准和舰体定位线。网格服务于空间感，不需要每 10px 一条高亮线。

舰体周围保持足够的呼吸空间。装备信息从真实挂点向外引出，而不是贴满船身。

左右功能区应该像工作台的仪器边栏：

- 不同区域依靠底色、留白、局部边线与对齐建立，不为每一块内容画完整矩形边框。
- 左边是装备与舰装的选择逻辑，拥有可靠列表密度。
- 右边是约束和效果，OP、幅能、关键属性形成有节奏的读数柱。
- 顶部是方案身份和主要行动，而不是网站导航。
- 底部是武器组的稳定控制区，与战斗中的组号和布局建立呼应。

舰体本身应比页面中任何一张图标、任何一段说明更有视觉重量。

**它可以是三段结构，但不能一眼看上去像“侧边栏 + CRUD 表格 + 详情卡”。**

## A09｜挂点与装备：每次选择都像一次精确装配

hover 挂点：

- 先出现局部轮廓与清楚的命中反馈。
- 相关尺寸、类型与射界以克制的图形呈现。
- 其余无关挂点适当降低强调，但不能消失到找不到。

选中挂点：

- 一条准确的细引导线把舰体位置和所选装备的上下文联系起来。
- 装备列表进入兼容内容。
- 当前装备、可替换装备和不能安装的原因清楚可见。

安装武器：

- 真实武器外观立即出现在对应位置。
- 挂点有一次短促、局部的确认反馈。
- OP 与相关参数同时更新。
- 可选的声音必须克制、可关闭；没有合适资源就不添加廉价 UI 点击声。

不要弹出“安装成功！”盖住舰体，不需要让整个页面闪光。

这种高级感应来自“一个小动作在空间里产生准确的对应结果”。

武器类型色只在点位、短标签或细条上出现。不要把整个左栏刷成当前武器颜色。

---

## A10｜把数据设计成仪器，而不是数字堆积

OP 是约束，幅能是能力边界，武器组是控制结构。它们应该在视觉上有所区别。

### OP：精密预算尺

使用大一些的当前读数、小一些的总量与一条准确比例的占用尺。武器、舰装、幅能等消耗可有轻量分段，但不要加入无法理解的彩虹。

剩余足够时平静；接近上限时提示；超额时清楚指出缺口与原因。

### 幅能：两套不同职责的仪器

容量与耗散分别呈现，不合并成一个抽象“能量评分”。

电容与耗散器的调整可以像设备刻度：明确的数量、上下界、增减操作和生效结果。操作可以精密，但不能把滑杆做成难以抓住的一像素装饰线。

### 参数：工程规格单

标签、数值与单位有固定对齐关系。重要参数适当放大，次要参数安静归组。

比较效果可以短暂标明变化值，随后回到稳定读数，不让每个数字一直跳动。

禁止伪造战斗力、预测胜率、设备温度或未知技术参数来填满画面。

## A11｜我的方案：像设计档案，而不是商品橱窗

方案列表也是艺术设计的一部分。

采用有节奏的档案行或清楚的舰船条目：

真实舰船剪影
方案名称
舰体型号
关键配置摘要
最近编辑状态
明确操作

每个条目有稳定的文本基线，选中方案与右侧或中央预览联动。

不要把方案做成电商商品卡，不出现价格标签、稀有度光柱或“购买”按钮。

没有方案时，空白不是错误。用一块有设计感的空工作台、一句明确说明和“新建舰船方案”即可，不需要大幅 AI 插画。

保存、复制、重命名和删除以清楚、低干扰的方式完成。确认框继续沿用同一台仪器的材质与文字语言。

## A12｜从设计台到战场：DESIGN BECOMES CONSEQUENCE

进入战斗时，视觉叙事从“观察”转为“行动”。

工程网格退去，挂点标注收起，舰体回到已有战场的真实比例与镜头，战斗仪表就位。

可以有一次简短而明确的出战过渡，但不要伪造曲速航行或新增一段与实际加载无关的片头。

所有花哨表现必须在玩家需要操作前退到后面。

**首页负责吸引，编辑器负责理解，战斗负责清楚。**

战斗里不再使用大标题遮挡、不让 HUD 随鼠标漂浮，也不让主页面的慢呼吸效果影响瞄准与警告。

玩家应该意识到：刚才在工程台上选的武器、幅能和分组，现在正在真正起作用。

这是整个游戏最有力量的视觉与交互呼应，不需要用一段营销文案解释。

## A13｜战斗 HUD：把艺术感压进精确，而不是拿掉艺术感

战斗 HUD 可以克制，但不能粗糙。

它的艺术感来自：

- 完整而清楚的仪表比例。
- 舰体示意图与真实舰船之间的呼应。
- 数字、标签、刻度与状态的精确对齐。
- 稳定的视觉节奏。
- 在必要时才出现的信号强度。

不要求每个区域都有一块不透明大面板。可以让部分读数贴近边缘，利用小面积底板、短分隔线和局部对比保护可读性。

幅能、结构、系统、武器组和雷达应像同一套舰桥仪器的不同模块，不能一块像复古像素游戏、一块像现代 SaaS、一块像浏览器默认表单。

保留战场星云与武器表现，但危险提示在实际明亮背景上也必须清楚。不能只在纯黑截图里好看。

---

## A14｜战后报告：从激烈回到安静

结算不是一张庆祝海报。

让画面重新获得稳定的结构：

- 清楚的战斗结果与本次方案身份。
- 经过组织的真实统计。
- 少量有意义的视觉强调。
- 明确的“返回改装”“再次试战”“返回主页面”。

标题可以比常规面板更有分量，但不占据半个屏幕。战果与损伤的强调不需要满屏红绿。

如果只是提前结束试战，就表达“试战已结束”，不要伪造胜利与完整结算。

返回编辑器时，再次看到原来的设计与配置。战斗留下的是对方案的理解，而不是被偷偷改成残血的设计文件。

---

## A15｜共同视觉语法：所有界面来自同一个制造者

建立可以反复识别的设计母题：

1. **基准线**：主页面的“舰船设计”按钮、编辑器标题、报告表头共享对齐逻辑。
2. **局部刻度**：OP、参数与 HUD 在合适位置使用同一种短刻度语言。
3. **轮廓焦点**：舰船、挂点、方案条目的选中反馈使用同一套层级。
4. **材质层**：空间、仪器、标注三层始终成立。
5. **数字语言**：型号、读数、单位和快捷键具有一致节奏。

不要每个页面都重新发明风格。

也不要把“统一”理解成所有区域都画相同卡片：

**统一的是设计语法，不是页面模板。**

细节可以包括短编号、分区名、真实舰体标识、方案状态和原生资源信息。它们应能解释界面，不是无意义地填入经纬度、NASA 编号或虚假科研参数。

---

## A16｜动效与质感：物体有重量，操作没有阻力

首页允许非常缓慢的环境变化与极小视差；编辑器强调局部即时反馈；战斗只保留服务状态的表现。

- 首页背景视差不超过轻微空间暗示，船不能追着鼠标跑。
- 进入编辑器采用短暂的空间连续过渡。
- 挂点与武器反馈约 80–160ms。
- 普通面板约 140–220ms。
- 只有首页 / 编辑器之间的关键转场可以适度更长，但要可打断和跳过。
- 所有真实状态与交互命中区域即时准确，不能等待动画结束才接收下一个指令。

优先 smooth / weighted / precise。

禁止弹弹乐、橡皮筋、不断摇晃的卡片和所有东西都慢慢淡入。

prefers-reduced-motion 下保留构图和对比，不依赖运动维持设计完整性。

---

## A17｜技术不是视觉借口，也不是炫技目录

不要求为了复刻原提示词的技术名词而安装 Three.js、R3F、GSAP、Lenis 全家桶。

当前的真实舰船资源、CSS、SVG 标记、Canvas 和已有 WebGL 渲染足以承载很强的视觉设计。先判断缺什么，再选择最小合适实现。

允许为首页与编辑器补充必要的轻量图形和展示效果，但不能强行重写战斗渲染器。

没有 3D 模型就不要宣传完整 3D。没有法线贴图或可信材质信息，就不要用伪灯光把舰体细节洗掉。

如果静态画面构图已经失败，加 shader 也不会变高级。

如果静态画面构图成立，少量准确的动态就能让它鲜活。

---

## A18｜禁止“正确但无聊”的交付

不要交付：

- 把标题、按钮和一张小船图随意拼在一起，就叫高级主页面。单按钮是用户要求的简洁入口，应通过构图、字体与舰船展示做出完成度，而不是增加菜单来填满画面。
- 标准后台三栏布局换成深灰色，就叫原作式改装台。
- 所有文字同样大小、所有面板同样宽度、所有区域同样亮。
- 带着昂贵形容词、实际只有 border 和 box-shadow 的普通页面。
- 随机发光边框、每个角都切角、每行数据都配无意义图标。
- 为了“克制”删掉所有构图张力和视觉主体。
- 为了“艺术”让编辑困难、告警不清、数据不真实。

**不是在艺术感与可用性之间选一个，而是让不同场景承担不同的表现强度。**

---

## A19｜实施与视觉验收：先证明艺术方向，再铺满所有页面

先完成一个可运行的视觉基准组：

1. 主页面静止画面。
2. 编辑器默认状态。
3. 编辑器选中挂点并打开武器选择的状态。
4. 使用同一方案的战斗 HUD。

它们必须同时满足：

- 视觉上能一眼认出属于同一款游戏。
- 主页面有足够的第一眼冲击力。
- 编辑器即使数据密集也有明确的视觉中心。
- 武器选择反馈精确，没有破坏布局。
- 战斗仍然清楚、可操作。

评估时先看静止构图，再看微交互，最后看跨页面转场。不要用漂亮首页掩盖普通编辑器，也不要用复杂技术说明掩盖粗糙视觉。

如果第一版看起来像套了深色主题的普通管理软件，必须重做艺术指导，而不是只再加几个图标。

功能连接与视觉基准同步推进：不能只做漂亮截图，也不能把艺术设计留到所有功能做完之后再补。

---

## A20｜最终标准

第一次看到：被舰船与空间吸引。

停留十秒：发现排版、标注、材质和精密细节。

开始编辑：每个选择都准确、直接、有反馈。

进入战斗：设计真正接受验证。

返回修改：所有界面仍然像同一个连贯的世界。

问自己：

“去掉功能说明，这几张界面是否仍然具有清楚的艺术观点？”

“去掉动效，主页面是否仍然是一幅完成度很高的构图？”

“从原作借来的操作逻辑，是否变成了真正可用的编辑器，而不是一张模仿截图？”

答案都必须是：是。

**船不应该被塞进网页里。整个界面应该围绕这艘船成立。**

最终成品应该冷静、厚重、精密、陌生而可信。

像一套原本就该存在于深空船坞里的舰船设计系统。

## B｜功能与工程附录：保证艺术设计真正可玩

以下内容规定真实行为、数据约束与验收，不是要求把所有页面画成功能表格。

视觉方向以前面的艺术指导为准；数据真实性、玩家操作安全与既有战斗可用性不可被装饰牺牲。

先兑现 A 部分的艺术表达，再用 B 部分确保每个可点击区域背后都有正确实现。两者需要同时成立。

### 一、先明确事实，禁止擅自扩大玩法

用户确认的现状：**目前只有局内战斗能够正常使用。**

用户确认的目标：

1. 一个完整的主页面。
2. 能够造船和编辑舰船，参考《Starsector》原游戏。
3. 使用编辑后的舰船进入已有局内战斗。
4. 重构并统一整个目标范围的 UI/UX。

这次将“造船 / 编辑舰船”按原作 Refit 改装模式落实：

**选定已有舰体 → 配置挂点武器、舰船插件、幅能与武器组 → 得到自己的舰船方案 → 试战。**

不是从零绘制舰体，不是网格拼装飞船，不是任意添加炮台或修改船体碰撞轮廓，不是战役工业生产。

不加入星区探索、殖民地、贸易、资源采集、生产队列、购买舰船、多人、故事任务或长期舰队经营。

代码里存在某个类、面板或数据字段，不等于功能可用，更不等于它已被用户选为产品玩法。现有舰队、持久损伤、存档和模组相关代码只能作为待核实的工程背景，不能直接决定主菜单与产品范围。

以下主页面、改装编辑器、舰船方案管理和改装到战斗的桥接，均是本次需要新增或补全的目标，不要描述成已经完成。

### 二、参考原作的方式

重点参考原作：

- 固定舰体、固定挂点与原生舰船资源。
- 舰体居中的改装交互。
- 挂点尺寸、兼容类型、射界与内置装备限制。
- 装配点 OP 的预算关系。
- 武器选择、舰船插件 Hullmods、幅能电容与幅能耗散器。
- 武器分组、齐射 / 交替射击、自动开火。
- 改装完成后进入模拟 / 战斗验证的循环。
- 深色工业面板、明确战术语义色、紧凑但有层次的信息。

参考原作的系统关系和信息结构，不是把原版全部游戏系统搬进浏览器，也不默认要求逐像素复刻某张截图。

可读取当前安装中的 `.ship`、`.variant`、`ship_data.csv`、`weapon_data.csv`、`hull_mods.csv` 与配置作为版本对应的依据。明确区分当前安装、可能受模组影响的数据，以及项目已经打包的数据。

不能凭记忆编造 OP、武器属性、舰装效果、兼容限制和幅能公式。原作某功能存在，不代表 Web 战斗引擎已经支持。

### 三、总体艺术方向：精密舰船设计与作战终端

保留参考提示词中的冷静、精密、未来工业感与空间张力，但去掉官网展示逻辑。

关键词：

Future Industrial / Naval Engineering / Tactical Clarity / Precision Instruments / Restrained Motion。

最终感觉应当是：

“我正在设计和调试一艘真实可驾驶的战舰，而不是在填一张网页表单。”

- 主页面：有游戏身份、有旗舰视觉、有空间感，入口直接。
- 改装界面：像精密舰船工作台，操作密集但不会迷失。
- 战斗界面：把可读性与操作可靠性放在首位。

它们属于同一套设计系统，但不要求同一套布局或同一种密度。

禁止 SaaS 风格、满屏圆角卡片、蓝紫渐变 UI、大面积毛玻璃、装饰性液态金属核心、机器人和无意义 3D。

这是太空游戏，已有星空、星云、护盾与武器光效可以保留；禁止的是新增与玩法无关的炫光，不是删除战场内容。

### 四、主页面：游戏入口，而不是宣传首页

主页面必须独立设计并实现，默认正常访问先进入主页面，而不是自动开战。

### 视觉构图

桌面采用非对称布局：

- 左侧：游戏标识、简短身份文字，以及唯一的“舰船设计”按钮。
- 中央偏右：当前选中的舰船方案预览；没有方案时展示明确标注的参考舰。
- 底部或右下：方案名称、舰体、配置摘要和必要状态信息。

舰船使用真实资源，配合少量轮廓线、挂点标记和低对比工程网格。不假装这是拥有任意 3D 舰船模型的项目。

主页面的展示性标题可以有强烈尺度反差、局部裁切和舰体前后遮挡，但必须另有清楚完整的游戏标识；操作文字、方案名与关键状态不可裁切，不能要求用户滚动才能开始。不要在“舰船设计”之前或之后，再加一道“ENTER”或“进入游戏”的中转页。

### 唯一入口：舰船设计

首页只显示一个按钮，文案固定为“舰船设计”。点击后直接打开编辑器，不先进入另一个功能选择菜单。

编辑器负责承接：

- 选择舰体、新建舰船方案。
- 打开 / 继续编辑、保存和管理已有方案。
- 配置武器、舰船插件、幅能与武器组。
- 使用当前合法配置进入战斗。
- 必要的上下文操作帮助。

初次进入没有方案时，在编辑器内展示舰体选择；已有有效草稿时可恢复草稿，并保留编辑器里的新建 / 打开操作。没有方案、配置不合法或存储异常不能把首页唯一按钮变成永久禁用：进入编辑器后再准确引导处理。

不在首页放新建、继续、我的方案、进入战斗、操作说明或设置等额外按钮。更不出现战役、殖民地、生产、舰队出征等无关入口。

### 状态与性能

首页可以展示少量不带操作的舰船或方案摘要；没有方案、未保存草稿、配置合法性与存储异常的详细处理放在编辑器内。仅首页自身无法加载时显示必要的故障说明，不擅自扩充常态菜单。

首页不启动正式战斗、不推进 AI、不消耗弹药、不触发结算。背景展示优先静态或低成本微动效。

浏览器不能运行 WebGL2 时，仍应尽可能进入主页面、查看和管理方案，不让战斗报错层锁死所有非战斗功能。

### 五、舰船编辑器总体布局

参考原作改装工作流，采用舰体居中的工作台，而不是一屏独立卡片。

建议区域：

1. **顶部状态栏**：返回主页面、方案名、舰体名称、草稿状态、保存与进入战斗。
2. **左侧配置区**：当前上下文的武器选择、舰装选择或分类列表。
3. **中央舰体区**：真实舰船、挂点、装备外观、选中与射界反馈。
4. **右侧参数区**：OP、幅能配置、关键舰船参数，以及所选装备详情。
5. **底部或固定子区**：武器组编辑和相关模式设置。

可根据分辨率调整，但舰体应始终是操作锚点。不能点一下挂点就弹出覆盖整个舰体的多层对话框。

顶部主操作保持稳定，滚动列表不能把“保存”或“进入战斗”滚到找不到的位置。

区分“选择舰体”和“修改方案”：换舰体可能使现有挂点与配置不兼容，要明确处理，不能悄悄丢弃装备配置。

### 六、舰体与挂点交互

- 新方案从实际受支持的舰体与可用预设开始，而非伪造可玩的空白舰体。
- 舰体轮廓、挂点位置、尺寸、朝向和射界来自真实数据。
- 挂点位置不能任意拖动，舰体装甲、引擎位置与战术系统不作为自由参数编辑。
- 悬停、键盘焦点和选中有不同且一致的表现。
- 空挂点与已装备挂点清楚区分，不能只靠图标颜色猜测。
- 选中挂点后，装备列表切换为相关内容，并显示当前武器与替换后的参数差异。
- 类型不兼容、尺寸不合法、内置装备等情况有准确的不可用原因。
- 武器大小与挂点大小匹配规则按原作及实际实现验证；不要误以为所有挂点都只能接受同尺寸装备。
- 允许卸下可替换武器，不允许拆下真正不可替换的内置装备。
- 装卸后更新舰体外观、预算、参数和武器组引用。

中央预览支持适度缩放、平移与一键恢复视图。滚轮只作用于当前区域，不能同时滚动列表或触发战斗输入。

拖放是可选增强，不是唯一操作方式。基础点击选择 / 安装 / 卸下必须完整可用，不能要求精确拖到几像素大的挂点上。

### 七、武器选择与参数

武器列表以“看得懂能不能装、装上后会怎样”为目标。

显示适用的信息：

- 名称、图标、尺寸、挂点兼容类型。
- 伤害类型、单发伤害或每秒伤害。
- 射程、幅能消耗、有限弹药与补充特性。
- OP 消耗。
- 项目真实支持的特殊说明。

基础射程与改装后的生效射程明确分开；持续输出、爆发输出和单发伤害不能混用标签。

搜索、尺寸 / 类型筛选与无结果状态必须真实工作。未知参数用“未提供”或省略，不填 0 假装有数据。

默认不加入市场价格、购买、仓储扣除或稀有度解锁循环。玩家使用本次明确支持的可用装备目录，不凭空引入经济条件。

对已装武器和候选武器做紧凑对比，正负变化不能只靠红绿区分。配置差异必须基于正确的计算链路，不播放虚假的属性提升动画。

### 八、OP、幅能电容与耗散器

OP 是编辑器的核心约束，不是装饰进度条。

- 清楚展示总预算、已使用、剩余与超额。
- 分项展示武器、可计费舰装、幅能配置及适用舰载机等消耗。
- 内置装备是否占用 OP、舰装随舰体大小的成本、相互约束等以真实规则为准。
- 幅能电容与耗散器分别显示数量、上限、OP 成本和最终效果。
- 加减按钮、数值输入或滑杆应同步，并处理整数、上下界、粘贴和键盘操作。
- 同时显示基础幅能容量 / 耗散与最终生效值。

不要把“界面数字变化”当作实现完成。配置必须真实传入战斗并影响容量、耗散等对应行为。

允许在编辑草稿中暴露清晰的非法状态，但不得将超额、未知装备、无效挂点或不支持效果的方案当作合法方案启动战斗。

未装满所有挂点不自动等于非法。空武器方案是否允许试战按实际规则处理，可以警告“没有可用武器”，不能臆造原作不存在的硬限制。

不要显示虚构的预测胜率或无法可靠计算的整舰综合战力分数。

### 九、舰船插件与舰载机范围

舰船插件 Hullmods 的选择方式参考原作：列表、说明、安装状态、OP 成本与适用限制。

- 内置与可拆卸舰装明确区分。
- 显示冲突、依赖或舰体不适用的原因。
- 安装 / 卸下后更新最终参数，避免重复叠加效果。
- 只将有可靠实现、能够在战斗中生效的舰装列为可安装。
- 不把完整原版舰装目录全部做成可点击后只修改说明文字的假功能。
- 需新补充效果时，明确列出实现范围与验证结果，不宣称已经复刻所有原作效果。

舰载机配置只对有机库、且现有战斗确实支持相关机翼的舰体开放。若纳入本次实现，需要同步处理数量、兼容性、OP 和战斗装载；否则不放一个无效的配置按钮，也不阻塞普通舰船改装闭环。

本阶段不引入故事点、S-mod 升级、D-mod 修复经济、军官与角色技能等额外成长系统。

### 十、武器组编辑

允许按原作式交互组织挂点到武器组，并配置齐射 / 交替射击与自动开火。

- 组号、对应快捷键、成员武器与模式一目了然。
- 点选组时联动高亮对应挂点。
- 更换或卸下武器后，组数据不残留不存在的挂点引用。
- 每个可分组武器的归属与引擎规则一致，不创建互相矛盾的重复归属。
- 默认预设可以提供合理初始分组，但用户修改后不得被启动战斗时的自动分组静默覆盖。
- 分组编辑与战斗 HUD 使用一致的组号、图标、模式词和状态色。

完成标准是玩家编辑的分组真实出现在局内并能被原输入方式控制，不是只保存一份与战斗无关的 JSON。

### 十一、方案、草稿与保存

为了支持重复编辑，本次新增的是**舰船设计方案管理**，不是长期战役存档系统。

方案至少以明确、版本化的数据表达：方案 ID / 名称、基础舰体 ID、挂点装备、舰装、幅能配置和武器组；纳入舰载机时再包含对应配置。

- 基础舰体与用户方案分离，编辑方案不污染全局模板或其他方案。
- 同一舰体可以有多个独立配置。
- 支持创建、打开、保存、复制、重命名与删除。
- 显示是否有未保存改动，离开编辑器时提供保存 / 放弃 / 取消的清楚选择。
- 删除指向明确的方案并保护未保存草稿，不能误删原作资源。
- 本地保存失败要可见，不显示假的“保存成功”。

使用独立命名空间保存方案，不能覆盖已有游戏存档。浏览器刷新后的设计恢复与战斗中途恢复是两件不同的事，不能混淆。

如提供 JSON 导入 / 导出，必须完成版本、ID、字段、数值范围与内容可用性校验；否则不展示该入口。不要假装兼容原作完整存档或所有 `.variant` 扩展字段。

### 十二、改装到战斗的真正连接

这是本次最重要的功能验收，不允许“编辑很完整，进入战斗还是默认船”。

启动战斗前：

1. 明确当前用于试战的方案或草稿。
2. 校验挂点、武器、舰装、OP、幅能和分组。
3. 从基础舰体与配置创建隔离的战斗快照。
4. 按确定顺序计算最终属性，避免原预设、用户舰装与战斗修正重复计算。
5. 将快照交给现有战斗会话和渲染流程。
6. 在局内使用实际装配、外观、武器组与生效参数。

优先复用当前已经可玩的遭遇与敌人设置。本次不要求再实现关卡编辑器、敌军部署器或多舰队编队系统。

“试战”默认是设计验证循环：

- 战斗损伤、剩余弹药、幅能、坐标和冷却是本场运行状态，不回写成设计蓝图的永久损伤。
- 战斗结束后可查看真实结果、重新试战或返回编辑器。
- 返回编辑器保留原设计和草稿，不把战斗残血舰误当作新的基础模板。
- 战斗未结束而选择结束本次试战时，明确提示会丢弃本次战斗进度；未经过真实结算条件，不伪造胜负与完整战报。
- 只打开战斗暂停菜单时维持正确暂停；编辑方案不同时热修改仍在运行的战斗对象。

本阶段不要求中途战斗保存。若需要保留旧有恢复能力，不改变它的语义，也不把它作为本次新玩法承诺。

### 十三、统一战斗 HUD

保留当前可用战斗的行为、控制和视野，以统一设计系统重构其表现层。

覆盖：玩家状态、结构与装甲、软 / 硬幅能、护盾、战术系统、武器组、弹药、目标、悬浮标牌、雷达、现有战术地图及相关状态提示。

优先级：

- P0：结构危急、幅能风险、过载 / 辐散、当前目标、当前武器组、有限弹药。
- P1：装甲、护盾、系统、战备值、速度及真实可用的舰载机状态。
- P2：完整说明、通信与开发诊断。

中央保留连续战斗空间，边缘仪表稳定，不随参数变化跳位。

- 硬幅能与软幅能可辨认。
- 满结构与满幅能的风险方向不同，不能套同一套“越满越绿”。
- 原生状态、时间与读数立即更新，不因美化延迟告警。
- 无目标不显示上一个目标的旧数据。
- 自动开火与选中组的反馈不混淆。
- 无限弹药显示 `∞` 或统一文案，不出现 Infinity / null / NaN。
- 同一装备在编辑器与战斗里的命名和单位保持一致，差异参数注明运行时状态原因。

地图和已有指挥功能维持现状，不借 UI 重构扩展成原作完整战术部署系统。

### 十四、统一视觉系统与组件

优先演进现有共享组件和主题，避免新首页、新编辑器、旧 HUD 三套样式并存。

基础色方向：

- 背景 `#080909`。
- 常规面板 `#121617`。
- 抬升面板 `#1A2023`。
- 分隔线 `#343C40`。
- 主文本 `#EEECE4`。
- 次级文本 `#B8BBB5`。
- 辅助文本 `#939C9C`。
- 交互强调 `#8DBEC6`。

数值是起点，最终根据实际背景对比调整。敌我与风险采用原作可辨认的语义，不把所有正常标签都做成荧光色。

保留挂点类型的既有颜色编码，例如实弹黄、能量蓝、导弹绿及复合类型颜色；尺寸另外编码，不能把类型色改成尺寸色。

- 默认中文优先，使用可靠本地字体回退。
- 数字 tabular-nums；等宽用于数字与短标识，不用于整段中文。
- 正文 / 控件约 13–15px；主要 HUD 标签约 12–14px。
- 标题按页面密度分级，首页可以比编辑器更大，战斗不放巨大标题。
- 4 / 8 / 12 / 16 / 24 / 32px 间距系统。
- 方正或极小圆角，细边框，有限层级，不滥用阴影。
- 面板、列表、读数行、按钮、输入、滑杆、选择器、标签、工具提示、确认框与通知共用规范。

DOM 与 Canvas HUD 从统一的主题语义获取颜色和字号，不在每帧重复读取 DOM 计算样式。

### 十五、页面、输入与反馈规范

页面导航与战斗模拟生命周期分离，不能靠每次换页重建整个 GameSession。

- 主页面仅通过“舰船设计”进入编辑器；方案列表和管理在编辑器内部打开，无需先开战。
- 共享编辑器内容不被重复包在多个巨型 Modal 中。
- 主菜单返回、编辑器返回、结束试战和重新开始分别表达，不用一个含糊的“返回”触发不同破坏行为。
- 弹窗管理 focus、Escape、Tab 顺序与关闭后的焦点返回。
- 键盘输入方案名称或筛选武器时，不触发战斗快捷键。
- UI 点击、滚轮和拖拽不穿透到射击、瞄准或地图缩放。
- 打开阻断式战斗菜单时清理按键和鼠标状态，防止恢复后卡键或自动开火。
- 关闭弹窗只恢复应恢复的暂停状态，多层确认不错误提前恢复战斗。

控件覆盖 default / hover / focus-visible / active / selected / disabled。异步行为才显示 pending，不为同步操作假装加载。

错误给出原因与可执行下一步。配置非法、保存失败与资源缺失不能只依赖瞬时 toast。

### 十六、动效与响应式

动效短、稳、可跳过：按钮约 80–140ms，面板约 140–220ms。优先 CSS transform / opacity。

- 选中挂点用轻量轮廓与局部反馈，不旋转整艘船作为每次点击动画。
- OP 与属性变化清楚但不持续跳字。
- 不用长转场阻止连续安装武器。
- 不用 Lenis、滚动叙事或装饰性自定义光标；已有战斗准星保留准确命中反馈。
- reduced-motion 下取消非必要位移、脉冲和背景运动。

验证 1920×1080、1366×768、1280×720、2560×1440，以及窄屏和低高度窗口。

- 首页在窄屏仍先暴露主要行动，不让舰船海报占掉数屏。
- 编辑器由三列改成舰体与上下文工作区切换，保留持续可见的 OP 和主操作。
- 不全页等比缩小，不把关键文字压到微型。
- 工具提示不超出视口，长中文 / 英文和大号字体仍可操作。
- 点击替代拖拽，键盘可访问主要编辑操作。

只承诺实际实现并验证的设备输入。不能只有键鼠控制却宣传完整触屏战斗，也不要放不起作用的虚拟摇杆。

### 十七、工程边界与真实性

项目：`C:/Program Files (x86)/Starsector/starsector-web`。

现有技术栈：React 19、TypeScript、Vite 6、Tailwind CSS 4、lucide-react，以及现有 WebGL2 战斗渲染与 Canvas2D HUD / 离屏绘制。

不迁移到 Next.js，不为首页或编辑器安装第二套 3D 引擎。

这次不再是“只能改 CSS”的任务：为实现真实改装，允许有边界地扩展方案数据、OP / 配置校验、支持的舰装效果、幅能计算与战斗装载适配。

但不得无关重写 AI、碰撞、武器基础规则、模拟节拍或战斗渲染。保留固定 60 Hz 模拟与渲染解耦，保持既有可玩战斗作为回归基准。

- 静态舰体、用户配置、最终计算结果、可变战斗实体分层。
- 不能直接修改 ContentRegistry 中的共享原型实现用户改装。
- 原资源目录只读，必要数据通过现有工具链形成最小运行时数据，不让浏览器读取安装目录。
- 引入新的 OP 和改装数据时记录依据；没有数据不能假设免费、零成本或无限制。
- 未实现的能力不以可安装 / 可启动的形式伪装成功。
- 现有游戏存档不删除、不改名覆盖；方案管理独立保存。
- 不重新创建已移除的测试工程，不进行手工资源哈希 / 大小审计。
- 不自行部署或发布。

性能以同场景对照验证，不编造 60fps 保证。不要让编辑器打字或选武器导致整场战斗每帧重渲染；离开页面清理监听器、预览资源与定时器。

### 十八、实施顺序

以下是功能依赖顺序，须与 A19 的视觉基准同步推进；不要将美术设计推迟到项目末尾。

1. 阅读代码并列出“真实可用 / 部分存在 / 缺失”的能力清单，以用户确认的“只有战斗可用”为起点验证。
2. 明确本次受支持的舰体、武器和舰装最小集合，以及对应原作依据。
3. 建立方案模型、OP / 兼容性校验与隔离装载路径，先证明自定义武器和幅能配置能在战斗生效。
4. 建立视觉 token 与共享组件，完成主页面和改装工作台。
5. 完成武器选择、幅能、舰装和武器组的真实编辑反馈。
6. 实现方案管理与主页面 → 编辑 → 战斗 → 返回编辑的闭环。
7. 统一战斗 HUD、结算、帮助、错误与现有开发工具外观。
8. 做不同分辨率和真实交互验证，清理确认已替代的重复表现层。

可以先做最小集合，但最终必须列明具体支持范围，不能把“能查看挂点”当作“能够改装”，也不能只做首页截图就宣布完成。

### 十九、验收场景

运行已有 typecheck、lint、build；临时交互验证使用隔离浏览器数据，避免污染用户现有存档。不重建测试运行器或测试文件。

至少验证：

- 首页常态只有一个可操作按钮，准确标为“舰船设计”，不随草稿状态改名或增加其他入口。
- 点击该按钮直接进入编辑器；无方案时在编辑器内选舰体，有草稿时按真实状态恢复。
- 从真实舰体创建方案、命名并保存，再次打开恢复一致。
- 安装 / 替换 / 卸下不同武器，挂点、预览、OP 和参数一致更新。
- 非法尺寸 / 类型、内置武器、OP 超额和无效配置有准确反馈。
- 幅能电容与耗散器改变真实战斗数值，不只改界面。
- 所有开放安装的舰装具有可验证的实际效果，反复装卸不累计错误加成。
- 修改武器组后，进入战斗保持用户配置，而非被默认预设覆盖。
- 同一舰体的两个方案互不污染；自己的修改不会改变敌舰或原始模板。
- 编辑方案 A 后进入战斗，检查实际武器、参数、分组；返回改为 B，再次试战能看到真实差异。
- 战斗损伤和弹药消耗不破坏保存的设计。
- 返回编辑保留草稿，放弃 / 保存 / 取消与结束试战语义准确。
- 存储失败、未知内容和 WebGL 不可用时有安全可用的界面。
- 键盘、焦点、滚轮、拖拽、弹窗暂停与战斗输入互不穿透。
- 代表性窗口尺寸下首页、编辑器与 HUD 无遮挡、无不可达主操作。

截图用于判断视觉，不能代替交互验证。分别报告已执行、代码检查和未验证，不笼统声称全部通过。

### 二十、交付与最终标准

交付：

1. 可操作主页面。
2. 原作式舰船改装编辑器，以及准确的支持范围。
3. 舰船方案管理与必要的数据校验。

5. 统一后的 HUD、结算、帮助和状态反馈。
6. 设计规范、关键界面截图、检查结果与未解决事项。

最终逐项自问：

- 打开主页面，能否立即理解这是一款“设计舰船并试战”的游戏？
- 首页是否只有清楚的“舰船设计”入口，进入编辑器后能否找到新建 / 打开 / 保存方案与进入战斗？
- 能否看懂一个挂点可以装什么、需要多少 OP、装上后改变什么？
- 编辑后的舰船进入战斗，是否真的是刚才那套配置？
- 回到编辑器后，能否继续完善同一个设计，而不是一切重置？
- 主页面、改装与战斗是否像同一款游戏，而不是三个拼起来的网页？
- 每个可点击控件是否都能完成符合文案的真实动作？

**我要的是一个参考原作改装体验的“舰船设计 → 实战验证”游戏，不是空有科幻皮肤的表单，不是扩张成未被要求的战役系统。**

视觉冷静、精密、有游戏身份；编辑时容易理解，战斗时看得清，来回调整时可靠顺手。
