# Phase35：原生接收端字段恢复（实现前）

Phase34是有证据的进展：排除定时器主因、拒绝避碰低收益实验；目标仍未完成。本阶段以完整捕获→编码→实际delta/压缩→解码→应用和真实多人路径为准，不用局部循环计时替代延迟/Hz。

当前代码证据：`CombatSnapshot.unpackRecord`、数组与ProjectileColumns、nativeProjection命名字段恢复，无论值是否为原始标量都会先动态读取`output[key]`。标量随后直接覆盖，旧值完全不使用。大快照会在接收端重复进行这些读；3/5人上一轮应用中位约4.83/6.15ms。

原版证据：本机`../decompiled/starfarer_api_source/com/fs/starfarer/api/combat/CombatEntityAPI.java`明确独立提供`getLocation/getVelocity/getFacing/getAngularVelocity`，可变实体状态与呈现不能通过丢字段代替。此改动只涉及Web网络DTO恢复，不改变原版物理/玩法/界面，无原版桌面实测。

候选：仅在现有显式nativeProjection契约（本机非Proxy实体+解码DTO，无自定义accessors）下，标量写入前不再读取被覆盖的旧值；结构/向量/typed数组仍读取旧对象，保持复用/引用/顺序/全部验证/深度检查。普通泛型分支完全不变。无跨tick缓存、不跳端点、不减精度、不降Hz。

验收：差分覆盖稀疏字段/自定义普通路径/极值/记录与模板/异常前缀/跨端点回调/对象identity；真实全世界投影与线上编码字节一致。冻结公共源码，3/5个离线副本A/B、B/A每对完整管线P50至少改善5%，P95不恶化超过10%；然后实际多人路径验证。达不到则保留负例而不启用。不改生涯、不用子代理、不操作桌面、不发布。

首个“只消除标量旧值读取”的候选已测：接收应用约快9.5–11.3%，完整管线约快0.9–5.2%，未过每对5%的整体门槛，负例保存在`phase35/benchmark/`。第二候选在同一契约内给常见Vector2叶子一个短恢复路径，绕过大型容器分派；仍保持$record/$undefined/$ship优先级、深度限制、完整坐标验证、旧向量对象与set方法，并保留稀疏数组every的索引存在语义。不改线格式、不对非法值容错。

第二候选应用快约11–12%，完整管线约快4.1–5.7%，仍未过所有成对门槛（原始结果保留）。进一步发现所有已解码帧都重复为同一字段字典分配Set并校验重复/禁用字段。第三候选加入有界原生字典验证复用：每次命中仍逐个比对所有键，只有同一已验证的完整序列才能复用；缓存只存冻结副本，输入修改不能污染缓存。仅缓存128键以内的字典，最多128桶，同首键+长度桶只存一个计划，超限/不命中继续完整原校验，不减少有效键/深度/重复字段/膨胀限制。一般/Getter/Proxy路径不使用缓存。

对照工具审计：前几个运行虽然捕获源码相同，却为两臂使用了不同函数实例/捕获缓存，capture计时出现系统性差异，而本次没有改捕获。后续正式判断改为**两个分支共用同一个捕获函数和codec实例，只替换接收应用函数**，不把控制端偶然更贵的捕获算成新恢复器收益。旧结果保留作前置实验，不作为最终启用证据。
