# 火控多线程原型：轨迹已验证，整步收益未通过（2026-09-17）

## 本轮真实进展

本轮不再继续叠加小型几何快路径，而是做出了可运行的火控 Worker 原型：**舰炮瞄准、目标选择和射线遮挡判断确实在额外四个 Workers 中计算，主线程仍按原顺序发射与结算。**

100 艘默认原生 Onslaught 的完整战斗状态对照已延长到 tick 660，全部 50 条检查点哈希一致。但完整模拟步仍然变慢，因此**原型只保留在 artifacts 中，没有在正式 src 或正常战斗页面启用，也没有新增已验收提速。**

## 当前版本整步数据

同一冻结对照，种子 0x51180，dt=1/60，预热 60 步、计时 600 步，逐步轮换执行顺序。i5-13490F，16 逻辑处理器，Chromium。

| 项目 | 基线 | 火控并行原型 |
|---|---:|---:|
| Worker 配置 | 4 个 AI | 4 个 AI + 4 个火控 |
| 整步平均耗时 | 45.80596 ms | 55.04294 ms |
| 模拟吞吐 | 21.83122 步/s | 18.16763 步/s |
| P95 耗时 | 59.59000 ms | 69.18500 ms |

**吞吐下降 16.781%，平均耗时增加约 20.165%。** 不能把从更慢的早期原型改善当成相对正式基线的提速。双方的原有 AI 多线程仍启用；历史工具标签 `4` 在本实验表示候选版，不表示候选总共只有四个 Workers。

### 额外火控阶段的成本

| 阶段 | 平均 ms/步 |
|---|---:|
| 火控快照打包 | 3.64274 |
| 分发、等候、返回 | 13.87037 |
| 输入校验与结果整理 | 3.04021 |
| 单个 Worker 最大同步时间 | 2.75966 |
| 单个 Worker 最大预测/火控计算时间 | 6.17260 |

后两项发生在等候期间，**不能再次相加**。这里的 Worker kernel 还包含影子舰船的前置状态预测，不是纯瞄准函数时间。

问题并不是任务没有分出去：原型持续生成约 1300 个挂点计划/步。更明显的成本是原有 AI 流程之后又做了一套完整快照、校验、同步，以及各 Worker 重复预测他舰前置状态。仅把函数搬到另一线程没有使整步更快。

## 具体实现

1. 原有四个 AI Workers 先完成。随后在舰炮更新之前暂停实验步，捕获本步输入。
2. 火控 Workers 按舰船分配挂点工作，并预测原来的顺序世界：前面的船已移动、后面的船未移动，而不是偷偷改成所有船同时读取旧位置。
3. Worker 中运行原生瞄准算法、每挂点独立的 tracker/RNG，以及从 decide 拆出的几何判断。主线程消费计划后，继续执行弹药节约、幅能预算、武器生命周期、共享战斗 RNG、弹丸和伤害结算。
4. 舰船数值快照使用共享 Float64/类型标签缓冲区，结果也使用共享 Float64 行；输出用 Atomics 发布步序。没有改用 Float32。
5. 每个 Worker 仅解码自己负责的武器节点；预测中省略与本步火控无关的武器后贴花/引擎尾部推进，正式主线程仍照常执行它们。
6. 没有降低 AI 或武器频率、跳步、增加 dt、删除主线程视觉更新，亦未改成每舰独立的权威战斗 RNG。

## 正确性证据与修复

- 早期审计模式对每次 Worker 计划再运行主线程原函数比较；已记录至少 310700 次瞄准和 301236 次几何比较通过。审计模式双算工作，其耗时不作为消费模式的性能结论。
- 当前消费模式真正使用 Worker 结果，不在每个命中计划上重复主线程几何。100 舰运行至 tick 660，50 条完整引擎图/隐含 Autofire tracker 哈希记录与基线一致，无页面错误。
- 末次阶段边界记录至少 856177 次瞄准消费、830189 次几何消费，计划缺失和全批输入失效均为 0。计数在 prepare 时采样，落后该步的实际消费，不伪称这是完成第 660 步后的精确总数。
- 第一版回填重建 tracker 改变了对象字段构造顺序；已改为使用原生 tracker 构造并更新现有状态，不靠弱化哈希来绕过差异。
- 原型 TypeScript 检查发现：几何函数拆出后，弹药护盾策略仍需要原来的 muzzle origin。现已保留原变量并传给几何函数；这也说明默认舰船轨迹检查不能代替静态检查和其他武器策略覆盖。
- 首次延长运行在 tick 270 之后遇到保留目标导弹已不在本步名单中的情况。现用名单外的无效占位保留旧 ID 供原生目标失效逻辑使用，不把它变成新的可射击目标；修复后重跑到 tick 660 全部匹配。失败记录没有删除。
- 冻结原型 TypeScript 检查及 Vite 构建通过。

## 不得误解的边界

这是**实验调度器**中的整步对照，不是正式 CombatSession.fixedUpdateScheduled/RAF 的完整集成验收。两版均计入玩家 AI、原有 AI 打包/等待/验证/回退、完整引擎步和视觉时钟推进；候选额外计入全部火控阶段成本。哈希不在计时区间。

以下工作尚未完成：

- 中途暂停、重启、销毁、输入到达时，新增等待点与正式 pending-tick 协议的安全衔接。
- Worker 故障或超时后的按原序继续执行，以及输出内容/引用/步序的完整失效回退验证。
- 动态增删舰船、改装、低 CR 故障、非默认舰船、模组回调与自定义状态的适用性门槛和依赖校验。
- 对共享输出行进行生产级、失败关闭的边界/内容校验。
- 真实页面 FPS、画质及大规模实战稳定性验收。

**不能把 tick 660 的默认舰船一致性外推成对所有场景无损；100 艘战列舰 / 180 FPS 仍未实现。**

## 下一步的明确方向

先消除第二套完整快照与同步，研究复用现有 AI owner pool/数据协议，而不是继续增加 Worker 数量。需要以新的整步对照证明总收益，再补齐上面的失效、输入和生命周期边界，才考虑正式接入。原型虽已计算正确，但当前更慢，不能上线。
