# 大规模模拟与低延迟：下一阶段方案（2026-09-24）

## 决策摘要

下一阶段不做全量 ECS 重写、不默认打开旧固定布局实验，也不继续以局部循环优化作为主路线。

采用两条独立验收的路线：

1. **交互延迟：定义与动态状态分离 → 安全的专用接收器 → 避免主线程重建整幅显示对象图。**
2. **模拟吞吐：基于现有原生火控事务，减少重复候选遍历和几何查询；保持原有提交顺序、随机数顺序与频率。**

首个生产改动建议是有界的“显示定义表”切片，而非同时迁移全部显示、Worker、AI。先补齐真实通道的延迟归因，再实施并集中验收这一切片。

本轮仅代码阅读、一次冻结构建的 CPU 剖析及本文档；没有修改生产代码，没有操作桌面、启动可见浏览器或调用子代理。性能百分比是成本归因，不是待实现方案的提速承诺。

## 1. 已测事实与证据边界

上一轮非 profiler ABBA，64 舰（2 Onslaught + 62 Hammerhead）：

| 阶段 | 优化后平均 CPU |
| --- | ---: |
| 模拟 | 14.05 ms |
| 捕获 | 7.24 ms |
| 二进制编码 | 5.63 ms |
| 解码 | 3.18 ms |
| 接收应用 | 17.31 ms |

这是串行 Node CPU 流水线，不包含浏览器渲染、网络和 IPC，不能把总和直接当实机帧率或控制延迟。

本轮对同一个冻结 after 构建剖析，240 tick 预热 + 240 tick 测量：

- 接收 apply 调用栈采样约 4318 ms。
- `DisplayDefinition.visit` 子树约 1217 ms，占 apply **28.2%**。
- `DisplaySnapshotCodec.assertDataField` 约 1102 ms，占 apply **25.5%**。
- 这两类工作互不包含，合计约 **53.7%**；其余递归 unpack、生成还原器与上层 restore 存在包含关系，不能继续相加。
- 模拟调用栈内，`ShipWeaponControlSystem.update` 约 **40.6%**，`updateShipAI` 约 **34.0%**；`assessThreats` 等又包含在上层路径中，不重复计入。
- 剖析影响计时，只用于选优化对象；不能将该轮约 18.96 ms apply 与无 profiler 的 17.31 ms 比较成性能退化。
- 原始工件：`artifacts/simulation-perf-20260924/receiver-analysis/{cpu.cpuprofile,result.json,profile-summary.json}`。该目录为测量工件，不是生产模块。

大规模模拟仍是另一个问题：上一轮本地串行 100 / 200 Onslaught 的模拟平均约 **29.06 / 67.81 ms**；200 舰 P95 约 98.29 ms。60Hz 的整步时间预算仅 16.67 ms。网络/显示优化不能解决这部分超支，64 舰混合场景的成本占比也不能直接外推为 200 舰占比。

## 2. 先纠正延迟测量，再改变调度

### 已有机制，不重复发明

- `host.worker.ts` 在完成物理步后、完整快照捕获前发布 motion；motion 带实际应用的输入序号。
- 已有 catch-up 步之间有界 yield、快照 credits、最新状态合并、后台暂停展示与重同步。
- `NetworkFeaturePolicy.mjs` 默认为自动 motion 协商；完整多频率 visual/combat 仍为实验策略。
- dedicated Worker 初始 `motionState:false`，随后 `lan-server.mjs` 根据实际接收者/控制通道启用。初始值本身不是故障。
- 接收端已有运动、炮塔、开火预测；`SnapshotPlayback` 在卡顿后最多应用最后两个端点，而非无限回放。

上一轮独立 Worker 延迟探针没有经过真实服务器协商，只观察完整快照 ACK。因此它没有测量已激活的 motion 路径，也不是输入到显示的延迟证据。

### 最小链路追踪

用 `inputSeq + authorityTick + match/sync epoch` 串联：

1. 客户端采样/发送输入；发送前受背压等待的时间单列。
2. 权威端收到输入、实际应用到哪一个完成的 tick。
3. motion/full/combat 各通道何时发布该应用序号，及通道是否真正协商并启用。
4. 客户端收包、解码、排队、应用、提交渲染分别计时。

只比较同一进程/时钟域的时间差；跨进程记录阶段时长和序号关联，不直接相减未校准的 `performance.now()`。端到端可使用客户端同一时钟统计发送至带对应序号的显示提交。

“服务端收到了输入”不能冒充“物理已应用”；RAF/render-submit 也不能冒充显示器实际发光。分别报告 applied-ACK、render-submit 延迟、P50/P95/P99、长任务、队列年龄、权威实时比例以及过载/恢复失败，不能只保留成功片段。

## 3. 第一切片：把重复定义移出每帧热路径

### 当前明确成本

`LanDisplaySnapshot.decodeShips` 已有 craftSpecs 去重与接收端不可变副本，但每帧仍计算 JSON 签名。武器 `weaponSpec`、系统 `definitionData` 仍随动态记录解包并递归验证；多个系统别名也反复经过恢复/验证。

`validateDisplayDefinition` 检查资源路径、数据预算、原型、描述符和禁止键。这些是可信边界，不允许为性能删掉。

### 拟议协议（尚未实现）

为一个协商的新 display 版本定义三类数据，不另叠一份完整旧快照：

- **定义表**：`definitionId + revision + kind + immutable payload`，覆盖武器显示定义、系统显示定义，随后复用到 hull/craft 定义。
- **动态状态**：携带精确的定义引用、实体身份与 tick；角度、冷却、弹药、开火状态、幅能、装甲、动态 range/speed 等仍按原语义发布。
- **基线/恢复**：完整列出该基线需要的定义；未知 ID/revision 不得显示旧定义凑数，也不得提前 ACK 为已应用。

接收端在每个新定义版本上完整验证并创建接收器拥有的深不可变副本。动态包仍要做数量、类型、合法数值（包括字段允许的 Infinity）、索引、实体引用及 tick/epoch 校验，但不再递归重走同一不可变定义。

### 所有权是硬条件

- 当前 mount spec 是可变的，不能按对象地址跨帧缓存，也不能只约定“调用者记得加 revision”。
- 第一步只对已登记的深不可变元数据安全复用。对原生可变定义，在发布边界生成独立定义快照并用受审计字段及变化追踪决定版本；不能直接冻结权威挂点。
- 未受控的自定义字段/accessor、原地修改或未知扩展保持完整采样/验证路径。若变化追踪代价抵消收益，则该类型不晋升快路径。
- 本地预测/显示修改进入独立 overlay；不得改共享不可变定义，也不得让一艘船的修改串到另一艘。当前可变显示扩展需要适配或走兼容路径，不无声改变接口契约。

### 恢复与边界

先使用自包含的有界定义基线，证明读集等价；再加同 epoch 的跨帧复用。旧接收端使用旧协议，不混用。定义和动态状态原子提交：验证全部成功后才让该 tick 可见。

限制定义个数、总字节、每帧新增数、嵌套深度；重连/切图/同 ID 新实体使用新 epoch 或 generation。避免 ID 冲突、重用后串读、缓存无界增长、缺定义状态排队和过早淘汰；定义缓存仍需保留当前插值端点所引用的版本。若引用依赖 ACK，必须使用已验证且已安装的定义回执，不使用仅“收到字节”的回执。

**验收重点**：稳态包体、捕获、编码、解码、apply 和总 CPU 一起测；冷启动/换装/大量定义同时变化不能隐藏。wire 格式改变后不能再要求新旧 wire 哈希相同，应比较权威状态与完整显示读集等价。

## 4. 第二切片：专用安全接收器，而非移除安全检查

`assertDataField` 的高成本来自对每次字段写入遍历目标/原型描述符，避免覆盖方法或访问器。现有生成还原器仍会做这个检查，仅继续生成赋值代码不能解决根因。

方案：对已经审计过的显示 schema，使用接收器私有固定槽位/数据存储，外部读门面与本地 overlay 分开。动态包只能通过已验证的 slot 和类型更新私有存储，不能用任意网络 key 修改带行为对象。

这样可将“是否允许写这个字段”的检查移到 schema/实例建立边界，同时保留逐包值与引用检查。不是把 `constructor + key` 的描述符检查结果永久缓存：旧显示对象可能被本地扩展修改，缓存会失效。

实施时必须覆盖 renderer、HUD、预测、模块/舰载机引用和本地可写显示字段；不能只迁移渲染器的一小部分，再每帧同步回完整旧对象图。

旧 fixed-display 实验已经实现过 buffer/read facade 与 overlay。其 renderer 局部收益不代表完整 LAN 收益：已有真实窄切片测量 P50 3.2589→3.3551 ms，P95 改善，故仍默认关闭。复用已有基础，但不把重新打开开关当成新方案；必须先证明其余对象图重建成本确实被移除。

## 5. 第三切片：Worker 的目标是缩短关键线程占用

协议和接收存储稳定后，才考虑把有界解码/定义校验移到接收 Worker。Worker 输出应是可转移的显示状态存储与少量已验证描述信息，主线程不再恢复第二份大型对象图。

- 仅把 `decodeBinaryState` 放到 Worker，再 structuredClone 整幅对象图回来，很可能只是移动成本并增加延迟。
- 网络 delta 基线/定义安装必须按协议顺序消费；只允许合并可替换的展示状态，不能丢掉重建后续包所必需的基线或定义。
- 声音、一次性 FX、生成/销毁、终局及确认事件保留可靠顺序与去重；插值端点仍需保留，不能简单“只留最新一帧”。
- 使用有界队列、明确 buffer 所有权；主线程还在读取的 buffer 不得被回收/写入。先用 Transferable，只有收益证据成立才评估 SharedArrayBuffer 的部署和同步成本。

现有浏览器 host 已有可选 SnapshotEncoderBroker，不能泛称“编码完全没有多线程”。dedicated Node 路径的适配须另查；即使移出编码，权威捕获本身仍占模拟线程时间。

最终延迟验收要跑真实协商的主机/接收端路径，不能用一个串行 Node 性能环代替；无头自动测试可做，不占用户桌面。

## 6. 模拟路线：扩展现有查询域，而非全帧结果缓存

### 已有设施

`FireControlQueryBatch` 已按单舰瞄准事务共享目标资格，并有友军遮挡/在途命中 blocker index。它不是全帧快照。当前原生资格扫描在 >=100 舰才启用；因此本轮 64 舰剖析没有覆盖该批处理收益。已有 AI multicore 也有准入、成本保护与串行回退，不应无条件增加 Worker。

### 下一候选

1. **火控 acquisition/preAim 的保守候选索引**：现有 blockers 索引不是完整的目标获取索引。复用原生只读事务，按武器有效范围、目标半径、相对运动和截获时域建立保守候选集，再按原世界顺序执行原精确解算、排序与 tie-break。不能用当前坐标固定圆筛掉高速进入射程的目标。
2. **复用真正重复的查询，不复用可变结论**：同事务内共享资格/几何边界；护盾、幅能、死亡、传送、阵营、名单或钩子变化结束有效期。逐舰更新与发射/伤害顺序照旧，不用“同 tick”假设掩盖前一艘舰已改变世界。
3. **按实际成本决定准入**：记录候选数、武器数、被宽相拒绝的次数、索引构建成本和 fallback 原因，再比较已有 >=100 阈值。不能因为 64 舰剖析热点高就直接下调阈值；密集近战可能不适合建索引。
4. **避免把资格审计变成新 O(N²) 热点**：若要扩展原生对象所有权/变更 revision，先限定一组受控写入口，保留不受控扩展的旧路径。OwnedCombatSession 已存在但未完成生产集成，上次全步约 1% 且 P99 变差，不以“有 ownership/ECS”作为提速证据。

并行化只针对隔离的只读候选/纯解算，结果带输入世界版本，按原顺序提交，过期则回退。不要把战舰 update 放进 Promise.all、并行修改世界或改变随机调用顺序。

模拟候选实施前仍须做项目要求的原版源码最小对照。边界场景覆盖高速目标、导弹/诱饵、站点模块、舰载机、遮挡、传送、动态改装、扩展回调及种子确定性。

## 7. 顺序、停止条件与交付

| 顺序 | 有界交付 | 晋升条件 |
| --- | --- | --- |
| 0 | 真实 motion/full 链路归因 | 可区分收到、应用、发布、展示；失败/过载不漏报 |
| 1 | 定义表切片 + 兼容回退 | 读集等价；定义变化/坏包/重连通过；全流水线稳定改善 |
| 2 | 专用接收存储消除重复反射 | renderer/HUD/预测均覆盖；不是双图同步；P95 不倒退 |
| 3 | 有需要才做接收 Worker | 主线程长任务与 render-submit P95 实测下降，无队列增长 |
| 独立模拟切片 | 原生事务内目标候选索引 | 24/64/100/200 舰及混编全步改善；原排序/RNG/权威结果一致 |

每一块完整实现后集中做一次类型检查、改动文件 lint、相关既有回归和配对性能对照，具体失败才定向复查。不先铺全套新测试工程，不同时迁移网络协议、所有权、Worker 与 AI，避免无法归因。

不接受的“收益”：减少舰船/弹丸、降低 AI 或物理频率、牺牲画质、取消输入确认/坏包校验、把过载掉帧当提速、只报均值或只挑成功轮次。没有通过默认真实链路验收的实现保持实验性，不宣称 200 舰 60Hz 或实际输入到画面改善。

## 后续实验结论：预瞄事务树未采用

2026-09-24 实施了不改频率/目标排序的单舰预瞄粗筛候选。先发现原生 ArmorGrid.cells 访问器使既有 batch 始终回退；以精确身份修正后，索引确实开启，但 100/200 舰模拟平均仍分别退化约 12.26% / 4.19%。资格修正与范围树均撤回，保留先前显示/捕获优化。不能再把“现有事务可直接复用”当成已验证低成本前提；下一步需先量化/重设计全名单资格重校验，且保持未知扩展安全回退。详见 preaim-query-performance-2026-09-24.md。

## 2026-09-24 后续：真实 Worker 验证修正

现已完成生产 local Worker + 嵌套 owner Worker 的真实无头对照，见 `real-worker-performance-2026-09-24.md`。旧原生 4-owner lane 在 100/200 Onslaught 场景实际提交大量预测，但整体输给串行；本轮修复其绕过现有成本保护的问题，收益来自按完整步耗时退出亏损路径，而非 GPU 或增加线程。固定 world wire 候选因尾延迟不佳已撤回。不要继续把本文较早的 Node 串行归因当作真实多核收益证据。
