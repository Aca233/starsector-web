# 预瞄事务粗筛实验：未通过性能门槛（2026-09-24）

## 结论

**否决运行时候选。** 预瞄范围树的保守包含性与当前场景行为检查通过，但模拟平均耗时增加；没有把局部候选减量当作整步加速。

已将本轮修改的 AutofireController.ts、FireControlQueryBatch.ts、ArmorGrid.ts、Ship.ts 恢复为实验前冻结源码，逐文件 SHA-256 完全一致；删除新 PreAimTargetIndex.ts。候选专用测试与导出恢复，实验源码/测试/结果留在本地 artifacts。此前已验收的快照/投影/捕获优化未撤回；显示定义表仍默认关闭。未修改并行生涯开发，未暂存、提交、推送、打包或发布，未操作桌面。

## 前置问题与隔离方式

现有 >=100 舰火控 batch 的资格审计无条件拒绝组件自有访问器，而内置 ArmorGrid.cells 已经是追踪外部引用逃逸的 getter/setter。故正常舰船不能进入 batch。此问题也见 ai-fire-planning-2026-09-22.md，但那次小舰队/降频候选不等于本次 >=100 舰、精确粗筛的实测。

实验中仅通过私有 getter/setter 的精确身份放行原生 cells；不执行任意 getter。公开数组逃逸后 cellMutationRevision 仍为 null，未借资格修正放开护甲内容缓存。分别冻结：

1. baseline-sources.json：本轮开始时的生产源图；
2. guard-sources.json：只修改内置访问器资格识别，启用既有 batch；
3. candidate-sources.json：资格修正 + 单舰发射前事务内的预瞄范围树。

资格修正本身也没有通过性能门槛，因而随候选一起撤回。**当前生产中的资格失配仍然存在，不能将其写成已修复。**

## 全步 CPU 结果

Node v24.13.1，既有 LocalCombatKernel 场景，seed=917，固定 dt=1/60；每个场景预热 40 步、测量 100 步，每步交替 before/after 的执行顺序，冻结源图独立构建。不并发运行测量。双方同一步比较在计时区间外执行。

主测试为同型 Onslaught。单位 ms；“串行总 CPU”包含 kernel.step、捕获及本地显示解码/应用，不包含 Worker 通信、渲染或网络。

| 实验（各自配对基线） | 舰数 | 模拟平均 | 模拟 P95 | 串行总 CPU 平均 |
| --- | ---: | ---: | ---: | ---: |
| 仅资格修正 | 100 | 20.52 → 23.68（+15.43%） | 23.04 → 26.31 | 37.77 → 42.24 |
| 仅资格修正 | 200 | 50.97 → 55.97（+9.80%） | 55.01 → 60.61 | 81.03 → 86.32 |
| 资格修正 + 预瞄树 | 100 | 23.00 → 25.81（+12.26%） | 28.89 → 34.32 | 41.03 → 43.68 |
| 资格修正 + 预瞄树 | 200 | 51.23 → 53.37（+4.19%） | 55.59 → 57.42 | 81.08 → 83.03 |

仅资格修正还测了 24/64 舰，它们按原阈值不启用 batch；不能把波动解释为加速。这是用于淘汰候选的短配对测试，不是长局、浏览器、多线程或实测交互延迟报告，也不宣称统计显著性。100/200 舰平均模拟均退化，已足够不予采用，因此没有为失败方案继续大规模重复测试。

## 确认候选确实启用（独立插桩，不用于计时）

各运行 30 步：

| 场景 | batch 数 | 建树数 | 树查询数 | 树输入候选 → 输出候选 |
| --- | ---: | ---: | ---: | ---: |
| 24 Onslaught | 0 | 0 | 0 | 0 → 0 |
| 100 Onslaught | 3,000 | 2,580 | 17,058 | 460,566 → 4,388 |
| 200 Onslaught | 6,000 | 5,580 | 41,059 | 1,108,593 → 4,367 |
| 100 Harbinger/Paragon | 3,000 | 1,230 | 3,690 | 95,940 → 95,940 |

以上只统计进入树查询的候选，不是全部火控调用或完整战斗成本。混编场景没有剪掉候选，不把构建索引本身称为收益。测试显示候选减少并未抵消资格审计/索引等综合成本；尚未通过细分 profiler 将所有退化归因于某一行。

- 数学测试覆盖 61,440 目标/查询配对，含相对运动、充能、beam、偏移护盾、护盾展开初期、极值与非有限回退；必须保持原名单顺序，不删除旧谓词接纳的目标。

## 下一步边界

不要再直接叠加每舰索引。先验证现有 FireControlQueryRoster.begin 的全名单重校验成本：它在每艘船前重新扫整表，具备二次规模增长。替代方案需要显式受控的读取阶段/变更记录，并证明每舰运动、系统效果、组件替换和外部扩展均能失效；**不得仅凭对象身份跨帧缓存，或直接删掉检查**。若无法低成本证明读集稳定，保持旧路径比强开“快速路径”更好。真实延迟仍需按 inputSeq / authorityTick 的实际通道做独立测量，CPU 数字不能代替输入到显示延迟。
