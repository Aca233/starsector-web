## 为什么不是继续加线程

最初的单独诊断采样（100 艘，60 步预热、90 步记录）测得：舰船移动约 0.195 ms/步；舰船武器/火控约 16.616 ms/步；弹丸/碰撞武器系统约 14.783 ms/步。该采样有探针和 CPU profiler 开销，且冻结版本早于最终配对，不计入上表。它表明仅并行移动难以带来明显整步收益。

本轮保留原有 4 个 AI 所有者 Worker、同步权威引擎以及 LAN 路径，没有声称实现整艘船的完整线程所有权。实际修改：

1. **护盾几何去重。** 原生 getShieldCenter 复用相同朝向的三角函数，仅分配独立的返回向量；不共享可变向量。火控和舰船碰撞复用精确的偏移长度，位置、朝向、护盾中心元数据变化立即失效；保留世界坐标舍入，不以理想旋转长度替代原结果。覆盖方法仍走原始回调。
2. **近炸距离的保守排除。** 距离受限查询先以包围方形证明护盾不可能触及引信；可能接近的舰船仍计算真实部署圆弧与舰体，特殊数值保守回退。没有以整圆/碰撞半径冒充护盾或舰体。
3. **爆炸接触减少分配。** 最近舰体边的循环改用标量计算，保留运算顺序和严格的小于比较，不改变等距边的选择顺序。
4. **Worker 数据校验减少垃圾。** 直接检查原对象节点身份，不为每舰每次检查重建节点元组；重复利用验证数组，移除挂点快照的双层 flatMap。所有节点、标量和输入变化验证仍在，失败仍执行原权威路径。

Worker 等待成本前后约 12.587 / 12.496 ms（包含 Worker 运算，不是纯通信耗时）；接受/回算均为每步 97.3 / 1.7 个结果。没有通过减少 AI 工作或增加回算外的漏算获得收益。

## 测量口径

- 13th Gen Intel(R) Core(TM) i5-13490F，16 个逻辑处理器；同机真实浏览器 SharedArrayBuffer + 4 个 Worker。
- 100 艘默认原生 Onslaught，相同密集阵形，种子 0x51180，固定步长 1/60 秒。
- 真实 CombatSession.fixedUpdateScheduled；计时包含玩家 AI、门禁、打包、分发、等待、验证、提交、回算以及之后的整个同步物理步。
- 每轮 60 步预热 + 180 步计时，两版本逐步轮换；第二轮反转页面准备顺序。按全部 540 步耗时合并，而不是平均百分比。
- 本任务的构建、性能采样和诊断串行执行。配对轮次存在墙钟波动，未用最佳单轮替代合并结果。
- 冻结期间工作区另有护盾过载等功能修改。旧基线首次检测到状态结构不同后，该配对已作废；最终在 rebased 中重新冻结两边，共享所有这些功能修改，仅去掉本任务的八处源码修改作为基线。初筛 v1 和作废 v2 不参与最终汇总。

## 正确性与构建

- 3 轮、66 条完整状态检查点记录全部一致，覆盖每轮第 1/2/3/30/60/90/120/150/180/210/240 步。包含引擎及玩家 AI 的可枚举对象图、引用、Map/Set、TypedArray 和特殊数值。函数用占位符、碰撞 kernelMs 归一化；这不是对隐藏闭包、WeakMap 或 WASM 内存的形式证明。
- 19 项定向交互/故障验证全部通过：护盾/排幅/系统/目标输入，命令、换装、增援、暂停、重开、换战斗、销毁，Worker 报错/超时，引擎损伤，强制系统启动/排幅，护盾修正、辅助系统、回调覆盖。核实等待期间不推进战斗时间、晚到结果不推进新状态、必要时确实回退。
- 真实固定步调度器每版 120 步，最大在途步数 1、最终状态一致，无调度错误。其耗时不并入性能表。
- 160,619 次数值/状态断言：12,000 组护盾中心与距离查询、10,000 组舰体爆炸接触查询、64 个节点身份替换，覆盖 NaN/Infinity/负零、修改位置/朝向/中心、独立返回向量、覆盖回调、退化及可变/冻结舰体。
- 2 艘和 50 艘的独立整步配对状态检查通过，不并入百舰性能表。
- npm run typecheck、npm run lint、npm run build 均通过；生产构建保留现有大块体积警告。
- 生产 Vite preview + 真实 CombatView/RAF/WebGL2 冒烟通过：100 艘、4-workers、实际提交 AI 结果、暂停时钟稳定、无页面错误。软件 WebGL 仅作功能冒烟，不作帧率证据。任务创建的浏览器与 preview 已关闭。
