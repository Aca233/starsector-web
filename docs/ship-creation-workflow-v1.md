# 玩家原创舰船设计流程 v1.1

初版：2026-09-25；更新：2026-09-28  
状态：制作规范；本轮仅更新文档，没有新增工坊功能、生成图片或改动战斗代码。  
适用：Starsector Web 的玩家原创舰船、配套武器及舰船系统。不是原版 Java 模组兼容规范，也不是游戏全局开发路线。

> 目标：让一个想法经过可追溯的设计、美术和试玩，成为有身份、有玩法、有取舍、符合远行星号视觉语言的舰船。不是把一张生成图配上高数值。

配套填写表：[原创舰船设计任务书](ship-creation-brief-template.md)。

> **2026-09-28 更新：** [舰船生产手册 v1.2](ship-creation-production-playbook.md)加入四档同档安装、无占位制作、2D/模型烘焙路线、动态锚点/战损、推进与攻击契约、独立航空和数值校准。执行时同时填写任务书11–20节；P0–P9编号与本文路径保留，旧版占位图建议不再适用。

## 1. 核心原则

1. **先查目标舰原作并实际看图，再讨论还原与改编；先有战术问题，再有机制；先验证机制，再扩展最终资产；无视觉探针或已批准正式资源即可验证，不引入占位。** 不以已经生成的漂亮图片倒逼无意义的玩法。
2. **创新是新的决策关系，不是新名词或更大数值。** 挂点、射界、机动、弹药、舰队分工的重新组合也可以创新，不必每艘船都新增引擎机制。
3. **深度来自情境变化，不来自说明书长度。** 默认只设一个核心设计命题，可有一个服务于它的辅助机制；增加例外必须说明必要性。这是本规范的复杂度预算，不是原版规则。
4. **优势、代价、反制必须同时成立。** 不把代价藏在永远不会遇到的情况里，也不靠自己的技能无条件抹掉自己的弱点。
5. **船体、挂点、武器、系统形成配合，但不锁死装配。** 专属武器可以体现风格，不应让全部可换装挂点失去意义。
6. **技术实现不等于玩法验收，漂亮原图不等于战斗画面合格。** 本地可玩、AI 可用、联机兼容、平衡验证分别标记。
7. **玩家保有作者决定权。** AI 提建议和草案；定位、核心取舍、轮廓和最终成品由玩家确认。不未经确认消耗多轮生图预算。
8. **运行资产禁止占位，四档严格同档换装。** S/M/L/XL、类型、固定/转动、内置/可换分别登记；渲染优先成熟原版能力，不为“专属”制造低质量替代。

### 证据 → 设计要求 → 验证

| 证据 | 采用的设计要求 | 验证方式与限制 |
| --- | --- | --- |
| 原版舰体配置将几何、挂点与图片分开 | 素材交付后必须完成几何与挂点验收 | 覆盖图、真实挂点射击、边缘碰撞检查 |

## 3. 流程与关卡

| 阶段 | 要回答的问题 | 必须交付 | 通过条件／失败返回 |
| --- | --- | --- | --- |
| P0 委托与查图 | 这是哪部作品、哪一版舰船，实际长什么样？玩家想扮演什么角色？ | 一页任务书、带来源的参考图片与外观核对记录 | 通过下述 P0-R 查图关卡；角色、范围明确，再进入玩法设计 |
| P1 定位与创新 | 它为什么值得存在？ | 参照舰对比、核心命题、决策矩阵 | 行为差异成立；只有换皮或数值全面提升则重做 |
| P2 机制与可行性 | 规则能否解释并实现？ | 规则卡、状态表、能力缺口清单 | 每项为已有／需新增／未知；不承诺未实现能力 |
| P3 纸面配装与预算 | 四档、绑定与射界怎样形成取舍？ | 安装/模块档案、初始规格、两套配装 | S/M/L/XL同档换装，内置与可换分别核对；无明显全能解 |
| P4 无占位规则验证 | 实际决策能否成立？ | 无视觉生产逻辑探针，或使用已批准正式资源的试玩记录 | 核心交互与基础AI有证据；未验证视觉不得冒充试玩完成 |
| P5 轮廓与制作路线 | 它看起来为何是这种船，如何制作？ | 多图参考板、同一母版、2D/模型烘焙选择 | 轮廓可辨、结构可信，原图/运行图/世界尺度分开 |
| P6 素材与反馈生产 | 哪些生图，哪些烘焙，哪些复用原版？ | 分层运行图、逐型航空、视觉契约、像素标定与来源 | 关特效也贴合；透明/实际尺寸正确；无静态假火焰或假装备 |
| P7 配置与接入 | 画面、碰撞和规则是否一致？ | 规格、几何、挂点、资源与行为引用 | 真实引擎接入及资源校验通过，不拿空壳演示替代 |
| P8 玩法与技术验收 | 谁会玩、如何赢、如何被克制？ | 人类／AI／技术／可选联机的分项报告 | 阻断项清零，主观体验有实际记录，不以总分掩盖硬伤 |
| P9 个人交付与分享 | 能否可靠保留和再创作？ | 舰船包、设计卡、版本及许可 | 独立导入使用验证；公开发布另由作者确认 |

概念验证可以只走到 P4；完成最终个人舰船至少走到 P8 并保存版本；社区公开分享需要 P9。任一阶段可以退回上游，不用沉没美术成本强行保留坏机制。

## 4. P0–P1：先查原作与图片，再定义体验和创新

### P0-R：原作外观与图像核对（强制前置）

这一步查的是**目标舰船的原作**，不能用“已看过远行星号素材”替代。先确认作品、舰名/别名、所属角色及拟采用版本，再检索并实际查看图片；不能凭记忆直接给结构或生图提示词。

1. **来源分级**：优先官方设定/概念图、原作游戏模型与实机截图、官方过场。Wiki/攻略转载注明页面和可追溯的原来源；同人重绘、模型复原和 AI 图单列，不能冒充官方定稿。早期官方概念也不自动优先于选定版本的成品模型。
2. **看图而非只看标题**：优先收集整舰全貌、顶部或近俯视、侧面/尾部及关键细节，按结构证据需要收集多张参考，不限定只能使用一张，也不设固定张数上限；不为凑数量重复同一视角。一张小图或几张同角度图片不能证明完整结构；三分之四透视不是正交俯视。
3. **记录可见特征**：轮廓与长宽关系、舰艏/舰桥、左右结构、主炮/炮位区域、机库开口、引擎喷口和配色。分开标注“图中可见”“文字来源支持”“推测/未知”。数值尺寸、喷口总数、挂点数量及不可见背面不得由模糊图猜定。
4. **把图片展示给玩家**：提供图片预览、来源页、作品/模式/版本、采用理由和未知项，不只交链接列表。无法访问或无法实际看图的来源只记为候选，不记为已核实。记录用户认可的参考组及每张图的用途，不要求只选一张基准图。
5. **多图分工与交叉核对**：建立“设计部位 → 参考图号 → 可采用信息 → 冲突/未知”的对照表。整舰图定轮廓，近俯视图核对平面布局，侧后图核对厚度与引擎，局部图看炮位/机库，材质图定表面表现。多张图可共同约束同一艘船；所谓基准是版本与结构一致，不是只允许一张图。无需选出一张什么都包办的“万能参考图”。
6. **冻结还原边界**：列出必须保留的识别特征、允许转译为远行星号俯视精灵的部分和待补证据。不同作品、舰级、普通战巡、特定旗舰、战役/合作/对战形象不悄悄拼接；混合方案必须注明为改编并取得作者认可。

**通过条件**：身份/版本已确认；实际查看并向玩家展示了足以判断主要结构的参考；参考组及采用方向获认可；来源、版本冲突与未知项有记录。未通过时可以补资料或记录临时玩法想法，**不得冻结结构/挂点、开始最终生图或声称已还原**。有限视角仍无法证明的局部须明确作为作者批准的改编，不能伪装成原作细节。

完全原创舰也要先查设计参照与远行星号风格图片，但不编造不存在的“原作设定”。参考图可研究不等于有权随包分发；来源和许可未知须保留为未知。

查原图前置不等于最终美术前置：**P0 查图 → P1–P3 玩法/结构草案 → P4 无占位规则验证 → P5 锁定美术 → P6 生产素材**。

### 一句话定位

使用句式：

> 这是一艘在【场景】中，通过【玩家主动行为】取得【战术优势】，但必须承担【可被利用的代价】的【舰级／角色】。

“不一样”“高科技”“很强”“需要操作”都不能单独充当定位。另写出玩家不使用专属系统时，船本身仍能完成的基础职责。

### 参照选择

选 2–3 艘参考舰：优先匹配部署费用区间与角色，再对照不同打法的反例。记录来源、版本、定位、挂点组织、机动／防御取舍；不要仅因舰级相同就视为同等战力。

填写“我保留什么、改变什么、放弃什么”。如果优势清单是更快、更硬、更远、火力更大而没有相应代价，暂停设计；抬高 DP 不是消除支配性设计的万能解。

### 创新命题

从以下关系中选一个主要方向，不要求全部使用：

- **位置：** 舷侧、射界、阵地、接近和撤离路线。
- **时间：** 弹速、蓄力、弹药窗口、攻击到达次序。
- **资源：** 幅能压力、有限弹药、恢复窗口、持续输出与爆发。
- **信息与承诺：** 提前暴露攻击意图换取收益，敌方可以改变计划应对。
- **舰队关系：** 谁保护谁、谁维持压力、谁抓住窗口；不把单挑胜率当唯一价值。

每条命题必须写出：新行为、收益来源、机会成本、对手反制、界面反馈。如果只能写“造成更多伤害”，继续设计。

### 决策矩阵

至少覆盖接敌、持续交战和不利局面，写出选择 A/B 和切换依据。阈值不是越多越好，选择要能由玩家读到的信息支持。

例：面对慢速重舰可部署侧翼火力；面对绕后的高速舰，应回收并保持机动。若任何情境都是“技能亮了就按、然后持续开火”，机制的情境价值尚未得到证明。

检查三个层次：
1. **入门可用：** 不记特殊连招也能履行基本角色。
2. **熟练有收益：** 时机、距离、朝向或资源判断可改善结果。
3. **对手有应对：** 通过可观察的状态能采取反制，不依赖猜隐藏计数。

## 5. P2：把机制写成能执行的规则

每个新武器／系统填写规则卡：触发条件 → 状态转换 → 结算时点 → 影响对象 → 资源账本 → 中断／退出 → 可见反馈 → AI 原则。

- 明确蓄力、活动、退出、冷却，或说明为何使用另一种状态机。不是所有机制都强塞进同一套阶段。
- 资源写明生成、支付、持有、退还和销毁，防止复制弹药、免费清除硬幅能、重复计伤或无限叠加。
- 明确哪些信息激活时锁定，哪些持续读取：落点、目标、朝向、武器规格、伤害倍率等。
- 列出过载、排散、停机、目标死亡、母舰死亡、超距、撤退、重开、暂停与恢复的行为。
- 相位、光束、导弹、战机、模块等兼容性必须逐项声明；首版可以不支持，但不能静默变成另一种效果。
- AI 使用同一套规则和可用信息，不获得瞬时转向、免费资源或隐藏目标权限。

### 技术分级

- **T0 数据组合：** 使用现有规格、武器、系统与合法配置；不写新行为。
- **T1 扩展行为：** 使用现有扩展点实现新逻辑，还需验证权威状态、显示投影、AI 与必要的序列化。
- **T2 引擎能力：** 新实体种类、物理交互、渲染或网络状态需要底层支持；单列研发验证，不让生图掩盖风险。

“能写回调”不代表 Worker 或联机自动可用。当前 `effectState` 的 WeakMap 属于实例本地状态工具，不自动成为可持久化／可同步协议。纯数值显示读取的准入也不应因注册成功就放开；对实时幅能敏感的结果不可仅按系统阶段缓存。

## 6. P3–P4：先证明配装和玩法成立

### 预算分开算

- **舰体预算：** DP 与同档角色对比；结构、装甲、护盾、机动、射界和持续作战能力共同占预算。DP 不是 OP 的换算结果。
- **配装预算：** OP 由武器、舰装、耗散通道和电容竞争；挂点类型与位置本身也是限制。
- **运行预算：** 武器幅能、护盾维持、系统消耗、硬幅能积累、弹药及有效作战时间。

可用 `容量余量 / 净幅能增长率` 粗估无受击时的开火窗口，但只适用于对应固定工况；明确护盾、系统、射击占空比和耗散假设。软／硬幅能、受击和阶段变化必须在模拟中分别核实，不能把这个估算当真实生存时间。

### 两套配装的要求

至少两套有效配装，改变交战距离、交战节奏、资源分配或舰队职责之一；不是同一方案换一门更贵的炮。

- 各有优先选择的场景与不利场景，不能 A 在全部场景都更好。
- 至少检验一套不依赖专属可换装武器的配装；若核心使用内置不可替换机构，应说明原因，并保留其他部分的取舍。
- 默认配装必须解释武器组、自动开火、散热和电容配置。OP 可以合理留余量，不强求填满；不能把大量闲置 OP 和全零散热电容当无说明的交付默认。
- 不人为要求武器幅能永远低于耗散；爆发型配置允许超出，但必须有实际能利用的输出窗口及恢复计划。

### 无占位规则验证

先用生产引擎的无视觉逻辑探针验证规则；需要可视试玩时使用已获批准、确实适用于本舰的正式资产。不得用几何船壳、借来的不相符机体、假武器或假特效冒充本舰。没有合格美术就明确该项未验证；可以先生产所需正式资产，但不跳过玩法验证。测试接敌、使用核心机制、受压、脱离和重新入场，保留既有操作习惯。

每轮先提出一个假设，例如“较早回收平台能在高速敌人绕后时保住火力”。记录观察结果和反例，优先改决策结构或反馈，不靠持续加伤害掩盖没有玩法的问题。

进入美术前，至少证明：基础循环可玩、一个有意义的情境选择出现、敌方有可执行反制、默认配置可用、技术路线没有未解决的核心阻断。不得把计划测试写成已经通过。

## 7. P5：远行星号视觉语言

### 不变项

- **正交俯视战术精灵。** 没有三分之四视角、透视缩短、镜头景深、地面投影或海报构图。
- **大轮廓先于细节。** 舰艏、主体、引擎和主要武器区有清楚层级；不能靠颜色或名字才能认出船。
- **结构可信。** 装甲板包覆结构，炮座有承载区域，发动机有合理喷口和排气空间。允许科幻，但结构要自洽。
- **细节服从实际显示大小。** 保留厚薄、面板、凹槽与机械暗部；避免全表面同等密度的刻线、金边和小灯。
- **材质对比克制。** 发光用于解释状态和技术节点，而不是每块装甲都发光。旧化和维修痕迹可用，但不是所有派系都必须锈蚀。
- **保持动态层独立。** 默认不把护盾、尾焰、弹道、巨大光晕和可旋转炮塔烘焙进舰体图。

### 技术路线是参考语法，不是僵硬配色规定

| 路线 | 可参考的形体／表面组织 | 避免的误用 |
| --- | --- | --- |
| 低科 | 厚重分块、机械凹槽、装甲与火炮的承载感 | 全舰棕色即低科；不顾角色无限堆管线 |
| 中线 | 清楚的功能分区、成组武器区、装甲与机械层的平衡 | 每艘都做成无区别的对称细长箭头 |
| 高科 | 更连贯的曲面或包覆结构、嵌入式节点、局部冷色亮点 | 通体霓虹、镜面塑料、白金装饰越多越高级 |
| 原创派系 | 指定一种主结构语法及有理由的偏离，统一舰队视觉家族 | 无约束混合宗教饰品、现代战机、写实影视和像素装甲 |

### 轮廓关卡

先出少量轮廓候选，比较远距辨识、正面／舷侧火力表达、结构与挂点草图的适配。选择后锁定大比例、主要缺口、引擎组和武器区；细化不得悄悄改变这些内容。

与参考舰按相近游戏显示尺寸并排检查；另看缩小预览和灰度阅读。灰度只是检查层级的辅助手段，不作为战斗最终配色。实战必须再看己方／敌方特效叠加后的辨识度，不能凭无背景原图通过全部视觉验收。

## 8. P6：生图与素材生产规范

### 生图前冻结的信息

主角色、核心机制、技术路线、轮廓、挂点区域、引擎布局、预期显示尺寸、必需分层、禁止烘焙的动态部件。AI 可以提局部改进，但需作者确认才能改变已锁定结构。

### 生产顺序

选择2D绘制或可信模型正交烘焙 → 整舰母版 → 必要模块/承座/炮头与前景 → 每型航空 → 技能图标/必要动态材质 → 几何/状态标定。模型、成图和生图均可混用，但保持同一材质与光照体系；原版尾焰、光束等已有合格能力优先复用，不为已有合格武器重复造图。细则以生产手册5.5–5.8为准。

### 可复用舰体提示词骨架

```text
用途：可用于 2D 太空战术游戏的独立舰体精灵，而非宣传海报。
视角：严格正交俯视，舰艏朝上，完整舰体，四周保留安全边距。
结构：遵守提供的轮廓与挂点区域草图；{主结构、引擎组、功能分区}。
画面语言：参考所附远行星号舰体的装甲分层、机械暗部、克制材质、硬边细节和实际缩放可读性；不要复制参考舰轮廓。
原创特征：{一个主要轮廓特征}，{一个服务玩法的结构特征}。
材质配色：{主色、辅色、少量状态亮点}，细节密度与参考显示尺度一致。
资源拆分：舰体只保留炮座／接口；可旋转炮塔、护盾、尾焰与技能效果另作。
输出：具有真实 alpha 的透明背景舰体图；无法输出真透明时明确说明，另行处理，不绘制棋盘格。
避免：透视、星空、文字、水印、展板、多视角、落地阴影、过曝辉光、通体微小刻线、改变已锁定挂点空间。
```

提示词不是质量保证。保留输入参考和生成版本；局部问题优先局部重绘，整船重画不得偷偷替换已确认几何。玩家可跳过生图直接上传手绘图，后续验收相同。素材来源、模型或许可未知时写未知，不编造来源。

### 文件质量关卡

- 真正的 RGBA 透明；不能把白底、黑底或棋盘格当透明。检查浅色与深色背景下的边缘残色。
- 不裁掉舰艏、喷口或独立模块；透明边距和中心不会随重绘无说明变化。
- 分辨率根据目标显示尺寸和缩放确定；保留高分辨率母版，实际运行贴图单独导出，不能用固定 1024 尺寸代替尺度设计。
- 独立炮塔记录旋转中心、朝向与枪口偏移，不默认图片中心就是轴心。
- 图标按游戏实际尺寸检查，不靠写在图上的小字表达技能。
- 任何缩放、去底或锐化完成后重新检查实际尺寸；生产图、运行图、截图各有用途，不相互冒充。

## 9. P7：工程接入与几何一致性

1. 保留原始素材；记录导出缩放和透明边距，不覆盖唯一源图。
2. 明确图像像素、运行贴图和世界单位的转换。对舰艏朝上的原创素材，可用 `forward=(pivotY-pixelY)*worldHeight/imageHeight`、`right=(pixelX-pivotX)*worldWidth/imageWidth` 作显式变换；pivot和pixel必须来自同一像素空间，裁剪/缩放先转换一致；不应以此掩盖错误的非等比变形。这不是所有原版导入器的通用公式，禁止再次套原版镜像转换。
3. 校准舰体中心、护盾中心、引擎方向、炮塔轴心和枪口。贴图空白区域不应凭空承载炮座。
4. 碰撞轮廓表示实体区域，不含尾焰与光晕。双叉缺口使用引擎确实支持的凹轮廓；封闭孔洞不能假装由单个简单多边形自动支持。能力不足时改表示方式或列为待实现。
5. 广相检测半径与精确轮廓分开检查；半径不能小到漏碰撞，也不能把外接圆当作精确舰体。
6. 通过标准规格、资源和行为入口注册。保持原创 ID 和稳定 `sourceHullId`；不要覆盖原版 ID 来省接入工作。
7. 生效条件优先基于声明能力或适配规则；确实专属的机制可显式限制，但不在通用战斗、HUD、输入或 AI 中堆内容 ID 特判。
8. 操作复用既有射击、武器组、系统、目标选择命令。确需新增操作先做可用性说明与确认，不暗改原版习惯。
9. 动态状态在权威侧结算，显示层只读取／插值。动画看起来触发不算伤害、消耗或回收真实生效。
10. 动态环/部件的挂点、火控、出射、遮挡与受损层共享当前姿态；接口不支持动态物理锚点时明确阻断，不只移动图像。
11. 每种舰载机独立检查轮廓、炮口/喷口和武器攻击契约。不同职责不默认共用同一张图和母舰特效；同型改装必须明确且有可辨差异。
12. 不强制所有船外喷尾焰；普通喷口、场推进和原生发光分别定义。所有效果验证怠速/激活/退出/禁用/损毁与暂停，不拿静态贴片冒充动画。

当前 `installContentPack` 要求资源先属于本地资源清单；`ModPackage` 当前主要承载舰船、武器与翻译，行为由可信应用代码注册。因此“用户任意拖入一个 zip，任意新技能立刻可用”是未来工坊能力，不是现有事实。

## 10. P8：验收与返工规则

### 集中验收，不无休止跑全套

一轮完整改动后集中检查，失败只复查对应问题。复用已有模拟和验证入口；没有明确要求时不重建测试工程，也不做重复全资源审计。无头测试不占用玩家桌面；实机操作由玩家自己进行或另行取得许可。

### 最小场景矩阵

| 场景 | 看什么 | 不能据此宣称 |
| --- | --- | --- |
| 无敌固定靶／功能靶 | 挂点、枪口、资源账本、弹道与状态恢复 | 已平衡或很好玩 |
| 同档常规敌舰 | 正常接敌、基本输出、脱离与恢复 | 克制所有角色 |
| 快速绕侧敌人 | 射界、转向、位置机制和弱点是否真实 | 低胜率就一定坏设计 |
| 高盾／高甲的不同对手 | 武器选择和两套配装是否有差异 | 单一伤害类型应通吃 |
| 多目标／舰队场景 | 威胁切换、护航价值、协同及 AI | 单挑数值等于舰队价值 |
| 反制场景 | 对手能否读懂并执行反制 | 必须让对手稳赢 |
| 退出重进与导入 | 配装、身份、状态隔离、资源完整 | 已有完整存档迁移 |
| Worker／多人（若承诺支持） | 权威资源、状态投影、事件顺序和实体生命周期 | 本地通过等于联机通过 |

对比固定场景与配置，再改变对手和局面；复现用的种子、引擎／内容版本要记录。不要只保留赢的录像；不得用同一套测试过度调参后宣称泛化已证实。

### 体验访谈

问试玩者：你什么时候改变了计划？为什么？什么时候不该按技能？怎么保护或暴露了自己的弱点？第二套配装让你做了什么不同的事？敌人怎么才能反制你？

若反馈只有“伤害大、特效亮”，没有能描述的决策，返回 P1/P4；若有决策但读不懂时机，先修反馈与规则说明；若某套装配始终无理由存在，返回 P3。

### 质量评审（项目内部标尺，不是原版规定）

各项 0=缺失／失败，1=有想法未成立，2=明确可用且有证据，3=多个局面验证良好。正式个人交付以每项至少 2 为目标，不求总分，不用美术分抵消玩法或技术失败。

- **创新：** 相对参照船是否改变行为或取舍，而非只改数值与皮肤。
- **可玩：** 正常战斗循环成立，默认装配无需修补才能使用。
- **深度：** 情境决策、配装差异和可执行反制有实际证据。
- **风格：** 正交结构、材质层次、原版参照和实战缩放相容。
- **可读：** 玩家和对手看得懂状态、代价与危险窗口。
- **工程：** 资源、几何、生命周期、AI 及宣称支持的运行模式可用。

性能退化、崩溃、状态不同步、破坏旧配装、明显无限资源漏洞均是硬阻断。实验内容可分享设计讨论，但必须标为实验，不能以评分替代安全和正确性检查。

## 11. P9：交付给玩家与社区

### 每艘船的交付物

1. **设计任务书：** 定位、参照、核心命题、决策／反制、已知限制。
2. **素材：** 可编辑母版或原始图、运行图片、来源及作者选择的使用／再创作许可。
3. **配置：** 舰体、挂点、碰撞、引擎、武器、系统与资源引用；行为依赖明确。
4. **默认与分支配装：** 至少两套，注明适合和不适合的场景。
5. **验证记录：** 本地、AI、Worker、联机、风格与实际试玩分别为通过／失败／未验证。
6. **版本说明：** 稳定内容 ID、版本、依赖、破坏性变更及旧版本处理办法。
7. **简短玩家说明：** 怎样开始、何时用系统、何时撤退、敌人如何反制。

发布页面分开显示“个人实验／机制已验证／多人已验证”和“平衡评价”；不把作者自称平衡当官方认证。缺依赖明确阻止加载并提示，不能静默替换默认船。旧版本先保留再迁移，禁止更新时无提示覆盖玩家命名或装配。

数据包不包含可自动执行的任意 JS。新行为代码需要受信任的安装与审核路径；联机房间明确内容版本和能力一致性，不能偷偷下载并运行其他玩家脚本。

原版素材可作本地研究参照，不因“本机可读”就推定可重新分发。玩家上传素材同样记录来源和授权范围；原创再创作必须遵循作者实际选择的许可。

## 12. 实际执行时的最小工作节奏

- **第一轮：** 任务书＋参照＋玩法规则＋两套纸面配装，确认“为什么值得做”。
- **第二轮：** 无占位验证核心交互；只有逻辑证据时明确视觉尚未验收，确认“真的有选择”。
- **第三轮：** 轮廓确认，选择生图/手绘/模型烘焙与原版材质；统一安装、航空、特效和动态几何，确认“关特效也贴合，开特效也对位”。
- **第四轮：** 集中技术与玩法验收、定向返工、作者确认个人交付。
- **第五轮（可选）：** 依赖／版本／许可整理，独立导入验证后申请社区分享。

最终判断不是“生成了多少素材、写了多少代码”，而是：**玩家能认出它、理解它、用不同方式驾驭它，对手也能与它博弈。**
