# 桌面客户端原生 Rust 战斗引擎集成方案（Web UI 保留 + 战斗核心纯原生）

**策划日期**：2026-10-09  
**策划状态**：待用户审阅确认（方案草案）  
**遵循约定**：AGENTS.md《先策划，后实现》与《原版先行》准则

---

## 一、 目标与玩家体验

### 1. 核心目标
将现有的战斗物理与规则模拟从**32 位 WebAssembly 浏览器沙盒**与**沉重的 TypeScript 序列化胶水层**中彻底解放，下沉为运行于 x86_64 宿主平台的**本地原生机器码动态库（Native Dynamic Library / Node-API Addon）**。
* **突破计算瓶颈**：使战斗模拟摆脱单线程 Wasm 沙盒与 4GB 内存限制，全面利用桌面 CPU 的原生 AVX2 向量硬件加速与多核心并行（Rayon 并行物理求交与 AI 评估）；
* **消灭跨界数据税（Zero-Copy Direct GPU Pipeline）**：彻底废弃“每帧把 Wasm 内存解构为成千上万个 JavaScript 临时对象并执行图对比”的低效流程，建立基于共享内存（Direct Shared Buffers）的直通渲染管线；
* **消除掉帧与卡顿**：杜绝战斗中因垃圾对象激增引发的 V8 垃圾回收（GC）长达数百毫秒的掉帧停顿，将高负载（22+ 艘主力战舰/数百架舰载机/数千发弹幕）下的单帧模拟耗时从当前的 **~160ms 压缩至 1~3ms**，实现 60~144Hz 的原生级极致流畅度。

### 2. 玩家体验
* **体验无缝继承**：100% 完整保留现有的所有 Web 富交互界面——包括高度还原原版 0.98a 的战舰改装台（`NativeRefit`）、技能树、情报面板、货舱清单、战术地图与 HUD 交互，玩家的视觉体验、操作习惯和交互流程完全不变；
* **感知纯粹升级**：玩家不会看到任何粗糙的自制新 UI，唯一的感知差异是大规模舰队交火时由原先的严重卡顿变为丝滑流畅；
* **桌面生态保持**：现有 Electron 桌面端（`desktop/main.mjs`）的 Steam 叠加层（Steam Overlay）、离线单机、本地局域网（LAN）联机和自动更新机制保持原生支持。

## 二、 本次范围与明确不做的内容

### 1. 本次开发范围
1. **原生动态库构建链建设**：
   * 在现有 `native/combat-core` 基础上，支持编译为原生 Windows 机器码目标（`x86_64-pc-windows-msvc`）；
   * 通过 Node-API（napi-rs 或轻量 C ABI）导出原生接口，供桌面端（`desktop/`）主进程或后台 Worker 直接加载调用。
2. **直通渲染数据通道（Zero-Copy Direct GPU Upload）**：
   * 废除 `RustCombatCore.ts` 中每帧对全量快照解包为 JS 对象的 `snapshot()` 逻辑；
   * 废除 `CombatPresentationEncoder.ts` 的全图对象遍历与增量比对；
   * Rust 原生侧直接按 WebGL 图元类型（战舰 Sprites、尾迹 Ribbon、护盾 Mesh、弹丸/光束 Instances）填充预分配的紧凑二进制缓冲区；
   * 前端渲染器直接从共享内存（TypedArray）读取缓冲并送入 WebGL 显存，实现真正的零反序列化。
3. **Rust 内部高并发与事务优化**：
   * 引入 **Rayon**：在原生多线程环境下对小行星碰撞、弹丸-舰体几何分箱、战术 AI 评估进行多核并发调度；
   * 消除 `state.rs:step_scene` 每帧对整个世界状态的深拷贝（Clone），改造为写时复制（CoW）或高效双缓冲机制。
4. **桌面原生加载接线**：
   * 在桌面客户端加载流中加入原生 Native 动态库优先检测；在原生库可用时启用原生超高速通道，同时保留 Web 端的纯 TS / Wasm 双后端降级兼容性。

### 2. 明确不做的内容（防止范围蔓延）
1. **不使用 Rust 原生 GUI 库重写界面**：
   * 明确不使用 `egui`、`iced`、`slint` 等 Rust 原生 GUI 重写改装台、技能树和菜单；已有的数十个精细 React 界面继续由桌面 WebView 呈现；
2. **不改变原版战斗数值与规则算法**：
   * 战舰数据、通量生成/耗散、护盾阻断、装甲网格计算、AI 行为权重严格对齐原版 0.98a 规则；
3. **不触碰生涯模式（Campaign）与存档结构**：
   * 生涯模式未完成内容保持现状，不修改存档 schema，不打包发布生涯改动；
4. **不放弃已有的 Web/跨平台可用性**：
   * 保持现有浏览器端 Wasm/TS 后端降级退路，确保普通 Web 访问不受原生桌面改造影响；
5. **不操作用户可见桌面与键鼠**：
   * 所有构建与自动化基准测试均在后台与无头（Headless）环境下进行。

## 三、 原版依据与当前差异

### 1. 原版依据
* **执行平台**：原版 Starsector（0.98a-RC8）为原生桌面游戏（运行于 JVM，基于 LWJGL/OpenGL 绑定），所有物理、AI、渲染均在同进程内高效进行，单帧预算严格锁定为 60 FPS（`settings.json:9 "fps":60`）；
* **无跨进程序列化**：原版各个实体（CombatEntity、Ship、Weapon）直接持有着状态与内存，无需跨越语言或进程边界进行 JSON/Array 序列化；
* **批处理渲染**：原版渲染系统基于 OpenGL 立即模式与精简的 SpriteBatch 缓冲，直接向显卡流式传输变换矩阵与顶点坐标。

### 2. 当前实现与差异
* **当前现状**：
  * Rust 核心被塞在 32 位 Wasm 沙盒中运行；
  * 每步推进后，Rust 把状态写平为 Float64 数组，TS 必须重新解包出数万个临时 JS 对象；
  * 编码器因对象引用失效而误判全场变化，导致呈现包膨胀到 1.27MB，Encode 暴增至 53ms，伴随剧烈 GC 停顿；
* **改造后预期**：
  * 架构向原版桌面端对齐：Rust 编译为原生机器码，同进程原生直接操作内存；
  * 渲染数据零拷贝直送显存，消灭全部中间胶水层。

## 四、 核心架构设计与数据流转

### 1. 架构拓扑
```
┌────────────────────────────────────────────────────────┐
│                   桌面客户端 (Desktop Shell)              │
├──────────────────────────┬─────────────────────────────┤
│   表现层 (Web View)       │   战斗核心 (Native Process)   │
│                          │                             │
│  React 19 / TypeScript   │   Rust (x86_64 原生编译)     │
│  • 战舰改装台 (Refit)      │   • 多核并行物理 (Rayon)      │
│  • 战术地图 / HUD 面板     │   • 战术 AI / 火控预测        │
│  • 技能树 / 装备目录      │   • 装甲网格 / 通量 / 护盾    │
│  • WebGL 批处理渲染器     │   • 粒子与弹药模拟            │
│            ▲             │              │              │
│            │ (读取渲染)   │              │ (直接填充)    │
│            └───────── Direct Buffer ────┘              │
│                 (共享连续内存 / TypedArray)              │
└────────────────────────────────────────────────────────┘
```

### 2. 交互与控制流
1. **轻量输入上报**：
   * 玩家在 Web 界面中产生的键盘/鼠标控制（`sample`）被压缩成数十字节的定长二进制控制结构体，直接写入原生共享输入槽位；
2. **原生并发模拟**：
   * 原生 Rust 内核在后台工作线程以固定 60Hz 执行；
   * 使用 Rayon 将上百艘战舰的多边形碰撞检测与 AI 决策分派给所有可用物理 CPU 核心；
3. **渲染数据直写（Zero-Copy Direct Fill）**：
   * Rust 物理步完成后，直接在预分配的平铺内存中填充本帧需要绘制的图元：
     * `ShipSprites`: `[x, y, rotation, sprite_id, scale_x, scale_y, alpha, color_tint...]`
     * `Beams & Ribbons`: `[p0_x, p0_y, p1_x, p1_y, width, color...]`
     * `ShieldMeshes`: `[center_x, center_y, radius, arc_start, arc_end...]`
4. **显卡直接上传**：
   * 前端渲染循环直接通过指针包装的 `Float32Array` 调用 `gl.bufferSubData(...)` 上传显卡并触发 Instanced Draw Call；
   * 彻底绕过所有 JS 堆对象创建。

## 五、 分阶段交付与实施计划

### 阶段 1 (P0)：本地原生动态库构建链与跨语言基础绑定
* **任务**：
  1. 为 `native/combat-core` 配置 Windows 原生编译通道（`x86_64-pc-windows-msvc`）；
  2. 实现轻量 Node-API / C-ABI 包装层，导出与原先 Wasm 兼容的核心生命周期接口（`create`、`step`、`apply`、`destroy`）；
  3. 编写无头原生测试验证：在 Node 环境下直接加载 `.node` / `.dll`，验证 22 艘战舰与原版 Wasm/TS 算力与见证严格一致（Witness 等价性）。

### 阶段 2 (P1)：直通渲染缓冲区（Zero-Copy Render Pipeline）实现
* **任务**：
  1. 在 Rust 内核中增加紧凑渲染图元格式（`NativeRenderBatch`）的直填接口；
  2. 重构前端渲染器：接入直接从二进制缓冲提取几何信息并提交 WebGL 的专用 Pass；
  3. 彻底移除此链路上的 `CombatPresentationEncoder` 和万行对象解析逻辑；
  4. 集中测试：验证高负载下内存不再产生波动，帧耗时显著下降。

### 阶段 3 (P2)：Rust 内部高并发与事务深拷贝消除
* **任务**：
  1. 引入 `rayon` 依赖，将密集计算模块（弹丸碰撞求交、小行星碰撞、AI 分析）并行化；
  2. 优化 `state.rs:step_scene`，消除每次步进时对 `world` / `roster` 的全量 Clone，替换为写时复制（CoW）；
  3. 执行无头基准测试：测量纯模拟耗时（Simulation Time）是否压缩至 3ms 以内。

### 阶段 4 (P3)：桌面宿主深度集成与双重验收
* **任务**：
  1. 在 `desktop/main.mjs` 中接入原生加载器，自动识别并优先启动原生 Rust 内核；
  2. 集中执行严格 ABBA 基准测试，记录完整模拟、渲染上传与端到端往返耗时；
  3. 验证战舰改装台、装备切换、战术地图与暂停界面的无缝交互。

## 六、 验收标准

1. **逻辑正确性与原版一致性**：
   * 原生 Rust 模拟的战斗结算结果（胜负判定、舰船损伤、弹药消耗）与当前已通过验收的 Wasm/TS 核心在容许几何误差内 100% 一致；
   * 保证回放见证（Replay Witness）与 RNG 种子序列严格匹配。
2. **性能与内存门禁**：
   * **模拟耗时（Simulation Time）**：22 艘主力战舰同屏混战下，原生 Rust 模拟均值从当前的 **88ms 降至 5ms 以下**；
   * **端到端往返（Roundtrip）**：从当前的 **~160ms 降至 8ms 以下**；
   * **GC 表现**：战斗持续运行 1000 帧以上，V8 堆内存波动平稳，杜绝 10ms 以上的 GC 掉帧停顿；
   * **包体膨胀**：生成的原生动态库体积控制在 10MB 以内。
3. **UI 与系统稳定性**：
   * 改装台（Refit）、战术控制、武器分组、自动驾驶逻辑无任何功能性回退；
   * 不改变生涯模式既有状态，不产生非授权的本地文件改动。

## 七、 待核实事项与建议确认

1. **原生桥接方式选择**：
   * **推荐方案**：采用 **Node-API (`napi-rs`)**。它能够直接把 Rust 编译为 Node 原生扩展（`.node`），完美融入现有的 Electron 桌面主进程与多线程 Worker，且支持直接操作底层 `ArrayBuffer` 内存；
   * 备选方案：纯 C-ABI 动态链接库（`.dll` + `ffi-napi`），稍显繁琐。
2. **退路机制确认**：
   * 桌面端默认优先加载本地原生 Rust 动态库；若在纯网页端（浏览器访问）运行，系统平滑自动退回已有的 Wasm/TS 引擎，确保“一套代码，既能网页访问，又能桌面极限性能”。
