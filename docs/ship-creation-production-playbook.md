# 舰船生产手册 v1.2 — 从设计到可玩交付

更新：2026-09-28。综合荣光女王、四档舰炮安装规范及亚顿之矛 v06–v20 的制作复盘；这是后续每艘船的生产约定，不表示已实现一键工坊、完整安装器或最终平衡。

配套：[设计流程 v1.1](ship-creation-workflow-v1.md) · [每舰任务书](ship-creation-brief-template.md) · [内容扩展契约](content-extension-contract.md)。本手册补充生产细节，沿用原有 P0–P9 阶段，不另建一套互相冲突的标准。v1.2取代旧版占位/三档制作表；[四档武器规范](weapon-art-four-tier-workflow.md)的安装字段继续有效。

执行仍遵守项目协作约定：不启用子代理，不占用桌面/可见浏览器，不停止用户服务，不覆盖已有改动或配装；原版实机操作须另获许可。本轮只是文档维护，不触发生图、整舰重测或发布。

> **先查原作、实际看图；再做值得玩的船，再做适合游戏的图；图、数据、行为、显示分别交付，最后放在真实战斗里验收。**

> **最小交付单位（2026-09-26澄清）：单舰自包含包。** 一包包含一艘整舰及其必需武器、模块、系统、舰装、航空、资源和配装；兼容宿主只安装此包即可完整使用，不手改源码、不依赖先装另一艘船。见[单舰自包含包规范](ship-pack-development-plan.md)。当前完整安装/升级链路尚未实现；多舰合集是可选的上层组合，不是本规范的前提。

## 1. 第二艘船从哪里开始

先复制任务书，完成其 **0A 原作与参考图片**。先认清是哪艘、哪一版，再实际查看和展示来源图片，记录轮廓、舰艏/舰桥、炮位区域、机库、喷口、配色及未知项。不要凭舰名印象开写生图提示词。

按[设计流程 P0-R](ship-creation-workflow-v1.md)执行：官方成品与设定优先；转载追来源；同人/复原/AI 单列；不能把透视图当俯视图，也不能把普通同级舰当特定旗舰。图片不足就继续补证据，不冻结结构、挂点或最终提示词。休伯利安的[参考记录](hyperion-reference-notes-2026-09-26.md)仅作查图档案例子，不用历史查图状态代表它目前的开发完成度。

参考不是单张主图：按“轮廓/顶部布局/侧后结构/局部接口/材质”分工，多张图一起使用，并记录各部分取自何图；遇到版本冲突时明确取舍，不机械拼接。

**有可旋转 3D 参考时，先实际旋转再写结构提示词**：至少取顶部与侧/尾视，靠喷口和明确的前端结构辨认舰艏/舰艉，不能把最宽处默认当舰艏。优先正交；查看器仅支持透视时用低 FOV 近顶视，记录真实相机参数并明确“近似”，不称严格正交。能找到第二份可靠模型就交叉核对；游戏资产、修改版、同人白模分级使用。截图中已有武器只作结构参考，不能直接当裸舰运行图。生成候选若改变了主要体块位置/比例，退回外形核对，不靠贴图细化或加槽掩盖。

参考方向明确后，再确定六件事：
1. 一句话角色：它解决什么战术问题，而不是什么都能干。
2. 一个核心决策：玩家什么时候应该改变打法？
3. 两项主要优势、两项会实际遇到的代价，以及对手的一种可执行反制。
4. 原版/主题参照：借鉴什么、不照搬什么，属于还原还是 Web 扩展。
5. 结构范围：普通舰/固定模块舰；是否确实需要专属武器、航空或新护盾。
6. 交付范围：个人单机可玩，还是另行验收多人；不把设计批准当发布授权。

**每舰必需**：定位与规则、舰体资源与几何、合法默认配装、接入目录与操作说明、验收记录。
**按需选择**：模块、专属武器、新主动系统、内置/可选插件、航空、新渲染效果。不是每艘都必须有这些。

创新可以是挂点布局、射界、弹药、机动和现有系统的新组合。不要为“独特”强行复制虚空盾、封舱、六甲板或另一套复杂状态机。

## 2. 标准流水线与交付关卡

| 阶段 | 实际要做 | 交付物 | 通过后才进入下一步 |
| --- | --- | --- | --- |
| P0 委托与查图 | 确认作品/舰船/版本，查原作图片并实际看图，再填范围 | 任务书、带来源的参考图与特征/未知项清单 | 图片足以支持主要结构，作者认可参考组及各图用途；不是凭印象设计 |
| P1 玩法 | 写接敌→收益窗口→承受代价→恢复/撤离循环 | 决策/反制矩阵 | 去掉名字和特效，仍有行为差异 |
| P2 规则 | 写触发、消耗、对象、阶段、中断、AI及状态归属 | 机制卡、来源/差异说明 | 已有、待扩展、未知清楚分开 |
| P3 配装 | 排S/M/L/XL四档槽、绑定/换装、射界、推进表达、甲板及模块预算 | 挂点/安装档案、默认与分支配装 | 同档换同档；可换与内置分别对账，不靠漏算成本成立 |
| P4 规则验证 | 用无视觉逻辑探针，或已批准且适用于本舰的正式资源验证核心交互 | 规则证据、缺口清单 | 不放占位图/假武器/假特效；移动、开火、核心决策及基础AI有证据 |
| P5 美术锁定 | 多图/模型核对轮廓，确定2D或3D烘焙路线、战斗尺度及接口 | 同一整舰母版/结构稿和制作路线 | 轮廓与结构认可；不靠无限换提示词碰运气 |
| P6 资产生产 | 生图/手绘、分层、几何标定、确定性导出 | 原图、运行图、元数据、导出脚本 | 透明正确、接口连续、没有烘焙动态内容 |
| P7 实装 | 内容注册、改装、模拟、Worker、显示投影 | 游戏内可选、可装、可打的整舰 | 不是仅在静态HTML里拼好看 |
| P8 验收 | 定向机制＋真实AI＋Worker画面＋整舰交战 | 带配置/种子/范围的证据 | 没有硬故障；未验证项明示 |
| P9 交付 | 锁定版本、玩家说明、依赖和许可 | 内容清单、版本记录、限制 | 作者试玩确认；发布另授权 |

美术可以先探索，但探索图不冻结生产几何。若玩法没成立，回到P1–P4；若机制可用只是图不顺，局部处理，不整舰推倒重来。

作者主要确认四次：**多图参考组与版本方向、玩法方案、轮廓与尺度、实装试玩**。普通坐标修正和工程接线不必每一步打断确认；改变已批准玩法、外观或范围则重新说明。

## 3. 深度不是技能数量

每个核心机制必须把下面这条链说完整：

**局面信号 → 玩家选择 → 收益 → 真实代价 → 对手反制 → 退出/恢复。**

荣光女王案例：选一舷集中火力，承担对舷减速、幅能压力和机动下降；对手可换边、压迫排散或打掉炮廊。价值来自方位与时机，不只“按F增加伤害”。

第二艘必须重新回答这些问题，不照抄案例：
- 不按主动系统时，它靠什么完成基本职责？
- 有没有明确“不该按”的时机？对手能看懂吗？
- 默认配装是否能上手，另一配装是否真的改变距离/资源/职责？
- 弱点能否被自己的另一个机制无成本抹掉？若能，取舍可能是假的。
- 主题还原依赖什么行为？“很大、很肉、火力高”只是规格，不足以表达全部特色。

## 4. 一舰一本账：先登记，后画图

### 4.1 挂点账本

每个真实挂点有稳定ID、所属模块、尺寸、类型、坐标、射界、默认装备、可否拆卸。数量以账本为准，不能以生成图上看见几个圆盘为准。

| slotId | 所属部件/路径 | S/M/L/XL | 类型 | 炮塔/固定 | 局部位置/基准角/射界 | 默认武器 | 可拆 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 作者填写 | 作者填写 | 作者填写 | 作者填写 | 作者填写 | 作者填写 | 作者填写 | 作者填写 |

检查三次总数相等：**设计表中的装备位 = 编译后的全模块装备位 = UI可换位＋明确展示的固定内置位**；装饰件不算装备位，内置位不要求可点击换装。重复子模块中的同名槽位必须用完整路径区分。

采用 **S/M/L/XL四档，只能同档换同档**。档位、武器类型、运动方式（转动/固定）、可换/固定绑定是四个独立维度；XL是Web扩展，不冒充原版三档规则。某槽可以永久绑定某武器，但必须有真实装备、耗费、伤害和UI说明，不能只有一张炮口图。安装档案与[四档武器规范](weapon-art-four-tier-workflow.md)使用同一事实来源。

大小槽还包括物理比例：小槽不能像主炮平台，大槽也不一定要画成空心巨洞。用少量重炮位、中型火力带、较小点防御位组织层级；具体数量服从定位。荣光女王的14大/14中/20小只是该舰实例，不是下一艘的模板数值。

### 4.2 预算账本

分别记录DP、每个模块的OP、武器、LPC、舰装、电容/耗散、一次性弹药与战斗资源消耗。解释射程、机动、耐久、火力的兑换关系，不能全部用“巨舰”豁免。

新增方案必须显式应用，并支持原有确认/取消/撤销流程。不得因为开发了新武器或飞机就自动覆盖玩家旧配装。

### 4.3 状态账本

每个新动态值记录：谁创建、谁更新、何时清理、谁显示、如何投影，以及是否需要权威存档/恢复。优先复用现有可同步状态，渲染端不另算一套资源。

## 5. 美术生产：完整舰体先认可，运行资产必须分离

### 5.1 统一画风与比例

- 直接看本机原版舰体素材，按相同游戏显示尺寸比较，而不是只看高清图。
- 正交俯视、大形清楚、分层装甲、暗机械腔、受控材质和颜色；别用海报灯光、透视和密集噪声伪装细节。
- 世界尺寸、运行贴图尺寸、原图尺寸分别记录。放大飞机不能只改PNG：碰撞、重心、炮口、喷口、尾焰和编队间距必须一起检查。
- 图片上方代表舰艏/炮口，是美术约定；如何映射引擎局部前向，由当前几何与渲染约定核实，不能默认图片中心就是枢轴。

### 5.2 资产分工

| 资产 | 可以画 | 不应烘焙进去 | 接入时标定 |
| --- | --- | --- | --- |
| 舰体/模块 | 装甲、机械结构、炮座接口、喷管内壁 | 可换装炮塔、尾焰、盾、动态技能效果 | 轮廓、中心、挂点、喷口 |
| 可旋转武器 | 炮座、炮塔、炮管、静态机械细节 | 射击火光、光束、固定长尾焰 | 旋转轴、后坐层、枪口 |
| 鱼雷发射器 | 空架、独立弹体、导轨/舱口 | 永远满弹的固定弹体组合 | 满/空状态、各枚弹位置、真实库存映射 |
| 舰载机 | 机身、固定集成武器、喷口 | 尾焰、投下的炸弹、盾泡 | 尺度、轮廓、机炮/弹舱出口 |
| 特效/图标 | 单独的纹理或图形 | 不能冒充已实现机制 | 阶段、事件、颜色、遮挡与缩放 |

固定集成炮可以画进舰体/机体，但必须保留真实挂点、出射轴和装备状态；不再叠另一座炮塔。**隐藏图片不等于固定射向**：运动由HARDPOINT/火控规则决定，不能用HIDDEN代替所有固定武器，否则可能漏掉蓄能或允许不存在的炮头转动。无机械转动的能量束可按明确规则偏转；可换装舰炮必须独立资源。

先决定本舰是否适合外喷尾焰：常规引擎才校准出口、方向、宽度、长度与推力；场推进/反重力可由舰体原生发光表达，不强行喷火。选外喷时优先原版引擎材质与绘制路径，不画静态火柱、不再叠第二份通用拖尾。详见5.6。

### 5.3 模块舰不能硬切

1. 先锁定同一整舰母版和坐标系，再划分核心、炮廊、动力等实际所有者。
2. 接口靠结构解释：上层搭接装甲、下层连接/机械骨架、管线或嵌套舱段；不要只是直线裁开。
3. 明确每层属于谁。拆掉某段后，其武器/喷焰随它消失；只留下确实属于邻段/核心的接口结构。
4. 核对完整、分离查看、单模块毁坏三种状态。展示用爆炸视图不等于游戏支持自由拆接。
5. 核心碰撞不能偷用整舰矩形；模块各自承担正确区域。亲缘关系、移动、旋转、导航、射击与物理碰撞规则一致。

若需要新增破损内部美术，另作资产，不声称裁图自动生成了原本不存在的结构。

### 5.4 生图执行规则

先写清这次交付的是“整舰母版”“一个模块”“一门炮”还是“一架飞机”，再给完整提示词；不能只补一句风格形容词。

提示词结构固定为：**用途 → 视角/朝向 → 已锁结构 → 材质/颜色 → 装备接口 → 禁止内容 → 输出格式**。

每次只解决一个明确问题。获认可后冻结轮廓，局部问题优先局部修订。需要切图/缩放等确定性导出时保留原始字节，不能暗中重绘。接口失败就说明失败并提供提示词或接收玩家成图，不擅自换模型，也不宣称成功生成。

### 5.5 制作路线：优先解决结构，不强制所有东西三维化

| 情况 | 优先做法 | 必须避免 |
| --- | --- | --- |
| 有可信且许可适用的模型，轮廓/环/机械结构复杂 | Blender等离线正交烘焙；保留相机、材质、光照、尺度和导出脚本 | 凭模型截图猜顶部结构；直接把宣传渲染当运行图 |
| 已有合格二维舰体/武器 | 保留原图，补安装结构与像素标定 | 为普通2D炮塔强制重建模型、强制96方向帧 |
| 缺少整舰/独立机体/武器美术 | 生图或手绘独立资产，再校准接口、边缘和实际尺寸 | 一张图画舰体＋可换炮塔＋尾焰＋盾；用生图决定精确槽数 |
| 需要动态环/开合/机械部件 | 分层或导出必要姿态帧，运行时按真实状态采样 | 用整船GIF代替实时受损、武器转动与独立模块 |
| 原版已有适合的尾焰/光束/等离子 | 先核实资源与源码，复用现有路径 | 为“专属”重新造更差的贴片特效或额外叠一套光晕 |

3D烘焙仍须调到远行星号的战斗尺度：统一舰体/炮头的光照方向、金属明度、边缘锐度、细节密度和接触阴影。**先关掉盾、尾焰、开火和技能光，检查空座、已安装炮头及转角极限是否像同一层画面**，再做特效。不能只调暗贴图或加辉光掩盖结构不接。

母版、开发工程、运行贴图分开保存；按实际画面需要定分辨率、帧数和压缩方式，记录包体、纹理内存和帧耗时，不以高清/帧数越多越好作为目标。运行中直接使用模型必须单独有性能与功能依据，不能作为普通舰船包的默认门槛。

### 5.6 推进、攻击与技能：先写视觉契约，再选素材

每种效果用一张契约记录：**所有者 → 真实触发事件/状态 → 锚点与坐标 → 阶段和时钟 → 材质/颜色/尺寸 → 遮挡 → 退出/损毁 → 资源依赖**。它是制作记录，不是已实现的通用JSON API。

- **尾焰**：以实际喷口为准，不以图片框底边或舰体中心代替。主推与辅推可有不同长度/宽度；覆盖怠速、推进、转向、零推力、单喷口失效、离屏。原版引擎路径已适合时直接复用，不用两张生图尾焰放大混合来冒充推进。特殊场推进只在本体正确遮罩内响应推力，母舰和舰载机可以使用不同推进表达。
- **武器**：独立规定炮口蓄能、发射、飞行、接触/命中。发射前跟随当前炮口；离膛弹体进入世界坐标；连续束的视觉起点跟随插值后的机体，终点来自真实射线/碰撞。不能从PNG中心发射、把机载炮套成缩小版舰炮、让枪口余晖变成假的第二发，或用远处爆炸填补没有命中的攻击。
- **固定/转动**：固定外壳、承座和前景不跟炮头转；旋转炮头、炮口与实际出射方向共用变换。已烘进船体的固定炮只增加所需动态光，不再盖第二座炮盘。
- **技能**：IN/ACTIVE/OUT/中断读真实权威状态；舰体增幅、盾面超载、修复反馈各有自己的材质/对象/阶段。修复读取真实结构上限和受损部件，不给满血部件画假的大规模修复；内置/可选插件不只是重复规格说明。
- **动画**：战斗用模拟时间，不用墙钟凭空动。改装预览可用独立预览时钟，但采样相同素材/姿态规则，隐藏页面暂停。暂停、加速、死亡、禁用与场景重开必须可解释。
- **素材选择**：生图适合可控独立材质/序列/图标，不保证适合整束光、整个尾焰或最终动画。没有合格资源或机制就标缺口，**不得用占位、随机噪声、临时几何光圈替代承诺的成品效果**。原版经过核实的运行时绘制不等于占位。

原版依据实例：0.98a-RC8 `combat/entities/G.java` 的战机三层尾焰，`PlasmaShot.java` 的torpedoray32构型，`pdlaser.wpn` 的光束参数；仅有源码/素材证据不能写“原版实机等价”。方舟当前采用了这些路径，但其少量专属ID桥接不是下一艘应复制的架构，新的可复用能力应收敛到受支持的规格/渲染扩展。

### 5.7 动态几何：武器、模块和战损共用当前姿态

几何档案记录源图尺寸、运行尺寸、pivot、裁剪/留白变换、模块归属、炮口/喷口、固定/旋转层和必要的逐姿态锚点。改装预览、战斗显示、真实出射坐标、战损遮罩从同一源档案导出。

- 武器装在静止舰体就用舰体局部锚点；装在旋转环/活动翼上，先决定锚点是否随该部件运动。若会移动，**物理出射、火控与显示必须同时支持相同姿态变换**，不只移动贴图。当前接口不支持时标明阻断或经确认迁到静止承台，不能假装已动态挂载。
- 动态部件必须逐姿态正确遮挡；受损层使用同一所有者、当前姿态和深度片。环/炮口已转动而中央受损贴图还留在旧位置，直接判失败。
- 拆掉模块后同时取消其武器/喷口/机库/专属增幅，只留下邻段确实拥有的连接结构。舰体死亡/撤退、资源失去供给和模块AI同步处理，不能只隐藏图片。
- 世界旋转至少检查0°、90°、180°和任一斜角；转动炮再查射界极限。检查正常战斗缩放和近景，不能只交放大彩图。

## 8. 三类机制各有硬要求

### 主动系统与内置/可选插件

- 主动系统：写明准备/生效/退出/冷却；何时扣费、锁定什么；过载、排散、死亡、禁用时如何撤增益。
- 内置插件：只留下实际规则，不把“巨舰”“很多甲板”“武器很多”等已有规格重复包装成三个假插件。写清核心/炮廊/动力舱归属，不可拆和成本规则真实生效。
- 可选插件：必须有成本和取舍，适用性/互斥/叠加顺序/卸下恢复可验证。与主动效果是相加还是相乘，写在规则里。
- 区域护盾：友军能穿越、友军能向外开火、外敌火被截、盾内来袭、溢出伤害、光束/爆炸、排散/过载、崩溃重建分别规定；不是画一个大圆就完成。
- 反馈：启动、稳定、受击、崩层、关闭、失效应可区别；规模、位置和节奏与船体结构协调，不只放大缩小圆环。视觉时长不能暗中决定无敌/伤害时长。

### 航空与弹药

分别记录：LPC成本、每队数量、射程、战损补充率、重建时间、存活飞机返航装填时间；不能混为一个“回血/补机计时”。

航空角色必须可观察：截击目标优先级、炮艇交战距离、轰炸机投弹窗口、明确攻击令、召回优先级。返航要真实飞行到移动的停靠点，装填必须依据真实库存；无设计授权不免费回血。停靠/隐藏/不可选中、起飞、母舰死亡/撤离都要闭合。

### 航空外观与火力配套

为每种机体同时提交**机体＋像素标定＋武器＋攻击特效契约＋发动机/推进契约＋LPC/AI＋资源闭包**。不能“母舰做完了，飞机暂时复制一份”。

截击、突击、轰炸等不同职能默认要有正常缩放下可辨的轮廓、武器表现与攻击节奏；确实是同型改装时须明确说明并保留看得见的改装差异，不能仅改数据/名称。双束、点射、等离子、鱼雷分别匹配实际武器，不能全用同一条母舰射线。射击原点、朝向、弹道、命中反馈与大小在同一近景中连续核对。

验收至少包括并排怠速/推进/转向、真实开火与命中、空弹返航/停靠/补弹、失去所属机库。独立使用战机或重建后也能加载全部资源，不依赖母舰恰好预加载过。允许成熟原版引擎能力复用，不为视觉区分另造第二套航空模拟。

### 数值校准不是把所有参数加大

先按战术角色选择同档参照，列出单发、实际齐射数、充能/连射/冷却、命中率、伤害类型、射程、转速/固定轴、幅能和弹药成本。界面DPS与实际事件时间线核对；不能忽略冷却重叠、打空、追转或射界而直接拿纸面乘法当实战输出。

分别测首轮爆发、持续输出、停火恢复、盾/装甲目标、侧后方快速目标；航空再加往返航程、重装和战损补充，巨型模块舰再加可同时朝目标开火的实际武器数与失段后的输出。先修错误出射/碰撞/射界，再调数值；不能用更高伤害补偿打歪。记录修改前后与改动理由，不自动改写旧方案。

### AI与权威显示

直接调用 `advanceAI()` 成功不够。必须用真实舰队场景，让系统穿过**选目标→导航/避碰→防御/幅能→射界→激活→增益→退出**的完整流程。

荣光女王的教训：技能自身判定正确，但导航把自己的八个模块当障碍，1800帧全在误报避碰。正确修复是统一导航和物理的同舰模块规则，不是删除技能的安全门槛。

显示快照能往返只证明显示；不能自动声称可恢复权威战斗、完整存档或双端联机。DTO增加字段也不代表Worker和渲染已经消费它。

## 9. 验收与完成定义

完成一个功能块后集中一次：**类型检查＋改动文件lint＋一个相关既有场景**。具体失败再定向复查，不每改一行重跑全套。文档更新不触发整舰重测。

| 层次 | 最低证据 |
| --- | --- |
| 几何与可用性 | 真Alpha；实际游戏尺度；可换槽位可点可换、固定内置位明确展示；炮口/尾焰位置；确认/取消/撤销/保存 |
| 机制闭环 | 真实耗费与收益；准备/结束/中断；空弹、过载、死亡等边界；无重复扣费/叠加/复活 |
| AI | 真正让AI驾舰和航空，不用测试手动激活掩盖问题；合法时会用，不合法时会拒绝 |
| Worker与画面 | 真正创建舰、武器、航空并步进；实际截图看比例/接口/反馈，不拿静态拼图替代 |
| 整舰 | 同档、高速、重甲、PD/航空等与定位有关的对手；时间、种子、配装、胜负与失败均记录 |
| 人工故障场景 | 初始损伤/指定指令与自然战果分开；别让胜利结算提前截断死亡后清理观察 |
| 多人/压力/平衡 | 各自独立验收；单机通过不替代其中任意一项 |

阶段标签用事实，不用“完成百分比”：
- **原型**：核心想法可运行，资产/内容可能缺失。
- **单机可玩功能版**：承诺的机制、配装、资源、AI、Worker与定向战斗有证据。
- **平衡候选版**：多种场景和真实玩家反馈支持其取舍；不是几次固定种子胜利。
- **多人已验证版**：指定房间/传输/版本范围实际通过。
- **可发布版**：相应验收、许可、兼容说明和发布授权齐备。

阶段可以并行，但标签不能互相冒充；每舰以自己的最新验收记录为准。亚顿之矛v20的飞机近景是生产引擎受控搭景，不是原版实机，也不能据此宣称完整自然实战、多人或最终平衡。

## 10. 玩家与社区如何复用

现在可复用的是工程流程、任务书、内容规格/扩展接口和配装路径，不是已经有一键造船工坊。

建议的社区交付流程：**玩家提案 → 原作多图核对 → 规则/安装档案 → 无占位规则验证 → 作者成图或模型烘焙/协助生图 → 几何与真实状态接入 → 玩家试玩 → 单舰包版本化交付**。该流程可人工执行；上传、审核、自动生图、一键分发界面属于以后单独开发的产品。

每舰保留：作者与稳定ID、原图/提示词/许可、几何和构建源、配置与行为依赖、默认/分支配装、操作说明、版本变更和验收记录。

命名空间要隔离作者/内容；显示名可改，稳定ID不能随意变。新行为走可信代码审核，不能让玩家JSON或房间数据任意执行JS。房间需明确内容/行为版本，不静默替换缺失内容。更新配装需要明确选择，不能覆盖旧方案。

有主题IP、原版资产或第三方参考时分别记录来源与允许用途；“本机可读取”和“玩家上传”都不自动等于可公开再分发。

## 11. 这次必须带到第二艘的经验

| 踩坑 | 下次的前置措施 |
| --- | --- |
| 船看起来大，但没玩法 | 先写选择、代价和反制，P4做无占位规则验证 |
| 船图把武器/火焰全画死 | 提示词明确目标资产和禁止烘焙项 |
| 模块像硬切碎片 | 整舰母版先确认，接口分层并明确所有权 |
| 槽少、漏槽、槽过大 | 账本先于细化美术；数据/UI逐槽对数和比例 |
| 飞机像蚊子、放大后又脆 | 世界尺寸、碰撞、生存、武器、尾焰一起评估 |
| 鱼雷永远满架 | 发射架/弹体分离，外观跟真实库存走 |
| “插件”只有重复说明 | 每条内置都对应实际规则、对象和边界 |
| 新装备做好却找不到/用不了 | 目录、方案入口、预算、确认、Worker一路验收 |
| 手动技能正常，AI不按 | 真实AI整链路验收，不只调用技能函数 |
| 测试对手先死，误判清理没执行 | 控制并声明测试初始条件，保证观察窗口 |
| 两种飞机外观相同、都套母舰武器特效 | 每型机体独立视觉契约；轮廓＋火力＋炮口＋喷口一起验收 |
| 生图尾焰像贴纸、母舰不适合喷火 | 先选推进表达；常规飞机优先原版尾焰，场推进不强塞喷口 |
| 舰体/炮塔不像同一图层 | 关特效，在实际尺寸检查材质、固定承台、接触阴影和遮挡 |
| 环转了，武器或战损没跟上 | 当前姿态、所有者、深度与锚点统一；物理/显示都要跟随 |
| 四档误写成三档、内置位被误判漏槽 | S/M/L/XL同档换装；可换位与固定内置位分别对账 |
| 图片/逻辑做完就说全做好 | 分别报告单机、AI、Worker、多人和平衡 |

下一艘的第一份交付，应是**填好的任务书＋结构/挂点草案＋核心规则＋两套纸面配装＋待补能力清单**，而不是直接一张最终彩图。


## 12. 本轮更新的执行入口与硬门槛

下一艘顺序不变：**查原作多图 → 定义决策/代价 → 四档安装与模块账本 → 无占位规则验证 → 选2D/烘焙路线 → 分层资产 → 标定和运行接线 → 数值/特效联动 → 整舰验收 → 单舰自包含交付**。

以下任一项未通过，不得写“完整做好”：
- [ ] 不依赖占位或调试兜底；默认配装及承诺的分支可用。
- [ ] S/M/L/XL、固定绑定、可换位数量、目录与OP一致。
- [ ] 关特效仍贴合；正常缩放可读；舰体/武器/航空都在同一美术体系。
- [ ] 炮口/喷口与运行数据对齐；旋转、动态部件和模块损毁不会错位。
- [ ] 推进/技能/攻击从真实状态驱动；有完整启动、维持、退出、中断反馈。
- [ ] 航空各角色可辨且完整返航重装；缺失母舰预加载不会漏资源。
- [ ] 实际AI、Worker、资源闭包及声明模式验收；受控画面、源码依据、原版实机明确区分。
- [ ] 独立包的兼容范围、缺依赖报错、许可和安装验证成立；否则标“工程集成版”，不冒充可拖入即用的包。
