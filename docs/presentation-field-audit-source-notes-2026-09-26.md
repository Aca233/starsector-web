# 显示字段冗余诊断：来源与边界（2026-09-26）

当前Worker CPU采样已经冻结315模块，并对真实Host进行150预热+60tick诊断。captureGraph含子调用782.786ms/60tick，是显示编码主成本；火控更新链也仍占大量模拟时间。旧形状缓存、标量分派、密集视觉目录等负收益方案不重试。

本轮只加测试构建计数，不改生产协议/算法。记录原编码器已经发出的Object行中：字段数量、相同布局旧行、实际改变的字段数量（tag或payload任意变化算一个字段）、可用稀疏行的数量。比较以原scalar已经执行的Object.is结果为准，NaN、-0和String实际值沿用原语义。

假设稀疏行使用id/kind/count三个头单元，每个改变字段使用index/tag/payload三个Float64单元；只在旧身份、种类、类型、字段次序均相同且数值单元确实更少时计算潜在节省。数组、Map、Set、Vector、typed、全新/重入/布局变更行保持原格式。不删任何显示字段、元数据、字符串或完整图预算。

这些是有效数值单元的理论格式估算，不是新codec、带宽、实际转移buffer容量、内存或速度收益。未来接收端必须重建完整行，并保持原来整条变更记录的写入/消费者变更覆盖语义，不能简单只写变化字段就声称等价。协议版本、原子性、畸形包验证和真实无插桩交付仍是以后候选的独立验收条件。

工具启用--graph-field-audit才插桩。现有同模块旧/新编码合同检查插桩不改字节；另用固定字段、特殊数字、类型变化、键重排、退休/重入的已知输入校核计数。集中一次typecheck/lint/相关定向场景，再单独跑200舰150预热+60tick真实Host。计数运行不做提速结论，不择优重测。

不改玩法/UI，因此本轮没有新的原版算法或画面还原承诺；不操作桌面、不启用子代理、不发布、不覆盖其他任务。
