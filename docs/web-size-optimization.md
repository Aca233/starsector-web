# Web 体积优化（2026-09-22）

## 范围与边界

只处理构建文件完整性和静态 HTTP 传输，不改玩法、UI、贴图像素、音频或联机快照协议。不删除历史产物、不更改存档，也不制作或发布包含未完成生涯功能的发行包。当前验证输出为本地内部构建。

## 防止重复构建和过期资源混入

Vite 的正常构建默认清理其项目内输出目录；不要通过合并多次构建或 `--emptyOutDir false` 来制作可分发的混合目录。

新增构建完整性插件：

- 仅接受本次 Rollup 输出及当前 `public` 文件；发现旧哈希 JS、缺失文件或额外文件会失败，不擅自删除这些文件。
- 逐文件校验复制后的 `public` 与源文件的大小和 SHA-256，确保已有字体优化确实进入构建。
- 写入 `web-build-manifest.json`，记录路径、大小和 SHA-256。此清单用于一致性检查，不是发行签名或真实性证明。
- Windows 便携版及 Electron 打包入口都校验清单，即使传入 `--skip-build` 也不能静默打包混合目录。历史无清单构建需要先重新构建；正常旧发行包运行不受影响。
- 包含符号链接、覆盖构建输出的 public 文件、构建后新增/改动/缺失的文件，都会被拒绝。

共享开发目录正在被其他任务使用时，使用一个**尚不存在的项目内目录**进行验证：

```powershell
npm run build -- --outDir artifacts/web-size-validation-UNIQUE --emptyOutDir false
```

这会执行类型检查及完整 Web 构建，但不会覆盖默认 `dist` 或制作游戏安装包。请将 `UNIQUE` 替换为新的时间戳。此时 `--emptyOutDir false` 仅用于新空目录，完整性插件会拒绝旧构建残留。

## 体积检查

```powershell
npm run size:report -- artifacts/web-size-validation-UNIQUE
npm run size:check
```

报告以字节为单位，包括实际磁盘文件总量、各扩展名占用、最大文件和文本/WASM 等的 Gzip/Brotli 传输估算。如果存在构建清单，会先验证完整性；旧目录没有清单时会明确返回 `verified: false`，仍可用于只读基线统计。

传输估算是所有可压缩资源的总和，不等于首页实际下载量、ZIP 大小或运行内存。压缩后的图片和音频不应反复套压缩；完整离线资源也不能在没有引用证据时删除。历史测试/发行产物清理需要另行确定保留范围。

## 静态 HTTP 压缩

LAN 静态服务器按 `Accept-Encoding` 协商 Brotli（quality 5）、Gzip（level 6）或原始响应。浏览器在普通 HTTP 局域网地址下可能不提供 Brotli，此时自动使用 Gzip；不要求客户端支持 Brotli。

- 压缩使用异步 zlib；只缓存压缩结果，最多 32 MiB / 128 项。
- 最多同时执行 2 个压缩任务；相同文件、版本和编码的请求合并等待。不建立无限任务队列。
- 最大压缩源文件为 16 MiB。超限、繁忙或压缩失败时，只在客户端允许的情况下回退为原始文件流；不发送被客户端禁止的编码。
- 按文件版本使缓存失效；`Vary: Accept-Encoding`、HEAD 与 `Content-Length` 对齐。临时失败响应不被长期缓存。
- PNG/JPEG/OGG/WOFF2 和 `music.bin` 不重复压缩；不落盘生成 `.br`/`.gz` 双份资源。
- 保留原有路径/Host 安全检查、COOP/COEP 和资源缓存策略。不改变 `/lan/info` 或 WebSocket 联机快照压缩。

## 无损 WebP 实施对照（2026-09-22）

用户确认直接使用 WebP。原版/当前资源证据：`public/game-assets/graphics` 保留原路径、像素尺寸、透明度和字体图集布局；舰船纹理经 `AssetResolver`，菜单图集经 `runtimeAssetUrl`，生涯图片存在直接 URL，CSS 存在原始 PNG/JPEG 路径。转换只改变物理编码和资源 URL，不改变逻辑资源 ID、采样器、布局或玩法。

预期：生产构建只携带经像素核验且比原文件小的无损 WebP；未知色彩描述、动画、位深或体积不划算的图片保持原格式。原版安装文件及 `public` 不修改。实现使用隔离的内容寻址缓存/暂存 publicDir，再交给 Vite 的原有复制、CSS 路径和构建完整性检查流程。

验证方法：编码后逐图对照解码 RGBA 和尺寸；保留 ICC/EXIF；检查资源清单、动态 URL、CSS 和字形图集路径；集中类型检查/lint/构建；后台浏览器对照颜色和透明度，确认实际页面资源加载。未验证前不把像素编码一致冒称为全部浏览器的画面等价。音频本轮不改，亦不制作发行包。

### 生产构建用法和依赖

- 正常 `npm run build` 自动准备无损 WebP；开发服务器继续使用原始资源，避免每次开发启动都编码。
- 构建机需要 Python 3.10+、Pillow 12.1+（官方 wheel 含 WebP/LittleCMS）：`python -m pip install --upgrade "Pillow>=12.1"`。可用 `STARSECTOR_PYTHON` 指定解释器。
- `npm run images:webp` 可单独预热缓存。缓存位于 `.vite/webp`，按源文件 SHA-256、编码器版本及设置寻址；缓存命中也核对解码像素和元数据。此目录已加入开发文件监视忽略列表。
- 不缩放、不减色、不丢弃透明 RGB；编码参数为 `lossless=true, exact=true`。这里的 quality=75 仅控制无损编码搜索，不代表 JPEG 式有损质量。
- 无损 WebP 反而更大、未知色彩/位深/动画、无法迁移的元数据等情况保留原格式；音乐与音效保持原样。
- 暂存 publicDir 对保留资源使用只读用途的硬链接（环境不支持时复制）；构建过程不会写回原始 `public`。内容寻址目录不通过递归删除刷新，因此不会误清其他任务文件。
- 物理文件采用 `原名.png.webp` 等唯一路径，避免同名 PNG/JPEG 冲突。原逻辑 ID 保留；资源清单 path/bytes/hash、图集引用、采样器查询、运行时 URL 和 CSS 一并适配。正常静态托管无需服务器重写规则。

本轮全量 `tsc -b` 暂被未改动的 `src/campaign/client/NativeProtocol.ts` 阻断：引用的 `OriginalColonyConstructionAction` 未从对应模块导出。WebP 打包验证会单独执行 Vite，并明确区分构建成功与全项目类型检查未通过。

### WebP 最终结果

- 独立验证构建：`artifacts/webp-validation-20260922-212419`，未覆盖当前运行用 `dist`。
- 扫描 2,410 张 PNG/JPEG；1,749 张转为无损 WebP（1,747 PNG、2 JPEG）。其余 661 张因色彩/元数据兼容性、编码核验或体积收益条件不满足保留原格式，不能为了凑“全转”而牺牲保真。
- 图片总量 **91.25 → 73.82 MiB**，减少 **17.42 MiB**。

- `.fnt` 文件内 page 路径也指向 WebP；字形位置、字距等其他内容不变。首次构建后发现这项描述符一致性缺口，已定向补齐暂存流程，刷新独立验证构建的 7 个字体描述符/资源清单，并重新校验整份构建清单；未重打或发布游戏包。

浏览器验证逐张覆盖全部 1,749 张转换图片：

- WebGL2 与游戏相同的 `UNPACK_PREMULTIPLY_ALPHA_WEBGL=false` 上传方式，读取原图/新图纹理，**差异字节数为 0**。
