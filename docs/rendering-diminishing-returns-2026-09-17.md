# 渲染优化与收益递减复核（2026-09-17）

## 结论：用户感觉“没什么提升”有数据依据

百舰完整浏览器工作负载中，本轮渲染 CPU 耗时下降约 **15.1%**，但整轮“模拟 + 视觉更新 + 渲染 + GPU 完成等待”均值只下降 **1.8%**。整轮 P95 还略有恶化，不能据此宣称卡顿改善。

优化后模拟仍需约 **204.63 ms/步**，占整轮约 **85.7%**。这不是继续减少 draw call 就能解决的问题。本轮不宣称达到 100 艘战列舰 / 180 FPS，也不将脚本工作轮次换算成真实游戏 FPS。

## 变更范围

保留：

- `src/engine/render/webgl/RibbonBatcher.ts`：导弹烟雾尾迹共享每个采样点的左右端点，使用 WebGL2 Uint16 索引与固定 primitive restart 分隔独立尾迹；法线按原公式逐点计算，保留重复点回退。跨容量边界携带最后一对顶点，保持每段三角形及顺序。其他缎带几何继续使用原 TRIANGLES 路径。新增 EBO 随上下文重建，并在 dispose 时释放。
- `src/engine/assets/AssetResolver.ts`：缓存成功的路径规范化结果，上限 2048 条；不缓存清单、采样器、纹理或失败结果。即使运行时修改 baseUrl，也会失效重算。路径校验策略不变。

撤回：

- 前一项八纹理 SpriteBatcher 实验。虽然百舰总 draw call 接近减半，渲染提交只改善约 5.7%，不值得引入额外采样器和着色器分支。仅恢复本项实验前的 SpriteBatcher，未回退此前已有优化或其他工作区改动。

没有降低模拟频率，没有缩短尾迹、删除采样点或削减特效数量。

## 方法

- RTX 5060，Chromium / ANGLE D3D11，2560×1440，DPR 1。
- 同一份冻结源代码图；基线已经包含上一轮增量导弹拦截优化。
- 两个独立生产页面，种子 `0x51180`，Onslaught 舰队，相同布局和相机；每步交替先后顺序，不并行运行两边工作负载。
- 每场 360 个固定 1/60 秒模拟步，前 60 步预热，记录后 300 步；每步进行一次渲染。视觉时钟、视觉随机源和渲染缓存均重置。
- 构建、剖析和计时对照分开运行。墙钟时间仍可能受 JIT、GC、系统负载影响，未进行统计显著性检验。
- 这是同步脚本 CPU/GPU 工作量检查，不是浏览器原生 requestAnimationFrame 的持续 FPS、输入延迟或物理 180 Hz 显示验证。60 Hz 模拟预算为 16.67 ms/步；180 Hz 展示预算为 5.56 ms/帧，两者都远未满足。

## 隔离渲染：仅索引尾迹，不含路径缓存

推进 180 步后固定战斗状态，交替渲染 180 次，前 30 次预热。此协议只量渲染 CPU 提交，不含模拟，也不是 FPS。

| 战列舰 | CPU 均值（ms） | CPU P95（ms） | 总 draw calls |
|---|---:|---:|---:|
| 10 | 4.30 → 4.01 | 5.50 → 5.10 | 983 → 983 |
| 100 | 37.68 → 34.20 | 45.10 → 40.60 | 9792 → 9786 |

这次节省来自几何构建和上传，而非显著减少 draw call。单条 20,000 点尾迹的验证用例中，上传数据（含新索引）为 3,839,808 → 1,360,136 字节，减少 64.6%。这是尾迹缓冲区数据量，不是全帧带宽降幅。

EXT_disjoint_timer_query_webgl2 可用，每侧每场取得 150 个样本：10 舰 GPU 均值 2.17 → 2.23 ms（未改善）；100 舰 32.92 → 31.07 ms。这些仅属于固定场景协议，不应推断实际游戏 GPU/FPS 提升。

原始数据：`render-paired.json`、`pixels.json`。独立 CPU 剖析位于 `artifacts/multi-texture-batching/render-before.cpuprofile`；其耗时不作为加速对照。

## 等价性与验证边界

- 10 组真实 WebGL2 直接绘制检查通过：空/单点、重复点与零长度、8,191 / 8,192 / 8,193 / 20,000 点跨容量、5,000 条独立短尾迹、纹理/混合/alpha-density 切换、与喷焰和菱形几何交错、显式 flush、反复 begin/end。
- 以上检查展开索引后的完整 Float32 三角形顶点数据与基线相同，像素相同，GL 无错误。这些小用例关闭了 MSAA。
- 另在百舰推进 180 步后的真实尾迹数据上，使用同一上下文、同一纹理与投影，仅重绘尾迹通道；开启真实游戏的 MSAA（antialias=true）。旧 → 旧、旧 → 新、新 → 新均逐像素相同，GL 无错误。结果：`real-contrail-pixels.json`。这验证了本次改动对应的真实尾迹通道，不代表其他通道的整图零差异。
- 路径规范化进行了 36,070 次前后对照，包含 7,740 次相同异常，覆盖缓存溢出、不同 baseUrl、运行时 baseUrl 变化、点段和反斜杠；结果、URL 和异常均一致，容量不超过 2048。
- **不能声称整个游戏画面逐像素一致**：独立页面完整截图比较不通过严格零差异。固定状态渲染的 100 舰截图有 979 个颜色通道不同，最大差 45/255；完整 360 步战斗截图有 658 个通道不同，最大差 31/255（每图共有 14,745,600 个通道）。差异很少，但不能隐瞒最大差值。
- 为排查截图基准本身，在同一 WebGL 上下文、不推进模拟的情况下重绘旧实现，旧 → 旧也有 431 个通道变化、最大 37/255；另一次旧 → 旧为 360 个通道变化、最大 27/255。因此完整渲染本身并非稳定的逐像素零差异判据，不能把跨页面全部差异归因于本次改动，也不能据此证明所有差异均无关。本轮没有修改这些其他渲染行为。
- 当前源代码图与计时使用的组合候选一致。`npm run typecheck`、`npm run lint`、`npm run build` 均通过。构建仍有大 chunk 提示。
- 当前生产构建的十舰运行、WebGL 上下文丢失/恢复通过：重建 RibbonBatcher 与 EBO，`resourceRecreations=1`，渲染 GL 无错误；会话 dispose 后 EBO 被释放。
- 验证辅助脚本和原始结果仅放在忽略的 `artifacts/indexed-contrails/` 下。未恢复项目测试套件，未进行资源哈希/大小审计。

## 下一步方向

保留本轮无删减的渲染节省，但不要继续将局部百分比当作百舰体感改善。优先重新测量模拟中的全舰/全弹丸遍历、威胁预测与拦截候选维护，针对占主导的工作量做数据结构和算法改变；不靠降低物理步频或减慢游戏时间达标。单纯移到 Worker 只能隔离阻塞，不能让一个约 205 ms 的模拟步满足 60 Hz 吞吐。
