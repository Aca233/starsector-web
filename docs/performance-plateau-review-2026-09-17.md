# 性能停滞复核与射程缓存实验（2026-09-17）

## 结论

**拒绝本轮候选优化，生产源码已恢复到本轮开始时的状态。** 没有回退之前已经保留的优化，也没有降低画质、AI 频率、物理频率或威胁预警窗口。

本轮尝试让 `WeaponRange` 在 ECM / 系统射程修正变化时复用原生舰体加成项，动态修正仍逐次读取；可变舰体及自定义 hullmod 回调仍走原计算。候选完整战斗收益太小且各规模不一致，不满足用户“收效很好、影响不大”的要求。

## 同轮生产浏览器前后交替对照

- Chromium / ANGLE D3D11，2560×1440，DPR 1。
- 10 / 50 / 100 艘 Onslaught；种子 `0x51180`；相同初始布局及相机设置。
- 各 360 个固定 1/60 秒模拟步，前 60 步预热，后 300 步统计。
- 两个隔离页面每一步交替执行先后顺序；不同时推进，也不与构建或剖析并行。
- 完整轮次包括模拟、视觉更新、渲染提交和 `gl.finish`。

100 艘完整轮次 P95：242.1 → 243.2 ms，没有改善尾延迟。三个规模的最终完整模拟状态摘要均匹配，脚本断言通过；页面 / WebGL 错误为零。这仅是上述战斗样本的行为对照，不代表完成全部数值边界验证。另准备的数值边界脚本未执行：性能已不足以保留候选。

**这些是脚本化工作耗时，不是实际 requestAnimationFrame / 180 Hz 显示器的 FPS 测量。** 不与其他报告的绝对毫秒数拼接计算加速比例。

## 为什么仍然感觉不流畅

180 Hz 展示预算只有 5.56 ms；60 Hz 模拟预算为 16.67 ms。当前百舰基线仅渲染提交就约 33.09 ms，模拟约 153.83 ms。即使再削减几个百分点，也不能把这种工作负载变成流畅的 180 FPS。

下一阶段应优先减少工作的数量，而不只是降低单次函数开销：

1. 对威胁预测的敌舰 × 挂载、炮弹 × 观察舰组合增加保守空间候选查询。必须覆盖接近速度、预测时长、偏移炮口、制导追踪和动态射程；不能简单截断远处威胁。
2. 独立量化各渲染 pass 的 CPU 几何构造与提交成本，再决定持久几何 / 实例化。只减少 draw call 而整轮耗时不降的方案也不保留。
3. 用完整战斗耗时、P95 和实际交互帧节奏验收，避免将局部函数加速当作游戏 FPS 提升。
