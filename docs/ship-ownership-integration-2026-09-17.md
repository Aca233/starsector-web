# 原生 Onslaught 多核 AI：正常战斗接入验收（2026-09-17）

## 结论

已接入正常单机战斗的 useCombatLoop → FixedTimestepScheduler → CombatSession 链路，不再依赖原型全局变量或 artifacts 导入。

**本次最终版本完整模拟步吞吐提升 +6.768%，耗时下降 6.339%。** 这是重新冻结基线、重新实测的结果；不是原型的 +15.807%，也不与之前单线程优化百分比相加。

| 指标 | 接入前串行 | 接入后 4 Workers |
|---|---:|---:|
| 完整模拟步平均耗时 | 61.748 ms | 57.834 ms |
| 计算吞吐（模拟步/秒） | 16.195 | 17.291 |
| 完整步 P95 | 88.050 ms | 83.055 ms |
| 有效计时步数 | 540 | 540 |

100 艘默认原生 Onslaught，固定种子 0x51180、固定 1/60 秒步长、相同密集阵形；3 轮配对交替执行，每轮 60 步预热 + 180 步计时。计时使用真实 CombatSession：含玩家控制/玩家 AI、能力门禁、打包、分发等待、输入复核、提交及串行回算。不含渲染；这不是屏幕 FPS，也不是已达到“100 艘战列舰 180 FPS”。Worker 初始化期间保持串行运行，启动成本没有冒充稳定运行收益。

## 安全接入

- 不在半个 fixedUpdate 内 await。主线程短暂预览原生、无 combatEffects 的可还原前置字段，发布快照后立即还原；等待期间仍是完整的上一逻辑步。
- 真正 fixedUpdate 仍同步。其原生 AI 阶段核对所有已发布输入的源状态、原生方法/静态读集及阵容；无变化才接受预测。派生运动/射程/炮口不重复计算校验，改核对全部对应源标量（含引擎状态）及小型非标量元数据。
- 等待时的控制、目标、战术命令、改装、增援可使预测失效；整段 AI 随即串行计算一次。前序 AI 改变邻船护盾/威胁状态时，保守依赖集合触发对应后续舰船回算。系统激活及排幅需要的副作用始终由原始主线程 AI 执行。
- 暂停同步收尾已采样的一步；重开/换船/新战斗/销毁丢弃旧预测并终止池。迟到结果不能推进新战斗。调度器同时最多一逻辑步在途，只在完成后计 TPS；暂停不积累追赶步。
- Worker 初始化失败、运行异常、消息异常或 3 秒超时均终止池并串行回退，不重复提交。共享 Float64/标签保留特殊数值；主线程不用 Atomics.wait 或忙等。
- 未改变固定 dt、AI 频率、碰撞精度、舰船数量或画质。

## 启用范围与部署

- 自动门禁：50–200 艘、默认注册的原生 Onslaught 及其默认武器 AI 读集、FRONT 护盾 / BURN_DRIVE / NONE 副系统；浏览器跨源隔离、SharedArrayBuffer/Worker 可用、至少 8 个逻辑处理器。
- 本报告性能数据只证明上述 100 舰基准。混编、改装/自定义舰体、外部效果、订单等未验证情况走串行；不能把结果推广成任意 100 艘船都加速。无 WebGL 渲染性能承诺。
- Vite dev/preview 设置 COOP: same-origin、COEP: require-corp；普通静态部署需服务器提供同样响应头，不具备时自动串行。LAN host.worker 保持原同步路径，未改变 LAN 服务的隔离/资产策略。
- 开发服务器忽略 artifacts 监听，避免诊断快照复制触发反复全量 HMR。本次曾观察到该监听造成 CPU 干扰，早期筛选数据没有混入最终三轮。
- 控制台：window.__combatSession.getMulticoreStatus() 可查看模式、回退原因、完整步均值和阶段成本；setMulticoreEnabled(false/true) 可关闭/恢复自动门禁。均值从该 session 的正常调度步累计，渲染回调不计为模拟步。
