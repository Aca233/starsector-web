# v0.2.5 双端会话日志分析（2026-09-20）

## 结论

这批记录确认安装的是 0.2.5，但没有证明低 Hz 问题解决。高负载 LAN 对局中，客机渲染维持约 60 FPS，接收/应用频率却降到 5–7 Hz；房主多数仍提供约 57–60 Hz，第 8 局也有本机快照产出下降（38 Hz）。优先瓶颈位于房主对远端的快照发送、网络链路及消费回执闭环，不是把客机显示器或物理步长提高到 60 就能解决。

本轮只分析日志和核对源码，未更改运行时代码、窗口限制、协议、超时、已安装程序或发布版本；未处理生涯模式。

## 瓶颈证据

### 1. 客机主线程不是这次 5–7 Hz 的首要限制

B 第 7/8/28 局解析中位数分别约 3.14/3.35/2.57 ms，应用约 6.48/6.89/5.11 ms；这些值不是数百毫秒的排队。三局的 longTaskCount 在首尾采样之间分别维持 3→3、2→2、2→2，累计长任务时间不增长。FPS 维持约 60，采样定时器也没有与 800 ms RTT 相当的持续停顿。

这不表示解码/应用无需优化，也不是单核 CPU 性能证明；只是它们不能解释接近一秒的主要等待。第 8 局房主快照频率确实下降，不能把所有问题都归到网络。

### 2. 同一 TCP 链路的原生 ping 也从约 61 ms 涨到约 760–840 ms

A 的远端 receiver.network 提供独立于客机 renderer 处理的 WebSocket 原生 ping/pong，桌面客机由后台 Node ws 应答。第 7/8/28 局 baselineRtt 中位数分别 61.15/61.75/61.30 ms，latestRtt 中位数 759.60/836.48/771.30 ms。

这说明不仅仅是前端 HUD 心跳回调慢；远端传输及后台处理链路同样出现大幅排队。约 61 ms 的空闲基线也不应被当成同一交换机有线直连的 1–2 ms。不过日志没有网络拓扑、压缩后实际字节、TCP 重传或路由信息，无法确定是 Wi-Fi、虚拟组网、中继、带宽限制、丢包，还是压缩/传输调度的哪一项主导。

### 3. 消费窗口饱和是直接的节流位置，不等于应该扩窗

三局容量均为 5 个在途快照；房主有效诊断样本里满窗比例分别约 86.7%、73.6%、81.3%。第 7 局中转发送中位数约 5.96 Hz，因消费窗口满而跳过约 41.48 次/秒；第 28 局约 6.60 Hz、跳过约 46.70 次/秒。

B 第 7 局第 1777 行是典型：房主产出/中转接收约 59 Hz，远端入队约 6 Hz，消费回执约 6 Hz，5/5 在途。约 5 帧除以 0.8 秒的确认环路，正好落在约 6 Hz 的量级；这只是瓶颈量级说明，不能把 inputAck 当成精确消费 ACK RTT。

窗口是在防止进一步堆积，不是应直接删除的限制。把它按拥塞后的 800 ms RTT 扩成几十帧会允许更多旧状态进入可靠 TCP 队列；也不能只缩成一帧就宣称改善了吞吐。

### 4. 增量已生效，但高负载增量仍然很大

根据 A 每局首末新鲜诊断中的累计计数差值（避免把累计总量当成本局量）：

|对局|平均原始状态 KiB|平均增量封包 KiB|增量/原始|增量字节交付前入队速率 Mbps|
|---|---:|---:|---:|---:|
|7|227.43|58.50|25.7%|3.508|
|8|250.28|69.34|27.7%|3.511|
|28|218.51|65.95|30.2%|3.535|

增量已经减少约 70–74% 字节，且没有出现“所有大包都退回 full”的现象；但每帧 59–69 KiB 仍明显过大。三场不同规模/频率的字节速率接近同一平台，支持受限于链路吞吐/排队的判断。

重要：encodedBytes 是 SLD1 封包大小，发生在 WebSocket permessage-deflate 之前；compression=true 只证明已协商压缩。上表不是物理网卡流量，不能宣称用户带宽就是 3.5 Mbps，也不能用当前低 Hz 的每包大小线性断言 60 Hz 所需带宽，因为提高采样频率会改变相邻增量大小。

### 5. 显示插值也在增加滞后，但不是收到 5 Hz 的根源

B 第 7/8/28 局 playbackDelay 中位数约 153/192/143 ms，个别样本超过 500 ms。这是在低更新率/抖动下的显示缓冲，不是网络 RTT；不能与不同阶段的 ACK 数字直接相加当作 input-to-photon。简单清零会导致跳动，不能增加接收频率。

HUD age 的源码定义是 now - receivedAt，仅表示距本机最近一次收到快照多久。即使包在 TCP 中排了很久，刚收到时 age 也会接近零，因此不能用它证明状态新鲜。

## Steam 部分

A 只有一场约 2 舰的小场景 Steam legacy-p2p 数据。房主本机 60 Hz；发送/网络确认累计计数在约 181 秒窗口内增长率约 38 次/秒，而不是 60。网络 ACK 耗时中位数约 81 ms，但 oldestAckMs 出现 2487/2433/3369 ms 的停滞（如 A 101、118、223 行，诊断值可能在相邻样本重复）。最后仍有后续确认，不是完整会话断线证据。

nativeSession.available=false，无法判定 Valve 是否走中继。缺少 Steam 客机同步日志，不能确定这些停滞发生在客机解码、回程、SDK 会话还是客机后台调度，也不能宣称 Steam 已修复。

## 后续实施顺序

1. 优先对快照做结构化的按实体/字段增量和包大小归因，减少真实变化不大的状态反复编码。当前日志不含完整战场，不能凭此臆断应删哪一类字段；应使用可复现快照录制验证，并保持完整状态精度、实体增删和重同步语义。
2. 在约 60 ms 基线、受限吞吐、22 舰与小场景之间切换的条件下做发送节奏/预算 A/B；保持可靠控制、消费窗口和有界队列。评价远端 Hz、控制延迟及状态新鲜度，而不只看房主 FPS。
3. 补充实际压缩后 TCP 写出字节、发送压缩/队列时间，以及接收→解码→消费 ACK 的本机分阶段计时，区别线路吞吐、重传与后台处理。尽量复用现有采样，不新增大量心跳。
4. 评估控制/回执不被大状态字节阻塞的通道设计。另开通道也不会凭空增加带宽，且需要重新验证消息顺序、重连、安全校验和兼容协商，不作为“改一行立即修复”。
5. 同网络同舰队分别对照 LAN 与 Steam，并采双方完整日志；不通过调高界面 Hz 数字、关诊断、扩大超时或扩窗口宣称完成。
