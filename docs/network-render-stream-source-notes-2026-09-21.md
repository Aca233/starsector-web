# Phase18：第三阶段重载渲染提交—实现前记录

## 证据与范围（2026-09-21）

Phase17 五人/22舰未通过，不能预设剩余问题仍是 TCP/Steam 带宽。`phase18/profile-before/cpu-0.json` 的真实房主页面采样（含 Profiler 额外开销）显示大量时间位于 WebGL `bufferSubData/drawArraysInstanced/bindTexture`：约2984/1767/1186ms self。不把采样时间与无采样性能混算，客机另一份 profile 的 `(program)` 不强行归因。

当前 SpriteBatcher 每次 flush 都向同一 VBO 的偏移0覆盖数据；该存储可能仍被先前 draw 使用，WebGL 驱动可能为此复制/等待。尝试在相同 flush 边界以 `bufferData` 上传本次使用的范围、重新指定存储，避免反复覆盖正在使用的数据。OpenGL 的 bufferData 存储替换是否实际更快取决于驱动，必须 A/B，不以减少某个调用证明收益。保留原路径作为测试/紧急回退。

原版证据：本机 0.98a 来源（沿用此前版本记录），`../decompiled/fs.common_obf/com/fs/graphics/Sprite.java:166–200` 按纹理、颜色、混合、旋转/尺寸和四个UV顶点绘制；`../decompiled/starfarer_api_source/com/fs/starfarer/api/graphics/SpriteAPI.java:8–24` 定义 normal/additive、尺寸/角度及定位。反编译接口与实现交叉查看，不能据此声称原版用 WebGL bufferData。这里是 Web 渲染实现的性能扩展，不是改变原版表现。

对照：保持相同 instance float 数据、texture、sampler、UV、draw 次序、blend、shader、flush 和 pass 边界；只改 GPU 提交存储策略。不减少画质、舰船/弹丸/特效、不降模拟频率，不改伤害规则。

验证：真实无头 WebGL 像素 A/B（1/4纹理、blend、显式flush、容量溢出、resume、重建/释放）、固定提交序列及五人22舰前后对照；检查网络和既有渲染回归。原版实机截图仍待许可，本轮不会启动可见窗口。浏览器运行不应预先标为软件 GPU：`--enable-unsafe-swiftshader` 只允许回退，下一次报告直接记录实际 GL vendor/renderer。

若候选没有可信收益则撤回该候选，不掩盖失败、不把五人轻载当重载。不得动生涯模式或提交/发布。

## 第一候选结果与第二候选（实现前追加）

bufferData 存储替换：11 个 WebGL 像素/边界案例通过，但五人22舰仍未通过，客机中位频率11–19Hz，未证明收益，已恢复 SpriteBatcher 原源码。候选与失败记录留在 phase18，不保留该生产修改。

第二候选：将主 SpriteBatcher 也使用已用于 FX 的四纹理批处理模式。沿用现有 shader、实例纹理slot与FIFO顺序，不按材质排序，不跨 blend/pass/容量边界合并；纹理满四种才flush。原版 sprite 绘制/混合次序证据不变。必须新增单纹理→四纹理的真实像素对照（不是把 bufferData 的测试套用过来），并做真正五人重载A/B后才决定保留。上下文重建也使用同一策略。记录紧急单纹理回退，未验证前不作性能声明。

## 后续调度修正（实现前追加）

`browser-hardware-repeat` 复测仍失败（阻塞窗口4次出版、要求至少5次），不能只报告前一轮通过。既有物理 Worker 在补算循环中只处理输入和yield，完整状态一般等最多6个固定步全部结束才发布；GPU争用/CPU调度导致单步 wall cost 增加时，物理接近60Hz不代表出版也接近60Hz。

尝试在已有8ms协作yield边界发布已完成的状态：优先交给现有 motion 小槽；完整捕获距离上次捕获起点至少一个目标周期才尝试，沿用显示/网络在途槽、原大小限制和消费回执。普通尾部、终局和单步算法不变，不增加物理步、不删除积压、不给过期回执授信。该共享完整状态路径同时适用于LAN/Steam；不借此把Steam motion标为已实现。

验证实际 `step()` 函数的6步补算/中途停止/终局/slot背压/不额外yield，默认路径浏览器压力与吞吐，诊断记录实际中途出版次数。若增加编码开销造成回归则保留失败证据并撤回本候选，不靠放宽断言通过。

## 中途捕获候选撤回与测量修正

`browser-catchup` 实测中阻塞观测窗口没有发布/ACK进展，出现主机恢复预算失败，物理中位55.098Hz、客机16Hz；未证明收益。已撤回所有中途完整捕获生产代码和开关，失败代码/单测/报告归档，保留四纹理批处理。旧压力测试还有时窗误差，不能从这一次断定唯一原因，但也不能将该候选默认交付。

压力测试现在记录明确测量起止、tick与随机seed（不冒充确定性A/B），排除阻塞和检查阶段的HUD样本；主线程阻塞以浏览器实际进入/退出时间为准，验证Node采样确在阻塞内；客机ACK按接收时戳记录，不再把可能延迟的evaluate查询当作阻塞期间收到。仍要求中间450ms至少5次发布，不放宽失败判定。

## 轻量间隙运动候选与断线错误（实现前）

只在已启动的direct I/O路径、既有完整固定步后的yield边界调用motionSnapshot；沿用motionEnabled协商、单槽回执、同tick去重与原字节限制，不增加完整世界捕获，不额外yield，不删物理债务。未协商运动的Steam/旧客户端保持原行为。新增实际产生次数诊断。保留原版固定步、伤害与终局顺序；网络通道属于扩展而非原版机制。

校准后的五人测试在全部ready前因持续过载失败，且发现close(undefined, "")转发给原生WebSocket会转换成非法code=0，导致Worker/native回退清理抛异常。这是单独可复现的网络关闭错误，不当作过载的唯一原因。修复无状态码关闭调用的实参数量；浏览器实测检查普通关闭和原生回退关闭，不放宽超时/恢复预算。

## 最终观测边界修正

五人 `browser-motion-five` 中 Playwright binding 回调延后到实际800ms阻塞结束后，校准断言成功拒绝了错误窗口；23次发布不能当作阻塞内证据。最终改为测试专用监听真实房主socket的message事件：原relay校验处理后，仅在room.lastSeq变化时记录接受时戳和tick；待浏览器返回实际起止后截取[start+200,start+650]，统计实际接受包数而非序号差，既不修改生产relay也不修改包内容。ACK仍用客机实际接收时戳。

`browser-motion-traced` 的时间窗有效，但五人22舰仍出现持续过载终止，窗口0次发布且无有效ACK进展，明确失败。三人22舰的此前校准窗口通过。保留失败，不增加恢复次数、不放宽最小5次发布要求。此轻量调度修正不是所有五人稳定60Hz的承诺。

## 轻量间隙推送候选也不默认交付

`browser-final-three-reconnect` 在重连前就已经过载停止（测量tick24→24），随后恢复同局超时，不能归为重连功能单独失败，也不能宣称三人稳定。尽管第一轮三人通过，单测也保持物理与捕获不变，仍不足以证明本候选在重载下有净收益/无回归。本轮撤回轻量间隙推送生产修改、开关与诊断计数，host.worker逐字恢复到已保留Phase17的试验前基线；候选代码和8项测试归档。最终只交付有独立像素/渲染工作证据的四纹理批处理、实际浏览器验证的关闭修复及测量改正。不放宽过载和断言来制造通过。
