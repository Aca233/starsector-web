# 多人慢链路控制隔离与排队修复（2026-09-21）

## 状态和范围

基线为 `d8566612834c8aeec63d574cb50b64900fd2bbf9`（已发布 v0.2.6）。这是后续**未提交、未发布**的传输修改，安装的 v0.2.6 不会自动获得这些代码。本轮没有打包，也没有混入生涯改动、修改 n2n / 防火墙或操作桌面。

用户三份会话的证据见 `network-multiplayer-session-v026-2026-09-21.md`。主机生产接近 60Hz，3–5 人大舰队下各客机交付差异很大，不能将问题归为统一渲染限帧。日志没有给出逐连接真实线速/丢包，不能断言 n2n supernode 是唯一原因。

本轮两个生产改动均为 LAN WebSocket 路径；独立通道由**桌面 LAN 桥**自动协商，普通浏览器仍走原路径。队列改动适用于已有消费额度协商的 LAN 客机。Steam 协议/传输未修改，不能将这些结果当作 Steam 修复证据。

## 1. 独立小控制通道

- 新增 `server/LanControlLane.mjs`，同一用户选定的主机、同一端口的 `/lan/control-ws`，使用第二条 TCP/WebSocket。没有服务器任意指定目的 URL、重定向或额外监听端口。
- 主连接通过原 hello 后才签发一次性 256-bit 随机 capability，10 秒过期、最多 64 个；Host/Origin 仍通过原服务的升级检查。主连接关闭/替换时撤销授权和附属连接。
- 入站只允许 `input`、`ping`、`state-consumed`、`sync-ready`；出站只有 `pong`、`controls-ready`。后者仅为原有战斗同步确认，不是新房间生命周期通道。快照、房间命令和终局仍走原通道。
- 入站重新进入**同一个主连接消息处理器**，复用 match/sync/席位/序列、动作水位、160 条请求预算和精确消费额度校验。没有第二套宽松的授权逻辑。
- 禁止压缩、二进制、超出 16KiB UTF-8 的控制消息；已排队控制写入以 32KiB 为界。超过限制的服务端回复回退到主通道，不截断内容。
- 桌面桥拨号 3 秒/握手 4 秒上限。对端不支持、反向代理拒绝、连接关闭/错误或发送堵塞时使用原连接；这不是放宽游戏掉线超时。
- 额外保留三种幂等控制各自最新的一条（总上限 48KiB），在附属通道失效时回退一次到主连接。避免“TCP 本地 send 成功、最后消费 ACK 却未到权威端”导致额度永久等待。消费 ACK 累计释放仍要求精确的已发送序列，重复输入/动作由原水位去重，未伪造 ACK。
- `welcome/launch/left/ended` 及主动离开清除旧回退缓存；收到 `controls-ready` 则移除待确认的同步请求。

### 测量口径必须保持

应用 `pong` 现在可能从独立通道回来，其 RTT 与快照 TCP 的延迟**不再是同一路径指标**。原生 WebSocket ping/pong 探针仍留在快照通道，原来的 idle 基线、拥塞 RTT 和探针来源检查不变，不能用更快的应用 pong 扩大快照窗口。

输入序列的权威执行确认仍包含于快照；本轮不等于完成了输入到画面全过程的低延迟改造。新通道也不能绕过两条 TCP 共用的 ISP/n2n 外部 FIFO 瓶颈。

日志增加每个 receiver 的 `controlLane.active/received/sent/fallbacks/bufferedBytes`。脱敏白名单不允许记录 capability、URL、身份或连接对象。

## 2. 仅在慢且已拥塞的路径减少旧快照排队

`SnapshotDeliveryWindow` 保留原来的拥塞检测、恢复迟滞和 idle 上限。只有测得队列膨胀，且 `idleRTT × 实际交付Hz < 0.5 帧` 时，使用两个总在途槽，而不是 `ceil(BDP)+2` 得到的三个槽。其余路径不改。

- 不是统一两帧上限；此前该方案会损害 4Mbps 交付，已放弃。
- 不降低模拟或目标发送 60Hz，不改数值精度、快照内容、断线超时。
- 不丢弃已入队状态、不伪造消费、不无限重传；旧额度必须由真实 ACK 排出后才可再发送。

### 真实录制的限速 TCP 回放（队列修改，不含独立控制通道）

使用既有冻结的 22 舰、241 个连续完整快照录制，实际压缩 WebSocket、生产增量编码器/接收器、独立收发进程、60ms 基础 RTT、固定 offered 60Hz；每次逐字节恢复校验。每档按 **旧→新→新→旧** 顺序运行 10 秒，排除头 2 秒。以下不是 FPS、真实互联网或实机联机数据。

|下行限速|旧实际交付 Hz（两次）|新实际交付 Hz（两次）|旧状态年龄 P50 ms|新 P50 ms|旧 P95 ms|新 P95 ms|
|---|---|---|---|---|---|---|
|1Mbps|3.750 / 3.750|3.625 / 3.625|796.1 / 766.8|517.1 / 515.8|1027.0 / 1025.0|1031.9 / 1035.0|
|2Mbps|9.000 / 9.000|8.750 / 9.125|282.2 / 281.8|192.5 / 236.3|331.5 / 331.1|303.4 / 302.5|
|4Mbps|19.750 / 19.875|19.750 / 19.625|143.2 / 142.8|143.1 / 130.3|188.6 / 180.6|189.6 / 179.7|
|32Mbps|46.000 / 46.625|46.125 / 46.000|50.5 / 50.2|50.2 / 51.0|54.3 / 54.6|54.1 / 55.4|

**取舍**：1Mbps 的状态年龄中位数下降约三分之一，但交付 Hz 下降约 3.3%，P95 没有改善；2Mbps 中位数/P95 改善；4/32Mbps 没有证明实质改善。不能只报道 P50，也不能把 32Mbps 的约 46Hz 写成 60Hz。保留此策略是为了减少最慢路径的旧状态排队，而非将其作为吞吐修复。

短录制循环会影响尾部，短回归也曾并行运行，存在 CPU 噪声。本机字节限速不模拟真实 TCP 丢包/竞争。状态年龄从发送方选择该快照时计算到客机解码/验证完成，不包含 GPU 呈现。完整数据和冻结旧窗口在 `artifacts/multiplayer-fix-20260921/queue-abba.json`、`SnapshotDeliveryWindow.before.mjs`、`LanStateCredits.before.mjs`。

## 未采用与仍待解决

- 树形差分、XOR literal、float32/定点量化的录制探针在低频大跨度或计算成本上不理想，没有接入生产。没有通过削减精度来“优化”。
- `CombatSnapshot` 已是 P1 呈现投影，不是全量可恢复模拟检查点。进一步减少慢链路字节需要审计字段消费者并拆分更新频率/静态变更，或实现可丢弃但可独立恢复的状态传输；不是改一个 Hz 常量。
- 本地 Node 的确定性回放不证明浏览器/架构间确定性；已有 lockstep 研究不能直接启用。
- **尚未解决 3–5 人大舰队在慢链路上的低交付 Hz 根因；未保证 60Hz 或彻底不卡。** 下一次真实复测必须同时比较实际接收 Hz、状态年龄/输入确认和快照路径 RTT，不能只看新的应用 ping。
