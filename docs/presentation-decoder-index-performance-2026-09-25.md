# 本地显示解码索引优化：验收与边界（2026-09-25）

## 结论
保留本轮改动：接收端不再每帧复制两份完整对象索引。真实200舰场景中，主线程解码均值减少约0.63ms（5.59%），解码P95减少0.74ms（4.93%）。这是局部、温和的收益，不是大规模模拟或整体尾延迟问题已经解决。

Worker往返加解码的均值减少1.02ms（1.16%），但P95增加0.60ms（0.58%）。**本轮没有证据宣称整体P95改善**，也不把单次配对结果称作跨机器、多轮统计显著结论。优化总目标继续保持未完成。

## 改动与不变项
生产改动仅 `src/engine/runtime/local/CombatPresentationDecoder.ts`：
- 用“本包plans覆盖旧索引、removed视作不存在”的只读查询替代完整candidate Map复制，并精确维护候选数量。
- 在完成全部验证后，将新Entry暂存于Plan；先分配、写入、重绑定，再就地提交原objects Map，去掉完整next Map复制。
- 保留旧Entry直到字段删除/写入、长度变化typed array的未更新父引用重绑定完成，维持对象身份与索引插入顺序。

没有省略完整可达图、边、元数据或预算验证；未更改协议/epoch/revision/tick、危险属性拒绝、keys复制、元数据管理和视觉包处理。非法包在任何显示状态修改前被拒绝，并且不消耗revision。原实现和新实现都不承诺消费者擅自冻结显示对象或安装setter后任意写入异常的事务回滚。

未修改AI、物理、精度、更新频率、数量、特效、玩法/UI和联机协议；没有增加GPU compute。之前已验收的编码器优化、联机预检和其它任务生涯改动保留。

## 仍未解决与操作边界
- deliveredMs只是Worker往返时间与apply时间之和，不包含渲染/显示等待；不是实际FPS、网络RTT或输入到屏幕延迟。
- 模拟仍约54ms，明显高于60Hz的16.67ms预算。更高CPU占用率本身不保证收益，本次两默认世界仍因多核实测亏损退出。
- 未在公网、真实两台电脑、其它规模/混编/模组或多次独立重复下验证本次收益。
- 本地显示Decoder不是普通联机房主的编码路径，不宣称直接解决历史0.2.11日志中客机回压/ACK延迟。
- 全程后台文件工作、独立无头浏览器；基准结束关闭其Worker、浏览器和临时服务器。没有子代理、可见窗口、键鼠注入、暂存/提交/推送、发布打包或安装替换。
