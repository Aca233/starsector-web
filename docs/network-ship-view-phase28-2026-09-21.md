# Phase28：舰船网络视图纵向试点结果（2026-09-21）

## 结论
**试点已经实现并跑完两批对照，但性能验收失败，不接入默认LAN/Steam。** 这不是交付“已经降低延迟”的版本，也不是认定所有网络视图方案无效；被否定的是本轮具体实现：抽出27个基础字段，同时继续捕获/还原剩余P1对象树的混合方案。

## 做了什么
- `src/network/experimental/ShipNetworkView.ts`：固定27字段（运动、船体、生命周期标志、动态幅能），float64、不量化，变化位图，直接应用到原生对象，保留Vector2/FluxTracker等身份。
- 显式version/epoch/seq/base/generation；创建全字段、更新、删除、CRC；缺失基准拒绝，完整锚点恢复；已被可靠有序链路接受后才提交发送基准。单流可以共享捕获和编码，不冒充跨不同基准任意共享。
- 预注册舰船最多64个，ID最长128字节，报文128KiB上限；未知实体/错误代次/异常字段掩码拒绝。生命周期指**网络视图记录**的创建删除；不是新spec舰船生成、换装或舰船实例迁移。
- 视图字段仍在采样边界逐一读取并登记差异，**没有在模拟写入点实现push式脏标记**，没有消除轮询。
- 其余武器、护盾、装甲、系统等完整P1舰船字段保留，并计入捕获/编码/压缩/解压/应用成本，没有只跑一个运动小包后宣称完成全舰同步。

## 可运行入口
从仓库根目录执行：

```powershell
npm run network:check:ship-view
npm run network:benchmark:ship-view
```

输出在 `artifacts/network-stream-20260921/phase28/`。基准脚本正常生成报告时exit0；**性能是否达标必须看result.json的passed，不得把exit0当性能通过**。目前两批均为false。

## 实验设计和重要边界
- 同一段预记录的原生战斗轨迹：seed917，22舰，初始位置缩放0.2以在有限时长内实际交火；120步预推进，30帧预热、120帧计量。轨迹内有127–161枚实际弹体参与原生模拟。
- A/B→B/A→A/B，三轮配对；之后完整复测一批。静止单舰、交战单舰、22舰分别分发到3/4/5个接收副本。
- **3/4/5是离线接收副本数，不是三次真人房间测试。** 传送的切片不包含世界弹丸/特效；弹体只参与轨迹生成，不冒称弹体分发已优化。
- 两组均使用当前P1 codec、二进制、可靠有序字节增量；配置motionReference=true，但当前运动参考只覆盖FX/弹体，舰船切片实测motionDeltas=0。保留该路径的检测成本，不把它宣称为已测整场运动参考增量。
- 每条消息使用相同deflate level6及inflate；载荷包含候选新增字段包、CRC、合包头和剩余P1包，不含真实WS/TLS/Steam头和路由成本。这不是实际socket测试。
- 总耗时是**一份生产端工作加所有接收副本阶段耗时之和**，不是单机帧时间、RTT、FPS或用户输入延迟；不能用1000除这个数得到客机Hz。生产端capture包含候选剩余视图构造；fieldView单列采样/登记/字段编码。
- 测试适配器通过esbuild在测试bundle里导出当前P1私有pack/unpack；不修改磁盘上的CombatSnapshot，也不改应用入口。候选影子对象的浅拷贝、删字段成本未排除，这也是此版实现的负担。
- 事前门槛：每种负载、每一对都需总耗时P50至少降低10%，P95不恶化超过5%，压缩载荷不增加超过5%，且语义一致。门槛未在看到结果后修改。

## 结果：没有稳定收益
下表为每批三个配对的总阶段耗时P50相对变化范围；正数=候选更慢，负数=候选更快。

| 场景 | 首批 | 复测 | 压缩载荷变化（两批一致） |
| --- | --- | --- | --- |
| 静止单舰/1副本 | -16.65%～+11.72% | -6.97%～+10.01% | +54.46%（约50.56→78.09字节/消息，绝对增量约27.53字节） |
| 交战单舰/1副本 | -8.74%～+5.08% | +4.59%～+18.45% | +2.32% |
| 22舰/3副本 | +1.51%～+11.39% | -1.74%～+8.86% | +0.098% |
| 22舰/4副本 | +0.60%～+7.36% | -2.96%～+11.13% | +0.098% |
| 22舰/5副本 | -4.93%～-0.50% | +2.42%～+5.72% | +0.098% |

复测4副本某轮候选P95出现明显尖峰（约59.66ms，而对照25.09ms）；原样保留，未删样本，不能仅凭这些阶段计时断言是GC、系统争用或某一函数造成。

阶段账本也没有显示出接收端主成本被消除。例如首批3副本第一对：对照capture中位约1.30ms，候选剩余capture约2.01ms，另有fieldView约0.33ms；三个接收端decode/apply仍合计处于约9–10ms量级。这些分项中位不能直接相加当总P50。

**可得出的结论：** 少量字段拆分确实能省掉这些字段的重复还原，但本版新增视图构造/编码/解码，加上未迁移的P1递归工作，未换来整体收益；静止状态还多了一份空字段消息头。不能把首批五副本的小幅改善挑出来作为成功。

**不能得出的结论：** 整个网络视图架构都没有价值、所有push式变更登记都没用、GNS没有意义、或真实LAN/Steam Hz已经改善。本轮没有实现这些完整方案。

## 正确性与失败记录
- 29项试点测试：精确字段及负零、无权威/RNG修改、原生对象身份、字段单独变化、回压未提交、丢基准恢复、epoch/顺序、创建删除代次、重复ID、CRC/版本/掩码/截断/NaN/布尔非法值、资源上限、引用、压缩往返、全部P1舰船状态及插值/UI getter一致性。
- 早期测试fixture只有两艘手动舰，未真正开火，断言失败。改成有AI、近距离的原生战斗fixture后通过，未删除“必须有真实弹体”断言。
- 最初基准还发现旧codec某些数字路径将-0规范成+0。因此完整未迁移P1部分按**原有编码后的精确合同**比对，独立字段协议仍另测负零精确保持；没有因此降低精度或改原编码器。
- 第一批保留原始日志、逐tick数据、源bundle及校验表；复测额外将轨迹保存为`trace.v8`并往返校验，保留负零，避免JSON轨迹丢失该信息。
- `benchmark-final/result.json`和`benchmark-recheck/result.json`全部保留。实机/跨机/Steam/n2n/WebGL没有在本轮执行，不使用旧阶段截图替代新验收。

## 下一步应改变什么，而不是马上发布
1. 不把这版混合字段流加入默认链路；先保留为对照与回归工具。
2. 后续若继续，应优先消除接收端真正昂贵的组件/武器对象树解包与还原，并避免每帧创建影子图；不能仅继续增加几个基础字段，或直接安装Colyseus就预期变快。
3. 对完整组件网络视图，仍要检查同版本原生对象、武器/组件顺序与生命周期、修改版扩展字段、缺失基准、回压与恢复；通过总账本才接通真实LAN，再单独验证Steam/GNS，避免同时改变多个变量。
4. 不动生涯模式、不提交、不推送、不打包、不发布，不影响当前游戏默认行为。
