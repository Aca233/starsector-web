# Steam 浏览器联机（协议 v17 / Spacewar 开发联调）

## 已实现的运行方式

仍然是浏览器游戏，没有 Electron 窗口。每台电脑的轻量 Node 启动器调用原生 Steamworks，监听本机 HTTP/WebSocket；浏览器只连接自己的启动器。房主的浏览器 Worker 运行权威模拟，启动器复用局域网房间核心处理权限、准备、配装、分队、输入与快照，再通过 Steam P2P 转发给客机启动器。没有部署到 Valve 的战斗计算服务器。

局域网版保留：它与 Steam 共用房间和战斗逻辑，但连接入口、身份和房间命名空间隔离。Steam 玩家不能拿六位房间码从 LAN socket 绕过 Steam 大厅身份；恢复凭证还绑定 SteamID 和 Steam 大厅 ID。

## 源码运行

- Windows x64，Node.js 22+（便携打包要求）和 Steam 客户端；每名玩家须登录自己的 Steam 账号。
- 首次执行 npm install，之后执行 npm run steam（构建并启动）。已有同一构建时可执行 npm run steam:serve。
- 默认 Spacewar AppID 480。自己的 AppID 可通过 STARSECTOR_STEAM_APP_ID 或 --app-id 参数设置。480 是官方示例 / 联调身份，不是正式发行许可。
- 默认只监听 127.0.0.1:32102；冲突时尝试 32103–32111，不终止其他程序。重复启动匹配版本时复用已有启动器，不抢占已经连接的浏览器页面。
- 浏览器访问启动器给出的 ?view=steam 地址。网页不能独立替代本机原生接口；Steam 不在线时保留网页排错与重试入口。

## 玩家操作

1. 每个人拿同一份包，打开 Steam 并登录，再双击「启动 Steam 联机.cmd」。本机组件隐藏运行，浏览器自动打开。
2. 房主创建好友房间或公开测试房间。进去后仍是原来的房间侧栏和中央改装台。
3. 房间 → 邀请朋友 → 复制完整 Steam 房间号；朋友在自己的入口粘贴并加入，有密码时另外填写。
4. 不发送本机 127.0.0.1 地址，也不发送侧栏的六位 LAN 编号。房间列表只显示相同游戏标识和构建的公开房间；480 共享环境下列表可能不完整，优先使用房间号。
5. Steam 邀请回调会预填房间号，玩家确认后才加入；不自动退出正在玩的房间。普通浏览器不支持 Steam 覆盖层，使用复制房间号。Electron 桌面版已接入窗口主进程浮层与真实可用状态检测，见 [桌面邀请说明](electron-desktop.md#steam-好友邀请)。
6. Steam 大厅最多 10 人；游戏房间可以设置 2–10 席位，实际容量由房间核心校验。AI 不占真人席位。
7. 离开房间后可点击「退出启动器」。仅关闭浏览器不会自动关闭本机组件。运行中的其他 LAN 房间也会阻止无意停止启动器。
8. 可在 Steam 入口或主菜单明确选择局域网，此时才启动可供其他电脑访问的 LAN 监听。不会自动修改防火墙、登录账号、注册开机启动或修改 Steam 安装文件。

## 分发

npm run package:steam 生成新的 Windows x64 ZIP，默认启动项为隐藏的 Steam 浏览器启动器；也包含「局域网联机.cmd」「单机试玩.cmd」「诊断 Steam 联机.cmd」。无需另装 Node/npm/Electron，需自行安装并登录 Steam。普通 npm run package:windows 仍输出原来的 LAN 便携包。

源文件由 esbuild 依赖图收集后原样复制，原生 steamworks.js 模块和 Steam API DLL 随包放置。不会带入个人浏览器资料、Steam 凭证或游戏存档。游戏资源与 Steamworks 的授权要求仍由各权利人决定，不因生成 ZIP 获得商业发布权。

## 传输与安全边界

- 当前原生绑定是 steamworks.js 0.4 的 ISteamNetworking P2P 可靠消息接口，不是声称已接入 ISteamNetworkingSockets / 专用 SDR Hosted Server。Steam 处理连接及可用中继，不保证具体路由、低延迟或所有网络一定可达。以后替换现代 Steam Networking 接口时，可以保留房间核心和浏览器 UI。
- 不发送超过 SDK 限额的单个消息：按 32 KiB 分片，较大数据使用 deflate level 1 压缩；同一广播快照共用压缩结果。当前源码的每个客机从 4 帧启动，按 ACK 排队反馈在 2–32 帧间调整（基线探测期间临时 1 帧），同时始终限制合计 64 KiB 压缩负载；单帧超过窗口时只允许独占发送，仍受原消息上限约束。窗口满时跳过新快照，不缓存旧帧待发；窗口由具体帧的 ACK 释放，避免旧版每个 RTT 只能收一帧。慢玩家不拖慢所有人的分发。
- 每条消息遵守原有 16 MiB 展示快照预算（传输封套另留少量余量）；重组总内存最多约 32 MiB，限制并发消息数、分片元数据、解压输出及 8 秒超时。恶意分片不会按声明长度无限分配。可靠传输仍可能队头阻塞，不等同于 UDP 回滚网络码。
- 只有当前大厅中被 Steam 标识的成员才能触发游戏消息；客机只能连接固定房主。namespace / build / protocol / owner 必须一致，所有权变化明确结束而非悄悄转移模拟。第三方 Steam 测试大厅不会被当作本游戏房间。
- 原生操作只接受本机同源、带专用请求头的 POST；WebSocket 校验 Host、Origin、大厅标识与单个活跃网页约束。不给网页任意原生调用能力，也不读取 Steam 登录凭证。
- 延用最新完整帧确认后再恢复控制的弱网门禁。普通浏览器断线可在 30 秒内续接，房主刷新导致 Worker 丢失仍不能恢复。Steam 退出登录、大厅被移除、原生组件退出或真正换主机不能保证续局。

## 验证与未验收项

已用临时 stdin 验证：分片乱序重组、压缩、超限元数据、缓存超时、邀请 AppID；模拟 Steam SDK 下的真实本机 WebSocket 大厅、房间权限、Steam/LAN 隔离、恢复身份绑定、分片快照/ACK、操作和续接。没有创建测试文件或测试运行器。

双独立 Edge 浏览器使用模拟 Steam 传输完成了：创建/加入 → 选择野狼级并应用配装 → 准备/开战 → 客机刷新恢复 → 房主结束 → 双方返回房间 → 离房/重建。确认房主创建 1 个战斗 Worker，客机不创建；邀请框使用完整 Steam Lobby ID，重复控制页面受限，非法号码不锁死操作；390px 入口无横向溢出。返回主菜单、未启动组件时返回、Steam 切换 LAN 及重复 LAN 启动合并均通过。页面未出现未捕获错误。

这些是流程验证，不是性能基准。默认无头渲染的双战列舰检查曾触发既有主机过载保护；改用 D3D11 无头渲染、1000×720 双护卫舰完成上述流程，不能据此承诺百舰流畅度。

TypeScript 类型检查、lint、生产构建和服务端语法检查通过（Vite 仍有既有大分块提醒）。已生成包含便携 Node、原生模块及 DLL 的 Windows x64 启动包。未运行 Steam 时，本机网页仍可访问，建房按钮禁用，重试显示真实错误，确认退出可停止组件。

原生 DLL 已实际加载。验证中有一次 SDK 短暂初始化成功，但随后本机接口未持续响应；重新探测时 Steam 未运行，返回“Cannot create IPC pipe to Steam client process”。已加入 Steam 断开/恢复事件的状态处理，并停止无大厅时的 P2P 轮询，但尚不能认定上述原生异常已在真实连接下修复。

**真实 Steam 建房、两个账号间 P2P、跨网络及 Valve 中继均未验收。** 当前包是开发联调包，不应把模拟通过当作实际 Steam 成功；下一步需保持两台电脑的 Steam 登录和启动器运行，实测邀请、准备、开战与断线恢复。

## 2026-09-19 第一轮桌面版高延迟／断线修复（固定窗口测试包）

- 0.2.1 发布包仍是单帧 stop-and-wait。新的有界流水窗口只改 Steam 分发，不改变 60 Hz 物理／捕获目标，不改变普通 LAN WebSocket 的背压策略，也不提高原有 8 秒 ACK、10 秒前端心跳、30 秒重连阈值。
- 合并已有但尚未发布的前端心跳修复：有有效消息但未成功发出探针时，不再因旧 pong 时间误判掉线。已经发出的探针不响应和真正静默仍断线。Worker 补步间让出任务队列的修复也包含在隔离测试包中，不包含其他开发中的舰船／配装改动。
- 桌面日志新增每 15 秒的 `[steam-transport]` 指标和断线／结束事件：ACK 往返、在途帧数、压缩负载、最老 ACK 等待、收到状态数量、Steam 断网回调、后台网页关闭码及战斗结束原因。日志不写 Steam ID、聊天、输入或快照正文。指标里的 skippedStates 仅统计 send 内部拒绝的帧，不包括 relay 在发送前跳过的帧；ACK 时间包含本机转发／排队，不能当纯线路 ping。日志仍按桌面程序既有 2 MiB 规则轮转。
- 回归：`node --test scripts/check-steam-transport.mjs scripts/check-steam-overlay.mjs`。受控模型覆盖 200ms RTT、128Kbps 限速、1500ms 可靠链路停顿、ACK 乱序／重复／旧连接、8 秒失联、消息发送失败与字节窗口。旧窗口与新窗口使用同一代码、仅 credit 数不同作对照，不是两个历史发布包的实网基准。
- 模型中约 2.45 KiB 的状态包，在 200ms RTT／1.024Mbps 下由约 4Hz 提升至 17Hz；128Kbps 加 1500ms 停顿后恢复，窗口不超过 4 帧。真实战斗负载与结果可能不同。仍使用可靠 P2P，丢包时仍会队头阻塞，不能保证 60Hz 远端显示或消除物理网络延迟。
- 这不是双账号跨网验收。用户报告的此次断线缺少当时的传输指标，不能断言其唯一原因；本轮补齐可测缺陷与后续取证。

## 后续：自适应窗口与输入积压（2026-09-19）

当前源码已合入客机可靠输入队列：最多 32 条未确认消息、256 KiB 线速字节阈值及有界待发 FIFO（单条大消息可独占越过阈值）。只合并相邻、尚未交给 Steam、无动作边沿的移动输入；动作、控制、非法消息、旧序号和 match/sync 边界不能被合并。主机收到客机数据时回复独立 ACK，旧 nonce／重复 ACK 无效。必须双方使用含此辅助进程的同一完整新构建，不能只换网页或混装后端。

固定 4 帧只是第一轮安全修复。当前源码的状态窗口按 ACK 延迟反馈缓慢扩大或收缩；**64 KiB 状态负载上限并未提高**，不通过积压大批旧状态来伪装高帧率。排队估计类似 Vegas，但它只是应用层 ACK（包含本机／网络／网页转发），不是 Steam 原生 RTT 读数。30 秒时间桶保留 RTT 下界；下界持续升高时先排空并测一个独立状态，再接受新基线，避免把长期积压学成正常延迟。真正失联阈值未放宽。

`npm run steam:check` 现在同时运行持久化的浮层、状态窗口、输入队列回归，不依赖 artifacts 中的旧源码。模型覆盖高 RTT、低带宽、3 秒可靠链路停顿、限流恢复、动作 FIFO、旧 ACK、清理、限速突变和 120 秒虚拟持续运行。具体范围和实测记录见 `docs/steam-adaptive-transport-2026-09-19.md`。第一轮 ZIP 仍保持原样，不含本节的后续变更。

## 后续：无损状态差分（2026-09-19）

当前 Steam 源码进一步降低真实战斗状态带宽，而不是扩大在途队列。辅助进程用前一条成功发送的完整状态作差分基准，客机校验并还原完整 JSON 后才转发给网页；每秒关键帧、基准丢失主动请求完整状态、旧 nonce／重复 ACK 防护均有回归。状态／补丁超出预算或压缩收益不足时发送完整状态。物理、输入语义、64 KiB 在途预算及失联保护保持不变。

生产编解码器回放 80 条合成双护卫舰开火的真实游戏状态，包含周期关键帧和分片头，流量减少约 71%，全部逐字 JSON 还原；这不是双账号 Steam 实网结果。`npm run steam:check` 新增持久化差分测试，设计、证据及未覆盖项见 `docs/steam-delta-transport-2026-09-19.md`。务必双方更新同一完整构建后重建房间，不能仅替换网页或混用旧辅助进程。

## 未发布候选：多人共享主机上行（2026-09-19）

当前工作区正在验证主机总 ACK 字节预算、保留等待者额度的发送顺序，以及按开销安排的完整检查点。三个本地前端的真实游戏流程与多个共享链路模型已通过，但新增九客机／300ms RTT／8Mbps 突降 256Kbps 的门禁仍失败：该阶段 `steam:check` 为 43/44，通过数量不能掩盖这项未解决的掉线。因此**这些后续源码不能称为已验收发布版，v3 ZIP 保持原样**。实验、采用／拒绝方案和下一步范围见 `docs/steam-shared-uplink-2026-09-19.md`。


## 未发布候选：原生会话诊断与锚点原型（2026-09-19）

当前源码补充 Windows x64 的只读 P2P 连接／relay／队列计数和原生失败错误码，不记录远端地址或身份，不用不明确的 Legacy 队列计数改变发送额度。Electron 与 Steam 便携打包显式包含诊断原生依赖，防止只在开发机可用。实验性可靠锚点差分仍未接入网关，不能简单把已有可靠 32KiB 分片改为 Legacy UnreliableNoDelay。

该轮新增回归后完整 `npm run steam:check` 为 **67/68 通过**，其中输入队列的 1,470 个断言已实际执行；唯一失败仍为上述九客机剧烈降速断线。类型／lint／离线 Windows 运行时导出绑定通过，**没有真实两账号跨网或新桌面包验收**。本轮范围、SDK 依据和未完成项见 `docs/steam-native-anchor-2026-09-19.md`。v3 保持原样。


## 未启用：Sockets v012 原生发送边界（2026-09-19）

固定匹配当前 DLL 的 v012 ABI，避免误用最新 v013 的 SendMessages 参数和所有权规则。新增三类优先级发送、原生身份校验和有界消息内存管理；15 项回归、815 个真实 C++／Koffi 离线断言通过。边界没有接入默认网关，也没有创建真实 Steam 连接；旧带宽骤降门禁仍未解决，v3 不变。现代 NoDelay 可拒绝新积压，但不是已接受消息的撤回保证。范围与后续连接管理需求见 `docs/steam-sockets-v012-2026-09-19.md`。
