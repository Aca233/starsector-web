# Windows 便携版自动更新

## 玩家使用

新版 ZIP 内的 `启动游戏.cmd`（Steam 包还包括隐藏的 Steam 启动入口）会在**启动游戏前**检查 [GitHub Releases](https://github.com/Aca233/starsector-web/releases/latest)。发现更高的稳定语义版本后，自动下载本包对应的 Multiplayer / Steam ZIP，核对大小和 SHA-256，解压到独立版本目录，再启动新版。

- 正在游玩时不下载或切换，也不覆盖运行中的 `node.exe`。同一安装目录的更新启动器使用进程锁；先退出旧启动器，再更新、回退或切换模式。不同解压目录之间不共享这个锁。
- 没有 Release、没有新版本、断网、GitHub 限流或下载/校验失败时，正常启动已有版本。元数据请求最多等待 10 秒；完整包下载最多 15 分钟。
- `检查更新.cmd`：只检查和显示版本，不安装、不启动游戏。
- `离线启动.cmd`：跳过网络检查，启动当前已选版本。
- `回退上一版.cmd`：只切换回上一版，不立即启动。再次正常启动即可；回退的问题版本被跳过，直到出现更高版本。
- 新版在启动后的 15 秒内异常退出时，自动切回上一版并尝试启动。正常退出/用户通过启动器中断不触发回退；这不是完整的游戏健康诊断。
- Steam 隐藏入口的进度写入 `.updates/launcher.log`；也可用 `诊断 Steam 联机.cmd` 查看。
- 浏览器方案库在浏览器存储中，更新器不读写它。保持原浏览器、IP、端口，才会使用原方案库；临时战斗状态不会跨重启保存。

始终使用**最初解压目录**中的启动脚本，不要在 `.updates/versions` 中直接启动另一套更新器。安装目录应当可写；存储目录不可用时会尝试跳过更新、运行基础包，不提权或修改权限。旧版本和失败下载会保留，需预留完整 ZIP 加解压目录的空间，不自动清理用户文件。

### 旧包如何迁移

此前没有更新器的 ZIP 不会凭空获得此功能。先手动下载并完整解压一次包含此功能的新包，然后使用新包的启动脚本。相同浏览器地址上的方案仍然保留。开发源码、`npm run dev`、原版游戏目录和非 Windows 包不在自动更新范围内。

## 开发与发布

当前基础版本为 `0.1.0`。自动更新使用严格递增的稳定版本 `x.y.z`，只读取正式 Release，忽略草稿和预发布，不按提交时间或打包时间判断新旧。

本地打包（Windows x64 / Node 22+）：

```powershell
npm ci
npm run package:windows -- --version 0.1.0
npm run package:steam -- --skip-build --version 0.1.0
npm run release:manifest -- --version 0.1.0
```

打包器写入 `portable-manifest.json` 的版本、构建号和更新协议；产生 ZIP、开发报告和 `*.update.json`。清单工具再次核对 ZIP，合并两种包到 `artifacts/releases/windows-updates.json`。同一版本/类型只允许一个候选包；如多次打包，用干净的输出目录制作正式发行，不要混用同版本的多套结果。

提交代码并推送后，推送对应版本标签会触发 `.github/workflows/windows-release.yml`：

```powershell
git tag v0.1.0
git push origin v0.1.0
```

工作流在 Windows 上安装依赖、Lint、构建两种 ZIP、生成清单，先上传到**草稿 Release**，所有附件上传成功后才公开。它不会覆盖已有 Release；上传失败留下的草稿应由维护者检查处理。也可以通过 GitHub Actions 的手动入口选择已有稳定标签。后续例如发布 `v0.1.1`，客户端才会从 `0.1.0` 更新；仅推送普通代码提交不会触发客户端升级。

Release 必须同时附带：

1. `windows-updates.json`（仓库、版本、两种包的附件名/大小/SHA-256/构建号/协议）；
2. 清单中指定的 Multiplayer ZIP；
3. 清单中指定的 Steam ZIP。

仓库固定为 `Aca233/starsector-web`。若 fork，应先修改代码中的固定仓库与发布工作流限制。不要上传开发报告 JSON（其中有本机路径）；工作流只上传两个 ZIP 和公共更新清单。原版游戏素材和 Steam 开发 AppID 的授权限制仍然适用，更新机制不授予新的分发权限。

## 安全和恢复边界

- 不接收网页/LAN 请求控制更新，没有公开安装 API；只由本机启动器操作。
- 仅从固定仓库的指定版本附件下载，所有请求只允许 GitHub HTTPS 与官方附件 CDN，不携带 GitHub token、不降级到 HTTP。
- SHA-256 校验的是完整 ZIP。清单与 ZIP 都受 GitHub Release 账号的信任保护，**不是独立的代码签名或防账号被盗方案**。
- 流式下载、ZIP 大小/展开总量/文件数上限；拒绝路径穿越、绝对路径、Windows 特殊路径、重复文件、链接、特殊设备和加密条目。仅解压到新的空目录。
- 完整校验包结构、构建号、版本和类型后才原子切换 `.updates/state.json`。中断下载不改变当前版本，原包和上一版均保留。
- `.updates/versions/<随机标识>/Starsector-Web` 为不可覆盖的安装目录。基础引导器协议版本为 1；不兼容的新引导器协议需要手动重新解压完整包。
- 普通崩溃留下的启动锁会核对主/子进程均已退出后恢复，不终止任何未知进程。极端断电导致锁文件未完整写入，或留下 `lock-recovery` 时，请先确认该目录的启动器和 Node 服务都已退出，再手动移走相应锁文件。PID 被其他进程重用时保守地拒绝抢锁。
- 不安装服务、不注册开机启动、不改防火墙、不提升权限，也不在游玩过程中热替换服务器或网页资源。
