# Phase10 — Steam Sockets 整帧准入、真实大包回放与测量纠错（2026-09-21）

## 结论 / 生效范围

**未完成“彻底解决延迟/客机Hz”。这不是可发布的架构定稿。**

本轮只修改网络传输实验与后台验证，不修改权威玩法、画面、Steam/n2n/系统设置，不启动可见窗口，不触碰或发布生涯内容，没有提交、推送、打包或发布。

`SteamSocketRoom` 仍只由离线 fixture 注入；正式 legacy Steam 路径没有被切换成本轮实验。LAN Phase7/8 分层通道仍默认关闭，LAN 五人完整世界约2736ms的 P95 陈旧问题没有因此解决。本轮也没有把完整世界吞吐叫作客机渲染FPS或权威物理Hz。

## 发现与保留的修复

1. **部分整帧同时开始，最终谁也收不齐**：每个客机轮流得到大快照的一两个片段，500ms lossy组装期限到达前无法完成；小数据测试看不到这个问题。先完成一个多片大状态的SDK准入，再轮到下一个；排队顺序保持FIFO，防止某个peer在每次释放位置后再次抢跑。单片状态与控制仍可使用剩余额度。
2. **可靠状态启动计时过早**：九个可靠anchor同时开始后，在共享链路崩塌时互相等待，导致八秒发送保护到期。可靠状态也使用同一准入所有权；没有延长超时。
3. **拥塞窗口恢复死区**：24576B最低窗口只能容纳两个8256B片段；若在扣除回执字节后才判断50%使用率，剩下8256B永远不能满足恢复条件。保留一般增长规则，只在窗口小于三个当前片段且确有未清债务时，使用这次真实回执前的利用率作为恢复证据。一个应用限速包清空所有债务不能证明需要扩大窗口。
4. 窗口上限128KiB→200KiB，起始49152B、最低24576B、peer49152B、packet2048及native pending限制不变。增长必须由实际经过认证的接收回执驱动。取消/过期/关闭仅释放排队资格，不清除不确定的在途债务。

涉及：`server/steam/sockets-flight-budget.mjs`。新增所有权/恢复/公平单测在 `scripts/check-steam-sockets-flight-budget.mjs`；既有保护断言没有放宽。

## 不能把测试模型当 Valve 实现

`steam-sockets-link-model.mjs` 使用真实room/session/wire/pacer，但SDK、拥塞控制、物理链路、ACK都由显式模型提供，**不是 Valve 算法或真实 Steam 路由**。

发现历史模型将包含40ms接收端ACK批处理的往返时间与60ms纯传播RTT比较：空链路也能被误判拥塞。仅改成最小观测ACK RTT还不够，连续大小混合包的batch wait不同。

保留历史模型作为默认，新增敏感性模型：
- `observedAckFloor=true`：以观测下界校准；
- `compensateAckDelay=true`：仅减去本次ACK在接收端的显式batch等待，不减去传播、序列化或FIFO时间；每个ACK持有独立batchDelay，重复包不能修改已发出的ACK样本。

真实录制benchmark默认同时启用这两个选项。新增单测验证空链路、持续大小混合负载、完整JSON还原。两种模型都不是实机网络结果。修正模型后旧发送器仍出现长时间没有完整状态，不能把失败全部归因于模型。

## 真正完整的22舰录制回放

脚本：`scripts/benchmark-steam-sockets-recording.mjs`。
输入：`artifacts/network-stream-20260921/particle-paired-exact/recipe`；本轮工件均位于 `artifacts/network-stream-20260921/phase10/`。

每帧仅重标tick/seq/产生时间及校验marker；其余完整世界内容不删减。每次收到完整状态，都对整个JSON与发送端SHA-256比对，不能只靠marker/tick检查。使用一条共享主机FIFO、独立guest上行、原生pending/在途与应用在途独立计费。

新增**观测陈旧时间**：每20ms采样最后一份完整世界的年龄，包含两次到达之间的等待。旧的“成功收到包时的年龄P95”会把客机十秒没更新藏掉。两者均不包括真正apply/render、插值或input-to-photon。

### 快网反例：不能隐藏吞吐代价

五人/32Mbps/RTT60ms、同一录制：
- 原预算：前三客机4.6/4.6/4.8Hz，第四客机0.8Hz；观测陈旧P95前三484–500ms，第四3164ms。
- 串行FIFO：各客机1.4–1.8Hz、观测陈旧P95约980–1000ms。
- 公平性/最差客机改善，但总吞吐下降，快的客机也更慢，**不能当作无代价最终方案**。文件：`actual22-fast-original.json`、`actual22-fast-final.json`。

尝试过按回执增长窗口允许1–4个并行大帧：`flight-adaptive-rejected.mjs`。4Mbps回放再次退化到0.6–1Hz、观测陈旧3120–5224ms；已撤回，未进入保留代码。相关`actual22-*-adaptive*`只是失败试验，不得用于最终收益宣称。不能继续用阈值放宽把此问题“调绿”。

## 其他失败试验（保留工件）

- 224KiB上限及更大最低窗口：健康吞吐提升，但弱网年龄/九人带宽崩塌失败，曾导致全员断线。
- 192KiB及guest16ms回执：弱网回归；回执间隔已恢复guest40ms/host100ms。
- 原本只序列化可靠anchor：小包门禁可全部通过，但真实大世界仍停滞。
- 多片大帧没有FIFO轮次：部分客机帧数27，另一位只有7；补FIFO而不是提高显示Hz。
- 首版large-state测试本身只生成了约25KiB压缩数据，未达到要求的≥5片断言；增加真实fixture负载而不是降低断言，最终约60KiB压缩大状态。失败日志保留。

## 验证与尚待工作

`npm run steam:check` 已纳入模型和大状态检查；最终准确计数/文件在下方补充。大状态回归使用完整合成内容（不是执行游戏），要求每个客机完整字节正确、每5秒窗口无长时间冻结、各peer进度公平、回收无内存/在途泄漏；未修改既有九人健康/崩塌/重排/120秒浸泡门槛。

继续架构工作的关键不是让每客机60Hz收整份世界：
1. 将稳定roster/baseline与运动、关键战斗、武器/装甲/系统、弹体/FX等有依赖的组件拆开，明确时钟和重同步规则。
2. Steam与LAN复用组件语义和共享预算调度，不只是复用codec；不能让大块世界阻塞小型即时战斗数据。
3. 大状态需要弱网完成性与快网并发兼得的调度，不能长期串行全部大包，也不能不受限并行后集体过期。
4. 保留完整世界1500ms断流/重同步保护，直到真实apply/render以及其它战斗组件已经覆盖；不要通过取消保护来掩盖停滞。
5. 再做真实多机Steam/n2n/不同硬件下的3/4/5人测试。当前实验完全不能证明这些环境已稳定。
