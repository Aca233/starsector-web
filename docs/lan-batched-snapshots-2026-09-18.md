# 联机快照批量记录优化（2026-09-18）

## 范围

继续降低同步处理和传输开销。不修改物理 dt、伤害/AI 规则、舰船与特效数量、SnapshotPlayback 或 MotionPrediction；不放宽恢复预算。保留 3005，以及其他任务的 3006 和此前的 3007。仅修改 CombatSnapshot.ts 与协议版本，未覆盖其他并行任务的 UI/AI 修改。

## 实现

- 一组具有完全相同字段布局的对象，不再逐行发送 `{ $record, values }` 包装，改为一个 `{ $records, values: [rowValues, ...] }`。沿用每帧自带的 layouts，不依赖上一帧，重连仍可直接还原完整状态。
- 数组顺序、行内每个值及浮点精度保持不变。混合类型、不同布局、空数组、单元素数组和稀疏数组保持原格式。稀疏数组检测使用 for-of，避免 Array.every 跳过空位后误判为同型记录。
- 解码按原有索引复用目标数组/组件，缩短数组时同步截断，保留 Ship、Vector2 和组件原型、Ship 引用及 typed-array 语义。
- 向量、单条记录等常见解码分支先处理，批量记录检测放在其后，避免每个坐标额外承担一次批量标记查询。最初把批量检测放在前面的版本，测得还原阶段回退，未作为最终版。
- 舰船根对象直接枚举自身字段，省掉每帧的临时展开副本；嵌套 Ship 仍编码为引用。world / ship state 根字段继续具名，满足服务器检查和显示时钟读取。
- 保留字段字典的数量、键名、危险字段校验及 64 层嵌套限制；批量记录另检查布局编号、values 类型和每行字段数。
- 协议从 19 升至 20。新读取器仍可解码上一版单条记录；联机握手仍按协议和构建号阻止混用新旧客户端。

## 同帧测量

8 艘守护者，tick 2340 的同一交火状态，预热 35 轮，再交替新旧执行顺序测量 120 轮。旧格式指上一轮已经启用字段字典的版本，并非最早的未压缩 JSON。

| 项目 | 上一版 | 本轮 |
| --- | ---: | ---: |
| UTF-8 快照 | 715,008 B | 678,126 B |
| 采集平均 | 3.45 ms | 3.31 ms |
| 编码平均 | 3.38 ms | 3.28 ms |
| 解析平均 | 2.79 ms | 2.50 ms |
| 还原平均 | 2.05 ms | 1.91 ms |
| 处理链平均合计 | 11.67 ms | 11.00 ms |

该样本体积进一步减少 5.16%，处理链均值减少约 5.69%。中位数分阶段合计仅约 10.10 → 9.90 ms，不能把均值收益当成稳定的整场 FPS 提升。较小样本（338,848 → 325,413 B）节省约 4%，处理链变化接近噪声；不是所有帧都获得同等加速。

记录：artifacts/lan-batched-records-benchmark.json、lan-batched-records-large-benchmark.json（中间解码顺序）、lan-batched-records-final-benchmark.json（最终版）。没有手工资源 hash/size 审计，以上测的是实际网络快照。

## 正确性验证

使用临时 stdin / Playwright 脚本，没有新增测试文件或测试运行器。

- 展开字段字典和批量记录后，与原投影逐字段相等；分别还原再采集，结果相等。
- 同型/混合/空/单元素/稀疏数组，undefined、NaN、Infinity、typed array、Vector2、Ship 自引用、循环普通对象，以及数组缩短均验证一致。
- 负数、越界、非整数布局编号，非法 values、非法行、错误字段数和危险字段名均拒绝。
- 两艘苍鹭及 12 艘动态战机：投影、还原与原型检查通过。
- 最终解码顺序再次验证还原结果与上一版相等。

记录：artifacts/lan-batched-records-validation.json、lan-batched-records-carrier.json、lan-batched-records-final-benchmark.json。

## 双端验证与限制

本轮修改前，3007 当前基线在同一浏览器双端和双独立浏览器中都跑满约 60 秒，无恢复或错误。这些对照带轻量 CPU 计时探针；计时探针约 1 ms/次，不能据此认定旧停顿已经定位。双独立浏览器的最初停止脚本被服务端重新同步拉起，因此只取 tick <= 3600 的首段统计，后续脚本修正了测试停止逻辑。

最终验证使用 3008 生产构建，不替换 Worker 源码，不加 CPU 探针。两端视口均 1600×1000，2 真人 + 每队 3 AI，共 8 艘守护者。通过实际导入/应用配装流程使用此前失败日志中的两份玩家设计；与原记录逐字段比较，所有战斗配装字段相等。房间开战通过已有 start 协议触发，因此这是完整战斗同步验证，不作为房间工具栏点击流程的验收。

- tick 3600，首尾快照墙钟 60,192.6 ms，计算推进约 0.9968×。
- 1094 个快照，最大 1,028,153 B；0 次恢复、0 次 Worker 错误、0 个 pageerror。
- tick 1800 后刷新客机，成功重新同步；随后客机 W 键输入到达主机并恢复操控。
- 末段 HUD：约 57 FPS、19 Hz 状态更新、1.00× 战斗速度。该 FPS 仅是此机器双画面实测，不是 FPS A/B 提升。
- 初次直接配置房间的尝试因编辑状态未确认而没有进入战斗；另一次工具栏流程也未得到进入加载阶段的确认，均未纳入性能结果。没有把准备阶段超时算作物理过载，也没有通过降低规模绕过。

记录：artifacts/lan-split-browser-60s.json、lan-same-browser-current-60s.json、lan-batched-live.json（准备阶段未通过）、lan-batched-live-fixture.json、lan-batched-summary.json。

此前数百毫秒物理墙钟停顿的根因仍未最终确认；不能用本轮一次成功宣称彻底修复，也不能把该结果推广为百舰/高延迟长时间稳定性保证。最大快照仍约 1 MB，远程带宽压力依然存在。
