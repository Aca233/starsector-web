# Phase55：纯五人掉速归因补测（非性能提升）

2026-09-22。沿用Phase54的5独立浏览器、5艘Onslaught、3对2、零额外AI、seed917、20秒预热/30秒测量。实际UI建房/加入/准备/开始，浏览器内部持续操控开火，无桌面输入。此轮仅改测试诊断，无游戏代码、构建、安装或发布；不涉及生涯。

## 先区分两次补测

1. `compiled-pure-five-profile`：房主Worker、房主/客机1主线程、Node同时CPU采样。客机1出现**显卡上下文丢失**并退出战斗，AI接管；五人条件不成立，最终缺少其测量期HUD，判FAIL。证据完整保留，不能把剩余四端的结果当成纯五人，也不能把它当作网络优化退化的证据。没有错误堆栈不代表没有运行失败：本次失败提示来自游戏界面。
2. `compiled-pure-five-relay`：针对失败，仅重跑既有场景的**Node侧采样**，关闭浏览器CPU采样器。PASS，五席位测量样本均5舰，存在真实弹体，零报错/上下文丢失，房主渲染线程800ms阻塞期间仍发布25帧，第5席位同局刷新后tick3209→3402。

测试入口新增WebGL上下文丢失观察；采样前和测量后都会明确检查。上下文丢失后的退出/AI接管不会再被笼统记成“缺少遥测”。新Node采样器只连接当前测试进程的inspector，不开放监听端口；始终关闭会话、定时采样及事件循环观察器。类型检查、oxlint通过；具体失败后的定向重查通过。两次浏览器和服务器均清理。

## 有效归因运行的数据与边界

**这不是优化A/B，也不是无采样基准。** Node进程同时运行转发服务和Playwright控制/日志传输；同机5个Chromium共享CPU、内存和GPU。采样负担与机器调度会干扰完整Hz，不可将结果和Phase54直接相减声称代码变差/变好。

- 30.005秒权威tick变化对应**60.190Hz**。这个短窗口会受起止tick和计时边界影响，不意味着修改了60Hz目标。
- 完整状态Hz：房主中位49、客机46/47/48/49；最低样本31–35。
- 画面FPS中位56.1–60.0；输入确认HUD平滑中位47.5–52.6ms。
- 这轮各端long-task累计计数有真实增量；它不同于Phase54部分席位计数全程不变的情形。不可把Phase54启动期134ms最大值算作测量期新卡顿。

Node CPU采样按**总采样时长（含idle）**归一化，inclusive项互相重叠，不能相加：

|归属|采样占比|
|---|---:|
|idle|46.00%|
|含LAN服务函数的调用栈|25.09%|
|含Playwright的调用栈|16.58%|
|转发元数据解码 `decodeBinaryStateForRelay`|8.59%|

未采到LanBinaryDelta/SnapshotMotionReference栈不能解释为所有网络路线都不使用它们。这里只报告本次采样覆盖，不据此改默认开关。

28个完整1秒Node事件循环区间，利用率样本中位0.661；10ms分辨率的调度延迟直方图P95中位17.02ms、区间最大值最高113.18ms。**这不是请求服务时间或网络RTT**，其中包括测试控制进程工作和OS调度，不能全部归咎于生产转发服务。

## 本轮结论

- 用户要求的纯五人场景应保留为主基线。Phase54不带CPU采样的59.898Hz物理、客机完整状态中位58Hz、画面中位60FPS仍是此构建的无采样结果；并非稳定全程60Hz，最低25–29Hz仍需处理。
- 本次纯五人权威物理仍接近目标，不能沿用22舰压力场景的“模拟持续算不动”作为全部解释。
- 转发元数据处理确实占用可测时间，接收端/普通主线程工作和调度也不能排除；目前**还没有定位到足以解释所有掉速的单一根因**。尤其不能把Node中Playwright的16.58%算成游戏服务必需开销。
- 下一步若优化服务器解码，应在原始字节与全部安全校验不变的情况下，对单次有界投影扫描做对照；若再做全链路归因，应先隔离测试控制与转发进程。不要因这次被仪器影响的数据直接调整信用数/Hz/画质或重复堆叠后台浏览器采样器。
