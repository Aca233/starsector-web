# Phase34 主机调度与发布账本（2026-09-22，诊断前记录）

上一轮是有验证的进展：默认捕获减少CPU/分配，字节一致。但整体Hz和输入确认延迟没有稳定改善，5人新版完整31–37Hz，不能把局部收益当作目标完成。

本轮先在冻结的当前代码中增加**仅测试用**Worker时间账本，测量真实host Worker + LanBattle + desktop bridge路径。记录：回调数/忙碌重入/每回调完成tick直方图、回调墙钟工作时间、yield耗时、回调间间隔、回调外snapshot耗时、snapshot总耗时。它不改变定时器、输入、模拟dt、快照信用或背压。回调间间隔减去快照也不是精确CPU空闲，还包含其他消息服务和系统调度；不直接当作可全部回收时间。

工作目标仍是正常联机的整体延迟/Hz，不预先认定setInterval就是罪魁祸首。若明确存在调度浪费，再写明候选与验收、实际同源成对验证；不得删债务、降目标Hz/精度、扩大恢复保护预算或只改显示数字。采样只增加少量累计数值，每秒一次测试console，不发送玩家身份/任意游戏对象。

网络调度属于原版没有的扩展，本阶段不改原版玩法/UI。已保留Phase33查阅的DamagingProjectileAPI和tpc_shot证据；如触及玩法需重新查对应本机原版源码并记录。本轮不碰生涯/并行AI源码、不使用子代理、不操作桌面、不发布。

## 避碰候选剪枝实验（实现前）

证据：本机 `../decompiled/starfarer_obf/com/fs/starfarer/combat/ai/movement/BasicEngineAI.java`（CFR 0.152，Ship.oo 反编译符号未完全解析）22–24、68–100 行分别保存/推进朝向、航向、速度分量，并使用实际速度与加减速指令。本次不声称 Web 的 8 步/11 候选策略是原版逐行移植；只保持当前有限加速度模拟与选择结果不变。没有修改界面，原版实机操作未做。

真实 Worker 诊断：过载窗口回调间隔不足约2ms/秒，而模拟约48Hz；换定时器不能消除主要负载。另一次有 profiler 的5人诊断成功跑通，但 fleetAI 约4.9ms、shipsWeapons约3.1ms/步，采样显示避碰风险积分值得试验。两次诊断负载不同，不混为性能对照。

候选：只在现有原生 AI phase、原生运动/向量读法且有限非负风险积分条件下，利用部分累计风险作为下界停止已不可能获胜的候选；已找到近零风险时，先检查偏离代价是否仍能胜出。完整原始方向风险、候选顺序、8步 horizon、浮点运算、1e-8 比较、目标Hz都不变。自定义/依赖记录路径保留原顺序。极值、非有限/非正半径与自定义方法必须差分覆盖。

先放测试候选，再用冻结同源的整场模拟 A/B、B/A 比较。启用门槛：结果/全帧字节/RNG完全一致，整步 P50 至少改善5%、P95不恶化超过10%，随后实际3/5人路径验证。失败候选保留证据而不默认启用。测试只在后台无头运行，绝不借降低物理Hz、删除过载保护或截断输入队列制造好看的数字。
