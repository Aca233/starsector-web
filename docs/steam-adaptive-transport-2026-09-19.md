# 自适应 Steam 状态窗口／输入积压（2026-09-19）

## 已确认问题

1. 原生可靠发送队列是不透明的。持续 60Hz 的输入在链路停顿后集中送到 relay，可能触发 160 条/秒限制，以 1008 / Rate limit 断开。旧原始 gateway 的受控模型在 3 秒停顿后到达 161 条；输入 ACK 窗口／相邻移动合并后，同类模型最高 74 条、不关闭、最新序号送达。不是放宽服务器限流。
2. 第一轮固定四帧窗口仍把高 RTT 下的同步率限制在约 4/RTT。后续自适应窗口保留 64KiB 字节预算，按每轮 ACK 估计排队，有余量时每 RTT 加一，排队时减一。正常 2–32 帧，学习新路径基线时临时 1 帧。
3. 短历史会把积压学习成新的 RTT 下界。初始控制器在 120 秒虚拟低带宽测试中末段帧龄约 828ms；改为按秒取最小值、基线上升先排空测量后，同配置约 518ms。保留此回归，不能仅凭十几秒短测试判断长期稳定。

## 本轮证据（不是 Steam 实网性能）

- `npm run steam:check`：18 项 node:test + 输入队列 1408 条断言；真实 gateway／codec／ACK 和虚拟链路／relay 双端模型。相关脚本位于 scripts，不依赖旧 artifacts。
- 300ms RTT、8Mbps、小状态（约 2.45KiB）、60Hz 生产者：末段到达 60Hz，接收帧龄约 153ms。**不是实际战斗 FPS，也不是降低了 300ms 物理 RTT。**
- 200ms RTT、8Mbps 降至 256Kbps 加有序抖动：自适应收缩，末段约 12.7Hz／228ms 帧龄。
- 120秒虚拟持续运行、降至 128Kbps：末段约 6.3Hz／518ms 帧龄，无超量队列或连接关闭。
- 300ms RTT、1.024Mbps、12KB 高熵负载：末段约 10.3Hz／323ms 帧龄，字节上限保持。
- 同一电脑、双浏览器上下文、真实前端／WebSocket／权威 Worker，Steam 通道模拟 300ms RTT／8Mbps、**双向 3 秒停顿**：不中断，停顿后恢复状态；客机合并了 81 个未发送移动输入，动作／控制不合并。刷新恢复控制、移动约 79 单位、结束并返回房间通过，页面错误 0。
- 构建、TypeScript、lint 通过；原有 Vite 大 chunk 提示保留。未调整 Steam、代理、防火墙或任何用户网络设置。

## 实际游戏仍有限制，目标未完成

双护卫舰实际快照压缩后约 8KiB；300ms 的上述浏览器测试达到字节窗口约 8 帧，未达到模型小状态的 60Hz。64KiB 上限防止弱网排队；简单改大上限会让带宽突然下降时堆积数秒旧状态，不能据此宣称优化完成。接下来需要降低真实状态带宽（可恢复基线／差分或其他有证据的方案），而非只调大窗口。

原生接口仍为可靠 P2P，不能取消已交给 Steam 的旧状态，重传队头阻塞仍在。大首帧重组仍按 8 秒总龄过期；已有边界诊断证明持续 9 秒传输的 16MiB 帧不能完成，本轮没有用放宽失联阈值掩盖这个问题。

当前未有两台电脑、两个 Steam 账号的真实跨网验证；也未验证十人共享上行、大舰队性能和长时间原生会话。整体目标“深耕游戏联机优化”继续保持 active。

## 被动压缩探针（给后续优化提供方向，尚未接入传输）

对同一场模拟双护卫舰的 10 个完整状态包逐一比较、并逐字节解压回验：平均原始 JSON 32732B，当前 deflate level 1 约 7962B；level 3 约 7781B（仅少约 2.3%），level 6 约 7287B（少约 8.5%）。使用至少 500ms 前状态末尾 32KiB 作为字典，level 1 约 6461B（少约 18.9%）。单次探针 CPU 均值分别约 0.31／0.33／0.68／0.54ms；这些不是多玩家性能保证。

仅调压缩级别或上字典都不足以把该战斗状态稳定压到满足 300ms RTT／64KiB 窗口下 60Hz 所需的约 3.5KiB。字典还需要连接隔离、基线丢失恢复、内存边界、重连／ACK 序列验证与多玩家 CPU 验证，因此本轮没有为了一个小样本收益直接改线格式。报告保存在 `artifacts/steam-snapshot-bandwidth-probe.json`。
