## 本次交付范围

用户要求把有效的性能与联机技术用于 LAN 和 Steam 两端。本次完成第一批生产路径对齐：把 LAN 已有的 **additive motion（附加运动状态）策略**接入默认 Steam P2P 网关，而不是把轻量运动帧继续塞进完整快照的可靠发送队列。

这不是“所有实验开关全开”：未改变权威模拟 60 Hz 的目标、20 Hz 战术规划策略、玩家指令执行、物理/伤害规则、显示插值或完整快照发送节奏；未改原版玩法界面，仅在已有 Steam 网络诊断区增加真实计数。没有修改生涯、暂存、提交、打包或发布，没有操作用户桌面。

## 新增 Steam 通道的约束

实现位于 `server/steam/motion-channel.mjs`，通过 `gateway.mjs`、共享 `lan-server.mjs` 和现有 `LanConnection` / `LanBattle` 路由连接。

- 运动帧自包含，无跨帧 delta 基线；玩家输入、离散动作、伤害和生命周期仍走原可靠路径。
- 使用 SDK `SendType.UnreliableNoDelay`（值 1）；完整快照仍为 Reliable（值 2）。这只表示应用选用的 SDK 语义，不保证 Valve 路由/操作系统层面绝无排队。
- 每包最多 1200 B（含 40 B 应用头）；原始展开 JSON 上限 16 KiB，校验 CRC、连接随机标识、match、sync 和 tick。只有压缩确实变小才使用 level-1 deflate。
- 每个房间共享 64 KiB/s 运动数据预算，突发上限 16 KiB；公平等待只保留标量意向，不排队保存旧运动负载。
- 每端最多 4 个 / 16 KiB 在途运动帧；250 ms 过期，不重发，不用丢包伪造消费 ACK。连续失去有效运动回执达到门限则本局停用可选运动路线，可靠完整状态继续。
- 接收端最多两份未完整重组的帧、16 个运动回执；旧包、重复包、缺片和坏包不阻断可靠解码器。
- 发送前必须有真实完整状态接纳回执；共享 `AutoMotionAdmission` 检查从发送开始的 750 ms 年龄及 tick 差。回执不参与网络 RTT 学习。
- 新完整状态先到达且已被接纳时，可清理被它覆盖的运动在途记录，独立计为 `superseded`，**不**计为运动接纳/丢包；避免健康链路因两种包竞争而误降级。
- 隐藏/恢复、launch/resync、换局和重连清理旧资格。后台恢复必须先接纳新的完整状态；旧回执不能重新获得资格。同局已触发的降级不会因 resync/visibility 被洗掉。
- Steam 运动接纳回执不能释放可靠快照额度。异步编码 Worker 仅增加可信 match/tick 元数据，不把大世界再次复制回主线程。
