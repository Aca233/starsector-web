# 后台降频被误判为持续过载（2026-09-18）

## 现场提示与确认

用户报告切屏后出现：`客户端无法继续：计算主机持续过载或暂停过久，恢复失败。请降低战斗规模后重试。`

检查当时正在使用的 `127.0.0.1:3005` 服务，协议 24、构建 `2026-09-18T09:10:12.585Z`，其中已包含前一轮后台心跳豁免。本次退出来自房主 Worker 的恢复预算，而不是心跳超时。没有改动此前排查时注意到、但并非这次错误来源的显卡上下文恢复分支。

## 可重复的缺陷

在真实引擎 Worker 代码上控制调度时钟，旧代码表现为：

- 连续 250 / 500 / 999 / 1000 ms 间隔的后台回调进入 `accumulator > 250` 分支，消费前台过载恢复预算，随后抛出与现场完全相同的错误。
- 连续 1001 / 2000 ms 回调虽进入后台豁免，但每次都将 accumulator 清零，始终不能推进 tick，也没有新快照完成同步。
- 原来的“单次暂停两分钟后恢复”测试没有覆盖这种持续降频，因此漏掉了该缺陷。

## 修复

`src/network/host.worker.ts` 现在分别记录回调开始和结束时间，区分：

1. 上次物理/序列化计算实际花费的时间；
2. 上次回调结束后等待浏览器再次调度的时间。

后台或恢复前台的首个回调，若调度空闲超过一个正常六步处理批次（100 ms），丢弃这段暂停墙钟时间，而不是转入前台过载恢复。保留此前真正的计算积压，只提供一个正常、固定 `1/60` dt 的六步处理批次，不以大 dt 或分钟级追帧恢复。

连续降频期间只进行一次清控制/重新同步；恢复前台时再清除旧输入。这样后台仍有回调时可以推进权威 tick 并发布新快照，不会一直重置同步门槛。**实际后台战斗速率仍受浏览器调度限制，不能保证切屏后保持实时速率。**

持续计算过慢、真实物理积压的恢复预算没有豁免。一次调度暂停超过五分钟仍拒绝恢复，并改用明确的“后台暂停超过 5 分钟”提示。

## 验证

`node scripts/check-background-heartbeat.mjs`：32 项检查通过，包含：

- 120、250、500、999、1000、1001、2000 ms 连续后台间隔，均能维持运行、推进 tick、产出快照，连续降频只触发一次恢复。
- 在真实物理步骤上注入 10 ms 计算耗时，后台降频时仍能运行；注入 250 ms/步，在 4 ms 与 500 ms 的调度空闲下都仍会触发真正过载保护。
- 从降频恢复前台清空待处理按键/动作，恢复正常 tick；已恢复过一次后再暂停超过五分钟仍停止。
- 原有前台心跳、后台心跳、30 秒断线恢复、真实 WebSocket 会话清理与后台房主期限检查。

类型检查和本次文件的 lint 通过。这里使用真实引擎代码与受控时钟，**不是实际物理 Alt-Tab 的系统调度测量**。
