# 确定性帧同步前置验收（2026-09-20）

## 用户明确的架构调整
每个客户端本机运行同一份完整战场；服务器仅给输入排序、形成统一逻辑帧并校验各端校验和。不采用房主单点计算，也不采用各玩家只算自己舰船的分片权威。此前本轮未完成的网页房主启动器改动已撤回，旧的服务器权威优化保留。

## 修改前证据和边界
- 原版0.98a-RC8：starsector-core/starsector.log:1；CombatEngineAPI.java提供统一世界的舰船、弹丸查询。本次是Web联机架构扩展，不改原版战斗规则/UI；不宣称原版有帧同步。无原版实机操作。
- 当前createLanWorld使用同一seed和稳定创建顺序；SimulationRandom保存state/idCounter；已有CombatLab仅验证单运行时短场景，不能证明跨浏览器/CPU一致。
- host.worker按performance.now判定500ms输入过期，按到达时刻插入部署/在线状态，并有掉帧追赶/过载恢复；这些不能直接用于锁步逻辑。须将所有影响战斗的事件放入确定的逻辑帧，不允许各端自行丢帧/超时清输入。
- setLanPerspective会重排playerShip/enemyShip/reinforcements；fixedUpdate又按playerShip技能调整时间。故模拟必须保持统一的seat0世界顺序，个人视角仅用于显示世界。
- RuntimeCollisionKernel自动Wasm只在window存在时加载，Worker没有window；初步验收统一使用串行Worker+TypeScript碰撞，不自动启用依硬件/耗时切换的AI并行。
- CombatSnapshot明确是呈现投影，不是可恢复完整模拟存档，忽略了AI、RNG等内部状态。不能拿旧快照直接冒充锁步断线续算检查点。
- 先做32艘实际战斗的输入录像回放：独立本地Node进程、浏览器Worker、云端ARM运行相同seed/输入/帧数；改变墙钟批次但不改变逻辑步长。逐检查点比较呈现字节及RNG游标。通过也只是这些配置的回归证据，不是跨平台数学或完整内部状态的形式保证。
- 此阶段不切换现有服务/不开放不一致模式；若发现分歧先定位，不以忽略校验或覆盖一端结果掩盖它。


## 第一轮实测结果：不能启用严格帧同步
32艘（2艘真人攻势+30艘AI锤头），seed=1511506142，固定1/60秒，1200步/20秒模拟；输入录像包括前进/横移/瞄准/开火/护盾/排幅；tick0起每60步采一次，共21个检查点。各副本独立创建世界，输出包含呈现投影及两个RNG游标；每个运行环境改变每批1步/13步的让出调度。此处云端ARM仅是跨环境回放对照，不是在改变未来服务器职责。

| 对照 | 结果 |
| --- | --- |
| 本地Node v24.13.1 x64两次独立进程、不同让出批次 | 21/21检查点相同 |
| Edge 153.0.4234.46两个隔离网页Worker、不同让出批次 | 21/21相同 |
| 本地Node vs Edge Worker | 第60步检查点已有差异；其后20个检查点均不同 |
| 本地Node vs云端Node v25.9.0 ARM64 | 第120步检查点起不同，19个检查点不同 |

这里是“最早检测到的检查点”，不是精确首个分歧逻辑帧。各端tick1200的combatRng和visualRng完全相同；初始tick0字节也相同，所以不能把问题简单归因于随机种子。首个保存的Node/浏览器差异为一枚弹丸速度x：-0.5008647066548414 vs -0.5008647066548（差约4.14e-14）。后续检查点出现舰船速度、位置、武器方向、AI油门等微小差异。本测试没有观察/证明已经发生不同胜负，但数值微差未来可能改变碰撞/阈值分支，不能用“四舍五入校验和”掩盖。

额外独立数学探针给两端相同的10000组参数：atan2有1730组、cos有357组、sin有334组二进制结果不同；该样本下hypot/pow未发现差异。这证实当前原生Math不是可直接依赖的跨运行时一致性契约；尚未追踪到实际战斗第一次分歧所执行的具体数学调用，故不把探针当作完整因果定位。也不能从一个Edge版本推广到全部浏览器、手机和CPU。

## 接入可玩房间之前必须完成
1. 统一并验证确定性数学核（含三角/反三角等）；完整检查所有影响状态的调用。不能只把输出保留小数，也不能认为换成Wasm包装原生Math就自动确定。
2. 抽出由已提交逻辑帧驱动的模拟执行器：同一初始内容hash/规则版本/seed/对象顺序；玩家控制、部署、撤退、断线接管均带明确tick/稳定序号；去掉本机墙钟对游戏状态的决定。
3. 中转服按席位收集/排序输入，广播不可变帧。缺输入必须使用统一等待/服务器决定的事件；不让各端自行补输入、跳逻辑步。输入延迟、慢机拖累和掉线策略需要显式验收。
4. 所有端在相同逻辑帧报告状态hash；不一致先停局并留回放诊断，不能继续各打各的。Hash只检测差异，不自行修复或保证客户端诚实。
5. 做真正的完整模拟checkpoint或确定性回放追帧后再支持重连；当前呈现快照不能承担恢复。覆盖AI状态、RNG、弹丸、部署、事件队列和稳定ID等。
6. 最后接入网页显示/输入、长局/多舰队/异构浏览器实战与网络乱序/延迟/断线测试，再决定启用范围。现有单房服务器性能数据不能作为此架构的帧率或延迟保证。
