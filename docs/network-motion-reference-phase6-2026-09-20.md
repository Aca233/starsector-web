# 低 Hz 优化 phase 6：可协商、逐字节修正的运动参考压缩（2026-09-20）

## 结论和范围

上一轮属于实质进展：流控及 n2n 日志已落地，但仅缩短排队，低带宽下仍约 6–13Hz。本轮继续减少每个完整状态的发送量，**没有把目标缩成只改善 ping 或改显示值**。

现已接入生产 LAN relay、主线程回退和 I/O Worker；n2n 使用该 LAN 通道。**Steam 尚未接入这个新格式，整体“完全解决”目标未完成**，也没有提交、推送、发布或更新正在使用的安装版。生涯和其他任务的改动均未编辑。

这是无损传输参考构造，不是玩法移植/改动：原版参数、世界更新、字段、浮点精度、特效、物理频率完全不变。参考计算可与真实运动不一致，修正包仍必须还原完整原始字节，故无需也不能用参考算法替换原有模拟或把它冒称为原版物理。

## 为什么选择这个方案

从干净 0.2.5 真实录制中逐项检查，22 舰某帧的弹丸压缩后约 19KB，FX 约 19KB；碎片、粒子、伤害文字等每次只发生规则运动，却被当作全新的浮点数据发送。

先验证解码世界→预测→重新编码的原型：压缩量可降，但每帧参考构造约 7–8ms，代价过高。随后改为直接扫描 SWB1/SWF2 中已存在的字段和 float64 字节位置，只在**新分配的私有字节副本**内改写参考值，不生成一个世界对象图，不重新序列化整帧。

微基准完整校验的压缩体积（WS level1/memLevel7/Z_SYNC_FLUSH；非网络吞吐）：

| 跳过的 tick | 原字节增量 | 运动参考后增量 |
|---|---:|---:|
| 1 | 35,806B | 21,624B |
| 3 | 39,624B | 26,226B |
| 6 | 40,759B | 28,091B |
| 12 | 42,830B | 31,353B |

低 Hz 跳帧后仍有约 27% 字节改善，不是仅对相邻帧有效。数据位于 `artifacts/network-latency-phase6-20260920/hardened-probe.json`。试验原型曾暴露 Node Buffer.slice 共享存储的问题，已在接入前修正；正式实现使用 Uint8Array.from，并有 Buffer/subarray/DataView/ArrayBuffer 输入不变与输出独占测试。

## 已实现

### 1. 传输无关的参考构造器

`src/network/SnapshotMotionReference.mjs`：

- 只识别既有 SWB1/SWF2 及 frame-local layouts、$record/$records、projectile columns。
- 定向扫描弹丸、particles、debris、hitGlows、floatingTexts；其它数据原样保留。无变化的整数/float32 编码不改成 float64，不改变字节布局。
- 1..60 个 1/60 步长，只用基础 IEEE 浮点加减乘除与 min/max；不调用 Math.exp/sin/hypot、引擎代码、随机源或本地游戏对象。此算法不必预测正确，网络修正负责精确还原。
- **v1 参考字节算法冻结**：将来如要改变有效输入的参考字节，必须使用新能力版本，不能静默覆盖 v1。
- 最多 2MiB 输入、96 层、262144 扫描节点、8192 预测行，另有限制 layouts/templates/rows/cells。没有网络输入可递归的对象 key；需要读取的 map 拒绝重复/危险 key。
- 不支持的布局/自定义值/预算超额返回 null，发送者保留普通精确增量。原完整快照验证仍然存在，该扫描器不是替代验证器。
- 不修改输入、静态模板或共享字段，不留世界历史。只生成一个临时参考，完整修正后仍以原目标字节作为下次基线。

### 2. LAN 能力协商和正确性边界

`server/LanDeltaTransport.mjs`、`server/lan-server.mjs`、`src/network/LanBinaryDelta.mjs`、`protocol.ts`、`lan-socket.worker.ts`：

- 新 hello/welcome 能力 `motionReference:1`；仅在原 stateCredits + binaryDelta + permessage-deflate 已协商的 LAN 路径确认。
- 老客户端、未确认的服务端、Steam relay 和未启用压缩的回环连接不启用新格式。
- SLD1 flags 的 bit2 表示使用 v1 参考，bits8..13 为 1..60 步数；只有 DELTA 时有效，其余未知位拒绝。未协商接收器仍拒绝这些扩展位。
- 基线序号/CRC 仍对应**原始已发送基线**，不是预测基线。接收端构造临时参考→应用原字节 patch→核验目标 CRC/size/match/seq，之后才交给原完整状态解码、应用和消费 ACK。
- 任何预测误差均由 patch 修正；不把预测值直接渲染或消费确认。缺基线、损坏、无效步数仍走原失败/重连路径，未延长超时。
- 跨 >60 tick、倒退/相同 tick、无法识别的基线自动使用原字节增量。seq 与 tick 分开处理，不能用 seq 之差冒充模拟步数。
- 支持缓存和普通缓存隔离，混合版本接收者不会复用错误 patch。仍只有每轮最多 2 次构建、4ms 启动准入预算；这与原逻辑一样是**启动准入**而非可抢占的单次 CPU 硬限。轮转、公平性、在途额度与输入/控制路径未变。
- 基线仍只保存完整字节，参考为瞬时额外工作，不扩成每帧历史或重传队列。
- 诊断增加 `motionDeltas`，计数实际提交的新参考增量，不代表预测正确率或节省字节数。

## 最终生产 codec 链路 ABBA

原始数据：`artifacts/network-latency-phase6-20260920/production-link-abba.json`。

独立 sender/receiver Node 进程，真实 WebSocket/permessage-deflate 和本机限速 TCP 代理，生产 LanDeltaSender/LanDeltaReceiver。双方都使用 phase5 新消费反馈窗口，仅开/关本次能力。基础 RTT60ms，60Hz offered，每速率 ABBA 四轮各 10 秒，steadyHz 排除开头 2 秒；所有交付状态均与原始 SWB1 逐字节核对。与原型 PXM1 包装器不同，这一轮已使用生产 SLD1 格式。

录制来自干净发布版 `ef043ecef4547321929dd0ffb0eee47074d08b13`，22 舰、生产投影/特效优化、241 个连续完整帧。没有裁剪字段、减少舰船或使用别的任务修改后的引擎。最终 ABBA 期间未并行跑浏览器/类型检查/网络压力测试；正常电脑使用造成的噪声仍可能存在。

| 整形链路 | 关闭：接收 Hz | 开启：接收 Hz | 关闭：状态年龄 P95 | 开启：状态年龄 P95 |
|---|---:|---:|---:|---:|
| 2Mbps | 6 / 6 | 8.625 / 8.625 | 608 / 579ms | 348 / 348ms |
| 4Mbps | 12.75 / 12.75 | 18.5 / 19 | 252 / 252ms | 187 / 191ms |
| 32Mbps | 46.125 / 46.75 | 46.875 / 46.375 | 53 / 60ms | 54 / 56ms |

- 2Mbps 接收率约 **+44%**；4Mbps 约 **+45–49%**。不是把低 Hz 根治到 60，也不是用户 n2n 实机结果。
- 32Mbps 吞吐基本持平；10 秒代理下行约 16.3–16.4MB→10.36–10.41MB。不能由轮间小差异宣称健康链路 Hz 确定提升。
- 成本：生产测试发送编码均值约 1.4–1.8ms→2.6–3.0ms；接收重建约 0.52–0.61ms→2.07–2.44ms，随后另有完整解析成本。没有隐藏新增 CPU 工作。
- 状态年龄是受控同机时钟下源端开始准备发送到接收端完成还原/解析的测量，**不是输入到屏幕、物理 n2n RTT、真实游戏 FPS**。多客机共享预算也只做机制测试，未将此单接收者吞吐推广为九人实战。

## 未完成，不可冒充已解决

1. Steam 仍用自身 JSON/结构增量通路，尚未复用这个新参考 codec；之前 3 个 Steam 压力失败不能靠 LAN 测试消除。
2. 实际双方桌面/n2n/Steam 仍需验证，n2n 中继容量、丢包和 NAT 打洞结果未由本机 codec 测试证明。
3. 低带宽重负载还未到 60Hz；继续减少完整状态成本与解决真实路由，不降低 Hz 显示、精度、模拟频率或超时门槛。
4. 没有打包、安装、提交、推送或发布；当前安装版不会自动得到未发布的源码改动。
