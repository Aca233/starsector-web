## n2n 证据范围

主机战斗 1/2 的 11/20 个路由采样全部 `mixed`；战斗 3–9 期间分别 9/3/6/14/8/18/4 个采样全部 `relay`。另一台客机大多数 `mixed`；8 核客机接口 `unavailable`。

这证明 n2n 隧道中存在持续中转流量，**不证明每条游戏 TCP 连接都走中转**，也没有测出 supernode 带宽或丢包率。不能从汇总计数给某座位强行绑定 n2n 路由。

## 结论与实现边界

1. 此次主要瓶颈是权威状态从中转到客机的分发/交付，而非主机只有 10–20Hz 或客机渲染限帧。主机第 7 场有轻微生产下降，但远不足以解释客机 3–4Hz。
2. 当前大状态复制对慢链路很重，可靠 TCP 的在途状态还会影响后续状态和控制回包时效。n2n 共享中转可能加剧它，但缺少逐连接线上字节/丢包指标，不能进一步断言唯一根因。
3. 不应继续放宽消费窗口、积压更多帧，或调低 Hz 后声称解决。现有防背压跳过未发送状态不是丢失已发送数据。
4. 当前 `CombatSnapshot` 已是 P1 呈现投影，不是可恢复整个模拟的检查点。后续减少带宽需要在现有投影上继续做来源/字段消费者审计，拆分静态或可靠变化与频繁位姿数据，不能误称只需把“完整模拟对象”换成渲染快照。需覆盖舰体/武器/弹体/特效/UI、部署/销毁、重连及 ACK 边界，不能未经核实删字段或降精度。另一条方向是可丢弃快照传输，需完整分片/认证/重建/协商/兼容测试，不能只换 UDP 就称完成。
5. 更换/直连 n2n 路由可作为部署层验证，但本次没有修改用户网络、没有把它当作已经完成的游戏修复。
