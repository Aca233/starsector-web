# 客机低 Hz：共享快照链路诊断（2026-09-19）

## 本轮范围

针对“客机只有 10–20Hz，高负载 LAN 曾降到 2Hz”，完成研究路线 A：让房主与客机能看到同步在哪一段降速。**这是定位能力，不是已完成的降延迟修复。** 对象/字段级增量、局部还原和新的传输分流尚未接入；没有承诺实战恢复 60Hz。

不改变：60Hz 目标、物理模拟、伤害/碰撞、舰船数量、快照发送准入、消费窗口大小和超时保护。没有启动 Steam、邀请玩家、修改防火墙、替换桌面安装包或覆盖根 `dist`。

## 新增测量

菜单 → **性能与网络诊断 → 快照全链路速率**：

| 指标 | 实际计数位置 | 不能解释成什么 |
| --- | --- | --- |
| 房主模拟步/秒 | `fixedUpdate` 完成后 | 快照到达率 |
| 房主产出帧/秒 | 编码后 `postMessage` 成功返回 | 已上传完成 |
| 房主发布等待解码 credit | 有新 tick、但已有快照未获解码容量时的回调 | 丢失多少模拟帧 |
| 本机上传入队/准入跳过 | `sendSnapshot` 返回值 | 网络发送完成/丢包率 |
| 中转接收 | 通过 host、match、seq 和状态校验后 | 客机收到 |
| 各客机发送入队/socket 忙/消费窗口满 | 原有中转准入分支 | 网络线路真实吞吐 |
| 消费回执 | 有效且精确匹配在途序号的 ACK | GPU 已呈现、纯网络 RTT |
| 本端接收/还原端点 | 已接受快照、`applyCombatSnapshots` 回调 | 渲染 FPS，或必然一一对应的阶段 |

Steam 使用相同的房主、上传和共享 relay 测量；不支持 LAN 应用消费 credit 的路径明确显示“未启用”，不显示假 0。Steam 后续网络分片/传输还需结合原有 Steam 诊断，**这里的 relay 入队并不覆盖全部远端 Steam 链路**。

## 时序与安全边界

- 房主 Worker 的小型性能消息原本就独立于完整快照；现在把白名单数据搭载在已有应用心跳上给 relay，再放进已有 pong 给客机。没有新增轮询请求和通道。
- 心跳仍走同一个网络 FIFO，仍受原有上传积压门禁限制。它不是独立优先通道，拥堵也可能阻塞诊断。
- 各进程用自己的单调时钟采样，首次窗口为未知；固定数量计数器不保存帧、实体或包。超过 5 秒的长暂停窗口不作为当前速率。
- 房主样本和心跳报告分别检查时效。收到延迟 pong 不会让旧报告重新变“新”：客户端保守加入本次心跳整个往返耗时。房主采样已知年龄仍无法包含未测量的房主到 relay 单向传输耗时，不用于声称精确单向延迟。
- 不同阶段不是严格对齐的同一时间窗；不能用一次瞬时差值自动断言根因。持续差异才值得进一步查证。
- 重连/新 match/终局/可见性切换清理客户端诊断 epoch；旧 epoch 的迟到 pong 不会填入新诊断。同步恢复重置本端接收/还原和上传窗口。
- 服务端仅接受当前运行对局房主的白名单样本；客机伪造、旧 match、过期或非法数值被拒绝。报告不含玩家名称、IP、SteamID、token 或 matchId。房主最多看到 9 个接收端，客机只看到自己。
- HUD 仍依赖本端渲染线程刷新；该线程完全卡住时不能继续实时显示，不能拿冻结的面板当实时诊断。

## 如何用结果推进根本修改

必须使用包含本轮前端 **和服务端模块** 的同一新版完整包，稳定运行到采样窗口预热，再对照房主和客机同一时段的面板；旧截图无法验证这些新指标。

- 模拟接近 60，而房主产出持续 10–20：检查捕获/编码，以及房主本地解码 credit，不先怪网络。
- 房主产出正常，但本机上传/relay 接收少：检查上传准入、I/O 队列、编码和上行成本。
- relay 收到正常，发出少：结合 socket 忙/消费窗口满、字节量和原有传输诊断区分下行积压与接收消费反馈；不要直接扩大窗口。
- relay 发出正常，客机接收/还原少：检查客机接收队列、解析、还原和主线程停顿；还原端点合并不自动等于故障。

接下来的对象级同步试点应优先核查弹丸/武器状态的完整捕获及还原成本，不能再用“整帧序列化以后增加一种压缩”冒充对象级 CPU 优化。必须覆盖实体出生/删除、ID 重用、跳帧、基准失效、重连和 mod 兼容，最终以同场景双机接收/应用率、状态年龄、输入确认延迟共同验收。
