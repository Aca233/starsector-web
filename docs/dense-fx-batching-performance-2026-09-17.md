# 密集百舰 FX 合批复核：局部收益不等于实际帧率提升

日期：2026-09-17。

## 结论

保留仅用于 FX 通道的四纹理实例合批。密集百舰的两次配对测量中，绘制提交平均耗时下降 **43.81% / 44.74%**，“模拟一步 + 视觉更新 + 渲染 + GPU 同步”完整周期平均耗时下降 **18.62% / 17.85%**。不是全局多纹理替换，不启用此前已拒绝的全局八纹理方案。

**用户觉得提升不明显有实际依据。** 普通布局没有稳定的绘制收益；真实调度压测仍约每秒一次画面更新。这一修改是爆炸密集场景的减负，不是流畅性达标，**100 艘战列舰 / 180 FPS 仍未实现**。

没有调低分辨率、MSAA 设置、粒子或爆炸数量、AI / 物理频率，也没有缩短威胁预测时间。存在极少量 MSAA 像素差异，严格逐通道容差检查失败；基于重复完整周期收益和已复核的稀疏差异保留，**不声称像素完全一致或全部验证通过**。

## 修改范围与机制

本轮只改两个生产文件，保留之前近炸船体粗筛、弹丸威胁索引和火控缓存等全部工作：

- src/engine/render/webgl/SpriteBatcher.ts：默认保持原单纹理 shader；可选四纹理模式复用 16-float 实例末尾的填充位记录纹理槽。保持精灵、透明混合及通道顺序，在第五张纹理、容量、混合或显式边界提交。纹理选择前计算 UV 导数，以 textureGrad 避免分支内隐式导数问题。绑定全部四个 sampler 槽，未用槽使用首纹理，并恢复活动纹理单元 0。
- src/engine/render/webgl/WebGLCombatRenderer.ts：FX 专用 batcher，在进出 FX 时提交并恢复对应 shader / blend 状态，其他通道不更换 shader。包含上下文重建、取消恢复、失败释放、正常释放与 draw-call 统计。

冻结 290 个源文件；本轮前后只有以上两处差异，最终当前源码与候选快照一致。配对生产构建同时冻结主模块和 Worker 模块。

## 为什么选这里

独立插桩的密集百舰基线 300 次测量中，绘制提交平均约 84.10 ms，其中 FX 总计约 13,381 ms、舰船通道约 8,483 ms。插桩计时用于定位，不与无插桩生产构建混算加速比例。

另一份最终场景计数诊断有 1,002 个爆炸、16,252 个 puff；三张爆炸纹理和环纹理交替造成大量提交。该诊断是预推进后的单个冷渲染，**只能引用计数，不能把其耗时用作性能结论**。

实际场景第 300 步的命令记录显示：完整场景 39,881 个精灵顺序和实例值不变，总 draw calls 18,028 → 5,808；仅 FX 场景 13,048 → 828；禁用 FX 时 4,965 → 4,965。draw-call 减少不是 FPS 增幅。

## 完整周期配对测量

Chromium / ANGLE D3D11 / NVIDIA RTX 5060，2560×1440，DPR 1；100 艘 Onslaught 的密集布局及 10/50/100 艘常规布局；seed 0x51180，360 个固定 1/60 步，前 60 步预热、后 300 步测量。前后独立页面，每步交替执行顺序，复测反转起始顺序。构建、插桩和其他重型验证未与测量并行。

“完整周期”包括模拟、视觉更新、绘制及 gl.finish；**不是实际 FPS，也不能直接取倒数宣传帧率**。单位为 ms；耗时变化负值为更快。

| 场景 / 轮次 | 完整周期均值 前 → 后 | 均值变化 | 完整周期 P95 前 → 后 | 绘制提交均值 前 → 后 |
|---|---:|---:|---:|---:|
| 密集 100 / 首轮 | 220.70 → 179.61 | -18.62% | 305.1 → 242.8 | 84.96 → 47.73 |
| 密集 100 / 复测 | 219.40 → 180.23 | -17.85% | 307.5 → 249.3 | 86.48 → 47.79 |
| 常规 10 / 首轮 | 10.56 → 10.32 | -2.27% | 14.3 → 14.3 | 4.53 → 4.38 |
| 常规 50 / 首轮 | 54.77 → 54.95 | 0.34% | 68.9 → 71.1 | 17.51 → 17.72 |
| 常规 100 / 首轮 | 130.96 → 128.78 | -1.66% | 162.2 → 159.5 | 32.30 → 32.75 |
| 常规 10 / 复测 | 10.31 → 10.17 | -1.39% | 13.2 → 13.8 | 4.30 → 4.43 |

| 常规 100 / 复测 | 142.46 → 132.20 | -7.20% | 173.8 → 160.8 | 34.01 → 32.87 |

密集复测中模拟均值 132.87 → 132.39 ms，绘制 86.48 → 47.79 ms，收益明确来自绘制。首轮密集模拟 135.69 → 131.82 ms 的变化不归因于该修改。

常规布局结果不稳定：例如首轮 50 艘完整周期慢 0.34%、绘制慢 1.22%；100 艘绘制慢 1.40%。常规复测完整周期看似改善 5.48% / 7.20%，但大部分来自**未改动模拟代码**的耗时波动；不能据此承诺普通战斗也有同等提升。全部配对最终引擎状态指纹和存活数一致，页面和 GL 错误为零；指纹仅忽略墙钟 kernelMs。

## 真实 rAF 调度：仍然严重过载

不是人为逐步调用的循环，而是 Chromium 原生 requestAnimationFrame 驱动生产 60 Hz 调度器、CombatSession.fixedUpdate 和插值渲染；没有 gl.finish 和 profiler。密集百舰预推进 180 步，预热 5 个回调，再观察 20 个回调，前后顺序独立运行：

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 测量回调数 | 20 | 20 |
| 回调间隔窗口 | 19.916 s | 18.633 s |
| 观察到的回调频率 | 1.004 Hz | 1.073 Hz |
| 间隔 P50 | 983.3 ms | 900.0 ms |
| 间隔 P95 | 1466.6 ms | 1383.4 ms |
| 完成模拟步数 | 120 | 120 |
| 模拟推进速率 | 6.025 TPS | 6.440 TPS |

每个测量回调都先跑 **6 个模拟步**再渲染。修改后单步模拟仍约 132 ms，连续模拟开销掩盖了单次绘制的节省。不能用本轮完整周期约 18% 的收益替代实际帧节奏结论，更不能只减少模拟推进来制造高 FPS 数字。

这里只是一组 20 回调的顺序诊断，不是持续游戏或统计显著性的证明；无头环境、脚本自动驾驶和固定相机，不包含完整音频、输入、UI 循环，也不是物理 180 Hz 显示器验收。首次 before 启动在尚未进入测量时等待就绪超时（30 秒）；保留日志，增加到 90 秒的就绪等待后重试成功，没有把失败启动计入结果。

调度器的 100 ms 墙钟截断与补步逻辑未更改。droppedSimulationSeconds=0 只表示没触发积压裁剪，不表示没有墙钟截断。

## 行为与画面验证：区分通过和失败

### 已通过的检查

- 8 项独立合批诊断覆盖单纹理、交替纹理、超过四纹理、混合模式、8,305 个精灵跨容量、外部 shader / VAO / 活动纹理变化、begin/end 和 mipmap。前 7 项像素精确相同；mipmap 仅 2 个通道差 1/255，在显式容差内。GL 错误为零，活动纹理单元恢复为 0。
- 同一真实场景、同一 GL 资源下，对照原 render 方法与当前方法；全部场景精灵纹理语义键、混合模式、顺序和前 15 个 Float32 实例值一致。未启用 MSAA 的四个场景在三轮诊断中都逐像素一致。
- 当前 typecheck、lint、生产 build 通过，保留已有大 chunk 警告；dist 已更新为此候选。
- 当前生产构建浏览器冒烟、上下文丢失/恢复、FX shader / VBO 重建、活动纹理状态、FX shader / VAO / VBO 与 ribbon EBO 释放检查通过，页面和 GL 错误为零。

### 严格 MSAA 检查失败，保留人工复核例外

原始 scene-pixels、controlled、review 三次诊断的严格 MSAA 通道容差（最大差 ≤1）都失败，退出码为 1。原始默认 MSAA 的完整场景最大差 29/255，共 43 个通道不同；原→原控制也存在最大 6/255 的差异。

第二轮显式 4×MSAA RGBA8 FBO + resolve 中，完整场景最大差 26/255、37 个通道，原→原最大差同为 26/255、61 个通道；近景最大差 6/255、115 个通道，控制最大差仅 1/255、8 个通道。**不能证明候选差异全部来自原有噪声。**

最后一次独立读回复核的显式 4×MSAA 结果（每幅图 1280×800，共 4,096,000 个 RGBA 通道）：

| 场景 | 前→后 最大差 / 不同通道数 | 原→原 最大差 / 不同通道数 |
|---|---:|---:|
| dense-all | 5 / 48 | 13 / 38 |
| dense-fx-only | 1 / 36 | 1 / 21 |
| close-fx | 6 / 105 | 1 / 8 |
| disabled-fx | 0 / 0 | 0 / 0 |

已查看从 resolve FBO 直接读回的前后近景截图，舰体、尾焰和爆炸未见明显劣化；该观察不代替上述严格失败。早期 scene-close-controlled.png 从默认 canvas 截图，画面实际在离屏 FBO，所以它是黑图，不用作视觉证据；scene-close-fbo-before.png / after.png 才是正确的直接读回图。

保留理由是密集完整周期两次稳定节省约 18%、没有主动减少模拟或视觉内容、差异极稀疏，符合用户允许低影响改动的方向。此结论仅适用于本次覆盖，不能保证所有 GPU 后端都无差异。

## 下一阶段验收方向

现在需要针对模拟主路径的结构性减负，并同时看实际回调间隔和 TPS，而不是继续堆 draw-call 百分比。60 Hz 模拟每步预算 16.67 ms，180 Hz 展示每帧预算 5.56 ms；当前模拟和绘制都远超预算，且单线程下共享可用时间。

Worker / 快照传输可作为避免主线程长时间阻塞的架构候选，但单纯搬线程不会消除模拟的总计算量，也不保证 180 FPS。任何后续方案必须保持碰撞/伤害结果、推进速率与可接受画面，再用持续真实调度压测验收，不能靠静默降模拟频率或少算实体刷高显示数字。
