# 火控只读批处理与运动遮挡粗筛 · 2026-09-21

## 结论与范围

已实现单舰瞄准阶段的只读查询批处理，以及保守的运动 BVH（包围盒层级）友军遮挡粗筛。保留精确几何、选敌/扫描规则、发射顺序、随机流及模拟/渲染频率，不减少舰船、弹丸或画面效果。

最终新路径仅在 `world.ships.length >= 100` 且整份名单满足原生读取资格时开启。小规模战斗在元数据资格审计前直接保留原路径；此前已有的 AutofireController 20 舰局部优化不变。舰船数是当前火控名单的成员数，不等于舰队部署点数。

百舰 Onslaught 的受控浏览器测试中，20 舰门槛候选的四轮完整工作耗时下降约 2.3%～5.0%；最终 100 舰门槛构建的标准/密集复测分别下降 4.49% / 5.53%。但同环境 A/A 校准有约 3% 的波动，**不能据此宣称统计显著、稳定的 FPS 提升**。本次是有明确查询减量、有限总耗时收益的优化，不是多舰性能问题已经解决。

## 实现与安全边界

1. `FireControlQueryRoster` 只复用原生读取资格审计及对象/回调身份，不缓存阵营、可见性、相位、存活、坐标、护盾或几何结果。作用域是 CombatEngine 原生同步舰船更新段，之后在 finally 中关闭。
2. `FireControlQueryBatch` 在每艘船运动、护盾和组件更新后、瞄准前建立，在发射及组轮换前通过 finally 关闭。不跨舰、不跨步，不新增可序列化战斗状态。
3. 每舰瞄准前重新检查名单成员/组件身份、外部相位、损伤回调及临时 modifiers 等失效条件。基本可选性按目标惰性缓存；只有实际重选或预瞄才构造完整有序候选列表，避免每步无条件过滤全表。
4. 友军列表及 BVH 同样惰性建立。小于 8 个阻挡物直接使用列表。节点保存位置边界和速度极值，查询包围 `[充能延迟, 充能延迟 + 接触时间]` 内的运动；包括真实舰体轮廓、偏移护盾及浮点误差余量。异常/非有限输入放行，不错误排除候选。
5. BVH 返回顺序与原名单相同。fighter 穿透规则、相对运动、`shipSegmentEntry` 的真实船体/护盾窄相及小行星检查仍走原逻辑，不缓存命中结果和 in-flight damage。
6. 自定义 combat effects、读方法/关键回调、数据 getter、可变嵌套武器元数据、母舰/模块依赖、多战术槽等不满足资格时回退。独立调用武器控制器且没有原生 roster 时也不启用。
7. 限制规模是实测后的保守选择：20 舰候选慢约 3.4%，50 舰基本持平，不为大场景优化强加小场景审计负担。阈值由一处导出常量统一管理，先做数量检查再审计。

资格检查不是任意 JavaScript 私有字段/原型在调用中恶意改写的安全沙箱。新增原生回调或把发射挪入瞄准循环时必须重新审计生命周期。

## 逻辑验证

最终版本 5 场、各 180 步，每 30 步检查一次：**30 个完整状态检查点全部相同**。百舰 Onslaught 和百舰 Harbinger/Paragon 各开启 18,000 个 batch（合计 36,000）；后者全部 batch 都在场上存在相位舰时开启，覆盖实际激活路径而非仅回退。100 Doom/Harbinger、100 Odyssey/Paragon 混编因名单/元数据资格不满足而回退，24 Onslaught 因规模回退，三者 batch 均为 0；不将这些回退场景算作新路径加速证据。

- 22 项真实对象契约：候选顺序、成员/射手身份、无证书回退、close、等长名单替换、新 batch 的阵营/存活变化、组件替换、外部相位/modifier 失效、系统/护盾/幅能/装甲回调与原型覆盖、多槽回退、数据/武器元数据 getter 不被审计调用，以及异常退出/首次发射前关闭。最终阈值覆盖 0、10、20、50、99 的回退和 100 的激活。
- 运动粗筛 9,600 次查询、80,040 个精确接触全部保留；307,200 原始配对缩至 96,744 候选（排除 68.51%）。包含运动横穿、充能延迟、超出 collisionRadius 的舰体、偏移护盾、旋转、极端量级与非有限输入；首个真实阻挡物顺序一致。
- 冻结源图独立编译 baseline/candidate。状态比较包含 engine、玩家 AI 及逐挂点 WeakMap tracker；不能仅依赖 Object.entries 遍历 WeakMap。保留 Map/Set、共享引用、非有限数和负零，只规范化函数及 kernelMs 墙钟字段。
- 独立插桩百舰 Onslaught、30 步：相位查询 **3,647,833 → 2,011,281（减少 44.86%）**；精确船体/护盾线段查询 **930,611 → 121,157（减少 86.98%）**；开启 3,000 次 batch。插桩数据不用于性能计时，减量不等于 FPS 增幅。

## 为什么多舰仍重

重复扫描部分接近“舰船数 × 挂点数 × 舰船数”，并非简单 O(N) 增长。当前优化减少局部重复，但原生资格审计、其他 AI/物理/弹丸、渲染提交仍占成本。已有多线程只覆盖支持场景的部分 AI 工作：当前单机 CombatMulticore 需 Worker、SharedArrayBuffer、crossOriginIsolated 和至少 8 个逻辑处理器；Eligibility.supportsOwnership 还限定 50～200 艘默认原生 Onslaught 等条件。混编/不同配置不应被假设已经跑在四 Worker 路径上；串行火控/状态推进也不能因增加 Worker 自动并行。这里是源码范围核实，并非用户实际运行时是否回退的实测诊断。后续需依据生产调度剖析扩展空间查询复用、批量数据读取及明确的读写/提交边界，不能仅凭本轮计数判断整引擎瓶颈占比，也不能悄悄用整帧快照改变原有顺序语义。

本轮不修改其他任务的渲染/网络/生涯工作，没有暂存、提交、推送或发布，没有恢复此前移除的测试体系。后台构建仅用于本地验证，不是发布打包。
