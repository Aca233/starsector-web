# 联机高 FPS 下的慢动作感（第二轮）

## 基准与诊断

用户确认测试的是 3004，而不是 3001。保留这两个入口及正在进行的对局，使用独立房间测量旧 3004 的 tick / 60 与 performance.now() 的比值。8 艘守护者、同机两个 Edge 客户端的四段采样约为 0.995、0.926、1.009、0.998 倍。该结果区分了短时实际落后与显示卡顿，不代表直接测到了用户自己的那局。

查到的呈现问题：
- 舰船虽然有跨快照起终点，但 alpha 每到一个包就从零重置，并以接收间隔 EMA 为动画时长，遇到抖动/降频会反复拉伸运动或跳回旧起点。
- 炮弹的 prevPos、prevBallisticTail、prevFadeProgress 仍来自主机上一物理步，而不是上一份显示快照。以 5 Hz 同步为例，只有 1/60 秒的位移被摊到约 1/5 秒，随后又跳到新快照附近。
- visualTime 直接取最新快照的 combatTime，连续视觉时间也跟着网络包跳变。
- 模拟 ms/步未包含序列化和丢弃的积压，因此原“模拟正常”不能证明实时时钟正常。

## 实现

- 新增 SnapshotPlayback：按模拟 tick 维护单调显示时钟，通常缓冲一个快照区间，不随包抵达重启动画。常规播放 1x；积压时有限 1.1x 追赶，断流停止在已知状态；初始/重同步/长暂停直接对齐最新状态。最多保留 8 个待呈现快照；卡帧恢复时最多还原最后两个端点，不连续重放八个完整世界。
- applyCombatSnapshot 在 unpack 前按炮弹 ID 保存位置、弹尾和渐隐端点，不按会删除/重排的数组下标匹配。新出现的炮弹、初次还原、新增战机及重同步直接落在权威位置，不从其他实体旧坐标飞入。仅修改显示世界，不修改主机的碰撞/命中状态。
- visualTime 在快照 combatTime 端点间连续插值；物理、AI、武器、伤害和结算仍只在主机运行。
- Worker 先完成本轮补步，再采集最新快照；尚欠两个物理步以上时优先追赶，不额外插入重序列化。快照频率预算同时考虑每秒 60 步的模拟占用与 capture + encode 耗时，给计算留余量，不改物理 dt、不减舰船数。
- 每约两秒测量主机 tick/墙钟与 combatTime/墙钟。顶部改为 FPS、状态 Hz、战斗倍率；详情同时显示计算推进倍率与显示缓冲。舰船时间系统可能影响 combatTime，不能与物理 tick 推进混为一谈。

## 验证与边界

没有创建测试文件或测试运行器。使用临时 stdin 和浏览器脚本：
- 2/5/10/20 Hz 规则供帧下，连续呈现时间速度均为 1x。
- 抖动时间轴不倒退；断流停在最后已知状态；重复包忽略，恢复不重放过期队列；批量还原最多两个端点。
- 炮弹删除/重排后仍按 ID 匹配；200 ms 间隔的 120 单位运动中点正确为 60 单位，而不是只移动半个物理步。权威对象未被修改；重同步位置直接对齐。
- 验证快照 CPU 预算随模拟开销提高而降频，而非将物理时间缩小。
- 中间版本双端实战曾触发过载保护；重复运行通过，但不能把这次重复成功当作问题不存在。因此补充了物理优先与共享 Worker CPU 预算。最终版本实战结果另见下方及 artifacts 中的日志。

限制：这仍是完整显示快照协议，不是紧凑增量协议。新生/消失的短命弹丸、粒子历史、光束和其他离散效果依然受同步频率影响；并未声称 5 Hz 与本地 60 Hz 模拟等价，也未证明重负载下绝不会再过载。缓冲会引入显示延迟；输入确认延迟与它是不同指标。客机仍只有自己的舰船有有限运动预测。没有修改时间加速系统的规则，也没有真实 Steam 跨网验收。

## 最终构建首次实战结果

- 同机双 Edge、8 艘守护者，四段墙钟比值为 0.999、1.002、1.001、0.986；越过 tick 1200 并完成客机刷新重连，无页面未捕获错误，仅房主一个战斗 Worker。
- 交火末段约 64–80 FPS，显示状态频率曾到 2.3–5 Hz、最新快照年龄 611 ms。这说明完整快照和机器负载仍是限制，不能把时间轴修复当作已经解决所有卡顿。
- 构建、TypeScript、lint、服务端语法和修改范围 diff 空白检查通过。与旧版不是锁定机器负载的受控 FPS A/B 对照，不宣称帧率提升倍数。
- 首次实战日志：artifacts/lan-motion-final-log.txt；基准与中间版本（包括失败记录）日志一并保留。

## 持续压力验证未通过（必须保留的结论）

随后将双端目标延长到 tick 2400 的独立重跑，在开始阶段就触发了主机恢复/过载保护，未到目标。收到两次恢复通知（1131 ms、381 ms）后失败；只收到初始 tick 0 快照。因此不能由首次 20 秒左右的成功样本宣称稳定性已经修好，也不能从快照停在 0 推断 Worker 没有执行物理步——过载时物理优先门禁可能抑制采集。日志保存于 artifacts/lan-motion-endurance-log.txt。

当前交付是已验证时间轴/炮弹端点修复的实验预览，不是“彻底解决联机卡顿”的稳定版本。真实过载仍需继续定位（包括完整快照投影的开销和共享机器的持续计算负载），不通过增加恢复次数、改物理步长或删减舰船掩盖失败。没有覆盖 3004 或要求用户把这版当作稳定替换。
