# Phase24：序列化线程拆分实验与验收

## 结论先行

**真实的编码 Worker 已实现，但性能与最终高负载稳定性验收未通过，因此没有默认开启。** 原来的 Phase23 优化继续默认工作；这不是回退已验证的优化，也没有把 Hz 数字改成 60。

新路径显式使用构建选项 `VITE_LAN_SERIALIZER_WORKER=true`。它是实验选项，不推荐为了“多开一个优化”强行打开。没有修改固定 1/60 物理步长、接收信用或协议大小预算。

## 实际改了什么

- `SnapshotTape`：将已完成 tick 的 P1 投影写成私有可转移数值缓冲和有界字符串表，避免跨线程结构化克隆整个世界对象图。仅用于本机刚采集的可信投影，不接收网络对象/自定义 getter/iterator。
- `SnapshotEncoderBroker` / `snapshot-encode.worker`：一个辅助 Worker、最多一个编码任务；采集和提取仍在权威线程，**没有声称整个 capture 已经移走**。
- `SnapshotEncodeMailbox`：编码结果通过共享内存就绪标记发布；权威可在完整物理步边界直接检查，不必等待 MessagePort 回调。复制成有独立所有权的字节后，走原来的网络/显示通道。
- 异步路径的音效按各通道实际发布的 ID 消耗；生成第二通道的候选字节不等于获得信用。只有真实消费回执回来才能发布，不能虚构远程 ACK。
- 超时、启动失败、超预算、终局、重连、换端口都有回退/取消；旧生命周期结果不能倒灌。取消正在运行的任务会终止辅助 Worker，不在旧共享缓冲上启动并发写者。
- 私有 tape 上限 4 MiB、两块各 2 MiB 输出槽。超过私有预算转原同步路径；原来可发送的 16 MiB 快照没有被新上限拒绝。
- 日志增加 `serializer` 的启用状态/原因、实际提交与完成数、取消/回退、准备/辅助编码耗时、等待时长。`tapeBytes` 是有效字节，`transferBytes` 是转移缓冲的容量，均不是网络流量；`workerMs` 是辅助重建与编码耗时，不是 RTT，也不包含结果槽复制。
- 测试探针同时统计同步与辅助 Worker 的实际发布，未将任务提交次数冒充发布 Hz。辅助线程时间单独归类，不能当成权威线程 CPU 时间。

## 尝试及实测结果

### 先排除无效中间格式

实际 22 舰、169 弹体、tick 600 的投影：

- SWF2：159,322 字节，编码约 1.28 ms。
- JSON：377,261 字节，stringify + UTF8 约 2.40 ms。更慢，放弃。
- 私有 tape：346,816 有效字节；优化后的准备约 0.789 ms，对照 SWF2 约 1.258 ms；辅助线程还需约 0.789 ms 重建再编码。

以上是局部微测，不是整局提升百分比或公网延迟。所有迭代比较最终 SWF2 字节，不改变协议精度。

### 五人、22 舰、开启实际渲染的配对试验

固定 seed 917、每次测量 20 秒、同机 Chromium/D3D11 回环。对照和候选的冻结源码图除本轮 host 改动外一致；顺序执行，未同时跑两个压测。

| 运行 | 房主完整 Hz 中位数 | 客机完整 Hz 中位数 | 客机运动 Hz 中位数 | 房主输入确认 P95 |
|---|---:|---:|---:|---:|
| 对照 v1 | 31 | 33–34 | 56–57 | 91.3 ms |
| Worker v1 | 22 | 27–28 | 57–58 | 109.0 ms |
| Worker v2 | 24 | 33–34 | 55–57 | 113.6 ms |
| 对照 v2（反向次序） | 29 | 30–34 | 50–56 | 102.9 ms |

v2 在辅助编码期间顺带准备另一通道，等它真实返还信用后一起发布，修复了 v1 客机完整吞吐下降的一部分。但房主完整帧率仍较差，房主输入确认仍增加。客机确认耗时有部分改善、有部分波动，**不能称为整体降延迟**。

所有这些运行物理模拟约 59.9 Hz；“模拟已经约60”仍不等于“每个客机每秒收到60个完整世界”。辅助 Worker 确实工作：v1 末次遥测完成 1129 个任务、v2 完成 977 个任务，均无回退；不是功能根本没启用。

整机负载在运行间有变化，原始 `host-load.json` 保留。它不是特定进程 CPU，也不用于替候选回退找借口。因此目前选择不默认开启，而不是拿微测的快几成当作游戏收益。

## 客机侧审计

- `LanBattle` 已从运动流立即处理输入确认，不需要等完整快照才确认。
- `SnapshotPlayback` 已将世界队列限制为8个、每次只恢复最后两个插值端点。
- 音效和开火事件在可替换的世界端点合并前独立接收；不能再用盲目丢包“优化”。
- 已有记录标量快速路径、向量/类型化数组目标复用与批量恢复。

没有找到足以在本轮直接默认上线的新客机改动；不再额外添加一个把整个解码世界克隆回主线程的 Worker，也不提前伪造消费回执。

最终自动化门禁及最新冻结图记录在本报告末尾。共享套件/Steam套件之间有重叠，不累加为唯一用例数。

未操作桌面，未使用子代理，未触碰生涯模式代码，未提交/推送/打包正式游戏/发布，也未调整 n2n、OS 或防火墙。生产嵌套 Worker 的打包验证仅输出隔离的测试资源，不是发布版。

下一步若追求有效改善，应减少采集本身和中间投影的重复遍历，或设计可校验的增量提取/恢复；**单纯把编码放到另一线程并不自动消除复制、调度和客机消费的成本。**

### 最后追加复测：两次过载失败，不能报稳定完成

`verified-default-5p` 与 `verified-optin-5p` 均失败，日志和清理结果全部保留，不重复挑选成功运行来掩盖它们：

- 默认路径：房主持续过载后结束战局，同局恢复等待超时；主线程阻塞的450ms观测段全量发布为0、客机输入确认未前进。失败前遥测：模拟约53.33Hz、完整产生约8.89Hz、回调间隔138.68ms、积压268.83ms。采样显示单步约15.11ms、采集6.34ms、编码3.24ms；这些是不同调用频率的墙钟时间，不能简单相加当CPU利用率或FPS。
- 实验路径：测量阶段已发生 `worker-runtime` 权威失败，未进入阻塞/重连验收。失败原因同样是持续过载恢复耗尽，而不是编译失败或未启动编码Worker。
- 两次都会正确清理资源，但清理通过不等于联机通过。整机负载记录只能描述环境，不能证明失败由外部进程导致。最后源码图还包含另一任务的 `CombatPresentation.ts` 变化，未撤销它，也未把不同时段/不同源码图的成绩当严格配对。

本轮共有10次实际浏览器场景：前8次连通性/生命周期断言通过，最后2次失败；候选性能默认启用的验收始终未通过。**当前仍存在高负载下低Hz和过载断线，未宣称彻底解决。** 新增Worker仅为可复现实验路径，之前已启用的网络优化保持原状。
