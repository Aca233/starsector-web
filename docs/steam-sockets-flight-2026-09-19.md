# Steam Sockets 端到端在途限制进展（2026-09-19）

## 状态：继续修复，不能发布或宣称实际 Steam 断线已解决

用户报告的是桌面 Steam 联机严重延迟后断开，不是已确认的程序崩溃。默认入口仍使用 legacy P2P；本轮实验 Sockets 路径未默认启用，没有启动或登录 Steam、邀请玩家、修改防火墙/代理，也没有新建发布包或覆盖冻结 v3。

此前 room/pacing 文档记录的是历史版本。本文件和 `artifacts/steam-sockets-flight-progress.json` 记录新增端到端反馈及本轮调度修正；末尾附最终检查结果。

## 为什么 native pending 限制还不够

已经被 SDK 发出的包可能仍排在操作系统或路由器中。SDK pending 为零不能证明网络畅通，也不能作为回收应用层在途额度的依据。新的离线模型把 SDK 三条优先级队列、native congestion flight、房主共享外部 FIFO、客机独立上行、物理串行化和传播分开建模。

这仍然是**真实 room/session/wire/pacer 代码运行在 JavaScript 网络模型上**，不是 Valve 拥塞控制实现、真实 Steam 路由测试或 native-backed 共享瓶颈测试。native C++ ABI fixture 是另外一层验证，不能混称端到端联机测试。

## 保留的实现

- 新增 `sockets-flight-budget.mjs`：房主共享初始 48KiB / 最小 24KiB / 最大 128KiB 的应用层在途窗口；每个 peer 上限 48KiB，最多 2048 个未确认分片。在 native pending 准入之外再次限流，不取代 native 准入。
- 只有当前会话实际送入 SDK 的 `(epoch,id,index)` 收到经过会话认证的远端 receipt，才回收相应字节。伪造、重复、错误会话、错误 epoch、未知或尚未发送的确认不制造额度；缩窗不抹去既有债务。
- 控制和心跳继续走可靠 lane 0；客机游戏输入使用客机原本空闲的可靠 lane 1，并独立限制为 8256 字节在途。状态继续使用 host lane 1 可靠锚点及 lane 2 可丢快照，不增加 native lane 数量。
- 接收输入的房主最多等待 100ms 合并 receipt，接收状态的客机最多等待 40ms 合并；每批至多 32 个三元组，暂存至多 256 个分片确认。单独协商 capability bit 8，不能与不支持的对端悄悄混用。
- 心跳收到匹配的远端 pong 才计为存活；完全不交付数据时不能只靠健康心跳无限续命。原有握手、可靠数据、重组及心跳的 **8 秒保护均未延长**。
- 稀疏弱网状态不再每 5 秒无条件为所有客机发大锚点：新锚点需满足至少 5 秒以及此前已发送快照字节足够摊薄一次完整锚点成本。快照独立依赖已确认锚点，不形成逐帧丢一帧就全断的差分链。
- flight-enabled 房间的快照可使用 8192 字节应用层分片，单个 native message 不超过 8256 字节。v1.63 Sockets 支持大于 MTU 的不可靠消息，由 native 分片重组；不能拿 legacy P2P 的 1200 字节上限套用。较大的不可靠消息仍有任一底层分片丢失导致整条消息丢失的风险。
- 本轮修正公平排队：为首个等待者保留下一包所需字节和一个包槽，其余真正空闲的额度允许后面的 peer 使用。之前严格队头独占与 native pacer 的轮转次序不一致，可能让整轮白等。仍然保留大可靠分片的额度，不允许小快照长期饿死它。
- 原生 backpressure 只取消等待顺序，不取消已经发出的债务；未发送的状态可由更新状态替换，已经开始的可靠事务必须完成或按原期限失败。

## 两个被拒绝的提速实验

1. **将 host 上限从 128KiB 改为 256KiB（仅测试注入）**：9 个健康客机约 45.8–48Hz、总和超过 420Hz，但 8Mbps → 256Kbps 骤降时外部队列达到 279577 字节，虚拟约 19.616 秒开始断线。这不是可以发布的优化，保留的源文件没有采用该上限。该实验运行在当时的两轮控制版本上，不是与最终单轮控制版本的严格单变量对照。
2. **每轮两次 bounded control pass**：正常 3 客机、混合 RTT 和 soak 表现改善，但在骤降测试里新增客机 6 的可靠状态 ACK 超时，在丢包测试里仍会 input delivery 超时。已撤回至原先一次 control pass；相关日志保留为 `steam-sockets-flight-double-control-*`，不能引用它们的好结果作为最终版本结果。

另外只做了合成 payload 大小研究：299 条差分快照，含 64 字节应用头，当前 JSON/deflate level 1 平均约 1714 字节；level 6 约 1637 字节；MessagePack/deflate level 1 约 1455 字节。MessagePack 合成样本的 JSON 往返相同，但**替代编码尚未实现、协商或启用**，不代表完整游戏编码安全、CPU 性能或真实网络收益。

## 仍需解决的风险和下一步

- 丢失的不可靠额度只能在 native 快照队列为空、之后新发的快照确实得到 receipt，并满足保守年龄条件后尝试对账。该机制依赖本模型共享 FIFO/因果排空假设；不能据此声称任意 OS/QoS、换路、Valve 调度下都安全。时间或控制 pong 本身不能回收额度；可靠数据绝不这样对账。
- 关闭连接仍保留无法证明已排空的在途债务，防止不断重连获得无限新窗口。但这会导致 orphan debt 占据房间容量；实际断开/重连后的回收协议仍是发布阻塞项，不能简单超时清零隐藏它。
- 正常 9 客机的吞吐目标未满足，不能为了防断线而宣布大幅降帧可以接受。应继续无损编码与共享准备成本优化，而非删游戏数据、减少输入采样或盲目放大发送窗口。
- 需要更多丢包相位、异步控制/输入相位、断开重连和 native-backed 共享瓶颈验证。固定一组确定性 loss/reorder 序列通过，不等于所有相位都通过。
- 必须保留原 legacy 骤降失败、正常链路性能目标和 8 秒保护；不能删测试、跳过或放宽阈值来制造全绿。
- 最终仍需真实两账号、不同网络的 Steam 桌面联机验证。此前及本轮没有做过这项验证。
