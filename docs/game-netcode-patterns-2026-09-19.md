# 成熟联机游戏怎样避免低更新率和状态积压（2026-09-19）

## 本轮目的与结论

本轮仅查阅一手文章/公开代码、核对当前源码、整理方案，没有修改生产代码、传输默认值或发布包。目标仍是改善其他玩家只有 10–20Hz、状态越积越旧的问题，不是把目标改成 20Hz，也不是用画面 FPS 替代联机接收率。

最相关的行业经验不是“换一个更快的压缩库”，而是：

1. **只生成明确的网络状态，不把运行时整个对象图当协议。**
2. **状态变化主动登记；对象/字段增量，而不是完整序列化之后才做字节差分。**
3. **把对象归组、缓存共享工作，避免对象数 × 客户端数的反复检查。**
4. **可被新状态替代的信息与必须到达的信息分别处理，保证状态新鲜度。**
5. **预测/插值负责观感，不能修复真正的吞吐和排队瓶颈。**

## 1. VALORANT：先分阶段测量，再消除复制系统的轮询成本

来源：Riot 2020 年官方文章《VALORANT's 128-Tick Servers》。这是开发时的架构经验，不宣称其当前所有版本实现完全相同。

文章说明早期 server frame 约 50ms，团队按 replication、网络、动画、物理、移动等分桶测量，再逐项优化；不能靠设置 tickrate 就获得 128 tick。128 次/秒对应单场每步 7.8125ms 上限，文章为了每核心容纳多场，设了更小的预算。

**最贴近当前项目的是 replication 一节：** UE4 旧属性复制需要每帧扫描所有标记字段，与每个客户端上次状态比较，即使没有变化也要检查。Riot 用适合的状态变化 RPC 替换部分轮询，让成本主要发生在状态改变时。文章举的是生命值变化事件，不仅是视觉粒子。

限制：文章所述 100–10000 倍改善针对某些替换场景，不是整场游戏帧率或我们项目的预期收益。事件也需要可靠性、幂等、重连检查点；不能把扣血广播改成可能重复/丢失的裸消息。我们更适合发送 `entityId + generation + revision + 权威当前值`，而不是无保护地重复累加/扣除数值。

另一篇官方《Peeking into VALORANT's Netcode》解释了：
- 服务器权威判定，自身移动在客户端预测，服务器纠正分歧。
- 固定模拟步长与渲染 FPS 解耦。
- 缓冲改善平滑但增加延迟；文章描述的是尽量小的运动缓冲，不是越卡越扩大。

对本项目：已有运动预测和播放缓冲，不要把“加插值/预测”再次当作主方案。真正可借鉴的是明确复制对象、变化登记、按阶段追踪 CPU。

来源：
- https://www.riotgames.com/en/news/valorants-128-tick-servers
- https://www.riotgames.com/en/news/peeking-valorants-netcode

## 2. Fortnite / Unreal Replication Graph：避免每个对象反复检查每个玩家

Epic 官方文档用 Fortnite 开局约 100 玩家、50,000 replicated Actors 作为规模例子。这里是文档示例，不是当前所有模式固定实体数。

传统方式由每个 Actor 判断是否给每个客户端更新，容易产生对象数 × 客户端数的 CPU 开销。Replication Graph 用跨帧持久化节点、空间/类型分组、预计算列表，在多个客户端间共享工作。

文档还明确指出：把对象错开发送或简单降低更新频率只能缓解问题，同时会降低客户端体验。图结构的目的在于减少重复判断成本，而不只是降 Hz。

文档例子包括：
- 根据位置/区域分组相关对象。
- 长时间不变的树等对象休眠，受损/销毁时才更新。
- 跟随玩家的装备与持有者一起更新。
- 始终与所有玩家相关的特殊对象单独保留。

对本项目：可借鉴静态设计/舰船配置按版本发送、按类型复用布局与编码结果、事件变更后唤醒。但太空战有战术地图、雷达、全场观察和远距离威胁，**不能直接“屏幕外就不发”**。可以区分全局战术必需信息与近处精细表现，后者需要明确产品/玩法语义，不能暗中降低玩家可见信息。

来源：https://dev.epicgames.com/documentation/en-us/unreal-engine/replication-graph-in-unreal-engine

## 3. Quake III：对象级增量和明确生命周期

id Software 官方开源的 `sv_snapshot.c` / `msg.c` 可以直接验证：
- 相同实体从上一基准做 delta；完全未改变且非强制时不生成实体更新字节。
- 新实体从 baseline 生成，消失实体发送 remove 更新。
- delta 绑定明确的旧帧；基准过旧/无效时回到完整基准。
- 根据客户端位置/可见性建立相关实体列表。
- `MSG_WriteDeltaEntity` 有固定网络字段表，并逐字段编码变化。

这是经典游戏的公开实现，不当作 CS2 当前协议，也不能把它说成完全无轮询成本：它仍会比较网络结构里的字段。

对本项目，重要差别是**先有小而明确的实体网络状态，再做字段增量**。我们现在仍遍历较大的舰船/世界运行时对象，再生成 SWF2，然后对字节做 SLD1。现有字节增量节省流量，但前面的完整捕获和后面的完整恢复还在。

Quake 源码为 GPL；这里只学习协议设计，不直接搬代码到当前项目，也不照搬其浮点/整数编码精度策略。

来源：
- https://github.com/id-Software/Quake-III-Arena/blob/master/code/server/sv_snapshot.c
- https://github.com/id-Software/Quake-III-Arena/blob/master/code/qcommon/msg.c

## 4. Factorio：同步操作，而不是所有对象的位置

Factorio 官方 FFF #76（2015）介绍 deterministic lockstep：各端运行整个模拟，网络主要传玩家操作，因此可以扩展到大量实体。

代价同样明确：需要严格确定性，微小差异会累计成 desync；客户端也要负担整个模拟。对弱机而言，这不一定减负。

FFF #76 还描述了当年的纯 P2P 拓扑，**这不能当作今天仍然纯 P2P 的证据**。FFF #149（2016）说明移除该旧拓扑、服务器通信独立编号、后台传地图并积累输入后追赶服务器。中心服务器拓扑与确定性操作同步是不同维度，不能混为一谈。

对本项目：不适合把全战场 lockstep 当低成本修复。当前客机是权威状态展示，并没有已经验证的跨引擎完全确定性；上一轮视觉粒子 Node/Edge 重建甚至存在约 5.7e-14 的三角函数差异。这些差异对纯视觉无关紧要，但也说明不能默认跨机所有物理过程逐位一致。要迁移锁步，需要另立大工程，不能顺手替换当前同步模式。

来源：
- https://factorio.com/blog/post/fff-76
- https://factorio.com/blog/post/fff-149

## 5. Valve GNS：可靠性和优先级分流，但不替你设计游戏状态

GameNetworkingSockets README 明确支持可靠/不可靠消息、多个 lanes、优先级与带宽权重；也明确**不提供上层实体序列化、变化字段增量和压缩**。

`ConfigureConnectionLanes` 的保证是同 lane 内可靠消息按序交付，不保证跨 lane 的接收顺序。lane 仍共享连接带宽；分流不是创造额外带宽或保证零排队。

适合本项目的候选分类（设计建议，尚未在本轮实施）：

| 信息 | 候选语义 | 需要的保护 |
| --- | --- | --- |
| 连续位置/朝向/速度 | 可替换，过期丢弃，必要时不可靠 | 对象 generation、状态序号、有效基准、缺失恢复 |
| 连续控制状态 | 新输入覆盖旧输入，必要时少量冗余 | 输入序号，不能把按键边沿误当可丢状态 |
| 出生/删除、装备变更、离散指令、终局 | 必须正确到达/恢复 | 可靠、幂等、revision、生效 tick |
| 进房完整检查点和大配置 | 有界、与实时流量区分优先级 | 同步 epoch、阶段确认、不能饿死恢复流 |
| 特效 | 展示事件，可重建 | 有限窗口、去重、过期清理 |

当前位置可替换，不代表生命值事件或一次开火指令可随意丢弃。单纯把发送 flag 改为 unreliable 会破坏依赖旧基准的 delta。LAN SLD1 的累计确认与两 anchor 模型依赖可靠有序链路，不能原样移植。

仓库已有 Steam Sockets 三 lane 实验代码，默认 gateway 仍有旧 Reliable=2 路径，应该审计并完善已有实现，不重复造同一套。普通网页也不能直接使用原生 UDP，LAN 桌面原生路径与浏览器 WebRTC 等候选应分别评估。

来源：
- https://github.com/ValveSoftware/GameNetworkingSockets
- https://github.com/ValveSoftware/GameNetworkingSockets/blob/master/include/steam/isteamnetworkingsockets.h

## 回到本项目：建议主线

### A. 确认限制哪一段，复用已有诊断

已有 HostPerformance、LAN relay/credit 统计、Worker 与主线程耗时、SnapshotReceiveRate。先用同一 match/seq 对齐：房主完成多少状态、relay 收到/发出多少、客机接收/应用多少、窗口在哪里等回执。缺什么补什么，不再另造一套重复 HUD。

把服务器模拟 Hz、快照产出 Hz、链路收到 Hz、应用 Hz、渲染 FPS 分开。不同机器的单调时钟不能直接相减；跨机单向延迟必须有时钟估计及误差说明，局部阶段先用各自时钟测耗时。

截图的 60 FPS、1.00x 计算推进、2Hz 实收、2114ms 应用往返支持优先调查同步管线，但**不是已经证明某个具体模块是根因**。截图 build 也不是上一轮新源码的双机实测。

### B. 用明确网络视图取代通用全树高频捕获

建议先做一个可验收的舰船试点：
- 网络实体 ID + generation + 类型/配置 revision。
- 高频平面数据：位置、速度、角度以及确实需要高频更新的战斗表现字段。
- 其余状态按字段变化性质分类；通量、炮塔指向等不能仅因“不是位置”就错误归为低频。
- 变化时登记的字段/组件；每次变化避免为每个客户端重复全树扫描。
- 出生、删除、恢复完整检查点是协议的一等操作。
- 客机只更新受影响实体/字段，不能仍将小 delta 展开成整份世界再完整恢复，否则 CPU 收益被抵消。
- 自定义/mod 字段有明确兼容路径，不能静默丢失。

先在现有可靠传输上验证数值与生命周期，再考虑不可靠状态；不改模拟、碰撞、伤害和目标快照 60Hz。

### C. 状态足够小之后，再评估分流与新鲜度

控制未发送状态的准入，过期可替换数据不持续积压；已进入 TCP 的旧字节无法靠主线程丢快照取消。若实测仍是可靠队头阻塞，完善对象级基准保留、显式确认和丢包恢复后，再推进已有 GNS 实验路径/LAN 相应方案。

### 验收而不是宣传

- 同一新版完整包，真实两台机器，复现用户原高负载场景。
- 带宽/CPU足够的正常 LAN 下，关键权威状态的有效接收/应用率应接近既定目标，且没有持续积压；不以偷偷降低目标来“达标”。
- 同时对照状态年龄 P50/P95、输入确认延迟、各阶段 CPU、排队占用、收发字节，而不只显示 Hz。
- 限带宽、抖动、断线恢复时保持有界资源及状态一致，不制造虚假高 Hz。

作为规模提示而非现场测速：上一轮生产路径录制的 LAN 压缩增量仍约 45KB/状态；若真的给一个接收端持续发 60 次/秒，应用负载约为 22Mbps，尚未计协议开销。这个例子说明只改目标 tick 或窗口不能凭空补足带宽；不表示朋友家实测带宽就是瓶颈。
