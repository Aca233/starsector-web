# Phase22：完整状态为什么不到60Hz——分段定位（2026-09-21）

## 结论先行

不是某个开关把所有客机锁在30Hz，也不能统一归因于客机显卡或房主物理算不动。两类证据必须分开：

1. **用户提供的旧多机/n2n/Steam日志**：房主物理、快照生产、中转入口都接近60Hz，但客机交付只有几Hz到几十Hz。瓶颈主要位于中转后的状态交付、拥塞及消费信用回路，而非客机绘制。
2. **当前工作区同一机器五开测试**：物理仍约60Hz，但权威Worker的完整状态发布先掉到35–39Hz，随后中转/客机基本跟随。物理、呈现投影、编码、回执处理挤在同一个Worker串行任务队列；单个I/O在途槽与回调末尾才发布的设计把忙时调度延迟转成跳过中间tick。

前一轮裁剪提高了画面和输入响应，但不能把这两段不同瓶颈都解决。尤其不能从同机五开33Hz断言朋友机器只能处理33Hz。

## 1. Hz到底在数什么

- protocol.json snapshotHz=60，是目标。
- host.worker.ts step() 固定1/60物理，单回调最多追6步，再调用snapshot。追赶后的多个物理tick可以只发布末尾一个完整状态。
- 客机HUD完整Hz来自SnapshotReceiveRate：LanBattle.accept里的playback.push成功后计数。它是实际接收的新完整状态数量，不是渲染FPS，更不是客机在完整重算60次权威物理。
- host Worker的本地显示与网络发布各自独立一个inflight；因此房主显示Hz可以高于网络发布Hz。
- motion/关键战斗/投射物虽有独立mailbox，发布函数仍在同一个step回调的snapshot之后。独立通道不等于独立的生产调度/计算预算。

## 2. 当前五开：先卡在生产/发布，不是主要丢在客机

在冻结的同一浏览器源码图和seed917上，使用真实5人22舰LanBattle、I/O Worker、桌面helper、中转服务。20秒测量，两次完整画面对照两次不画图消融。添加的探针只存在于测试Vite源变换，不修改生产文件。

以下为同一测量窗口累计计数/秒，非把不同时间的HUD中位数直接相减：

| 环节 | 完整画面第一次 | 完整画面重复 | 不画图第一次 | 不画图重复 |
| --- | ---: | ---: | ---: | ---: |
| 权威物理步/s（Worker探针） | 59.33 | 59.91 | 59.97 | 60.00 |
| 网络完整状态发布/s（Worker探针） | 35.19 | 39.48 | 52.49 | 54.60 |
| 中转实际入口/s（完整20秒计数） | 35.10 | 39.45 | 51.70 | 53.75 |
| 客机实际转发/s（各席） | 33.45–34.05 | 37.60–37.85 | 51.35–51.40 | 53.55–53.65 |
| 因socket忙跳过/s | 0 | 0 | 0 | 0 |
| 因消费额度跳过/s（各席） | 1.05–1.65 | 1.60–1.85 | 0.30–0.35 | 0.10–0.20 |

Worker探针仅取完全包含在测量内的约18–19秒窗口；中转取完整20秒，故相邻值不要求逐小数严格相等。**35Hz的入口不可能靠客机渲染优化变出60个独立权威完整状态。** 放大客机消费窗口至多捡回这里约1–2帧/s，解决不了生产端缺的约20帧/s。

不画图实验保留真实接收、解析、状态恢复、输入和ACK，仅跳过renderer.updateVisual/render。其报告中的60数字是原测试的RAF心跳，已明确标为非渲染FPS，不用于性能宣传。这是定位消融，不是交付模式。

## 3. 发布端为什么掉频：已经量到的排队位置

第一次完整画面，权威Worker每秒观测到：
- 物理步（含控制处理）耗时合计约557ms；
- 呈现投影capture约166ms；编码约106ms；
- 上述合计约829ms/s，尚不含其它回调/整理/消息/GC。这里是performance.now墙钟区间，含同机调度抢占，**不能冒充线程CPU利用率**。

一个网络状态经私有MessagePort交给I/O Worker，再把本地发送结果回到权威Worker：
- 正向排队平均0.19ms；
- I/O封装+WebSocket本地send平均0.44ms；
- **回执从I/O完成到权威Worker处理，平均12.54ms**（重复12.23ms）；
- 不画图时回程等待降至约3.80–4.62ms。

这不是远端网络RTT：AuthorityIoBridge在本地send后立即返回io-snapshot。真正长的是权威Worker忙于自己的串行任务、不能及时处理返回消息。在这一回执处理前，directInFlight槽仍被占用。此时物理继续追赶，但snapshot不为网络排旧帧；等放行时发送最新tick。

结果：两次完整画面约31.7%/32.4%的网络发布跨过不止一个物理tick，间隔可达2–6步，第一次还有9步。物理时钟基本追上60，完整状态次数却被合并掉。**“配置60Hz + 不降低物理目标”并不等于每秒成功生产和交付60份大状态。**

不是只怪1个槽：本轮没有放宽它。平均回执往返也不是独立硬上限公式；它与capture/encode、回调相位和catch-up共同作用。盲目增槽可能多发旧状态和增加排队，需要后续有界实现验证。

## 4. 单独权威对照：不存在固定30Hz上限

用相同seed/5艘真人Onslaught+17艘AI Hammerhead/队伍布局的真实host Worker，在独立无头页面运行。消费者仅为本地MessagePort测试接收器，无中转、真实客机、渲染和操控循环，所以只测上限，不能当正常联机验收。

| 对照 | 物理Hz | 网络完整发布Hz |
| --- | ---: | ---: |
| 本地显示+网络两个消费者，立即归还私有本地回执 | 59.98 | 59.98 |
| 仅网络消费者，本地显示持有额度 | 59.98 | 59.93 |
| 仅物理，持有完整快照额度 | 60.01 | 不发布 |

同一个host Worker可以达到60Hz。五开中的问题是实际负载/调度/发布依赖，不是硬编码30Hz或每个朋友CPU必然达不到。单机五个浏览器共享CPU、GPU、DevTools观察开销，与五台物理电脑有显著区别。

## 5. 用户原始多机日志：另一段瓶颈更严重

重新核查2026-09-20T15-23/27/35三份文件，build均为2026-09-20T14:58:55.362Z。不能拿旧日志宣布当前代码仍以同样程度失败，也不能拿本机当前测试证明旧多机问题已经修好。

已按hudFresh/tick/人数核实的详细统计见network-multiplayer-session-v026-2026-09-21.md。关键事实：
- 5人/27舰：房主生产约59.93Hz、中转入口59.60Hz；一台客机完整接收约2Hz，画面60FPS，应用RTT约1408ms。
- 4人/29舰：房主生产59.84Hz、中转59.20Hz；同一慢客机约3Hz、画面60FPS、RTT约798ms；另一台144FPS客机约16Hz，链路差异明显。
- 重场景客机parse约2.5ms、apply约5ms，不能解释接近一秒的等待。
- 慢链路窗口多为3帧且常满，原始状态计费在途约0.5–0.68MB；忙时RTT远高于约84–169ms的空闲基线。很多候选状态由于无额度根本没再发出去。额度是控制积压的机制，不应把放宽它当根治。
- 原始呈现状态约177–225KB；已存在binary delta/压缩，不能说它们没开。HUD字节、credit字节、delta编码字节都不是VPN/IP线上实测字节，**不能由这些数算实际Mbps或断言上行带宽不足多少**。
- n2n汇总有mixed/relay，只证明隧道存在中转流量，不能绑定每个游戏连接，更没有测出supernode带宽/逐连接丢包。
- Steam旧场景约180FPS但只有1–2Hz状态，中转入口仍约60Hz，native路由状态不可用；观察到传输背压/可靠发送等待，不能断言一定Valve中转。

因此对用户原始问题，已确认瓶颈段为“中转→客机交付/确认回路”，但现有旧日志不足以把该段继续唯一归因于n2n某节点、丢包、带宽或操作系统队列。

## 6. 应当改什么，而不是继续错位优化

1. **生产端**：把高频权威步/小型战斗状态的调度与大状态投影、编码解耦；用有界不可变紧凑记录/可转移buffer，避免把整个对象图structured-clone到另一Worker（Phase21已测过无稳定收益并撤回）。不能让小状态永远排在大capture/encode后。
2. **交付端**：进一步拆分当前已有P1呈现投影中的变化频率/可靠性，静态舰船/武器配置和持久伤痕按变化同步，高频姿态/关键状态小包更新；对完整重建保留校验、基线和重连。当前并非在传完整可恢复模拟检查点，不能把“改成渲染快照”当从零未做的优化。
3. **验收**：补真实多机最新构建的逐阶段/逐连接测量，确认网络线路排队位置；不混淆FPS、物理Hz、motionHz和完整状态Hz，不用关闭画面或本地假接收器宣称实机60Hz。
