# 原 AI 撤离逻辑修复：掩护失效不等于危险解除

日期：2026-09-18。状态：**已接入实际规则 AI 并构建；不是强化学习权重上线，也不是整体战力提升认证。**

## 先复现，后修改

使用真实 CombatEngine、60 Hz 物理、原版损伤/死亡机制和 BALANCED 残差动作，固定三个编成 × 两个种子（211、307），每局最多 60 秒：

- 双方 hammerhead，LINE。
- hammerhead + wolf 对 sunder + lasher，STAGGER。
- hammerhead + lasher + wolf 对 sunder + hammerhead + lasher，WIDE。

三舰场景 seed 211 中，`ship_1` 从 5.53 秒开始承受约 2.8–3.2 的局部压力比。它反复寻找 `player_ship` 的掩护；队友幅能从 79.9% 升至 80.5%–81.7% 后失去掩护资格，舰队计划便从 REGROUP 直接回到 PRESSURE，尽管当前船面临的压力并未解除。例如：

| 时刻 | 掩护舰幅能 | 局部压力比 | 原行为 |
|---|---:|---:|---|
| 5.95 秒 | 80.52% | 3.18 | WITHDRAW → ENGAGE |
| 6.07 秒 | 79.94% | 3.12 | ENGAGE → WITHDRAW |
| 6.17 秒 | 81.58% | 3.11 | WITHDRAW → ENGAGE |
| 6.48 秒 | 80.00%（未四舍五入值低于 80%） | 2.94 | ENGAGE → WITHDRAW |
| 6.67 秒 | 81.22% | 2.83 | WITHDRAW → ENGAGE |

这是“是否撤离”和“撤往哪艘队友”被绑在一起的逻辑缺陷，不是训练量不够。压力比是原有可见单位/有效火力估计，不是精确战力倍数。

## 实际修改

生产代码仅涉及 `FleetTactics.ts`、`CapitalShipAI.ts`：

1. 将撤离意图和掩护目的地分开。压力过大时，有合格队友用 REGROUP；没有则用新增的 DISENGAGE，自主拉开距离。
2. 两种撤离任务共用原来的压力滞回：超过 2.5 触发，恢复至 1.6 以下才解除压力条件。退出战斗邻域另加 200 距离单位的滞回带，避免在单一距离边缘逐帧切换。
3. 低船体条件不额外启动均势单挑中的无掩护撤离；若已在撤离，掩护失效仍允许继续。
4. DISENGAGE 不分配进攻接近航道、不计为已投入攻击的舰队火力，不会被局部火线调整改回接近敌人。两类舰船系统回调获得一致的撤离意图。
5. 压力撤离不自动停火：原火控的友伤、障碍、弹药和幅能约束继续决定开火；高幅能恢复阶段仍保留原来的进攻停火限制。
6. 玩家显式命令、禁止后撤属性及 ASSAULT/EXTRACT 系统覆盖保留。没有敌情时不继续追踪隐藏目标。

不改武器数值、命中/损伤规则、物理频率或学习权重。既有强化学习候选保持冻结，生产策略仍 `enabled: false`。

## 同场景前后回放

主证据保存在 `artifacts/ai/behavior-2026-09-18/`。每个版本在一场回放中控制**双方**，不是“新版对旧版”的胜率测试。下面所有计数按整局双方统计：

| 场景 / seed | 压力仍 >2.5 时恢复交战：前 → 后 | 半秒内返回前一交战/撤离模式：前 → 后 |
|---|---:|---:|
| 双驱逐 / 211 | 0 → 0 | 0 → 0 |
| 双驱逐 / 307 | 0 → 0 | 0 → 1 |
| 混合双舰 / 211 | 0 → 0 | 0 → 0 |
| 混合双舰 / 307 | 0 → 0 | 0 → 0 |
| 三舰 / 211 | 7 → 0 | **8 → 0** |
| 三舰 / 307 | 1 → 0 | 0 → 0 |
| 合计 | **8 → 0** | **8 → 1** |

“半秒内返回”只是行为诊断，不是所有快速切换都错误。修复后双驱逐 / 307 的一次返回发生在压力从约 1.62 降至 1.59、满足恢复门槛时；不能为了让统计变为零而强行拖延合理恢复。REGROUP 与 DISENGAGE 之间仍可能切换目的地，本轮没有消灭所有横向转向或所有任务抖动。

### 不掩盖负面结果

- 混合双舰 / 307：原来 38.85 秒己方全灭；新版到 60 秒仍存活，双方归一化剩余船体为 0.224 / 0.499。这是超时，**不是胜利**。
- 三舰 / 211：即使上述抖动消失，己方仍全灭，且从 35.40 秒变为 34.38 秒；敌方剩余船体从 0.901 增至约 1.000。
- 三舰 / 307：己方全灭从 32.92 秒推迟至 58.17 秒，但敌方剩余船体反而从 0.924 增至 0.993。
- 双驱逐 / 307：双方仍超时，己方剩余船体略降。双驱逐 / 211 完整轨迹不变。

因此，这次可以确认的是**修好了一个不合理的撤离决策条件**，不能确认胜率提升，也不能把活得更久直接算为更强。接下来若评估强度，应进行控制双方版本、交换阵营的独立对抗；若继续排查失误，应关注有效输出和撤离后的重新接战，而不是继续优化这六局的分数。

## 验证与隔离

- 新增 `scripts/check-ai-withdrawal.mjs` 的 12 项检查，覆盖掩护失效、80% 幅能反复跨线、掩护舰死亡/撤出/泄能/过载、压力及距离滞回、均势残血单挑、视野、显式命令、系统覆盖、停火约束及手动分配边界。
- 旧版本运行第一项回归检查会失败：错误地输出 PRESSURE，而不是 DISENGAGE。失败记录为 `baseline-red-check.txt`；新版本 12 项通过。
- Worker owner 内核和同步路径在三个连续发布帧上给出一致的 DISENGAGE 诊断与控制变更。这不是完整浏览器多人/手动游玩验收，也不是 Worker 性能测试。
- `npm run ai:check`：**72 项检查通过**（原 60 + 新增 12）；lint、生产构建通过，构建保留已有大分块警告。
- 修复后六场完整回放各重复一次，事件、逐秒状态、结局和物理校验值全部一致。
- 工作区存在其他并行修改，因此效果对照使用冻结的 `baseline.mjs`、`candidate.mjs`。审计确认：排除两个规则模块及一个测试用 `weaponRange` 导出后，两个 bundle 的其余字节完全相同；冻结的两个规则模块与验证时当前源码构建结果一致。没有把并行火控性能修改的效果混算进本轮。
- `audit.json` 保存哈希、完整配对指标、重复一致性和当前规则匹配结果。`final-*` 保存本轮最终源码/脚本快照。
